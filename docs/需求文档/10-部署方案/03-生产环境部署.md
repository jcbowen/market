### 9.3 生产环境部署

#### 9.3.1 生产环境准备

部署前需要准备：

- 一台或多台 Linux 服务器（建议 2 核 4G 起步）。
- 已备案域名，并解析到服务器公网 IP。
- SSL 证书（可通过 Let's Encrypt 或云服务商获取）。
- 生产级 MySQL 8.0 和 Redis 7 实例（可使用云数据库，也可以自行部署）。
- 微信支付、支付宝支付、短信服务等第三方账号与密钥。

#### 9.3.2 构建发布镜像（Docker 方案）

在本地或 CI/CD 环境中执行 [deploy.mjs](file:///Users/bowen/projects/mine/market/deploy.mjs)：

```bash
# 完整构建
node deploy.mjs

# 构建完成后直接启动（仅适用于单机测试，生产建议分步发布）
node deploy.mjs --up

# 不使用 Docker 缓存重新构建
node deploy.mjs --no-cache

# 依赖不全时只报告原因，不自动执行 go mod tidy / npm install
node deploy.mjs --no-auto-fix
```

该脚本会依次完成：

1. 安装前端依赖（若缺失）。
2. 构建管理端（`src/admin`）。
3. 构建 C 端 H5（`src/client`，含 iframe 后处理）。
4. 使用 [build.mjs](file:///Users/bowen/projects/mine/market/build.mjs) 交叉编译后端二进制。
5. 构建所有 Docker 镜像。

构建产物仅包含在 `bin/` 目录中，最终镜像通过 `.dockerignore` 过滤，不会携带源码。

依赖不全的处理与 9.2.1 的「依赖自愈」一致（同样由 `deps-tools.mjs` 承担）：脚本会先抓取失败输出判定原因，npm 依赖缺失、`go.sum` 缺行、基础镜像拉取失败都会自动补齐后重试一次，`go.mod` 中 `replace` 指向的本地模块缺失则直接报出期望路径。在 CI/CD 上不希望脚本改动 `go.mod`/`go.sum` 时，加 `--no-auto-fix`。

#### 9.3.3 生产配置调整

生产部署前，必须修改 [bin/config.docker.yaml](file:///Users/bowen/projects/mine/market/bin/config.docker.yaml) 中的以下关键项：

| 配置项 | 说明 | 示例 |
|---|---|---|
| `web_server.enablessl` | 是否启用 HTTPS | `true` |
| `web_server.certpath` / `web_server.keypath` | SSL 证书与私钥路径 | `/app/ssl/cert.pem` |
| `db.host` / `db.password` | 生产数据库地址与密码 | 云数据库地址与强密码 |
| `redis.host` / `redis.password` | 生产 Redis 地址与密码 | 云 Redis 地址与密码 |
| `jwt.secret` | JWT 签名密钥，必须替换为随机强密码 | 随机 32 位以上字符串 |

**配置文件 key 命名注意**：`web_server`、`db`、`redis` 三段由 jcbaseGo 结构体解析，其字段没有 yaml tag，yaml.v3 按“字段名全小写”匹配。因此必须写成 `enablessl`、`certpath`、`keypath`、`drivername`、`parsetime`、`singulartable` 等全小写形式；`enable_ssl`、`driverName` 这类带下划线或驼峰的写法会被**静默忽略并回落默认值**。`jwt`、`log`、`grpc` 等其余段在项目自身结构体上声明了 yaml tag，正常使用下划线（如 `access_token_ttl`）。

**支付/短信类配置已不在配置文件中生效**：微信支付、支付宝、渠道开关（enabled_channels）等已迁移至数据库 `pay_config` 表，由管理后台「支付设置」页面维护（见 `common/config/config.go` 顶部注释与 `services/payment/service/payconfig.go`）。配置文件里残留的 `wechat`、`alipay`、`sms`、`payment` 段不会被后端代码读取，生产部署无需修改，密钥也不要写入该文件。

#### 9.3.4 生产 Docker 部署调整建议

生产环境使用 Docker 部署时，建议基于 [docker-compose.yml](file:///Users/bowen/projects/mine/market/docker-compose.yml) 做以下调整：

- 本地附件模式依赖 `./bin/attachment` 宿主机共享目录（默认配置已挂载）：product 服务将上传文件落盘至容器内 `/app/attachment`（可执行文件同级 `attachment/`），gateway 通过 `/uploads` 静态路由读取同一目录，两个容器必须挂载同一宿主目录。目录不存在时，[start-all.mjs](file:///Users/bowen/projects/mine/market/start-all.mjs) 与 [deploy.mjs](file:///Users/bowen/projects/mine/market/deploy.mjs) 会自动执行 `mkdir -p` 创建；运行时代码在上传时也会按需创建子目录。该目录持久化于宿主机，容器重建不丢失。若改用 OSS 直传模式，则不依赖该目录。
- IP 定位数据库（GeoLite2-City）依赖 `./bin/data/geoip` 宿主机目录（默认配置已只读挂载到网关 `/app/data/geoip`）：数据库文件不入 git 仓库，需在服务器上执行 `node download-geoip.mjs` 下载，并按 7.10 节配置 crontab 定期更新；目录为空时 IP 定位接口优雅降级，不影响其他功能。详见基础设施规范「IP 定位服务」。
- 去掉 gateway 对 `./bin/static/admin` 和 `./bin/static/h5` 的宿主机挂载，改为将静态资源打包进镜像。
- 保留或改造 gateway 的运行时配置快照：网关首次启动时从只读模板 `bin/config.docker.yaml` 复制出 `bin/runtime/config.yaml`，之后网关只读取该快照（由 docker-compose.yml 的 gateway command 实现）。注意：支付设置保存在数据库 `pay_config` 表，**不会**写回该文件，快照本身不会被运行时代码修改；若需让模板修改重新生效，删除 `bin/runtime/config.yaml` 后重启网关即可。
- 将 MySQL/Redis 替换为云数据库或独立集群，不再使用 docker-compose 内置服务。
- 使用外部网络或反向代理（如 Nginx、Traefik）处理 HTTPS、域名绑定和负载均衡。
- 开启容器资源限制与日志收集。
- 配置数据库定期备份策略。

如果使用外部 MySQL/Redis，可以使用项目已提供的 [docker-compose.external-db.yml](file:///Users/bowen/projects/mine/market/docker-compose.external-db.yml)：

```bash
# 1. 将 bin/config.docker.yaml 中的 db/redis 地址改为外部实例
# 2. 启动服务（不包含 MySQL/Redis 容器）
docker compose -f docker-compose.external-db.yml up -d
```

#### 9.3.5 非 Docker 生产部署

如果服务器不使用 Docker，可以直接部署后端二进制：

**1. 构建产物**

在本地或 CI/CD 环境中执行：

```bash
# 后端三平台交叉编译，Linux 产物在 bin/linux/
# 注意：build.mjs 的 Linux 产物固定为 arm64（PLATFORMS 中 linux 仅配 arm64），
# 只适用于 arm64 服务器（如鲲鹏/Apple 云主机/微信云跑在 arm 上的机器）
node build.mjs

# 若服务器是常见的 x86_64（amd64），需额外手工编译 Linux amd64 产物：
cd src/backend
for svc in gateway services/user services/product services/order services/cart services/payment; do
  name=$(basename $svc); [ "$name" != "gateway" ] && name="${name}-service"
  GOPATH=<项目根目录的绝对路径> CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -o ../../bin/linux/${name} ./${svc}/
done
cd ../..

# 前端产物输出到 bin/static/admin 与 bin/static/h5
cd src/admin && npm run build
cd src/client && npm run build:h5
```

（`GOPATH` 指到项目根目录是因为依赖模块缓存位于仓库内 `pkg/mod/`，与 `build.mjs` 的做法一致。）

也可以直接执行 [deploy.mjs](file:///Users/bowen/projects/mine/market/deploy.mjs)，它会一次完成前端构建、`build.mjs` 后端交叉编译与镜像构建（非 Docker 部署时忽略其镜像构建步骤即可）。

**2. 上传产物到服务器**

将以下文件上传到生产服务器同一目录（例如 `/opt/market`，二进制取自 `bin/linux/`）：

```
bin/
├── gateway
├── user-service
├── product-service
├── order-service
├── cart-service
├── payment-service
├── config.yaml
├── data/
│   └── geoip/
│       └── GeoLite2-City.mmdb   # IP 定位数据库，node download-geoip.mjs 下载（不入 git）
└── static/
    ├── admin/
    └── h5/
```

**3. 准备 MySQL 与 Redis**

生产环境建议直接使用云数据库，只需创建空库与账号（库名 `market`，字符集 `utf8mb4`、排序规则 `utf8mb4_unicode_ci`），**不要执行任何建表脚本**：全部表结构由各微服务启动时通过 GORM AutoMigrate 自动创建（见 `src/backend/services/*/main.go` 的 `autoMigrate`）。

`deploy/init.sql` 是测试数据脚本，含弱口令管理员与示例社区/商品数据，**禁止整体导入生产库**。若首次部署需要一个可登录的后台账号，有两种做法：

- 推荐：先启动全部服务让 AutoMigrate 建好表，再只执行 `deploy/init.sql` 中的 `admin_roles`、`admin_users` 两条 INSERT（对应口令 `admin/admin123`），并把 `admin_users.community_id` 改为 0——超级管理员不受社区限制（见 `src/backend/services/user/service/admin.go` 的 `ListAdminCommunityIDs`），无需先建社区。登录后台后立即修改密码并新建正式管理员。
- 或由 DBA 自行用 bcrypt（cost 10，与 `admin_users.password` 现有算法一致）生成强口令哈希后插入 `admin_roles`、`admin_users`。

无论哪种，都不要把 `communities`、`users`、`categories`、`products`、`product_skus`、`product_images` 等测试行带入生产。

**4. 修改生产配置**

编辑服务器上的 `bin/config.yaml`，将 `db`、`redis`、`jwt`、支付、短信等配置修改为生产值。

**5. 启动服务**

项目未提供宿主机侧的服务编排脚本，非 Docker 部署按下述方式逐个启动（`CONFIG_FILE` 未设置时，各进程读取自身同级目录的 `config.yaml`）：

```bash
cd /opt/market
mkdir -p logs
for svc in user-service product-service order-service cart-service payment-service gateway; do
  CONFIG_FILE=/opt/market/config.yaml nohup ./${svc} > logs/${svc}.log 2>&1 &
done
```

停止服务：

```bash
cd /opt/market
pkill -f '/opt/market/(gateway|user-service|product-service|order-service|cart-service|payment-service)'
```

生产环境建议配合 systemd（Linux）或 launchd（macOS）实现开机自启与异常重启。

#### 9.3.6 部署后验证

发布完成后，按以下顺序验证：

1. 访问 `https://your-domain.com/health` 确认网关返回 200。
2. 访问管理后台 `https://your-domain.com/b/` 并能正常登录。
3. 访问 C 端 H5 `https://your-domain.com/s/` 并验证首页、分类、购物车等核心流程。
4. 测试下单、支付回调、退款等关键链路。
5. 检查各微服务日志是否有异常报错。
