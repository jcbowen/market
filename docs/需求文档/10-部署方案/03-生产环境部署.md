### 9.3 生产环境部署

#### 9.3.1 生产环境准备

部署前需要准备：

- 一台或多台 Linux 服务器（建议 2 核 4G 起步）。
- 已备案域名，并解析到服务器公网 IP。
- SSL 证书（可通过 Let's Encrypt 或云服务商获取）。
- 生产级 MySQL 8.0 和 Redis 7 实例（可使用云数据库，也可以自行部署）。
- 微信支付、支付宝支付、短信服务等第三方账号与密钥。

#### 9.3.2 构建发布镜像（Docker 方案）

在本地或 CI/CD 环境中执行 [deploy.mjs](../../../deploy.mjs)：

```bash
# 完整构建
node deploy.mjs

# 构建完成后直接启动（仅适用于单机测试，生产建议分步发布）
node deploy.mjs --up

# 不使用 Docker 缓存重新构建
node deploy.mjs --no-cache

# 依赖不全时只报告原因，不自动执行 go mod tidy / npm install
node deploy.mjs --no-auto-fix
```

该脚本会依次完成：

1. 安装前端依赖（若缺失）。
2. 构建管理端（`src/admin`）。
3. 构建 C 端 H5（`src/client`，含 iframe 后处理）。
4. 使用 [build.mjs](../../../build.mjs) 交叉编译后端二进制。
5. 构建所有 Docker 镜像。

构建产物仅包含在 `bin/` 目录中，最终镜像通过 `.dockerignore` 过滤，不会携带源码。

依赖不全的处理与 9.2.1 的「依赖自愈」一致（同样由 `deps-tools.mjs` 承担）：脚本会先抓取失败输出判定原因，npm 依赖缺失、`go.sum` 缺行、基础镜像拉取失败都会自动补齐后重试一次，`go.mod` 中 `replace` 指向的本地模块缺失则直接报出期望路径。在 CI/CD 上不希望脚本改动 `go.mod`/`go.sum` 时，加 `--no-auto-fix`。

#### 9.3.3 生产配置调整

> 本节针对多容器 compose 部署（修改模板 `bin/config.docker.yaml`）。**一体化镜像部署（9.3.4a）不走本节**：其配置修改统一编辑宿主机 `./data/runtime/config.yaml` 源配置文件（首启自动生成，见 9.3.4a「修改业务配置（源配置文件）」），无需挂载覆盖模板。

生产部署前，必须修改 [bin/config.docker.yaml](../../../bin/config.docker.yaml) 中的以下关键项：

| 配置项 | 说明 | 示例 |
|---|---|---|
| `web_server.enablessl` | 是否启用 HTTPS | `true` |
| `web_server.certpath` / `web_server.keypath` | SSL 证书与私钥路径 | `/app/ssl/cert.pem` |
| `db.host` / `db.password` | 生产数据库地址与密码 | 云数据库地址与强密码 |
| `redis.host` / `redis.password` | 生产 Redis 地址与密码 | 云 Redis 地址与密码 |
| `jwt.secret` | JWT 签名密钥，必须替换为随机强密码；生产环境检测到默认占位值将拒绝启动，推荐改由 `JWT_SECRET` 环境变量注入 | 随机 32 位以上字符串 |
| `security.trusted_proxies` | **仅 gateway 读取**。可信反代网段列表（CIDR 或单个 IP），决定 `ClientIP()` 是否采信 `X-Forwarded-For`。宿主 nginx 反代容器发布端口时必须填 compose 网络实际网段（`docker network inspect market_default` 取 `Configurations.Subnet`）；留空=不采信任何代理头（所有用户共用代理 IP 这一个限流桶，正常流量会被整站 429），填 `0.0.0.0/0`=任何人可伪造头绕过限流与登录锁定。推荐改由 `TRUSTED_PROXIES` 环境变量（逗号分隔）注入，网段随部署环境变化不该写死在入库配置里 | `["172.18.0.0/16"]` |
| `SITE_BASE_URL`（环境变量，**仅 gateway 读取**） | 部署域名基址，形如 `https://shop.example.com`（`scheme://host`，不含路径与尾斜杠）。作为后台「站点设置」未配置时的**兜底默认值**：站点设置页会把该值回填进输入框，在页面保存后即以站点设置的 `base_url` 为准（网关派生支付回调地址、附件外链基址与 HTML 品牌注入按生效域名计算）。适用场景是新环境首次启动、尚未进后台配置时先固定一个域名。留空且站点设置也未配置时按当前请求域名现推（回调地址与附件外链会随访问 host 变化，正式上线务必二选一固定，页面会标记来源为 `request` 提示未配置） | `https://shop.example.com` |

**配置文件 key 命名注意**：`web_server`、`db`、`redis` 三段由 jcbaseGo 结构体解析，其字段没有 yaml tag，yaml.v3 按“字段名全小写”匹配。因此必须写成 `enablessl`、`certpath`、`keypath`、`drivername`、`parsetime`、`singulartable` 等全小写形式；`enable_ssl`、`driverName` 这类带下划线或驼峰的写法会被**静默忽略并回落默认值**。`jwt`、`log`、`grpc` 等其余段在项目自身结构体上声明了 yaml tag，正常使用下划线（如 `access_token_ttl`）。

**支付/短信类配置已不在配置文件中生效**：微信支付、支付宝、渠道开关（enabled_channels）等已迁移至数据库 `pay_config` 表，由管理后台「支付设置」页面维护（见 `common/config/config.go` 顶部注释与 `services/payment/service/payconfig.go`）。配置文件中 `wechat` 段仅 `app_id` / `app_secret` 两个字段会被读取（微信小程序登录用，见 `gateway/handler/auth.go`）；`mch_id`、`api_v3_key`、`cert_serial_no`、`private_key`、`notify_url` 等支付字段只是 `WechatConfig` 数据载体的残留，运行时以 `pay_config` 表为准；`sms` 段为预留、当前代码不读取。配置文件不含 `alipay`、`payment` 段，相关密钥也不要写入该文件。

#### 9.3.4 生产 Docker 部署调整建议

生产环境使用 Docker 部署时，建议基于 [docker-compose.yml](../../../docker-compose.yml) 做以下调整：

- 本地附件模式依赖 `./bin/attachment` 宿主机共享目录（默认配置已挂载）：product 服务将上传文件落盘至容器内 `/app/attachment`（可执行文件同级 `attachment/`），gateway 通过 `/uploads` 静态路由读取同一目录，两个容器必须挂载同一宿主目录。目录不存在时，[start-all.mjs](../../../start-all.mjs) 与 [deploy.mjs](../../../deploy.mjs) 会自动执行 `mkdir -p` 创建；运行时代码在上传时也会按需创建子目录。该目录持久化于宿主机，容器重建不丢失。若改用 OSS 直传模式，则不依赖该目录。
- IP 定位数据库（GeoLite2-City）依赖 `./bin/data/geoip` 宿主机目录（默认配置已只读挂载到网关 `/app/data/geoip`）：数据库文件不入 git 仓库，需在服务器上执行 `node download-geoip.mjs` 下载，并按 7.10 节配置 crontab 定期更新；目录为空时 IP 定位接口优雅降级，不影响其他功能。详见基础设施规范「IP 定位服务」。
- 去掉 gateway 对 `./bin/static/admin` 和 `./bin/static/h5` 的宿主机挂载，改为将静态资源打包进镜像。
- 保留或改造 gateway 的运行时配置快照：网关首次启动时从只读模板 `bin/config.docker.yaml` 复制出 `bin/runtime/config.yaml`（由 docker-compose.yml 的 gateway command 实现）。注意：框架（jcbaseGo）加载配置后会每次启动将配置结构体全量回写该文件，因此该文件必须对容器内 uid 10001 可写；docker-compose.yml 的 command 已内置自愈——检测到快照不可写（如 Windows Docker Desktop 9p 把宿主遗留文件映射为 0755 root:root）时自动删除并从模板重建。Linux 宿主机按下方「容器安全加固」执行 `chown -R 10001:10001 bin/runtime` 后不受影响。支付设置保存在数据库 `pay_config` 表；快照重建后即回到模板内容，若需让模板修改重新生效，删除 `bin/runtime/config.yaml` 后重启网关即可。
- 将 MySQL/Redis 替换为云数据库或独立集群，不再使用 docker-compose 内置服务。
- 使用外部网络或反向代理（如 Nginx、Traefik）处理 HTTPS、域名绑定和负载均衡。
- 开启容器资源限制与日志收集。
- 配置数据库定期备份策略。

如果使用外部 MySQL/Redis，项目提供了 [docker-compose.external-db.yml](../../../docker-compose.external-db.yml) 作为起点，**但需注意该文件未同步主 compose 的安全加固**，直接用于生产前需自行补齐：

- **凭据注入缺失**：各服务未注入 `MYSQL_PASSWORD` / `REDIS_PASSWORD` / `JWT_SECRET` 环境变量（主 compose 经 `.env` 注入并覆盖配置文件），外部库口令只能写死在 `bin/config.docker.yaml` 里——不符合"敏感凭据不入库"约定；
- **卷挂载缺失**：gateway 未挂载 `./bin/runtime`（运行时配置快照不持久化，`config.runtime.yaml` 落在容器可写层，容器重建即丢、框架回写不落宿主）与 `./bin/data/geoip`（IP 定位库读不到，接口优雅降级）；
- **无自愈 command**：gateway 的 command 仅是 `cp` 模板到容器内路径，没有主 compose 的 runtime 快照不可写检测/重建逻辑；
- **依赖就绪弱**：`depends_on` 全部为 `service_started`，无健康检查条件（主 compose 为 `service_healthy`），冷启动时下游可能先于依赖就绪。

该文件适合本地/内网快速起外部库联调环境；生产使用请对照主 `docker-compose.yml` 逐项补齐上述差异（文件本身暂不修改）。

```bash
# 1. 将 bin/config.docker.yaml 中的 db/redis 地址改为外部实例
# 2. 启动服务（不包含 MySQL/Redis 容器）
docker compose -f docker-compose.external-db.yml up -d
```

**容器安全加固（已落地）：**

- **非 root 运行**：全部服务镜像（[Dockerfile.gateway](../../../src/backend/deploy/Dockerfile.gateway)、[Dockerfile.service](../../../src/backend/deploy/Dockerfile.service)）以固定 UID 10001（appuser）运行，即使容器被攻破也难以逃逸获得 root。Linux 宿主机部署时挂载的宿主写目录需授权：`chown -R 10001:10001 bin/runtime bin/attachment`（Docker Desktop/VirtioFS 无需处理）。
- **健康检查**：gateway 镜像 HEALTHCHECK 探测 18080、微服务镜像探测各自 gRPC 端口（busybox nc TCP 探活）；docker-compose.yml 中各服务依赖 MySQL/Redis 及下游服务一律以 `depends_on.condition: service_healthy` 等真正可服务后再启动。
- **口令经 .env 注入**：MySQL/Redis 口令一律经项目根目录 `.env` 提供（compose 自动读取，`.env` 不入 git）。`MYSQL_ROOT_PASSWORD`、`REDIS_PASSWORD` 为必填项，缺失时 compose 直接报错拒绝启动；`JWT_SECRET` 同样从 `.env` 读取，经 `MYSQL_PASSWORD`/`REDIS_PASSWORD`/`JWT_SECRET` 环境变量在服务启动时覆盖配置文件（见 `common/config/env.go` 的 `ApplyEnvOverrides`）。请从 `deploy` 相关示例复制并填入强口令，勿将真实口令写入任何入库文件。
- **JWT 密钥 fail-fast**：`APP_ENV=production` 时，若 JWT 密钥仍为随配置文件入库过的公开默认占位值（`market-secret-key-change-in-production`），各服务启动即拒绝（`EnsureSecureJWT`），必须通过 `JWT_SECRET` 注入随机强密钥，防止攻击者用公开默认密钥伪造任意身份 token。
- **端口收敛**：docker-compose 中 MySQL/Redis 仅绑定宿主机 `127.0.0.1`（3306/6379 不对公网暴露），唯一对外入口为 gateway `18080`，HTTPS 由前置 Nginx/SLB 终结。

#### 9.3.4a 一体化镜像部署（all-in-one，单机部署推荐）

将 MySQL 8.0 + Redis 7 + gateway + 五个微服务 + 前端静态资源打包为**一个镜像**（[Dockerfile.allinone](../../../src/backend/deploy/Dockerfile.allinone)），服务器上只需 `docker pull` + 一条 `docker run` 即可运行。所有状态数据经 bind mount 落宿主机，重装/升级镜像不丢数据。

**镜像内容与进程编排**：入口脚本 [entrypoint.sh](../../../src/backend/deploy/entrypoint.sh) 以 root 引导（负责初始化与目录授权），业务进程降权为 uid 10001 运行，mysqld/redis 使用发行版内置用户；子进程崩溃由守护循环自动拉起；对外仅发布 18080，MySQL/Redis 容器内监听 0.0.0.0、端口发布侧绑定宿主机 127.0.0.1（不对公网暴露，供第三方工具直连调试，见下文「MySQL/Redis 调试连接」）。

**数据映射**（宿主机目录建议 `/opt/market/data/`）：

| 数据 | 容器内路径 | 挂载建议 | 说明 |
|---|---|---|---|
| MySQL 数据 | `/var/lib/mysql` | `./data/mysql` | 库文件，必须 |
| Redis 数据 | `/data` | `./data/redis` | RDB 持久化，必须 |
| 附件 | `/app/attachment` | `./data/attachment` | 上传文件，必须 |
| 运行时配置 + 超管凭证 | `/app/runtime` | `./data/runtime` | **源配置 `config.yaml`（用户可编辑的唯一配置源，首启自动生成，见下文「修改业务配置」）** + 每进程私有副本 `config.<svc>.yaml`（自动分发，含回填的 DB 口令，0600，勿手改）、`admin_credentials.json`，必须 |
| 业务日志 | `/app/logs` | `./data/logs` | 建议 |
| IP 定位库 | `/app/data/geoip` | `./data/geoip`（ro） | 可选，`node download-geoip.mjs` 下载 |

**镜像仓库与可见性**（CI 推 `v*` tag 时自动双发）：

| Registry | 镜像地址 | 可见性 |
|---|---|---|
| Docker Hub（推荐，国内拉取快） | `jcbowen/market:{tag}` / `:latest` | 公开（个人账号推送自动建仓默认公开，无需登录即可 pull） |
| GHCR | `ghcr.io/jcbowen/market:{tag}` / `:latest` | 默认私有（仓库私有所致）；如需公开：GitHub → Your packages → market → Package settings → Change visibility → Public，一次性设置永久生效 |

> CI 双发依赖仓库 Secrets：`DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`（Docker Hub → Account Settings → Security → New Access Token，权限 Read & Write）。未配置时自动降级为仅发 GHCR。

**构建与发布**（需先 `node build.mjs` 产出 bin/linux-{amd64,arm64} 与 bin/static；常规发版直接推 tag 走 CI，无需手工构建）：

```bash
# 本地构建本机架构镜像（验证用）
node build-image.mjs

# 多架构构建并推送镜像仓库（手工发布用）
node build-image.mjs --tag jcbowen/market:v1.0.0 --push
```

**服务器运行（docker-compose 方式，推荐）**——在 `/opt/market/` 下创建 `docker-compose.yml`：

```yaml
# market 一体化镜像部署：单容器承载 MySQL+Redis+全部服务+前端
# 数据全部落宿主机 ./data/，重装/升级镜像不丢数据
services:
  market:
    # latest 随每次发版（CI 推 v* tag）自动更新，docker compose pull 即可升级；国内服务器推荐 Docker Hub
    # 需锁版本（生产求稳）：到 GitHub Releases 页取最新 tag 替换，如 jcbowen/market:v0.1.3
    image: jcbowen/market:latest
    # image: ghcr.io/jcbowen/market:latest
    container_name: market
    restart: unless-stopped
    # 优雅停止等待时间（给 mysqld 落盘留足余量，等同 docker run --stop-timeout 30）
    stop_grace_period: 30s
    ports:
      - "18080:18080"
      # MySQL/Redis 绑定宿主机回环：仅本机可连，供第三方工具（Navicat 等）调试，
      # 跨设备调试配合 SSH 隧道（见下文「MySQL/Redis 调试连接」）；勿改为 0.0.0.0 对公网暴露。
      # 宿主机 3306/6379 已被占用时（如本机另装了 MySQL），改用其他宿主侧端口即可，
      # 如 "127.0.0.1:13306:3306"；或直接删除这两行（调试改走 docker exec，见下文）
      - "127.0.0.1:3306:3306"
      - "127.0.0.1:6379:6379"
    environment:
      APP_ENV: production
      # 强口令必改！MYSQL_ROOT_PASSWORD 仅首次初始化生效，之后不可变更
      MYSQL_ROOT_PASSWORD: "改成强口令"
      REDIS_PASSWORD: "改成强口令"
      JWT_SECRET: "改成至少32位随机字符串"
      # 可信反代网段（仅 gateway 用）：宿主 nginx 反代 18080 时必填 docker 网络实际网段，
      # 留空=不采信代理头（全站共用一个限流桶），0.0.0.0/0=可被伪造绕过，禁止
      TRUSTED_PROXIES: "172.18.0.0/16"
      # 部署域名基址（仅 gateway 用，可选）：设置后优先于后台「站点设置」的 base_url，
      # 支付回调地址、附件外链与 HTML 品牌注入都按它派生；留空则以站点设置为准
      # SITE_BASE_URL: "https://shop.example.com"
      # 初始超管账号（可选；密码不设则随机生成，docker logs 可查）
      # MARKET_ADMIN_USER: admin
      # MARKET_ADMIN_PASSWORD: ""
    volumes:
      - ./data/mysql:/var/lib/mysql        # MySQL 数据
      - ./data/redis:/data                 # Redis 持久化
      - ./data/attachment:/app/attachment  # 附件
      - ./data/runtime:/app/runtime        # 运行时配置 + 超管凭证（config.yaml 为源配置，见下文）
      - ./data/logs:/app/logs              # 业务日志
      # - ./data/geoip:/app/data/geoip:ro       # 可选：IP 定位库（缺失自动降级）
    healthcheck:
      test: ["CMD", "bash", "-c", "exec 3<>/dev/tcp/127.0.0.1/18080"]
      interval: 15s
      timeout: 5s
      retries: 10
      start_period: 120s                   # 首启含 MySQL 初始化 + 自动迁移，放宽
```

```bash
mkdir -p /opt/market/data/{mysql,redis,attachment,runtime,logs}
cd /opt/market && docker compose up -d
docker logs -f market   # 首启观察初始化与超管凭证输出
```

**服务器运行（docker run 方式，等价）**：

```bash
mkdir -p /opt/market/data/{mysql,redis,attachment,runtime,logs}
docker run -d --name market --restart unless-stopped --stop-timeout 30 -p 18080:18080 \
  -p 127.0.0.1:3306:3306 -p 127.0.0.1:6379:6379 \
  -e MYSQL_ROOT_PASSWORD='<强口令>' \
  -e REDIS_PASSWORD='<强口令>' \
  -e JWT_SECRET='<随机强密钥>' \
  -e TRUSTED_PROXIES='<宿主 nginx 所在的 docker 网络网段，如 172.18.0.0/16；无反代则留空>' \
  -e SITE_BASE_URL='<对外访问地址，如 https://shop.example.com；留空则以后台站点设置为准>' \
  -e APP_ENV=production \
  -v /opt/market/data/mysql:/var/lib/mysql \
  -v /opt/market/data/redis:/data \
  -v /opt/market/data/attachment:/app/attachment \
  -v /opt/market/data/runtime:/app/runtime \
  -v /opt/market/data/logs:/app/logs \
  jcbowen/market:latest
```

GeoIP：`-v /opt/market/data/geoip:/app/data/geoip:ro`（缺失时 IP 定位接口优雅降级）。宿主机 3306/6379 已被占用时，将 `-p 127.0.0.1:3306:3306` 改为 `-p 127.0.0.1:13306:3306`（Redis 同理），或删掉这两个映射（见下文「MySQL/Redis 调试连接」）。

**修改业务配置（源配置文件）**：

首次启动后，entrypoint 会自动在 `./data/runtime/config.yaml`（容器内 `/app/runtime/config.yaml`）生成一份源配置，它是全部 7 个服务进程共用的唯一配置源。日常调整端口、日志、gRPC 地址等配置只需：

1. 编辑宿主机 `./data/runtime/config.yaml`（`db.password` / `redis.password` 保持空占位，口令由环境变量 `MYSQL_ROOT_PASSWORD` / `REDIS_PASSWORD` 注入，勿写入文件）；
2. 重启容器生效：`docker restart market`（docker compose 方式为 `docker compose restart market`）。

生效原理：每次启动 entrypoint 以源配置为模板分发 7 份进程私有副本（隔离框架的配置回写，避免多进程回写竞态）。若源配置内容无效（空文件或缺少 `web_server:` / `db:` / `redis:` 配置节），启动日志会告警并回退内置模板分发，保证服务可用——直接删除源配置文件重启即可用内置模板重建。

镜像升级带来新增配置字段时，运行副本由框架启动时自动补全，源配置缺失字段不影响运行；如需保持源配置完整，可对照仓库 `bin/config.allinone.yaml` 手工同步新增字段。

**初始超管账号**：

- 环境变量 `MARKET_ADMIN_USER`（默认 `admin`）、`MARKET_ADMIN_PASSWORD` 可指定初始账号；密码缺省时**随机生成并输出到容器启动日志**（`docker logs market` 可查），同时写入 `data/runtime/admin_credentials.json`（0600）。
- 交互式管理（查看列表 / 查看密码 / 重置密码，支持选择账号与密码生成方式）：

```bash
docker exec -it market ./market-admin
```

- 注意：凭证文件仅记录由 `market-admin init` 创建或经该工具重置的密码；之后在管理后台修改过的密码以后台为准（可随时用上面命令重置）。

**MySQL/Redis 调试连接**：

容器内 MySQL/Redis 监听 `0.0.0.0`，但端口发布侧仅绑定宿主机 `127.0.0.1`（不对公网暴露）。排查问题时可通过以下方式连接：

- 宿主机第三方工具（Navicat、DBeaver、Another Redis Desktop Manager 等）：在服务器本机连 `127.0.0.1:3306`（库 `market`、账号 `root`、口令 `MYSQL_ROOT_PASSWORD`）与 `127.0.0.1:6379`（口令 `REDIS_PASSWORD`）。
- 端口冲突处理：映射是**可选**的调试便利，不发布端口时容器内 MySQL/Redis 与宿主机完全隔离（互不影响）。若宿主机已有服务占用 3306/6379（如本机另装了 MySQL），`-p 127.0.0.1:3306:3306` 会因端口被占导致容器启动失败（`address already in use`）——改用其他宿主侧端口即可（如 `-p 127.0.0.1:13306:3306`，工具连 `127.0.0.1:13306`），或删掉该映射走下面的 docker exec 方式。容器内监听 0.0.0.0 本身只作用于容器网络命名空间，不影响宿主机已有的 3306 数据库。
- 从开发机远程调试：走 SSH 隧道把远端回环端口转发到本地，本地工具改连 `127.0.0.1:13306` / `127.0.0.1:16379` 即可：

```bash
ssh -N -L 13306:127.0.0.1:3306 -L 16379:127.0.0.1:6379 <user>@<服务器>
```

- 无工具时用容器内 CLI：

```bash
docker exec -it market mysql -uroot -p'<口令>' market
docker exec -it market redis-cli -a '<口令>'
```

安全提醒：发布侧 `127.0.0.1` 绑定是防止数据库对公网暴露的关键，请勿为图方便改为 `0.0.0.0`；若确需内网多机访问，绑定内网网卡 IP 并确保防火墙/安全组仅放行可信网段。

**数据迁移与备份**：

- 开发环境数据上服务器：不要直接拷贝 MySQL 数据目录（跨构建版本有风险），用 `mysqldump` 导出后经容器导入；附件目录直接拷贝；Redis 为缓存可不迁移。
- 备份：`docker exec market mysqldump -uroot -p'<口令>' market > backup_$(date +%F).sql`（建议 crontab 定期执行）；附件/配置直接复制宿主机 `data/` 目录。
- 升级镜像（compose 方式）：在 compose 目录执行 `docker compose pull && docker compose up -d`，容器以新镜像重建，`latest` 即最新版，数据原样保留。
- 升级镜像（docker run 方式）：`docker pull` 新版本后 `docker stop market && docker rm market`，用**相同的数据目录映射**重新 `docker run` 即可，数据原样保留。
- 回滚：把 compose 中的 `latest` 改回历史精确 tag（如 `v0.1.2`）后再 `up -d`；历史版本 tag 永久保留在镜像仓库，随时可切。
- 注意：`MYSQL_ROOT_PASSWORD` 只在首次初始化时写入 MySQL；数据目录已存在时修改该环境变量会导致启动失败（entrypoint 有明确报错与指引）。

#### 9.3.5 非 Docker 生产部署

如果服务器不使用 Docker，**推荐直接下载 CI 自动发布的产物包**：推 `v*` 格式 tag（如 `v1.0.0`）时，`.github/workflows/ci.yml` 的 release job 会自动执行 go test 回归 → 交叉编译 linux/darwin/windows × amd64/arm64 共 6 平台后端 → 构建前端 → 打包并上传到 GitHub Release。产物命名 `market-{ver}-{os}-{arch}`，其中 linux/darwin 为 `.tar.gz`、windows 为 `.zip`；生产服务器使用 `market-{ver}-linux-{arch}.tar.gz` 包。

```bash
VERSION=v1.0.0   # 替换为实际 tag
# 按服务器架构选择 amd64 / arm64 包
wget "https://<仓库域名>/<owner>/<repo>/releases/download/${VERSION}/market-${VERSION}-linux-amd64.tar.gz"
tar -xzf "market-${VERSION}-linux-amd64.tar.gz" -C /opt
mv "/opt/market-${VERSION}-linux-amd64" /opt/market
```

包内布局与下述 `/opt/market` 结构一致（6 个服务二进制 + `config.yaml` 模板 + `static/` 前端产物），下载后可跳过本节第 1、2 步，从第 3 步继续；GeoIP 数据库仍需在服务器上按 9.3.4 说明执行 `node download-geoip.mjs` 下载。

若无可用 CI 产物（如 runner 离线），也可在本地按以下方式手动构建：

**1. 构建产物**

在本地或 CI/CD 环境中执行：

```bash
# 后端多平台交叉编译，Linux 产物在 bin/linux-amd64 / bin/linux-arm64/
# （build.mjs 按 bin/{os}-{arch}/ 布局输出，覆盖 linux/darwin/windows × amd64/arm64）
node build.mjs

# 若只需手工补某一架构产物（示例：linux amd64，服务器最常见的 x86_64）：
cd src/backend
for svc in gateway services/user services/product services/order services/cart services/payment cmd/market-admin; do
  name=$(basename $svc); [ "$name" != "gateway" ] && name="${name}-service"
  [ "$svc" = "cmd/market-admin" ] && name="market-admin"
  GOPATH=<项目根目录的绝对路径> CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -o ../../bin/linux-amd64/${name} ./${svc}/
done
cd ../..

# 前端产物输出到 bin/static/admin 与 bin/static/h5
cd src/admin && npm run build
cd src/client && npm run build:h5
```

（`GOPATH` 指到项目根目录是因为依赖模块缓存位于仓库内 `pkg/mod/`，与 `build.mjs` 的做法一致。）

也可以直接执行 [deploy.mjs](../../../deploy.mjs)，它会一次完成前端构建、`build.mjs` 后端交叉编译与镜像构建（非 Docker 部署时忽略其镜像构建步骤即可）。

**2. 上传产物到服务器**

将以下文件上传到生产服务器同一目录（例如 `/opt/market`，二进制取自 `bin/linux-{amd64,arm64}/`）：

```
bin/
├── gateway
├── user-service
├── product-service
├── order-service
├── cart-service
├── payment-service
├── config.yaml
├── data/
│   └── geoip/
│       └── GeoLite2-City.mmdb   # IP 定位数据库，node download-geoip.mjs 下载（不入 git）
└── static/
    ├── admin/
    └── h5/
```

**3. 准备 MySQL 与 Redis**

生产环境建议直接使用云数据库，只需创建空库与账号（库名 `market`，字符集 `utf8mb4`、排序规则 `utf8mb4_unicode_ci`），**不要执行任何建表脚本**：全部表结构由各微服务启动时通过 GORM AutoMigrate 自动创建（见 `src/backend/services/*/main.go` 的 `autoMigrate`）。

`deploy/init.dev.sql` 是开发环境测试数据脚本，含弱口令管理员与示例社区/商品数据，**禁止导入生产库**。若首次部署需要一个可登录的后台账号，有两种做法：

- 推荐：先启动全部服务让 AutoMigrate 建好表，再只执行 `deploy/init.dev.sql` 中的 `admin_roles`、`admin_users` 两条 INSERT（对应口令 `admin/admin123`），并把 `admin_users.community_id` 改为 0——超级管理员不受社区限制（见 `src/backend/services/user/service/admin.go` 的 `ListAdminCommunityIDs`），无需先建社区。登录后台后立即修改密码并新建正式管理员。
- 或由 DBA 自行用 bcrypt（cost 10，与 `admin_users.password` 现有算法一致）生成强口令哈希后插入 `admin_roles`、`admin_users`。

无论哪种，都不要把 `communities`、`users`、`categories`、`products`、`product_skus`、`product_images` 等测试行带入生产。

**4. 修改生产配置**

编辑服务器上的 `bin/config.yaml`，将 `db`、`redis`、`jwt`、支付、短信等配置修改为生产值。

**5. 启动服务**

项目未提供宿主机侧的服务编排脚本，非 Docker 部署按下述方式逐个启动（`CONFIG_FILE` 未设置时，各进程读取自身同级目录的 `config.yaml`）：

```bash
cd /opt/market
mkdir -p logs
for svc in user-service product-service order-service cart-service payment-service gateway; do
  CONFIG_FILE=/opt/market/config.yaml nohup ./${svc} > logs/${svc}.log 2>&1 &
done
```

停止服务：

```bash
cd /opt/market
pkill -f '/opt/market/(gateway|user-service|product-service|order-service|cart-service|payment-service)'
```

生产环境建议配合 systemd（Linux）或 launchd（macOS）实现开机自启与异常重启。

#### 9.3.6 部署后验证

发布完成后，按以下顺序验证：

1. 访问 `https://your-domain.com/health` 确认网关返回 200。
2. 访问管理后台 `https://your-domain.com/b/` 并能正常登录。
3. 访问 C 端 H5 `https://your-domain.com/s/` 并验证首页、分类、购物车等核心流程。
4. 测试下单、支付回调、退款等关键链路。
5. 检查各微服务日志是否有异常报错。

#### 9.3.7 客户端渠道上线配置（2026-10-18 起必做）

小程序登录凭证已从 `config.yaml` 的 `wechat` 节点迁移至数据库 `client_channels` 表（后台「系统管理 → 渠道管理」维护），**yaml 中的 wechat 配置已废弃**。内置渠道种子数据默认状态：

| 渠道 | code | 默认启用 | 说明 |
|---|---|---|---|
| 微信小程序 | mp | 否 | 需先配置 AppID/AppSecret 并手动启用 |
| 微信公众号 | gzh | 否 | OAuth 授权链路未开放，暂不可用 |
| App 应用 | app | 否 | App 支付 SDK 未接入，暂不可用 |
| 浏览器 H5 | h5 | 是 | 无需凭证 |

**升级/首次部署后若不配置 mp 渠道，小程序登录将直接报「微信小程序渠道未启用或未配置」**。上线步骤：

1. 登录管理后台 → 系统管理 → 渠道管理，点击小程序卡片配置生产 AppID/AppSecret 并保存；
2. 打开「启用」开关（服务端校验凭证完整性，凭证不完整时拒绝启用）；
3. 在「支付配置」中确认微信支付的「适用客户端渠道」勾选（全部不勾选 = 所有已启用客户端渠道可用）；
4. 用小程序真实登录一次验证 Code2Session 链路。

注意：渠道凭证保存后即时生效（登录/支付链路现取现用，无需重启）；AppSecret 不回传明文，留空保存表示保留原值。
