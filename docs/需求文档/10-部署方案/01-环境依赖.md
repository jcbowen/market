## 九、部署方案

### 9.1 环境依赖

项目支持两种部署方式，默认使用 Docker 方案。

#### 9.1.1 默认 Docker 方案

| 依赖 | 版本要求 | 说明 |
|---|---|---|
| Docker | 20.10+ | 容器运行时 |
| Docker Compose | v2+ | 服务编排，推荐随 Docker Desktop 一起安装 |
| Go | 1.26+ | 后端交叉编译（`node build.mjs`；Dockerfile 仅打包编译产物，构建镜像本身不需要 Go） |
| Node.js | 20.19+ 或 22.12+ | 前端构建（admin 用 vite 8，`engines` 为 `^20.19.0 \|\| >=22.12.0`；18 与 20.0~20.18 会在 `npm run build` 直接失败） |
| npm | 9+ | 包管理 |
| buf | 1.70+ | proto 代码生成（**仅开发期需要**，修改 `src/backend/common/proto/` 下 proto 后重新生成 pb.go；运行/构建不需要） |

**buf 安装与 proto 生成（2026-10-18 起，替代直接依赖 protoc）：**

```bash
# 安装（跨平台一致，需 Go 1.26+ 与 protoc 插件）
go install github.com/bufbuild/buf/cmd/buf@latest
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

# 生成（示例：product 服务；配置文件 buf.yaml / buf.gen.yaml 位于 common/proto/ 下）
cd src/backend/common/proto
buf generate --path product/product.proto
```

**本机没有 buf 时的 protoc 兜底（2026-10-24 实测）：**`buf generate` 是本仓库的生成约定，但产出物只取决于 `protoc-gen-go` / `protoc-gen-go-grpc` 两个插件与 `paths=source_relative` 参数，因此未装 buf 的机器可以直接用 protoc 生成同一份文件，无需为此安装新工具：

```bash
# 在 src/backend 下执行（--proto_path 指向 common/proto，import 路径与 buf 保持一致）
protoc --proto_path=common/proto \
       --go_out=common/proto --go_opt=paths=source_relative \
       --go-grpc_out=common/proto --go-grpc_opt=paths=source_relative \
       common/proto/payment/payment.proto
```

代价只有一处：生成物头部注释会是 `// protoc vXXX` 而非 buf 的 `// protoc (unknown)`，即与仓库里 committed 的 pb.go 有**一行版本注释差异**（已用 `common.proto` 逐字节比对取证，除该行外产物完全一致）。提交前把头部那行改回与存量一致的形态即可，不要把整份生成物重排。

除命令行工具外，后端构建还有两项仓库外的前置条件，`build.mjs` 在编译前会逐项检查：

- **本地 replace 模块**：`src/backend/go.mod` 用 `replace` 把 `github.com/jcbowen/jcbaseGo`、`github.com/jcbowen/wego`、`github.com/jcbowen/alipay-sdk-go-all` 指向仓库同级目录 `../../../jcbaseGo`、`../../../wego`、`../../../alipay-sdk-go-all`（即与 `market/` 平级的同名目录）。这些仓库不在本仓库内，需要单独获取到期望路径；缺失时脚本直接报出「缺哪个模块、放在哪个路径」并终止，不会代为下载。依赖获取方式见下文。
- **Go 模块缓存**：构建把 `GOPATH` 设为项目根目录，模块落在 `pkg/mod/` 下（不污染全局 GOPATH），因此换机器或清空 `pkg/` 后首次构建需要重新下载依赖。`go.sum` 缺行、`go.mod` 与 `go.sum` 不一致时，脚本会自动执行 `go mod tidy` 补齐后重试（`--no-auto-fix` 可关闭）；网络不可达时不做重试，只提示 GOPROXY 与 npm registry 的配置建议。

**依赖获取方式：**

- **本机开发**：把 `jcbaseGo`、`wego`、`alipay-sdk-go-all` 三个仓库克隆到与 `market/` 平级的目录（对应 replace 路径），构建直接使用本地源码，修改框架代码即时生效。`go.work` 仅作本地多模块联调用途，**不入库**。
- **本地依赖更新**：多台机器开发时，运行 VS Code 任务「pull-deps（拉取本地依赖最新代码）」（或 `node pull-deps.mjs`）即可批量更新上述仓库。清单直接读 `go.mod` 的本地 replace，各仓库执行 `git pull --ff-only`：已是最新、有未提交改动（跳过并提示）、无上游分支、分离头指针会分别报告；不执行 stash / merge / reset，不覆盖本地工作区。每个仓库同时输出最新 tag（HEAD 越过 tag 时注明落后提交数）、最新提交摘要与提交时间，换机器后不必逐个 `cd` 进仓库查看版本。
- **CI / 无本地依赖环境**：去掉 replace 后从公共模块代理拉取已发布版本（版本以 `go.mod` 的 require 为准：`jcbaseGo v0.15.7`、`wego v0.1.0`，均已推送至公共 proxy，无需私有仓库凭证）：

```bash
cd src/backend
go mod edit -dropreplace=github.com/jcbowen/jcbaseGo -dropreplace=github.com/jcbowen/wego
go mod download github.com/jcbowen/jcbaseGo github.com/jcbowen/wego
```

#### 9.1.2 非 Docker / 二进制方案

如果选择直接在宿主机运行后端二进制，需要额外准备：

| 依赖 | 版本要求 | 说明 |
|---|---|---|
| Go | 1.26+ | 后端编译 |
| Node.js | 20.19+ 或 22.12+ | 前端构建与运行跨平台脚本（脚本本身 18+ 可跑，admin 的 vite 8 把下限抬到 20.19/22.12） |
| npm | 9+ | 包管理 |
| MySQL | 8.0+ | 数据持久化，需自行安装或外接 |
| Redis | 7+ | 缓存与会话，需自行安装或外接 |
