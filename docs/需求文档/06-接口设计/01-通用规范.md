## 六、接口设计

### 6.1 通用规范

- 基础路径：`/api/v1/`（C端）、`/api/v1/admin/`（后台管理）
- 请求头：`Content-Type: application/json`，`Authorization: Bearer <token>`
- C 端版本与渠道请求头（`src/client/src/api/request.ts` 全部请求与上传统一携带，后端可用于版本统计、问题排查与灰度判断；当前后端仅透传不消费）：

| 请求头 | 取值 | 说明 |
|---|---|---|
| `X-Channel-Code` | `h5` / `gzh` / `mp` / `alimp` / `android` / `ios` / `pos` | 客户端渠道标识（与后台「渠道管理」的渠道 code 一一对应）：构建期按条件编译决定——H5→`h5`、微信小程序→`mp`、支付宝小程序→`alimp`、App 按运行系统→`android`/`ios`；`gzh` 待公众号 OAuth 授权链路开放后由服务端识别；`pos` 不携带该头，由网关在门店收银台入口固定按 `pos` 解析。未携带该头时服务端按 `h5` 口径兜底（渲染支付方式与解析登录/支付凭证均按此渠道） |
| `X-App-Version` | 如 `0.1.0` | 应用版本号（构建期从 git tag 读取，剔除 `v` 前缀与 `-beta` 预发布后缀——iOS App Store 强制 `x.y.z` 三段纯数字） |
| `X-App-Version-Code` | 如 `3` | 版本编号 = git tag 数量（每次打 tag 递增；App versionCode 同口径） |
| `X-App-Env` | `dev` / `release` | 运行模式：开发模式（uni dev）还是发布模式（uni build），按编译模式判定 |
| `X-App-Stage` | `develop` / `trial` / `release` / `gray` | 版本类型（小程序专属概念）：开发版/体验版/正式版/支付宝灰度版，经 `uni.getAccountInfoSync().miniProgram.envVersion` 运行时判定；H5/App 恒为 `release` |

  - 版本来源与注入机制见 `12-授权体系/02-小程序发版方案.md` 第 5.4 节。
- 响应格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

- 顶层结构由 `common/response.Response` 定义为 `code` / `message` / `data` / `total` 四个字段：`data` 为空时省略（`omitempty`）；`total` 为可选顶层字段（指针类型，网关当前所有接口均未填充，省略），分页总数以 `data.total`（`SuccessWithPage` 分页壳内）为准。
- **HTTP 状态码**：所有业务响应（含错误）均返回 **HTTP 200**（`response.Success` / `Error` / `GRPCError` 一律 `c.JSON(http.StatusOK, ...)`），真实结果看 body 的 `code`；前端以 `code == 0` 判断成功，不依赖 HTTP 状态码。

- 分页请求（网关统一以 `DefaultQuery` 解析查询参数，默认 `page=1`、`page_size=10`；个别接口有自定义默认值，如附件选择器列表默认 12）：

```json
{
  "page": 1,
  "page_size": 10
}
```

  - **单页条数上限 100**：所有网关分页解析必须走 `parsePageParams`（`gateway/handler/pos_shift.go`，`maxPageSize = 100`）收口，否则调用方可用 `page_size=100000` 把「列表」变成全表捞取 + 全量序列化，单请求即可打垮服务与网关内存。越界处理：`page<1` 归 1；`page_size<=0` 或无法解析回落缺省值；**超过上限时截断为 100 而不是重置为缺省值**（导出类调用方若突然只拿到 10 条会出现分页口径错乱）。新增列表接口不得自行 `strconv.Atoi` 后直接透传。
  - 服务层另有二次上限（网关截断后再兜一层，直连 gRPC 的内部调用同样受约束）：履约工作台列表 50、班次与营销列表 100、SKU 搜索 200、进销存报表 100。以服务端返回的为准。

- 分页响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [],
    "total": 100,
    "page": 1,
    "page_size": 10
  }
}
```

**文案覆盖机制（重要）**：body 的 `message` 不一定是上表默认文案，来源有两处——(1) 服务层（gRPC）错误带业务文案时，网关经 `common/response/grpc_error.go` 的 `TranslateGRPCError` 翻译：剥除 `rpc error: code = Xxx desc =` 包装后，有明确业务语义的状态码（如 `PermissionDenied`→11005、`FailedPrecondition`→10004、`NotFound`→10003、`AlreadyExists`→10006、`Aborted`→10007（乐观并发冲突：设置类整份覆盖保存的版本号已过期）等）**透传服务层自定义文案**；基础设施类状态码（Internal/Unavailable/DeadlineExceeded 等）与非业务语义码不透传原始消息，统一回落到上表通用文案（防内部细节泄露）。(2) 网关 handler 直接调用 `response.Error(c, 通用码, "自定义文案")` 覆写文案（如 C 端对门店单确认收货的网关前置拦截返回 `10001 门店订单请联系门店处理`）。因此 02/03 文档中「11005 门店订单请联系门店处理」（取消/退款经 order 服务 `PermissionDenied` 翻译而来）、「11005 您不是本社区履约人员」这类提示，实为**通用码 + 服务端/网关自定义文案**，前端应主看 `code` 分派逻辑、`message` 仅作展示。

### 6.1.2 管理端权限码目录

后台权限点命名统一为 `模块:动作`（个别三级如 `payment:raw:view`）。**唯一清单源**为
`src/admin/src/constants/permissions.ts`（前端角色管理与社区权限页共用），网关侧在每条管理路由上
以 `RequirePermission(...)` 声明，两侧必须一一对应——只在一侧登记会出现「能勾选但不生效」或
「接口可调用但页面不可见」。新增权限点须同时改三处：前端常量表、网关路由、社区权限上限白名单
（系统级权限点还要确认是否进可分配列表）。

| 分组 | 权限码 | 说明 |
|------|--------|------|
| 工作台 | `dashboard:view` | 工作台与个人设置页入口 |
| 商品 | `product:view` / `product:create` / `product:update` / `product:delete` | 商品与分类管理；`create` 同时是应用中心「数据导入」的路由门槛（另需超管） |
| 库存 | `inventory:view` / `inventory:create` / `inventory:update` | 库存工作台、进销存单据与报表 |
| 订单与售后 | `order:view` / `order:update` / `order:create` / `refund:view` / `refund:update` | `order:create` 是收银台全部接口的门槛（含班次、挂单、直接收款） |
| 支付（系统级） | `payment:raw:view` | 支付异常报文原文查看。**不进社区管理员默认上限**，实际仅超管可勾选生效 |
| 会员 | `user:view` / `user:create` / `user:update` | 会员列表、资料与状态维护 |
| 营销 | `marketing:view` / `marketing:create` / `marketing:update` / `marketing:delete` | 优惠券、秒杀、满减、免配送费、Banner |
| 统计 | `statistics:view` | 数据统计与全平台统计 |
| 门店（社区级） | `community:config` | 门店设置与常用应用（社区级覆盖式共享写入） |
| 社区（系统级） | `community:view` / `community:create` / `community:update` / `community:delete` | 社区管理与社区权限上限 |
| 行政区划（系统级） | `region:view` / `region:update` | 行政区划数据与更新 |
| 系统设置（系统级） | `settings:view` / `settings:update` | 站点/支付/渠道/售后/附件配置 |
| 员工 | `admin:view` / `admin:create` / `admin:update` / `admin:delete` | 员工账号与任职 |
| 角色 | `role:view` / `role:create` / `role:update` / `role:delete` | 社区私有角色（社区角色总览页只读） |

判定规则（`gateway/middleware/permission.go` 的 `RequirePermission(permissions ...string)`）：

- **多码任一命中即放行**：如统计类接口挂 `RequirePermission("order:view", "statistics:view", "dashboard:view")`，
  只具 `order:view` 的账号同样可访问营收报表；文档中「A / B」写法即此语义，不是「两者都要有」
- 超管（`admin_users.is_super`）与权限集含 `"*"` 的角色直接短路放行
- 其余账号按「管理员 × 当前社区」**实时**解析任职角色权限并集，再与该社区权限上限取交集后判定；
  令牌里的权限快照不参与判定，改权限即时生效
- 非 `admin` 类型令牌（C 端会员令牌）一律拒绝

### 6.1.3 运维与静态接口

以下路由不属业务接口，但同由网关 18080 提供，部署、探测与排障依赖它们，故一并登记。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/health` | 健康检查（免登录）。响应 `{service:"gateway", time:<unix秒>, debugger:{...}}`。compose 健康探针、测试框架 `globalSetup` 与负载均衡探活均以此为准 |
| GET | `/` | 301 跳转 `/s/`（C 端 H5 入口） |
| GET | `/s/*filepath` | C 端 H5 静态资源；入口 HTML `no-cache`，`/s/assets/` 长缓存 |
| GET | `/b/*filepath` | 后台管理静态资源；入口 HTML `no-cache`，`/b/assets/` 长缓存（`public, max-age=31536000, immutable`） |
| GET、HEAD | `/<local_dir>/*filepath` | 附件静态目录，默认 `/uploads/`，目录名由附件配置 `attachment_config.local_dir` 驱动（改名后网关路由随之变化，既有 URL 需同步迁移） |
| GET | `/api/v1/site-info` | 免登录站点品牌信息（站名/logo/favicon/页脚/SEO），供 H5 与后台登录页使用；均未显式配置部署域名时 `base_url` 与站内图片地址按当前访问域名现推兜底返回（仅响应层，不入库） |

附件静态路由的两条特殊规则：

- `/uploads/seed/**` 为镜像内置演示素材，随镜像打包（不入库），仅供演示数据引用
- `/uploads/exports/**` **固定返回 404**：导出文件属私有数据（含订单与会员信息），不提供静态直链，
  只能经带归属校验的 `GET /api/v1/admin/orders/export-tasks/:id/download` 鉴权下载
  （普通管理员仅可下载自己创建的任务，超管可下载全部，删除仅超管）

附件 URL 出库拼装口径（`common/attachmenturl` 全系统统一，product/user/order/cart 共用）：

- 数据库一律存附件相对路径；出库统一拼为「配置的附件访问域名 + 附件路径」的完整地址
- 附件访问域名只来自显式配置（后台手填、站点设置 base_url / `SITE_BASE_URL` 联动），
  运行期不做请求域名补写（避免首访域名固化成错误配置）
- 均未显式配置时的兜底：网关把当前请求的 `scheme://host` 经 gRPC metadata（`x-request-base`）
  透传给各服务，出库按该基址拼完整 URL——小程序/APP 端 image 组件无法解析站内相对路径；
  基址不可用（后台任务/进程内调用）时降级为站内绝对路径 `/<local_dir>/<path>`，由浏览器按
  当前访问域名解析。兜底仅发生在响应层，一律不入库

### 6.2 C端接口
