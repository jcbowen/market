| 方法 | 路径 | 说明 | 认证 |
|------|------|------|------|
| POST | /api/v1/auth/weixin-login | 微信小程序登录 | 否 |
| POST | /api/v1/auth/login/phone | 手机号验证码登录 | 否 |
| POST | /api/v1/auth/phone-code | 发送短信验证码 | 否 |
| POST | /api/v1/auth/refresh | 刷新 token（凭 refresh_token 换新 access_token；**同时轮换 refresh_token，返回与登录一致的完整登录信息（含 user）**；public 组注册，不需要 access_token） | 否（凭 refresh_token） |
| POST | /api/v1/auth/logout | 登出：清除后端下发的 httpOnly refresh cookie（H5 用），不要求登录态 | 否 |

> **当前实现状态（上线前置项）**：手机号登录为**测试模式**——`POST /auth/login/phone` 仅校验手机号格式即登录/注册，**不校验验证码**（请求体 `code` 字段仅作兼容保留，传任意值均不校验）；`POST /auth/phone-code` 为测试桩，直接返回成功、**不调用真实短信服务**。正式上线前必须接入真实短信渠道并恢复服务端验证码校验，否则任意手机号可冒名登录。

> **默认昵称口径**：登录链路自动建号时补默认昵称——有手机号取「会员+尾号 4 位」（与后台/收银台注册会员同口径），无手机号（微信等渠道登录）取「微信用户」；仅在昵称为空时写入，已有昵称不会被重复登录覆盖，用户改名走 `PUT /api/v1/user/profile`。

```json
}
```

**手机号登录请求：**
```json

```

**登录响应：**
```json
{
  "code": 0,
  "data": {
    "access_token": "eyJ...",
    "refresh_token": "eyJ...",
    "expires_in": 7200,
    "user": {
      "id": 1,
      "nickname": "用户昵称",
```

说明：`user` 含 `community_name` 字段（当前网关签发登录态时固定回传空串，社区名称前端按 `community_id` 从社区列表/详情接口取）。

**`refresh_token` 的两种承载方式（按请求头分岔）**：登录请求带 `X-Refresh-Cookie: 1`（H5）时，响应体**不含 `refresh_token`**，令牌改由 httpOnly cookie `market_refresh`（`Path=/api/v1`、`SameSite=Lax`、`Max-Age` 取 `jwt.refresh_token_ttl`）下发；不带该头（微信小程序、App）时按上例在响应体返回，由前端本地存储。与后台同源同域，故**两端 cookie 分名**（后台为 `market_admin_refresh`、`Path=/api/v1/admin`）——共用一枚会让后台登录覆盖会员令牌、后台登出把会员会话一起踢下线。属性与安全口径详见 `07-基础设施/01-端口与认证.md` 的「refresh_token 的承载方式」与「refresh 令牌轮换与吊销」。

**刷新 token 响应（`POST /auth/refresh`）：** 结构与登录响应完全一致——除新 `access_token` 外**同时轮换 refresh_token** 与 `user` 完整信息，前端应替换本地旧值（cookie 承载方式下响应体不带 refresh_token，cookie 由后端直接续发）。令牌来源为「cookie 优先、请求体兜底」，故 H5 的刷新请求体可为空对象，小程序/App 仍传 `{refresh_token}`。校验口径：仅 `type=user` 且用途为 refresh 的 token 可刷新（用 access token 换取返回 11005），token 无效/过期返回 11002，两者皆无返回 11001，用户被拉黑返回 11008「系统错误，请联系工作人员」。**旧令牌一次性消费**：刷新时旧 refresh 的 jti 以 Redis `SETNX` 原子登记为「已用」，同一枚令牌被并发提交两次只有一次能换出新令牌，其余按 11002 拒绝；登出（`POST /auth/logout`）同样吊销当前令牌，故 7 天有效期内被盗/已注销的令牌不再能续命。Redis 不可用时该防线降级放行（与登录锁定同契约，缓存故障不关闭认证入口）。

补充说明（2026-10-17，商城流程审查修复批次）：
- **秒杀价临时关闭**：秒杀活动的价格计算逻辑当前已在服务端全局关闭（`flashSalePriceEnabled=false`，秒杀库存扣减与限购校验尚未实现，防止超卖资损），下单与免配送费试算均按 SKU 基础售价计算，不叠加秒杀价；待库存扣减与限购完整实现后重新开放，届时本说明同步更新。
- **重复下单防护**：同一用户 + 社区 + 配送方式 + 优惠券 + 商品列表（SKU 与数量排序后哈希）在 5 秒窗口内重复提交会被拒绝，返回 `10001`「请勿重复提交订单」，防止网络抖动/重复点击造成重复下单；窗口内修改数量、SKU、配送方式或优惠券视为不同指纹，不受影响（2026-10-18 扩充指纹维度）。下单失败（如库存不足被拒）时立即释放指纹，用户修复后可立即重试，不被去重窗口拦截。当前为网关单实例内存实现，多实例部署需替换为分布式存储。
- **数量上限校验**：`items[].quantity` 须在 1~999 之间，超出范围（含 0、负数）返回 `10001`「单品购买数量须在 1~999 之间」。
- **服务端购物车兜底清理**：下单成功后，服务端异步按 `items[].sku_id` 删除该用户购物车中对应 SKU（不依赖前端是否传 `cart_item_ids`），防止客户端崩溃/网络中断导致已购商品残留在购物车。
- **per-user 限流**：本接口在通用 IP 限流之外，额外启用按用户维度的令牌桶限流（桶容量 5、补充速率 0.08/s，约 12.5s 补 1 个令牌），超出返回 HTTP 429 `10005`「操作过于频繁，请稍后再试」。

**支付宝 H5 交互流程**（`src/client/src/utils/pay.ts`）：

- 非微信内置浏览器：`location.href` 直接跳转 `alipay_pay_url`（服务端 `alipay.trade.wap.pay` 经 `PageExecute` GET 取得的带签名网关 URL），进入 `redirected` 状态，支付结果以回跳后的订单状态为准
- 微信内置浏览器：无法唤起支付宝且收银台无「继续浏览器付款」兜底入口，跳转独立**免登录引导页**（`pages/pay/alipay?no=<payment_no>&order_id=<order_id>`），进入 `guided` 状态；引导页只携带支付单号不携带支付链接（支付链接含 `#`/`?` 保留字符，经 uni-app H5 路由 query 传递会被框架编解码破坏导致支付宝报 `missing-method`），页面打开后凭单号调 `GET /payments/alipay/url` 实时换取链接——微信内展示分步指引与「复制支付链接」，系统浏览器打开时自动唤起支付宝收银台
- 微信小程序/公众号等微信生态内：技术不可用，返回 `unsupported`（支付宝仅 H5 端可用，后台渠道勾选已同步禁用 `mp/gzh/app` 组合）
- 跳转前先注册一次性回站监听（`visibilitychange`/`pageshow`）：用户从支付宝回站（`return_url` 回跳或手动切回标签页）自动刷新订单状态，消除与站内路由的竞争和重复发起支付；非 H5 端为空实现
- 支付单状态最终以异步通知回调落账为准，`return_url` 回跳仅作展示刷新用途

**说明：** 仅待支付（status=1）订单可发起支付；对已支付或已终态的订单发起支付返回 `10004 订单当前状态不可支付`，支付服务层亦存在幂等拦截，订单已有支付成功记录时返回 `10006 订单已支付，请勿重复支付`；渠道未开启或配置不完整时返回 `10001 当前支付方式未开启或配置不完整`；支付单查询发生数据库异常（非"记录不存在"）时返回 `10002` 并拒绝建单，防止故障被当作无支付记录而导致重复支付——该错误为 gRPC Internal 类，对外文案统一回落为「服务器内部错误」（原始文案「支付状态查询失败，请稍后重试」仅记录服务端日志，不透传），底层细节见 01 通用规范文案覆盖机制。
