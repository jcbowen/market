
#### 认证模块

| 方法 | 路径 | 说明 | 认证 |
|------|------|------|------|
| POST | /api/v1/admin/auth/login | 管理员登录（请求带 `X-Refresh-Cookie: 1` 时，`refresh_token` 改由 httpOnly cookie 下发、响应体不再返回；不带则维持响应体下发，兼容旧前端缓存与未更新的 POS 端） | 否 |
| POST | /api/v1/admin/auth/refresh | 刷新 token（令牌来源**cookie 优先、请求体兜底**（兼容 JSON body 与 form 表单）；仅换发新 access_token，**不轮换 refresh_token**） | 否 |
| POST | /api/v1/admin/auth/logout | 登出：清除后端下发的 httpOnly refresh cookie，不要求登录态 | 否 |
| GET | /api/v1/admin/auth/info | 当前管理员信息 | 是 |

说明：登出需调用 `POST /api/v1/admin/auth/logout`——`refresh_token` 改由后端 httpOnly cookie 承载后，JS 删不掉它，必须由后端下发同名负 `Max-Age` cookie 清除（access_token 仍由前端自行删除）。承载方式与安全口径详见 `07-基础设施/01-端口与认证.md`。

**管理员登录请求：**
```json
{
  "username": "admin",
  "password": "123456"
}
```

**刷新 token 响应（`POST /api/v1/admin/auth/refresh`）：**
```json
{
  "code": 0,
  "data": {
    "access_token": "eyJ...",
    "expires_in": 7200,
    "expires_at": 1760007200
  }
}
```

说明：
- 实际响应结构为 `{access_token, expires_in, expires_at}`（`expires_at` 为 access_token 到期秒级时间戳）；**不返回新 refresh_token、不轮换**——与 C 端 `/api/v1/auth/refresh`（轮换 refresh_token 并返回含 `user` 的完整登录信息）**行为不同**，前端勿复用同一刷新逻辑。
- 强校验 token 用途：仅 `type=admin` 且用途为 refresh 的 token 可刷新；未传 refresh_token 返回 `11001`，token 无效/类型或用途不符返回 `11002`。

**新增商品请求：**
```json
{
  "category_id": 1,
  "name": "新鲜西红柿",
  "description": "当日采摘",
  "cover_image": "https://...",
  "images": ["https://...", "https://..."],
  "unit": "斤",
  "is_multi_spec": true,
  "min_buy": 1,
  "sort": 0,
  "specs": [
    {
      "id": 0,
      "temp_id": "new_spec_1",
      "name": "规格",
      "sort": 0,
      "values": [
        { "id": 0, "temp_id": "new_value_1", "name": "大果", "sort": 0 },
        { "id": 0, "temp_id": "new_value_2", "name": "小果", "sort": 1 }
      ]
    },
    {
      "id": 0,
      "temp_id": "new_spec_2",
      "name": "重量",
      "sort": 1,
      "values": [
        { "id": 0, "temp_id": "new_value_3", "name": "500g", "sort": 0 }
      ]
    }
  ],
  "sku_items": [
    {
      "id": 0,
      "spec_value_ids": ["new_value_1", "new_value_3"],
      "sku_code": "XHS-001",
      "price": 5.99,
      "original_price": 6.99,
      "cost_price": 4.50,
      "stock": 100,
      "safety_stock": 20,
      "image": "https://...",
      "barcode": "6901234567892"
    },
    {
      "id": 0,
      "spec_value_ids": ["new_value_2", "new_value_3"],
      "sku_code": "XHS-002",
      "price": 3.99,
      "original_price": 0,
      "cost_price": 3.00,
      "stock": 80,
      "safety_stock": 10,
      "image": "https://..."
    }
  ]
}
```

说明：
- `specs` 为规格树（规格名 + 规格值），仅多规格商品提交；单规格传空数组，只提交一条默认 `sku_items`
- 新增的规格名/规格值不传 `id`，传 `temp_id`（如 `new_spec_1`）；`sku_items.spec_value_ids` 引用同一 `temp_id`，服务端落库后自动映射为真实 ID
- 已存在的规格名/规格值传真实 `id`，`temp_id` 可省略
- 服务端按本次提交做 diff，未提交的规格名/规格值/SKU 将被软删除，并回写商品的价格区间与总库存
- 更新商品（PUT /api/v1/admin/products/:id）请求体与新增一致（多 `id` 字段）；`images` 传空数组视为不变更（保留现有图片），非空时全量替换
- `sku_items.sku_code` 留空时：已存在的 SKU 保留原编码，新建的 SKU 由服务端自动生成（`P{商品ID}-{随机后缀}`），避免与历史（含已禁用）编码冲突
- `sku_items.original_price` 划线价/原价（选填，0 表示未设置；`SkuItemReqItem` 字段，随 price/cost_price 一并入库回显）
- `sku_items.barcode` 商品条形码（选填，挂 SKU 级，多规格商品每个规格可各配一条；纯数字 6-20 位宽松校验，不做 EAN 校验位强校验；同社区内在售 SKU 间唯一——重复时返回 10001 并提示占用商品名；商品软删后其条码自动回收可复用；条码精确查询见 `GET /admin/products/barcode/:code`）
- `on_sale_at` 定时上架时间（选填，格式 `YYYY-MM-DD HH:mm:ss`，须晚于当前时间）：非空时商品保存为下架+预约，到点由 product-service 定时上架调度器（每分钟，Redis 分布式锁 `scheduler:product:sale:upload:lock` + 原子条件 UPDATE）自动上架；修改商品时传空串取消定时；列表「仓库中」Tab 可见预约中商品（`on_sale_at` 字段随商品详情/列表返回）

**上下架请求：**
```json
{
  "status": 0
}
```

**进销存口径要点：**

- 采购单状态机：`1 草稿 → 2 已下单 → 3 部分入库 → 4 已完结`，`5 已取消`；入库回写 `received_quantity` 驱动 2→3→4，接口不做跳状态。
- 单据响应 proto 全 `omitempty`：`supplier_id=0` 等零值键会从 JSON 中消失，前端与测试均需按缺省值容错。
- 单据不存在由服务层以 `InvalidArgument` 返回（映射 10001），**不是 10003**。
- 报表流水口径：`type=1` 入库、`type=2 AND ref_no=''` 才是销售出库（计入毛利），出库单流水 `ref_no` 为单号故不计毛利；`type=3` 盘点、`type=4` 释放、`ref_no='FORM'` 为表单调整。
- 报表时间窗只约束聚合值、不筛行：窗口内无流水时期初=期末=当前库存（SQL 用 `COALESCE(fr.before_stock, s.stock)` 回退）；`start_date/end_date` 缺省为「今天往前 30 天」，且不校验格式，非法日期/起止倒挂静默按「窗口内无流水」处理。
- 已知缺陷（未修，见《测试覆盖补齐-待办清单.md》）：① 报表/批次/预警 SQL 缺 `p.status <> 2`，软删商品的 SKU 仍会出现（与 `/inventory/skus` 口径不一致）；③ `products.stock` 汇总列仅由商品编辑回写，入库/出库/下单扣减不更新，导致商品列表「已售罄」Tab 口径不可靠。
- 分页入参归一（c4f5287 起，原缺陷 ②「`page=0` 使 `offset` 为负触发 10002」已修）：网关 `parsePageParams` 把 `page<=0` 归一为 1、`page_size<=0` 归一为该接口默认值（多数 10，常买排行为 5）并封顶 100，服务层 `reportPage` 同样兜底；回显的 `page/page_size` 是归一后的值，不是请求原值。管理端常买接口因此恒走分页模式（`total` 为真实去重数），C 端不传 `page` 的 limit 模式不受影响。

说明：

**代客退款请求（`POST /api/v1/admin/orders/:id/refund`）：**
```json
{
  "reason": "顾客电话申请",
  "mode": 2,
  "amount": 20.00,
  "items": [],
  "refund_freight": false
}
```

字段说明：
- `mode` 退款模式：`0/1` 按商品退（`items` 指定订单商品行与退货数量，为空=整单退，退商品并回补库存）；**`mode=2` 仅金额退**——不退商品、不回补库存，`amount` **必填**且不得超过订单剩余可退金额
- `reason` 必填；`amount` 按实付口径由服务端汇算，按商品退时仅允许调低（mode=2 时为自定义金额）；`refund_freight` 整单退时按运费退还策略生效
- **可退状态门禁**：订单须为 已支付(2)/备货中(3)/配送中(4)，或**到店单（`delivery_type=3`）的已完成(5)**；其余状态返回 `10001 订单状态不允许退款`。到店单收款即在事务内自动完结为 5（非用户确认收货），故放行，否则门店售出订单无法退款；自提/配送的已完成单仍不可退。退款完成后：全额退完 → 订单 8 已退款；未退完 → 回到进入退款中(7) 之前的来源状态（到店单回 5，其余回 2/3/4）。前端入口统一走 `constants/order.ts` 的 `canAdminRefund`，与后端 `adminRefundable` 同口径

**订单详情 `refunds` 数组（GET /api/v1/admin/orders/:id）：** 返回本单全部退款单（每次售后一条），元素字段：`id`、`refund_no`、`order_id`、`order_no`、`amount`（退款金额）、`freight_amount`（退运费）、`type`（1整单退 2部分退）、`reason`、`status`（退款状态）、`reject_reason`、`refund_time`、`created_at`、`items`（退款商品明细：`id`/`refund_id`/`order_item_id`/`sku_id`/`product_name`/`spec_name`/`quantity`/`refund_amount`）。

**订单详情支付区块（2026-10-21 新增，同一次 GET 返回）：**

- `payments`：支付尝试明细数组（一笔单可多次发起支付），每行 `id`、`payment_no`、`pay_type`/`pay_type_text`、`amount`、`status`（1待支付 2成功 3失败 4已退款 5已关闭）、`transaction_id`、`pay_time`、`created_at`、`confirm_source`（0未确认 1渠道回调 2对账补偿 3后台手动同步/人工标记 4线下收银台）、`confirm_ref`（`cancel-guard`/`manual-sync`/`manual-mark`/`reconcile:支付单号`）、`reconcile_count`、`last_reconciled_at`
- `payment_summary`：`{ attempts, succeeded, succeeded_amount }` —— `succeeded>1` 即重复支付（同一订单被扣两次），详情页据此提示立刻走退款
- `payment_logs`：该单的支付通知/对账时间线（复用异常流水行结构，`include_ok=true` 口径，含确认成功的正常轨迹，最多 50 条）
- `can_view_payment_raw`：当前管理员是否具备 `payment:raw:view`（决定 `payment_logs` 内是否下发报文原文字段）
- `payments_error` / `payment_logs_error`：支付服务调用失败时的错误文案。**必须区分「没有记录」与「查不到」**——前者是空数组、后者带错误文案，前端不得把 RPC 失败渲染成「该单未发起过支付」

**「同步支付状态」请求/响应（`POST /api/v1/admin/orders/:id/payment-sync`）：**

```json
{ "payment_no": "" }
```

- `payment_no` 可选：同一订单可能有多次支付尝试，默认核实最近一笔待支付的渠道单；排查特定一笔时才传
- 允许空 body（绑定失败按空值继续）
- 操作人身份不在请求体里：网关从登录态取 `admin_username` 与用户 ID 填入 gRPC 请求的 `operator_name`/`operator_id`，用于挂账待办的类别归属（`kind=3` 系统 / `kind=8` 人工核实）、`detect_remark` 留痕与订单状态日志的 `operator_type`。前端既不需要传、也无法冒充系统
- 订单状态 1待支付 / 100取消处理中 走「核实并补同步」，6已取消 走「渠道核实挂账」（只读渠道 + 产出待办，2026-10-23 放开），其余返回 `10004 订单当前状态无需同步支付状态`
- 响应字段显式列出，零值不被 omitempty 吞掉：

```json
{
  "code": 0,
  "data": {
    "paid": false,
    "changed": false,
    "channel_state": "NO_PAYMENT",
    "transaction_id": "",
    "amount": 0,
    "payment_no": "",
    "message": ""
  }
}
```

- `channel_state` 为渠道侧事实：`PAID` 已收款、`PAYING` 渠道处理中、`CLOSED` 交易已关闭、`NOT_EXIST` 渠道无此交易、`ERROR` 渠道查询失败、`NO_PAYMENT` 本地没有可核实的渠道支付单（订单从未发起支付，或只有现金/货到付款单）
- 只有 `PAID` 且补同步成功时 `changed=true`；其余一律 `paid=false`、`changed=false`，本地状态零改动，可重复点击。**`ERROR` 表示未能确认收款状态，调用方不得据此判定资金状态**
- 支付单已是成功态（重复点击）时回传 `PAID` + `paid=true` + `changed=false`，`message` 为「支付单已确认支付，无需同步」，不再打扰渠道
- 社区隔离：跨社区订单按不存在处理；订单不属当前社区语境时返回无权限

**人工「标记已支付」（`POST /api/v1/admin/orders/:id/payment-mark-paid`）：**

```json
{
  "payment_no": "ZF...",
  "transaction_id": "渠道交易号",
  "amount": 12.5,
  "remark": "商户后台截图核对，回调未达"
}
```

- 四字段均 `binding:"required"`，缺失返回参数错误并提示「支付单号、渠道交易号、收款金额与核实依据均必填」
- 仅 `status=1` 待支付订单可用；已取消/已支付订单返回 `10004`，提示资金挂账须到支付异常页走退款（`6→2` 在订单状态机上必然失败，只会造出半截数据）
- 服务端校验链：支付单存在（否则 `支付单 xxx 不存在`）→ 非现金/货到付款（否则「无需人工标记」）→ 状态为待支付 → 填写金额与应付金额**分位一致**（否则提示改用退款流程）
- `remark` 落库前自动追加 `（操作人 admin:<用户ID>）`，保证可追责；`confirm_source=3`、`confirm_ref=manual-mark`

**支付异常队列（`GET /api/v1/admin/payments/anomalies`）：**

| 参数 | 说明 |
|---|---|
| `handled` | **筛选选择器**，不是落库值：`1`=只看待处理（DB `handled=0`）、`2`=只看已处理（DB `handled=1`）、`0`/缺省=全部。前端选项与接口入参同口径，勿与行数据的 `handled` 字段（0待处理/1已处理）混用 |
| `order_id` | 按订单过滤（订单详情时间线入口） |
| `include_ok` | `true`/`1` 时包含结果=确认成功的正常轨迹；默认只回异常（`result<>1`） |
| `page`/`page_size` | 分页 |

响应：`list`（行结构同 `payment_logs`）、`total`、`pending`、`can_view_raw`、`community_scope`。

- 行字段：`id`、`kind`（1渠道回调 2对账补同步 3挂账检出-系统 4渠道关单 5后台手动同步 6放弃对账 7人工恢复退款收敛 8挂账检出-后台人工核实）、`result`（1确认成功 2幂等忽略 3验签/解密失败 4金额不符 5处理异常 6渠道未支付 7渠道无此交易 8关单结果 9资金挂账 10订单同步失败 11人工恢复退款收敛）、`channel`、`payment_no`、`order_id`、`order_no`、`community_id`、`pay_type`、`amount`、`error_msg`、`handled`、`created_at`、`can_view_raw`、`has_raw`
- `detect_remark` / `remark`（2026-10-24 新增随行下发）：前者是**检出留痕**「谁、在什么本地状态下登记了这条流水」（系统触发标注为系统），后者是**人工销账依据**。两者分列是因为销账 SQL 整列覆写 `remark`，写在一起责任链会在销账那一刻断掉。前端「留痕/依据」列优先显示 `detect_remark`，历史数据无留痕时回落 `remark`
- 「去退款」直达入口按 `result=9 资金挂账` 判定，不按 `kind=3`——挂账拆成 3/8 两个来源后，按 kind 判会让人工检出的那批丢掉入口
- `raw_body` / `headers` **仅当具备 `payment:raw:view` 时随行下发**（该权限点刻意不进社区管理员默认权限上限，实际只有超管可见）；`headers` 中签名与证书序列号入库前已掩码，支付宝的 `raw_body` 是含 `sign` 原文的通知参数 JSON、微信的是渠道密文正文
- `community_scope`：当前可见社区（超管为 `0`=全量，社区管理员为本社区 ID）；`community_id=0` 的流水（验签失败连支付单都解析不出）只对超管可见
- `pending` 是**社区口径**的待处理数（红标依据），不随 `handled`/`order_id` 筛选变化
- 销账 `POST /api/v1/admin/payments/anomalies/:id/handle`：`remark` 必填；未命中（他人已销账或 ID 过期）返回「记录不存在或已销账」，据此刷新列表而非当作系统故障

**优惠券发布状态机与编辑边界（M 第①期）：**
- `publish_status`：0草稿（默认）→ 1已发布，通过创建时 `publish_status=1`（存草稿不传）或 PUT 传 `publish_status=1` 发布；**无反向流转**（下架用 grant_status 停发）。
- **草稿态** PUT：全字段可改（名称/类型/门槛/面值/数量/限领/领取窗口/有效期/进中心开关/规则文案/scopes 全量替换）。
- **已发布态** PUT 仅接受：`total_count`（仅允许增大，补充数量）、`grant_status`（1发放中/0停发）、`rule_text`；其余字段（名称/门槛/面值/有效期/范围等）传了也会被服务端忽略，前端同步置灰。
- 原启用开关 `status` 已由发布状态机取代，PUT 不再透传。
- 删除券：草稿或已发布均可删除（已领取的用户券随之失效）。
- 商品范围 `scopes`：scope_type 2=包含分类 3=包含商品 4=排除分类 5=排除商品；不传或空=全部商品可用。下单时门槛与优惠基数均按「范围内商品金额」计算，范围外商品金额不计入。
- **规则文案 `rule_text`（M 第③期）**：后台表单支持「按当前配置一键生成」初版文案（按类型/门槛/面值/有效期/领取窗口/商品范围拼装），生成后可人工编辑；纯前端拼装，接口无新增。

**附件预签名响应：**
```json
{
  "code": 0,
  "data": {
    "attach_id": "12",
    "hit": false,
    "url": "https://bucket.oss-xxx.aliyuncs.com/images/20261011/11/mkt080102123456.jpg?签名参数",
    "method": "PUT",
    "headers": { "Content-Type": "image/jpeg" },
    "final_url": "https://bucket.oss-xxx.aliyuncs.com/images/20261011/11/mkt080102123456.jpg",
    "remote_path": "images/20261011/11/mkt080102123456.jpg"
  }
}
```

附件上传流程说明：
- **上传大小上限是「分口径」而非统一值**，实际生效的是链路上最严的一道：
  - 网关请求体上限 12MB（`http.MaxBytesReader`，覆盖后台图片上传、C 端图片上传、支付证书上传等全部 multipart 路由），超出即报「缺少文件字段 file 或文件超过 12MB 上限」；网关不校验单文件大小。`gin` 的 `MaxMultipartMemory` 未设置（默认 32MB），因请求体已被截断在 12MB，该项不构成绕过风险，无需调整。
  - 图片大小上限由 product 服务把守，默认 5MB，可由后台附件设置 `attachment_config.max_size`（单位：字节，0=默认 5MB）调整；本地直传与 OSS `presign` 同口径，超出报「文件大小超出限制（最大 NMB）」。**因此 5MB~12MB 的图片会在网关放行后被 product 服务拒绝**，前端提示以服务端返回为准。
  - 支付证书上限 64KB（payment 服务 `payCertMaxSize`，PEM 通常小于 10KB），扩展名限 `.pem/.key/.txt/.crt`。
- **OSS 模式**：前端分块计算文件 MD5 → `presign` → `hit=true` 时直接使用 `final_url`（秒传）；否则以 `method + url + headers` PUT 直传 OSS → `confirm`（回传 `attach_id` 与 `md5`）激活秒传记录
- **本地模式**：multipart 直传 `/api/v1/admin/upload/image`，响应 `url` 即可直接访问的地址（`<scheme>://<host>/uploads/<remote_path>`）
- **图片字段存储规则**：商品封面/图库、Banner 图片等业务表图片字段统一只存相对路径（remote_path），写入时后端自动剥离域名；查询响应由后端按附件配置拼接为完整 URL，前端直接渲染回显即可，无需自行转换
- `md5` 统一为文件完整二进制内容的标准 MD5、32 位小写十六进制（等价 `md5_file()`）

#### 后台 WebSocket 推送模块（新订单语音通知，2026-10-24）

订单**支付成功**后实时推送后台，前端收到事件播放提示音并语音播报。事件由 order 服务在
`UpdateOrderStatus` 目标状态为 2 时（全部支付路径的收口：渠道回调、线下现金/货到付款、
付款码、后台补同步、调度器补同步，含到店单收款即完结 2→5）经 Redis 频道
`market:order:paid` 发布（`common/eventbus`），gateway 订阅后按社区过滤推送。

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET（WS 升级） | /api/v1/admin/ws | 后台 WebSocket 连接：事件推送通道 | order:view + 社区校验 |

**握手约定：**

- 浏览器 WebSocket 握手无法自定义请求头，鉴权令牌来源分两级（2026-10-24 加固）：
  **httpOnly cookie `market_admin_access` 优先**（后台登录/刷新时随 `X-Refresh-Cookie: 1`
  声明由后端下发，与 refresh cookie 同域同路径 `/api/v1/admin`，随同源握手自动携带，
  令牌不落 URL 与网关/代理访问日志）；**查询参数兜底**（旧前端缓存、POS 等未携带
  cookie 的客户端）：`ws(s)://<host>/api/v1/admin/ws?access_token=<access_token>&community_id=<当前社区>`。
  网关 `WSAuthMiddleware`（gateway/middleware/ws.go）把令牌与社区声明映射回标准
  `Authorization` / `X-Community-Id` 请求头后，完整复用既有 admin JWT → 社区校验 →
  `RequirePermission("order:view")` 鉴权链，与普通 admin 接口同一套口径
- 握手声明的 `community_id` 决定该连接的推送范围；前端切换社区须断开重连刷新
- 连接经 gorilla Hijack 升级，网关 HTTP Server 的 60s 读写超时对其不生效；
  服务端每 ~54s 发协议层 ping，浏览器自动回 pong 维持存活

**服务端消息（JSON）：**

```json
{ "type": "hello", "data": null }
{ "type": "order.paid", "data": { "order_no": "20261024...", "community_id": 1, "pay_amount": 12.5, "delivery_type": 3, "source": 2, "status": 5, "pay_time": "2026-10-24 19:20:00" } }
{ "type": "order.refund", "data": { "order_no": "20261024...", "community_id": 1, "refund_no": "TK2026...", "amount": 12.5, "delivery_type": 3, "source": 2, "action": "completed", "operator_type": "admin", "reason": "", "event_time": "2026-10-24 20:30:00" } }
```

- `order.refund`：退款事件（频道 `market:order:refund`），两个发布点——
  C 端申请退款成功（`action="apply"`，退款单待审核，需后台处理）与
  退款成功统一收尾 `completeRefundSuccess`（`action="completed"`，覆盖后台代客、
  审批同意、重试退款、调度器同步全部完成路径）；货到付款未收款订单的直接取消
  无资金动作，不发此事件。`operator_type`: user 会员申请 / admin 后台操作 /
  system 系统自动（如 72h 超时自动同意）

- `hello`：握手成功欢迎，前端收到后复位重连退避
- `order.paid`：支付成功事件，载荷结构与 `common/eventbus.OrderPaidEvent` 对齐
  （`delivery_type`: 1自提 2配送 3到店；`source`: 1C端用户 2收银台代客；
  `status`: 支付完成后的订单状态，到店单为 5，其余为 2）
- 未知 `type` 前端静默忽略（前向兼容）

**前端接入（src/admin/src/utils/orderNotify.ts）：** 登录就绪且具备 `order:view` 权限、
已选定社区时建立连接（App.vue 全局 watch 驱动）；断线指数退避重连（2s 起步封顶 60s）；
收到事件后 WebAudio 合成"叮咚"提示音 + Web Speech 语音播报（首次用户交互解锁自动播放限制，顺带申请浏览器通知授权，仅 WS 已连接的账号申请、拒绝即静默降级）；页面失焦且已授权时追加浏览器系统通知兜底视觉通道（前台不弹，避免与语音重复打扰）。

**测试：** tests/api/76-admin-ws-notify.spec.ts（未登录拒绝 / C 端 token 拒绝 /
hello / 支付成功收到事件 / 代客退款收到 completed 事件 / 异社区不接收）。
