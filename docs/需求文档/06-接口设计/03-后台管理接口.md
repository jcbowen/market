
#### 认证模块

| 方法 | 路径 | 说明 | 认证 |
|------|------|------|------|
| POST | /api/v1/admin/auth/login | 管理员登录 | 否 |
| POST | /api/v1/admin/auth/refresh | 刷新 token（body: refresh_token，**兼容 JSON body 与 form 表单**两种传参；仅换发新 access_token，**不轮换 refresh_token**） | 否 |
| GET | /api/v1/admin/auth/info | 当前管理员信息 | 是 |

说明：登出由前端清除本地 token 实现，服务端不提供 logout 端点。

**管理员登录请求：**
```json
{
  "username": "admin",
  "password": "123456"
}
```

**刷新 token 响应（`POST /api/v1/admin/auth/refresh`）：**
```json
{
  "code": 0,
  "data": {
    "access_token": "eyJ...",
    "expires_in": 7200,
    "expires_at": 1760007200
  }
}
```

说明：
- 实际响应结构为 `{access_token, expires_in, expires_at}`（`expires_at` 为 access_token 到期秒级时间戳）；**不返回新 refresh_token、不轮换**——与 C 端 `/api/v1/auth/refresh`（轮换 refresh_token 并返回含 `user` 的完整登录信息）**行为不同**，前端勿复用同一刷新逻辑。
- 强校验 token 用途：仅 `type=admin` 且用途为 refresh 的 token 可刷新；未传 refresh_token 返回 `11001`，token 无效/类型或用途不符返回 `11002`。

      "sort": 1,
      "values": [
        { "id": 0, "temp_id": "new_value_3", "name": "500g", "sort": 0 }
      ]
    }
  ],

    {
      "id": 0,
      "spec_value_ids": ["new_value_1", "new_value_3"],
      "sku_code": "XHS-001",
      "price": 5.99,
      "original_price": 6.99,
      "cost_price": 4.50,
      "stock": 100,
      "safety_stock": 20,
      "image": "https://...",
      "barcode": "6901234567892"
    },
    {
      "id": 0,
      "spec_value_ids": ["new_value_2", "new_value_3"],
      "sku_code": "XHS-002",
      "price": 3.99,
      "original_price": 0,
      "cost_price": 3.00,
      "stock": 80,
      "safety_stock": 10,
      "image": "https://..."
    }

```

说明：
- `specs` 为规格树（规格名 + 规格值），仅多规格商品提交；单规格传空数组，只提交一条默认 `sku_items`
- 新增的规格名/规格值不传 `id`，传 `temp_id`（如 `new_spec_1`）；`sku_items.spec_value_ids` 引用同一 `temp_id`，服务端落库后自动映射为真实 ID
- 已存在的规格名/规格值传真实 `id`，`temp_id` 可省略
- 服务端按本次提交做 diff，未提交的规格名/规格值/SKU 将被软删除，并回写商品的价格区间与总库存
- 更新商品（PUT /api/v1/admin/products/:id）请求体与新增一致（多 `id` 字段）；`images` 传空数组视为不变更（保留现有图片），非空时全量替换
- `sku_items.sku_code` 留空时：已存在的 SKU 保留原编码，新建的 SKU 由服务端自动生成（`P{商品ID}-{随机后缀}`），避免与历史（含已禁用）编码冲突
- `sku_items.original_price` 划线价/原价（选填，0 表示未设置；`SkuItemReqItem` 字段，随 price/cost_price 一并入库回显）
- `sku_items.barcode` 商品条形码（选填，挂 SKU 级，多规格商品每个规格可各配一条；纯数字 6-20 位宽松校验，不做 EAN 校验位强校验；同社区内在售 SKU 间唯一——重复时返回 10001 并提示占用商品名；商品软删后其条码自动回收可复用；条码精确查询见 `GET /admin/products/barcode/:code`）

**进销存口径要点：**

- 采购单状态机：`1 草稿 → 2 已下单 → 3 部分入库 → 4 已完结`，`5 已取消`；入库回写 `received_quantity` 驱动 2→3→4，接口不做跳状态。
- 单据响应 proto 全 `omitempty`：`supplier_id=0` 等零值键会从 JSON 中消失，前端与测试均需按缺省值容错。
- 单据不存在由服务层以 `InvalidArgument` 返回（映射 10001），**不是 10003**。
- 报表流水口径：`type=1` 入库、`type=2 AND ref_no=''` 才是销售出库（计入毛利），出库单流水 `ref_no` 为单号故不计毛利；`type=3` 盘点、`type=4` 释放、`ref_no='FORM'` 为表单调整。
- 报表时间窗只约束聚合值、不筛行：窗口内无流水时期初=期末=当前库存（SQL 用 `COALESCE(fr.before_stock, s.stock)` 回退）；`start_date/end_date` 缺省为「今天往前 30 天」，且不校验格式，非法日期/起止倒挂静默按「窗口内无流水」处理。
- 已知缺陷（未修，见《测试覆盖补齐-待办清单.md》）：① 报表/批次/预警 SQL 缺 `p.status <> 2`，软删商品的 SKU 仍会出现（与 `/inventory/skus` 口径不一致）；② `page=0` 使 `offset` 为负触发 10002；③ `products.stock` 汇总列仅由商品编辑回写，入库/出库/下单扣减不更新，导致商品列表「已售罄」Tab 口径不可靠。

**订单列表查询：**
```
GET /api/v1/admin/orders?status=1&order_no=&receiver_name=&receiver_phone=&start_time=2026-10-01&end_time=2026-10-14&page=1&page_size=20
```

查询参数说明：
- `status` 支持 1/2/3/4/5/6/7/8，另支持聚合虚拟状态：`90`=待发货（2∪3）、`9`=售后（7∪8）
- `order_no` 订单号模糊匹配；`receiver_name`/`receiver_phone` 收货人姓名/电话模糊匹配
- `start_time`/`end_time` 下单日期范围（YYYY-MM-DD，闭区间）
- `user_id` 按会员过滤（会员列表"订单"弹窗使用）
- `shift_id` 按收银班次过滤（交班记录"查看班内订单"入口使用；0=全部）
- `source` 来源过滤：1=C端 2=收银台（0=全部）；响应行含 `source`/`operator_name`（收银台单经手人快照）
- `community_id` 仅超管可传，`0`=跨社区查全部订单（响应行含 community_id/community_name）；不传=当前社区语境
- 响应行与详情均含 `pay_type`/`pay_type_text`（1微信 2支付宝 3货到付款 4现金；0=未支付/未知）

- 订单归属当前社区语境（X-Community-Id），来源固定 `source=2`，经手人取当前管理员（operator_id/operator_name 快照）
- `user_id=0` 为散客（散客不可用券）；配送单必须填联系人/电话/地址（收银台无地址簿，直填 contact_*）
- `delivery_type`：1自提（出取货码，可核销）2配送 3到店（2026-10-15 新增，仅收银台：即买即走，不生成取货码、无需核销，C 端下单被拒）；自提/配送受社区渠道开关（enable_self_pickup/enable_delivery）校验，关闭后下单返回「当前社区未开启xx渠道」；到店不受开关控制恒可用
- 支付方式 `pay_type`（2026-10-15）：0/缺省默认现金 4，当前仅开放 4（后续扩展微信/支付宝付款码预留 5/6，传未开放值返回参数错误）；支付单创建即成功并同步订单状态，备注「门店现金收款」；**实付为 0（全额优惠）时统一创建 `amount=0` 的支付单**，保持「订单必有支付记录」口径便于对账
- 响应含 `id/order_no/pay_amount/delivery_fee/pickup_code`（自提单）与 `paid=true`
- 下单与收款是两步 RPC，收款极端失败时订单保留待支付态，响应报错并提示订单号去订单列表处理

**优惠券发布状态机与编辑边界（M 第①期）：**
- `publish_status`：0草稿（默认）→ 1已发布，通过创建时 `publish_status=1`（存草稿不传）或 PUT 传 `publish_status=1` 发布；**无反向流转**（下架用 grant_status 停发）。
- **草稿态** PUT：全字段可改（名称/类型/门槛/面值/数量/限领/领取窗口/有效期/进中心开关/规则文案/scopes 全量替换）。
- **已发布态** PUT 仅接受：`total_count`（仅允许增大，补充数量）、`grant_status`（1发放中/0停发）、`rule_text`；其余字段（名称/门槛/面值/有效期/范围等）传了也会被服务端忽略，前端同步置灰。
- 原启用开关 `status` 已由发布状态机取代，PUT 不再透传。
- 删除券：草稿或已发布均可删除（已领取的用户券随之失效）。
- 商品范围 `scopes`：scope_type 2=包含分类 3=包含商品 4=排除分类 5=排除商品；不传或空=全部商品可用。下单时门槛与优惠基数均按「范围内商品金额」计算，范围外商品金额不计入。
- **规则文案 `rule_text`（M 第③期）**：后台表单支持「按当前配置一键生成」初版文案（按类型/门槛/面值/有效期/领取窗口/商品范围拼装），生成后可人工编辑；纯前端拼装，接口无新增。

**手动发放优惠券（M 第②期）：**
```
POST /api/v1/admin/coupons/:id/grant
{"user_ids": [3, 4]}
```
- 仅「已发布 + 发放中 + 启用」的券可发放；券归属社区必须与操作语境一致（跨社区直接拒绝）。

{
  "name": "盘龙金茂悦",
  "address": "…",
  "contact_phone": "…",
  "pickup_address": "…",
  "delivery_fee": 0,
  "min_order_amount": 0,
  "business_hours": "09:00-21:00",
  "enable_self_pickup": true,
  "enable_delivery": true

```

说明：
- `enable_self_pickup`/`enable_delivery`（2026-10-15 新增）：自提/配送渠道社区级开关，C 端确认页与收银台共用此配置渲染可用渠道；到店渠道（delivery_type=3）不受配置控制恒可用
- 未传布尔字段时按 false 处理是 JSON 零值语义，后端下单仍有渠道兜底校验；超管「修改社区」整表覆盖接口（PUT /admin/communities/:id）会先回填当前值再覆盖，防止 bool 零值误关渠道

附件选择器说明：
- 可见性按上传管理员隔离：服务端仅返回 `admin_id` 等于当前登录管理员、`is_display=1` 且 MIME 为 `image/*` 的记录，软删除记录不返回
- 上传链路（本地上传与 OSS presign）写入 `admin_id` 与 `is_display=1`；客户端用户上传链路不传该标志默认 `is_display=0`（不进后台选择器），该默认值由服务端保证
- 响应 `url` 由后端按附件配置统一拼接（与业务表图片出库规则一致）

**退款配置（运费退还策略）请求/响应：**
```json
{
  "refund_freight_policy": "always"
}
```

字段说明：`refund_freight_policy` 为整单退时是否退还运费的策略——`always`（默认，整单退一律退运费）、`never`（整单退不退运费）、`user_decide`（发起整单退款时由用户勾选决定）；部分退不涉及运费。

**附件预签名请求：**
```json
{
  "filename": "cover.jpg",
  "md5": "5d41402abc4b2a76b9719d911017c592",
  "content_type": "image/jpeg",
  "size": 102400,
  "width": 800,
  "height": 600
}
```

**附件预签名响应：**
```json
{
  "code": 0,
  "data": {
    "attach_id": "12",
    "hit": false,
    "url": "https://bucket.oss-xxx.aliyuncs.com/images/20261011/11/mkt080102123456.jpg?签名参数",
    "method": "PUT",
    "headers": { "Content-Type": "image/jpeg" },
    "final_url": "https://bucket.oss-xxx.aliyuncs.com/images/20261011/11/mkt080102123456.jpg",
    "remote_path": "images/20261011/11/mkt080102123456.jpg"
  }
}
```

附件上传流程说明：
- **统一大小上限 12MB**：本地上传、OSS presign、支付证书上传同口径，请求体超出时返回「缺少文件字段 file 或文件超过 12MB 上限」
- **OSS 模式**：前端分块计算文件 MD5 → `presign` → `hit=true` 时直接使用 `final_url`（秒传）；否则以 `method + url + headers` PUT 直传 OSS → `confirm`（回传 `attach_id` 与 `md5`）激活秒传记录
- **本地模式**：multipart 直传 `/api/v1/admin/upload/image`，响应 `url` 即可直接访问的地址（`<scheme>://<host>/uploads/<remote_path>`）
- **图片字段存储规则**：商品封面/图库、Banner 图片等业务表图片字段统一只存相对路径（remote_path），写入时后端自动剥离域名；查询响应由后端按附件配置拼接为完整 URL，前端直接渲染回显即可，无需自行转换
- `md5` 统一为文件完整二进制内容的标准 MD5、32 位小写十六进制（等价 `md5_file()`）
