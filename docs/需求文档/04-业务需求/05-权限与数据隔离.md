### 4.5 权限体系（权限点级 RBAC，全局角色 + 社区权限双体系）

角色不是固定三级，而是「账号 — 角色 — 社区任职」三层可配置模型，权限粒度到权限点（`模块:动作`）。

#### 4.5.1 数据模型

| 层 | 表 | 关键字段与语义 |
|---|---|---|
| 账号层 | `admin_users` | `username`（唯一）、bcrypt 密码、`is_super`（是否超管）、`status`；**只承载账号身份**，旧的 `role_id`/`community_id` 列已废弃（DB 保留、代码不再读写） |
| 角色层 | `admin_roles` | `community_id = 0` 为**全局角色**，`> 0` 为某社区的**私有角色**；`permissions` 为权限点 JSON 数组；唯一键 `(community_id, code)`，故同一 `code` 可在各社区各有一条 |
| 任职层 | `admin_communities` | 一行 = 某管理员在某社区担任某角色，唯一键 `(admin_id, community_id, role_id)`；支持一人多社区、同社区多角色，权限取并集 |
| 社区上限 | `admin_roles` 中的内置角色 | 每个社区一条内置「社区管理员」角色（`code = community_admin`，`community_id` = 所属社区），其权限集即**该社区的权限上限**；不可删除，业务侧角色管理页只读，仅超管可通过「社区权限」页修改 |

- 内置社区管理员默认权限集（新社区的默认上限）：覆盖社区日常运营——工作台、商品增删改查、库存查看/创建/更新、订单查看/更新、收银台下单（`order:create`）、售后查看/更新、会员查看/创建/更新、营销增删改查、统计查看、员工与角色管理、门店设置（`community:config`）；**不含系统级权限点**（`community:*`、`region:*`、`settings:*`），系统级能力只能由超管按社区显式下发。

#### 4.5.2 权限点

- 命名规范 `模块:动作`（`view`/`create`/`update`/`delete`，个别为专用动作），`*` 为通配（视为全量权限）。
- 清单集中维护在前端共享常量 `src/admin/src/constants/permissions.ts`（按模块分组：工作台、商品、库存、订单与售后、会员、营销、统计、门店（社区级）、社区（系统级）、行政区划（系统级）、员工、角色），角色管理与社区权限页共用。
- 实际使用示例：`product:view`、`inventory:create`、`order:view`/`order:update`/`order:create`（收银台代客下单）、`refund:view`/`refund:update`、`user:view`/`user:create`/`user:update`、`marketing:*`、`statistics:view`、`community:config`（门店设置）、`community:view`/`region:view`/`settings:view`/`settings:update`（系统级）、`admin:*`、`role:*`。

#### 4.5.3 双套角色入口

| 入口 | 路由 | 可见性 | 作用 |
|---|---|---|---|
| 全局角色 | `/system/roles-global` | 系统管理空间，仅超管 | 维护 `community_id = 0` 的全局角色 |
| 社区权限 | `/system/community-permissions` | 系统管理空间，仅超管 | 按社区设置**权限上限**（写入该社区内置 `community_admin` 角色的权限集）；保存后运行时解析即与其取交集，对社区全员立即生效；系统级权限点不进入可分配列表并在载入/保存时自动剔除；收紧上限时提示受影响的本社区私有角色 |
| 角色管理（社区私有） | `/system/roles` | 门店管理菜单组（`role:view`） | 维护**当前社区**的私有角色；内置角色只读；普通管理员只能勾选自身当前社区已有的权限点，防权限放大 |
| 员工管理 | `/system/admins` | 门店管理菜单组（`admin:view`） | 当前社区的任职员工：username 已存在则复用账号追加任职，否则新建；编辑本社区多角色任职（全量覆盖）；移除仅删本社区任职 |
| 账号管理 | `/system/accounts` | 系统管理空间，仅超管 | 只管账号本身（新增/启停/重置密码/超管标记），社区任职不在此维护 |

#### 4.5.4 鉴权链路（前后端双体系）

- 前端：路由 `meta.permission` 声明所需权限点，全局守卫按 `authStore.hasPermission(code)`（含 `*` 通配与超管判定）放行/拦截——无权限时保留登录态跳 `/403` 提示页，仅当账号无任何可用页面（权限为空）才登出兜底；左侧菜单按权限点与 `superOnly` 过滤，系统空间（`meta.space = 'system'`）仅超管可入，非超管直连 URL 回落业务首页；页面内按钮再按 `hasPermission` 细控（如附件配置的 `settings:update`）。
- 后端：网关每条管理路由挂 `RequirePermission("xxx")` 中间件，具备所需权限点之一即通过，否则返回无权限；令牌类型非 `admin`（C 端令牌）直接拒绝。
- **实时解析而非登录快照**：多社区模型下权限随当前社区变化，中间件逐请求按（管理员，当前社区）调用 user 服务 `GetAdminContext` 解析——取该管理员在该社区全部任职角色的权限并集，再与该社区的权限上限（内置角色权限集）取交集（任一侧含 `*` 视为该侧无限制：上限含 `*` 直接用角色权限并集，角色含 `*` 收敛为上限本身）；超管直接返回"全量放行"。解析结果在同一请求内记忆化，只解析一次。
- 纵深防御：出款链路（后台代客退款、审批、重试、拒绝）在 order 服务层再次校验退款单归属订单的社区（`community_id <= 0` 视为内部系统调用跳过），跨社区直接拒绝；网关侧另有 `ensureOrderInCommunity` 第一道防线；角色更新/删除校验目标角色必须属于当前社区，防跨社区改权。

### 4.6 数据隔离

- 隔离维度是社区：商品、SKU、分类、库存与库存流水、订单、会员、优惠券/秒杀/满减/Banner、收银台挂单与班次等均按 `community_id` 归属；网关管理端接口一律以「当前社区语境」取数（约 60 处 `getAdminCommunityID`）。
- 当前社区语境：登录后**必须选定一个具体社区**（超管与普通管理员一致，不存在跨社区聚合视图）；多社区账号无上次选择、或超管首次进入时，守卫强制进入 `/select-community` 选择页；选定值持久化本地（`current_community_id`），由请求拦截器注入 `X-Community-Id` 请求头，顶栏「切换社区」即切换数据视图。
- 社区合法性校验 `RequireCommunityAccess`：请求头声明的社区，超管任意合法；普通管理员须在其绑定社区范围内（先查令牌快照，未命中时实时查任职，覆盖登录后新授权社区），越权直接返回无权限。未携带该头时回退令牌默认社区。
- 会员隔离按会员-社区关联表 `user_communities` 实现（会员列表 = 该社区的关联会员），不是按"购买过"隐式统计；同一会员可在多个社区分别建立关联，来源标记区分后台/收银台注册。
- 超管：可切换查看并管理任意社区数据，账号级全局配置（社区管理、行政区划、全局角色、全局 Banner、支付/售后/附件配置）仅超管可用。
- C 端例外与越权防护点：
  - C 端「我的订单」返回该用户全部订单，不按社区过滤（用户可能在多社区下过单）；订单归属社区在下单时由服务端按用户实时归属确定。
  - 地址读/改/删/设默认均带 `user_id` 归属条件，删除命中 0 行返回「地址不存在或无权操作」，防越权操作他人地址。
  - 下单/存地址/运费试算要求服务端已绑定社区，未选社区（`community_id=0`）服务端直接拒绝；社区停业、自提/配送渠道关闭均由服务端兜底拒绝（防前端缓存与按钮隐藏被绕过）。
  - 履约工作台接口实时校验当前用户在其归属社区具备履约人员身份（员工编辑页绑定会员的员工，取消绑定/任职后入口与接口立即失效）；核销校验订单社区归属与重复核销。
  - 门店订单（`source=2`）在 C 端只读，取消/退款必须由门店（后台）处理。
  - 拉黑会员（`status != 1`）在登录与令牌刷新两处同时拦截，已登录会话无法静默续期。
