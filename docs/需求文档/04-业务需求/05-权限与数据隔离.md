### 4.5 权限体系（权限点级 RBAC，社区角色 + 社区权限上限双体系）

角色不是固定三级，而是「账号 — 角色 — 社区任职」三层可配置模型，权限粒度到权限点（`模块:动作`）。

#### 4.5.1 数据模型

| 层 | 表 | 关键字段与语义 |
|---|---|---|
| 账号层 | `admin_users` | `username`（唯一）、bcrypt 密码、`is_super`（是否超管）、`status`；**只承载账号身份**，旧的 `role_id`/`community_id` 列已废弃（DB 保留、代码不再读写） |
| 角色层 | `admin_roles` | 角色一律**社区私有**（`community_id > 0`）；`community_id = 0` 为历史保留值，仅存量兼容数据（已禁止新建、结构上不可指派）；`permissions` 为权限点 JSON 数组；唯一键 `(community_id, code)`，故同一 `code` 可在各社区各有一条 |
| 任职层 | `admin_communities` | 一行 = 某管理员在某社区担任某角色，唯一键 `(admin_id, community_id, role_id)`；支持一人多社区、同社区多角色，权限取并集 |
| 社区上限 | `admin_roles` 中的内置角色 | 每个社区一条内置「社区管理员」角色（`code = community_admin`，`community_id` = 所属社区），其权限集即**该社区的权限上限**；不可删除，业务侧角色管理页只读，仅超管可通过「社区权限」页修改 |

- 内置社区管理员默认权限集（新社区的默认上限）：覆盖社区日常运营——工作台、商品增删改查、库存查看/创建/更新、订单查看/更新、收银台下单（`order:create`）、售后查看/更新、会员查看/创建/更新、营销增删改查、统计查看、员工与角色管理、门店设置（`community:config`）；**不含系统级权限点**（`community:*`、`region:*`、`settings:*`、`payment:raw:view`），系统级能力只能由超管按社区显式下发。其中 `payment:raw:view`（支付报文原文）是**刻意排除**的一个：即便社区管理员已能看订单/售后，也不给展开回调报文的能力（原文含顾客标识与签名信息），只在超管勾选后生效。

#### 4.5.2 权限点

- 命名规范 `模块:动作`（`view`/`create`/`update`/`delete`，个别为专用动作），`*` 为通配（视为全量权限）。
- 清单集中维护在前端共享常量 `src/admin/src/constants/permissions.ts`（按模块分组：工作台、商品、库存、订单与售后、会员、营销、统计、门店（社区级）、社区（系统级）、行政区划（系统级）、支付（系统级，`payment:raw:view`）、员工、角色），角色管理与社区权限页共用。
- 实际使用示例：`product:view`、`inventory:create`、`order:view`/`order:update`/`order:create`（收银台代客下单）、`refund:view`/`refund:update`、`user:view`/`user:create`/`user:update`、`marketing:*`、`statistics:view`、`community:config`（门店设置）、`community:view`/`region:view`/`settings:view`/`settings:update`/`payment:raw:view`（系统级）、`admin:*`、`role:*`。
- 与支付可靠性相关的四个入口权限（2026-10-21）：「同步支付状态」「标记已支付」「异常销账」复用 `order:update`，异常队列列表复用 `order:view`（社区管理员可用），报文原文额外要求 `payment:raw:view`（仅超管）。

#### 4.5.3 角色相关入口

| 入口 | 路由 | 可见性 | 作用 |
|---|---|---|---|
| 社区角色 | `/system/community-roles` | 系统管理空间，仅超管 | 跨社区角色**只读总览**：`GET /api/v1/admin/roles?scope=all` 返回各社区角色并回填所属社区名与任职人数，可按社区筛选；写操作通过「到该社区管理」切社区语境后在角色管理页完成；`community_id=0` 的遗留行标「遗留·全局」，仅超管可删除清理 |
| 社区权限 | `/system/community-permissions` | 系统管理空间，仅超管 | 按社区设置**权限上限**（写入该社区内置 `community_admin` 角色的权限集）；保存后运行时解析即与其取交集，对社区全员立即生效；系统级权限点不进入可分配列表并在载入/保存时自动剔除；收紧上限时提示受影响的本社区私有角色 |
| 角色管理（社区私有） | `/system/roles` | 门店管理菜单组（`role:view`） | 维护**当前社区**的私有角色；内置角色只读；普通管理员只能勾选自身当前社区已有的权限点，防权限放大 |
| 员工管理 | `/system/admins` | 门店管理菜单组（`admin:view`） | 当前社区的任职员工：username 已存在则复用账号追加任职，否则新建；编辑本社区多角色任职（全量覆盖）；移除仅删本社区任职 |
| 账号管理 | `/system/accounts` | 系统管理空间，仅超管 | 只管账号本身（新增/启停/重置密码/超管标记），社区任职不在此维护 |

#### 4.5.4 鉴权链路（前后端双体系）

- 前端：路由 `meta.permission` 声明所需权限点，全局守卫按 `authStore.hasPermission(code)`（含 `*` 通配与超管判定）放行/拦截——无权限时保留登录态跳 `/403` 提示页，仅当账号无任何可用页面（权限为空）才登出兜底；左侧菜单按权限点与 `superOnly` 过滤，系统空间（`meta.space = 'system'`）仅超管可入，非超管直连 URL 回落业务首页；页面内按钮再按 `hasPermission` 细控（如附件配置的 `settings:update`）。
- 后端：网关每条管理路由挂 `RequirePermission("xxx")` 中间件，具备所需权限点之一即通过，否则返回无权限；令牌类型非 `admin`（C 端令牌）直接拒绝。**「超管专用」接口在路由级也挂权限码**（全局账号管理 5 条挂 `admin:view`/`admin:create`/`admin:update`，社区员工指定 3 条挂 `admin:view`/`admin:update`）：处理器内的实时超管判定是第二道闸，两层都做——否则内层判定日后被重构掉时，这些写接口会静默退化成「只要登录即可调用」。仅「读取自身资料 / 可进入社区列表 / 关于页」这类自服务接口保留只要求登录；`PUT /app-preferences` 是社区级覆盖式共享写入，挂 `community:config`（原先无权限码，任意登录管理员可改掉本店所有人的常用应用）。
- **实时解析而非登录快照**：多社区模型下权限随当前社区变化，中间件逐请求按（管理员，当前社区）调用 user 服务 `GetAdminContext` 解析——取该管理员在该社区全部任职角色的权限并集，再与该社区的权限上限（内置角色权限集）取交集（任一侧含 `*` 视为该侧无限制：上限含 `*` 直接用角色权限并集，角色含 `*` 收敛为上限本身）；超管直接返回"全量放行"。解析结果在同一请求内记忆化，只解析一次。**实时解析失败一律拒绝（fail-closed），不回退令牌快照**：同一请求后续在 `RequirePermission` 上本就是 403，回退快照换不到可用性，只会把降权/解除任职前的旧授权续到令牌过期。
- 纵深防御：出款链路（后台代客退款、审批、重试、拒绝）在 order 服务层再次校验退款单归属订单的社区（`community_id <= 0` 视为内部系统调用跳过），跨社区直接拒绝；网关侧另有 `ensureOrderInCommunity` 第一道防线；角色更新/删除校验目标角色必须属于当前社区，防跨社区改权。
- **服务层社区校验是 opt-in，不是默认拦截**：RPC 里的社区过滤普遍写成 `if req.CommunityId <= 0 { /* 不做社区限制 */ }`（内部调度/系统调用要跨社区取数，语义上 0 = 无社区语境）。这意味着**网关漏传 `community_id` 不会报错，只会退化成全库取数**。因此新增管理端接口必须两层都做：① 网关 handler 以当前社区语境（`getAdminCommunityID`）显式填入 gRPC 请求，不得留 0；② 服务层按 `community_id` 过滤，凡是「先按 ID 取行、再按社区判归属」的写操作要显式校验归属并在不一致时拒绝，不能只靠列表查询的过滤条件。跨社区越权的回归用例族见 `tests/api/`，新增同类接口应同步补用例。
- **交易链路的「无社区语境」先观测后硬拒（2026-10-24 C5）**：`scope<=0` 在管理端是合法语义（超管跨社区、内部调用不设语境），但交易侧（`require_sellable=true`：加购取商品档案、下单批量取商品/SKU）意味着成交社区没传进来，`EnsureScope` 的归属比对会被整体跳过。现口径是在 `EnsureTradeAccess` 落一条 `[WARN] 交易入口缺少社区语境`（带 `product_id`/`sku_id` 便于定位调用方，用例 `sellable_test.go:TestEnsureTradeAccessWarnsOnMissingScope` 守卫「只有交易口径+缺 scope 才打，管理端口径与带 scope 都不打」），**不改硬拒**——静态无法证明所有内部调用方都已补齐 `community_id`，硬拒会打死未知调用方（宁可多一条日志，不可让下单链路 500）。观测一轮确认零命中后，再把它升级为 `FailedPrecondition` 拒绝（已记入 `11-开发计划.md` 上线前置项第 82 项）。

### 4.6 数据隔离

- 隔离维度是社区：商品、SKU、分类、库存与库存流水、订单、会员、优惠券/秒杀/满减/Banner、收银台挂单与班次等均按 `community_id` 归属；网关管理端接口一律以「当前社区语境」取数（约 60 处 `getAdminCommunityID`）。
- 当前社区语境：登录后**必须选定一个具体社区**（超管与普通管理员一致，不存在跨社区聚合视图）；多社区账号无上次选择、或超管首次进入时，守卫强制进入 `/select-community` 选择页；选定值持久化本地（`current_community_id`），由请求拦截器注入 `X-Community-Id` 请求头，顶栏「切换社区」即切换数据视图。
- 社区合法性校验 `RequireCommunityAccess`：请求头声明的社区，一律按实时口径判定——超管（`IsSuper`）或该社区仍有任职（`Bound`）才合法，越权直接返回无权限；实时解析失败同样拒绝（fail-closed）。令牌快照里的 `role`/`community_ids` 不参与判定（登录时绘制，降权/解除任职后照抄等于续期旧授权）。未携带该头时回退令牌默认社区。
- 数据归属与超管特判（`getAdminCommunityID`、`scopeCommunityID`、`checkOrderCommunity`、`ensureBillInCommunity`、Banner/统计的跨社区传参等）同样只认实时超管口径（`middleware.IsSuperAdmin(c)`，复用请求内记忆化的解析结果，不额外增加 RPC）。
- 会员隔离按会员-社区关联表 `user_communities` 实现（会员列表 = 该社区的关联会员），不是按"购买过"隐式统计；同一会员可在多个社区分别建立关联，来源标记区分后台/收银台注册。
- 超管：可切换查看并管理任意社区数据，账号级全局配置（社区管理、行政区划、社区角色总览、全局 Banner、支付/售后/附件配置）仅超管可用。
- C 端例外与越权防护点：
  - C 端「我的订单」返回该用户全部订单，不按社区过滤（用户可能在多社区下过单）；订单归属社区在下单时由服务端按用户实时归属确定。
  - 地址读/改/删/设默认均带 `user_id` 归属条件，删除命中 0 行返回「地址不存在或无权操作」，防越权操作他人地址。
  - 下单/存地址/运费试算要求服务端已绑定社区，未选社区（`community_id=0`）服务端直接拒绝；社区停业、自提/配送渠道关闭均由服务端兜底拒绝（防前端缓存与按钮隐藏被绕过）。
  - 履约工作台接口实时校验当前用户在其归属社区具备履约人员身份（员工编辑页绑定会员的员工，取消绑定/任职后入口与接口立即失效）；核销校验订单社区归属与重复核销。
  - **履约人员模型（2026-10-18 起）**：履约人员 = 「在本社区有任职、且账号绑定了会员（`admin_users.user_id`）、账号未禁用（`admin_users.status=1`）的员工」，判定 SQL 见 user 服务 `CheckFulfiller`（`admin_users JOIN admin_communities ON admin_id AND community_id=?`）。旧的 `user_communities.is_fulfiller` 列**已废弃并在服务启动时 DropColumn**，任何代码与测试造数不得再读写该列；设置/取消履约身份即「PUT /api/v1/admin/admins/:id 绑定/解绑 `user_id`」（`user_id=0` 为解绑，且该字段仅超管可改），解绑后立即失效。
  - 门店订单（`source=2`）在 C 端只读，取消/退款必须由门店（后台）处理。
  - 拉黑会员（`status != 1`）在登录与令牌刷新两处同时拦截，已登录会话无法静默续期。
