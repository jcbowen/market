**payment_notify_logs - 支付通知与对账流水表（2026-10-21 新增）**

记录「渠道通知 / 主动回查 / 人工同步」三类动作的完整轨迹，承担两个职责：一是**取证**（验签或解密失败的原始报文必须留痕，否则事后无法区分「渠道发过但被拒」与「渠道根本没发」）；二是**出口**（把散落在 stderr 的 `[CRITICAL]` 挂账、金额不符、放弃对账变成可查询、可销账的后台队列）。

| payment_no | VARCHAR(50) | 是 | 支付单号，验签失败时可能解析不出，为空串 |

说明：
- `handled=0`（待处理）的判定：金额不符(4)、资金挂账(9)、订单同步失败(10) 不分来源都进队列（钱可能少收/多收，或已收而订单已取消，或支付单已确认而订单没流转）；此外 `kind=3 挂账检出（系统）`、`kind=8 挂账检出（后台人工核实）`、`kind=6 放弃对账` 必进，`kind=1 渠道回调` 仅在验签失败(3)或处理异常(5)时进。成功、幂等忽略、渠道明确未支付属正常轨迹，落库备查但不打扰人工；`kind=7 人工恢复退款收敛`（`result=11`）是人工动作的留痕，同样不进待办队列，但会顺带把该退款单此前的 `result=10` 待办销账；`kind=9 付款码扣款`（收银台 B扫C 的同步确认）与 kind=1 分开——付款码支付没有异步通知，记成渠道回调会污染「回调丢失率」口径。
- 挂账待办按**检出来源**拆 kind（3 系统 / 8 后台人工核实），因为两者成因相反：kind=3 说明回调或链路有洞，kind=8 说明该单早已超出对账窗口、靠人工点开按钮才查到。去重**跨这两个 kind**（`hasStuckLog` 用 `kind IN (3,8)`），否则同一笔挂账会在异常页出现两条等价待办；已有待办时重复核实不再登记，但会落一条 `kind=5 后台手动同步 / result=2 幂等忽略` 留痕（不进待办队列，只证明「又核过一次、结论一致」）。
- 检出留痕写入 `detect_remark`，销账依据写入 `remark`——两列必须分开：销账 SQL 整列覆写 `remark`，若把「谁核实的、当时本地是什么状态」写在 `remark`，责任链会在销账那一刻断掉。该不变式由 `stuck_audit_test.go` 的 `TestStuckAuditTraceSurvivesHandling` 断言。
- `raw_body`/`headers` 只在具备 `payment:raw:view` 权限点时由网关回填下发（该权限点刻意不授予社区管理员），列表页默认只回摘要与 `has_raw` 标志。
- 过期清理由 payment 对账调度器按 `business.payment_reconcile.notify_log_retention_days`（默认 30 天）执行，且**只删 `handled=1`**：`handled=0` 的待办流水到期也保留（删除等于抹掉「这笔钱挂过账」的事实），清理前统计过期未销账条数并输出 `[CRITICAL]` 日志。

**payment_scheduler_failures - 支付对账失败记录表（2026-10-21 新增）**

记录渠道回查/挂账检测中处理失败的支付单，供下一轮优先重试，重试上限与状态口径与 order 侧 `order_scheduler_failures` 一致；待重试行的唯一性是本表独有的加固（order 侧不查三方渠道，重复记录只是噪声，本表重复会放大渠道调用量）。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| payment_no | VARCHAR(50) | 是 | 支付单号，默认空串 |
| order_id | BIGINT | 是 | 订单 ID，默认 0 |
| task_type | VARCHAR(24) | 是 | 任务类型：`reconcile_pending` 待支付单渠道回查 / `reconcile_stuck` 已关闭单挂账回查 / `channel_close` 渠道侧交易关闭 |
| status | TINYINT | 是 | 1待重试 2已处理（本轮成功收敛或已被其他路径解决） 3放弃（超重试上限或支付单已不存在），默认 1 |
| pending_slot | VARCHAR(16) | 否 | 待重试占位标记（值恒为 `pending`），转终态时置空 |
| error_msg | VARCHAR(500) | 否 | 失败原因 |
| retry_count | INT | 是 | 已重试次数，上限 5（`MaxFailureRetry`，与 order 侧一致），默认 0 |
| created_at | DATETIME | 是 | |
| updated_at | DATETIME | 是 | |

索引：`uk_failures_pending(payment_no, task_type, pending_slot)` 唯一索引、`idx_payment_scheduler_failures_order_id(order_id)`（GORM 无名索引默认命名）

- 去重口径（2026-10-22 调整）：MySQL 没有部分唯一索引，改用「唯一索引里放一个可空列」实现「同一支付单同一任务只允许一条待重试行」——待重试态写 `pending_slot='pending'`，转终态（2/3）时置 NULL，NULL 行彼此不冲突，历史放弃/已处理记录仍可保留多条。

**refund_payments - 退款记录表**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| refund_no | VARCHAR(50) | 是 | 退款单号，唯一索引保证幂等 |
| payment_no | VARCHAR(50) | 是 | 关联支付单号 |
| order_id | BIGINT | 是 | 订单 ID |
| amount | DECIMAL(10,2) | 是 | 退款金额 |
| status | TINYINT | 是 | 1待退款 2退款成功 3退款失败 |
| transaction_id | VARCHAR(100) | 否 | 第三方退款交易号 |
| retry_count | INT | 是 | 退款查单收敛的连续失败次数，默认 0；达上限（代码常量 `refundQueryMaxRetry=10`）即退出自动批次并转人工待办 |
| escalated | TINYINT | 是 | 已转人工待办标记 0未转办 1已转办（仅作待办去重，不决定是否继续查单），默认 0 |
| refund_time | DATETIME | 否 | 退款成功时间 |
| created_at | DATETIME | 是 | |
| updated_at | DATETIME | 是 | 兼作退款查单的节流指针（批次按 `updated_at` asc 轮转，处理完一笔就刷新） |

索引：`uni_refund_payments_refund_no(refund_no)`、`idx_refund_payments_payment_no(payment_no)`、`idx_refund_payments_order_id(order_id)`、`idx_refunds_status_updated(status, updated_at)`

- 微信退款是异步受理语义（`PROCESSING` 为常态），故「待退款(1)」不是缺陷而是中间态：终态由 payment 调度器 `reconcileRefunds` 按渠道查单收敛，查单/落库失败按笔累加 `retry_count` 并推进 `updated_at`，两条腿保证既不饿死队首也不无限打扰渠道。
- **放弃收敛的唯一出口（2026-10-24 B2）**：`retry_count` 达上限后流水永久退出自动批次，而微信退款允许 1-3 个工作日到账，渠道后来给出终态也没人来收。后台「售后管理 → 恢复自动收敛」（`POST /api/v1/admin/refunds/:id/reset-retry`，串起 payment `ResetRefundFlow` 与 order `ResetRefundRetry`）把 `retry_count`/`escalated` 归零、`updated_at` 刷到当前时间，流水重新被查单任务捞起。**门禁**：只有待退款(1)可重置——已成功(2) 拒绝（放开等于允许 order 侧再触发一次渠道出款），已失败(3) 拒绝（失败态本就允许以同一退款单号重新发起）；核实依据（`remark`）必填并写 `kind=7/result=11` 留痕，同时按退款单号把此前登记的转办待办（`result=10`）就地销账。
- 与订单侧的对应关系：`refund_payments` 只管渠道出款事实，订单能不能收尾由 order `refunds`（同表名不同库，见 04-订单服务表结构）的 `status` 决定，两者靠 `refund_no` 对齐；两侧的重试预算各自独立归零，故「恢复自动收敛」必须一次动作两侧都改，只改一侧会出现「订单在起劲重试而流水已放弃」的半截状态。


**pay_config - 支付配置表（多行存储，2026-10-30 重构）**

支付配置（微信支付/支付宝凭证）由 config.yaml 迁移至本表并改为**多行存储**：同一平台可建多条配置（如「支付宝-H5」「支付宝-小程序」），每条独立启停，行由 `name + platform + enabled + 凭证字段组` 组成。通过后台「系统管理 → 支付配置」维护，保存后即时生效（payment 服务按 `updated_at` 版本检测热更新，无需重启）。

> 2026-10-30 绑定关系反转：原单行表的 `enabled_channels`（启用支付渠道 wechat/alipay/cash）与 `wechat_channels`/`alipay_channels`（适用客户端渠道勾选）三列**已删除**。「哪个客户端渠道启用哪些支付配置」改由渠道侧 `client_channels.pay_methods` 表达（见下），支付配置页不再勾选渠道。
>

- 各客户端渠道的访问凭证（AppID/AppSecret）不在本表，统一由 user 服务 `client_channels` 表管理（见下）；渠道与支付配置的绑定关系（`pay_methods`）也落在渠道侧

**client_channels - 客户端渠道表（user 服务）**

后台「系统管理 → 渠道管理」维护各客户端访问凭证、启用开关与支付方式绑定；小程序登录（Code2Session）、按端支付下单均取用此处配置，保存后即时生效（登录/下单链路每次现取，无缓存）。

> 2026-10-30 重构：渠道集合对齐现实业务（7 个内置渠道）；`sort` 排序列**已删除**（列表按固定常用顺序返回 h5 → gzh → mp → alimp → android → ios，pos 恒在末位）；新增 `pay_methods` 绑定列——「渠道启用哪些支付配置」由渠道侧表达，替代原支付配置里的渠道勾选。
