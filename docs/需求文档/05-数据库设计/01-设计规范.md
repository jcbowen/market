## 五、数据库设计

### 5.1 设计规范

- 所有表使用 InnoDB 引擎，字符集 utf8mb4，排序规则 utf8mb4_unicode_ci
- 主键统一使用 `id BIGINT AUTO_INCREMENT`（有符号；代码模型 tag 为 `type:bigint`。不采用 UNSIGNED：改列类型需 DDL 迁移且有锁表风险，自增 ID 用量远达不到有符号上限）
- 时间字段：`created_at`、`updated_at` 所有表必含；`deleted_at` 仅软删除表在模型中显式声明（如 product_specs、product_spec_values、attachment），不声明即物理删除
- 金额字段统一使用 `DECIMAL(10,2)`
- 状态字段使用 `TINYINT`，枚举含义以各表结构文档为准；业务状态普遍为 0 表示禁用/下架、1 表示正常/启用，部分表扩展更多枚举值（如商品 status 含 2 删除、优惠券 publish_status 含 2 已下架）
- 索引命名：普通索引 `idx_表名_字段名`；单列唯一约束使用 GORM `unique` 标签，自动生成 `uni_表名_字段名`；复合唯一索引使用命名 `uniqueIndex`（如 `uk_user_sku`）。注意：单列唯一不得使用 `uniqueIndex` 标签，GORM 增量迁移时会误判并尝试删除不存在的约束导致迁移失败
- 迁移策略：所有表统一走 GORM AutoMigrate（服务启动时执行），禁止手写 CREATE TABLE / ALTER TABLE 等幂等 DDL 迁移函数；每个服务新增模型后必须加入该服务 main.go 的 autoMigrate 列表，不允许存在不参与迁移的模型
- **新增列的唯一约束会滞后一轮启动落地**（2026-10-28 源码级取证 + 实测复现）：对**已存在的表**，AutoMigrate 走 `AddColumn` 建列，该路径不创建唯一约束；`unique` 标签对应的单列唯一要等**下一次启动**的列唯一性比对（`MigrateColumnUnique` → `CreateConstraint`）才补上，而 `uniqueIndex:名` 的复合唯一走索引解析，当轮即建。故「加一个唯一标记列（如班次 `active_flag`）来原子化并发写入」这类演进，第一次启动只有列没有约束，唯一性保护从第二次启动才生效——验收必须重启一轮，并以 `information_schema.statistics` 查到约束名为准，不能只看首轮启动日志
- AutoMigrate 能力缺口（删列、列改名与数据搬迁）：AutoMigrate 只增不减，废弃列与「两列合一」这类演进必须显式清理，属于上一条禁令的**受控例外**，一律登记进 5.1.1 台账、带 `HasColumn` 守卫（跑完一次即空操作）、失败只打日志不阻塞启动
- 默认值写法：DECIMAL 字段的 tag 默认值必须写 `default:0.00`（与 MySQL 存储值一致），写 `default:0` 会导致每次启动误发 ALTER TABLE
- 模型对齐：模型 tag 必须与 DB 实际列定义逐项对齐（type、not null、default、comment），AutoMigrate 对已有表做全量比对，不一致即触发 AlterColumn
- 幂等验收：同一份代码连续启动两次服务，第二次启动的迁移日志中不允许出现任何 DDL 语句
- 数据隔离：涉及社区的表均含 `community_id` 字段，联合索引隔离

#### 5.1.1 手写 DDL 受控例外台账

AutoMigrate 不会删除列、不会改名、不做数据搬迁，以下显式清理是有意保留的例外。共同约束：都用 `Migrator().HasColumn` 守卫（清理完成后即为空操作，仍满足「第二次启动无 DDL」的幂等验收），失败只 `log.Printf` 不阻塞启动，迁移类额外要求「迁移成功才清理旧列，失败时旧列保留、下次启动重试」。

| 位置 | 对象 | 类型 | 移除条件 |
| --- | --- | --- | --- |
| `src/backend/services/user/main.go` | `user_communities.is_fulfiller` | 废弃列清理（履约人员改为员工绑定会员，见 `admin_users.user_id`） | 各环境（测试服与生产的 market-mysql）执行 `SELECT COUNT(*) FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='market' AND TABLE_NAME='user_communities' AND COLUMN_NAME='is_fulfiller'` 全部为 0 后删除该段 |
| `src/backend/services/user/main.go` | `site_configs.copyright_text` / `icp_number` | 两列合一为 `footer_html` 的数据搬迁 + 旧列清理 | 同上逐列查询为 0，且后台页脚设置已按富文本口径回显无误后删除该段 |

**2026-10-29 复验**：本地整库重建后，上述三段守卫在 `information_schema.COLUMNS` 口径下天然为 0（表全新创建、模型已不再声明这些列），启动日志无清理动作，`HasColumn` 返回假即空操作，成本为两次元数据查询。守卫**本轮不删**：线上单容器实例的库是否已同步重建无法从本机确认，删守卫会让仍带旧列的库永久留下孤儿列；待线上逐列确认为 0 后，随下一次改动一并移除本表两段与对应代码。

新增例外必须同时登记本表并在代码注释里写明守卫与移除判据；未登记的 `DropColumn`/`CREATE`/`ALTER` 视为违反迁移策略。
