
#### 微信支付

- 支付方式：JSAPI（微信小程序；公众号内 JSAPI 需 OAuth 链路，暂未开放）、H5 支付（微信外浏览器）
- 支付流程：
  1. 前端调用 `POST /api/v1/payments` 传入 `order_id` 和 `channel="wechat"`，不传 openid，并通过 `X-Channel-Code` 请求头声明所在客户端渠道（mp/gzh/app/h5）
  2. 后端校验微信支付 V3 配置完整性，不完整时直接返回错误；同时校验该支付渠道在当前客户端渠道上可用（pay_config 适用渠道勾选 ∩ 渠道管理就绪状态），不可用时拒绝
  3. 网关按客户端渠道解析 openid 与 AppID：mp 渠道 openid 取用户渠道身份表（user_channel_identities，mp 渠道回落存量 users.openid），AppID 取渠道管理的 mp 渠道配置；h5 渠道无 openid 走 H5 下单，AppID 优先取 mp 渠道 AppID；gzh/app 渠道链路未开放直接拒绝；未携带渠道头按存量口径（users.openid + pay_config 默认 AppID）
  4. 创建独立支付单（`payment_no` 使用 `ZF` + UUID），有可用 openid 走 JSAPI 统一下单（wego 请求级 AppID 覆盖），否则走 H5 下单
  5. 返回调起参数给前端：小程序端用 `uni.requestPayment` 调起 JSAPI（`signType` 为 RSA），H5 端跳转 `h5_url`（uni-app 未封装浏览器支付）
  6. 用户支付完成后，微信回调 `POST /api/v1/payments/callback/wechat`
  7. 后端通过 wego 验签解密，仅处理 `TRANSACTION.SUCCESS` 通知，更新支付单和订单状态
- 幂等性：
  - 支付回调通过 `payment_no` 保证幂等处理
  - 退款通过 `refund_no` 唯一索引保证幂等，重复提交直接返回成功
- 多次支付：一笔订单在支付成功前可多次发起支付；同订单、同支付方式且金额一致时复用已有待支付单及其调起参数，不再新建（复用仅限微信/支付宝这类需第三方调起参数的渠道）；订单已有支付成功记录时拒绝创建。`GetPayment` 仅查询支付成功（status=2）记录，因此待支付单不会被幂等校验误拦
- 校验失败按 fail-closed 处理：幂等校验与待支付单复用查询若发生数据库异常（非 `ErrRecordNotFound`），直接拒绝创建并返回内部错误，不把故障当作"无支付记录"放行，否则会产生多笔可实际扣款的支付单；底层错误只写服务端日志，对客户端返回统一业务文案
- 多次退款：一笔支付单支持多笔部分退款，累计退款金额不超过支付单金额；支付单累计退完时才标记为"已退款"
- 配置展示：当 `wechat` 支付 V3 配置不完整，或该支付渠道在当前客户端渠道上不可用（适用渠道勾选未命中 / 客户端渠道未就绪）时，C 端不展示微信支付选项
- 前端约束：仅支付真实完成才提示"支付成功"；用户取消、跳转 H5 支付页或渠道未开通时不提示成功，统一回到订单详情以便重新支付
  - 跳转外部收银台（`redirected`）后不再与站内路由竞争：先注册一次性回站监听（`visibilitychange`/`pageshow`）再跳转，用户从支付宝/微信回到本站tab即自动刷新订单状态，避免停留在「支付中」而重复发起支付
  - 微信内置浏览器选择支付宝（`guided`）时跳转独立引导页（免登录），不叠加 toast 打断操作步骤
- 上线前置：开启微信渠道原本要求先完成「回调兜底、待支付单生命周期、prepay 时效」三项——原因是 wego 无 CloseOrder 接口，订单取消后其待支付单在微信侧约 2 小时内仍可被支付，而该回调会因状态机拒绝 `6→2` 而回滚，形成"钱已扣、系统无成功记录"的资金挂账风险。2026-10-21 支付可靠性改造后这三项已落地（关单前调渠道 `CloseOrder`、取消前置渠道确认、挂账检出进异常队列，见下《支付回调可靠性》小节），仍必须在真实商户环境验证的只剩渠道 `QueryOrder`/`CloseOrder` 回执与自动退款回执（开发计划第 51–53 项）

#### 支付宝支付

- 支付方式：手机网站支付 `alipay.trade.wap.pay`（H5 浏览器跳转支付宝收银台）；微信小程序/公众号处于微信生态内无法唤起支付宝、App 支付 SDK 未接入，这些客户端渠道即使后台勾选也不展示支付宝选项
- 环境切换（沙箱/生产）：`pay_config.alipay_gateway_url` 为空即生产网关 `https://openapi.alipay.com`，填支付宝沙箱网关 `https://openapi-sandbox.dl.alipaydev.com` 则整条链路（下单、退款、回调验签）切到沙箱。该列可留空，不参与 `IsConfigured()` 必填口径
  - 网关地址入库前由 `normalizeAlipayGateway` 规范化：SDK 自行拼接 V2 的 `/gateway.do` 与 V3 的接口路径，而开放平台复制来的「网关地址」通常自带 `/gateway.do` 后缀，直接入库会拼成 `/gateway.do/gateway.do` 而 404，故只保留到协议+域名（含端口）
  - 沙箱与生产是两套独立的 AppID、应用私钥与支付宝公钥，混用必然签名/验签失败；后台切换网关时若支付宝渠道已启用需二次确认，且沙箱的异步通知同样由支付宝服务器发起，回调地址仍需公网可达
- 加签方式（公钥模式 / 公钥证书模式）：`pay_config.alipay_mode` 取值 `public`（默认，空串按公钥模式兼容存量）与 `cert`，后台支付配置页用单选切换，两种模式的必填项与录入控件不同
  - 命名对照：支付宝开放平台控制台的选项叫「密钥」和「证书」，与官方文档的「公钥模式 / 公钥证书模式」是两个名字同一件事。后台单选按「主名（平台叫法）」展示为 `公钥模式（密钥）`/`公钥证书模式（证书）`，并在说明区写明各自必填项，避免选错方式导致签名/验签失败；存储值与 proto 字段均不受命名调整影响
  - 公钥模式：AppID + 应用私钥 + 支付宝公钥（ textarea 粘贴）；异步通知地址不在本页展示（下单时随请求携带，开放平台无对应配置入口）
  - 公钥证书模式：AppID + 应用私钥 + 应用公钥证书 + 支付宝公钥证书 + 支付宝根证书；三份证书为 `pay_config` 的 `alipay_app_cert`/`alipay_public_cert`/`alipay_root_cert`（mediumtext），**只能经上传接口写入、GET 不回传内容只回传 `*_cert_uploaded` 标志**，保存请求不携带这些列（单行全量覆写会把已上传证书清空）
  - 模式必填口径彼此独立：切换模式后另一模式的残留值（如公钥证书模式下的支付宝公钥）不参与判定，未补齐当前模式必填项即判未就绪（fail-closed），避免「切了模式以为还能用」
  - 公钥证书模式打通 SDK `NewAlipayConfigUtil` 的证书初始化（传入三证书 Content 而非路径），SDK 据此计算 `app_cert_sn`/`root_cert_sn` 并在请求公共参数中携带，响应验签按 `alipay-sn` 头从证书缓存取公钥
- 就绪判定与离线自检：就绪 = 当前加签方式的必填项齐全 **且** 密钥自检通过
  - 自检不联网（`checkAlipayKeys`）：私钥两种模式一致，走与真实下单相同的签名路径（SDK `AloneRsaSign` → `security.RSASign`）；公钥模式校验支付宝公钥可解析（`security.ParseRSAPublicKey`，与回调验签同路径）；公钥证书模式分别按 `CertSN`/`CertPublicKey`/`RootCertSN` 校验三证书可解析（与执行器构建、通知验签同路径），把「私钥粘错、把应用公钥错填成支付宝公钥、证书传到别的位置」这类错误在保存或上传时就暴露，而不是等真实用户点支付才失败
  - 证书与私钥的录入接口（`cert_type` = `app_cert`/`alipay_public_cert`/`root_cert`/`private_key`）在写库前按同一口径校验内容可解析性，失败即拒绝且不覆盖原内容，原因经 `FailedPrecondition` 原样透传到后台界面
  - 根证书为多段文件，真实支付宝根证书中除 RSA 段外还含**国密 SM2 段**（Go 标准库 `x509` 无法解析，报 `unsupported elliptic curve`）。SDK 侧 `RootCertSN` 与通知验签的根证书遍历均改为**跳过无法解析的段**（这些段本就不参与 `root_cert_sn` 计算，与 PHP/Java SDK 只取 RSA 段的口径一致），仅在一段可用 RSA 证书都取不到时才判内容非法；此前"任一段解析失败即整体报错"会让合法的根证书上传失败
  - 录入成功（上传或粘贴）后前端只回写服务端的就绪/上传状态位与乐观锁版本号，**不整份重读配置**：证书写入是即时落库的，而此刻表单里往往还有未保存的编辑（刚切换的加签方式、已填未存的 AppID），整份重读会把它们覆盖回服务端旧值，表现为「证书上传成功但表单跳回公钥模式」
  - 后台录入支持「上传文件」与「直接粘贴内容」两种方式：粘贴时前端把文本包成 `.pem` 文件复用同一录入接口，扩展名白名单、64KB 上限与内容校验口径完全一致，服务端无分支差异；因 GET 不回传明文，粘贴框恒为空且留空不提交即表示不修改，界面对此有明确提示
  - 自检失败原因经 `pay_config` → proto `alipay_ready_message` → 网关 `alipay_ready_message` 回传后台展示；后台「已配置」状态、C 端是否展示支付宝、下单是否可用三者同口径（均由 `AlipayConfigStatus` 计算），避免「后台说已配置、用户点了却失败」
- 异步通知地址格式：自 2026-10-20 起本页不再有手填入口，地址一律由「站点设置」的部署域名派生（`{域名}/api/v1/payments/callback/alipay`）并在保存时写库；2026-10-22 起本页也不再展示该地址（手机网站支付的 notify_url 是接口请求参数，开放平台无对应配置入口，展示只会误导用户去平台找地方填；派生值改在「站点设置 → 派生地址」一处核对）。服务端 `SavePayConfig` 仍保留 `checkNotifyURL` 兜底（允许留空，非空必须是带域名且无空格换行的 http(s) 绝对地址），作为派生值与存量数据的防线。通知地址写错时支付宝会持续重发但永远打不到网关，表现为「用户已付款而订单仍未支付」，属只能在写库前拦住的一类配置错误
- 支付完成回跳 `return_url`：同为派生只读项（`{域名}/s/#/pages/order/list`），仅作体验用途，支付结果一律以异步通知与订单状态为准
  - 存量为空时下单不携带 `return_url`/`quit_url`，用户在收银台完成支付后不会自动回到本站；C 端 H5 以回站监听兜底（`utils/pay.ts` 的 `onReturnToSite`，`visibilitychange`/`pageshow` 一次性绑定），用户手动切回浏览器即刷新订单状态，不会停留在「支付中」而重复下单
  - 派生值必须是浏览器可访问的 http/https 绝对地址，故其质量取决于「站点设置」的部署域名（或 `SITE_BASE_URL`）；填 localhost/内网 IP 时手机根本打不开回跳页，站点设置页对此有标黄提示
- 微信内置浏览器引导（商户侧自行实现，官方已在新签约产品中下线收银台「继续浏览器付款」兜底入口）：C 端按 UA（MicroMessenger）识别微信内置浏览器，选择支付宝时不再直接跳转收银台，改为跳转独立**免登录引导页**（`pages/pay/alipay`）——微信内展示分步指引「点击右上角 ··· → 在浏览器中打开」并提供「复制支付链接」按钮（Clipboard API 优先、execCommand 兜底）；普通浏览器保持直接跳转
  - **引导页 URL 只携带支付单号，不携带支付链接本身**（2026-10-22 修复）：支付链接含 `#`/`?` 等保留字符，经 uni-app H5 hash 路由 query 传递会被框架编解码破坏（实测 `?` 会被改写为 `=`，与编码层数无关——一层、两层 encodeURIComponent 均复现），破坏后的链接发到支付宝网关即报 `missing-method`。引导页在系统浏览器打开后凭单号调公开接口 `GET /payments/alipay/url` 实时换取新签名的收银台链接（顺带解决旧链接 timestamp 过期问题），微信内则用换取到的链接作复制兜底；payment_no 是 ZF+UUID 不可枚举凭据，接口与状态查询同级别注册在公开路由组，仅对待支付的支付宝单返回链接
- SDK：`github.com/jcbowen/alipay-sdk-go-all`（自研，对齐支付宝官方 PHP SDK 结构；当前为本地 replace 依赖，合入前需推送 GitHub 并移除 replace）。CI 会 `go mod edit -dropreplace` 后从公共 proxy 拉已发布 tag，故**改动 SDK 必须打新 tag 并同步上调 `go.mod` 的 require 版本**，否则本地 docker 已修好而 CI 镜像仍是旧行为（2026-10-21 的根证书国密段跳过即属此类，待 `v0.0.4`）
- 支付流程：
  1. 前端调用 `POST /api/v1/payments` 传入 `order_id` 和 `channel="alipay"`，通过 `X-Channel-Code` 请求头声明所在客户端渠道
  2. 后端校验支付宝配置完整性（AppID + 应用私钥 + 支付宝公钥），不完整时直接返回错误；同时校验该支付渠道在当前客户端渠道上可用（pay_config 适用渠道勾选 ∩ 渠道能力就绪），不可用时拒绝
  3. 创建独立支付单（`payment_no` 使用 `ZF` + UUID），调起参数：`out_trade_no`/`total_amount`（元，两位小数）/`subject`/`product_code=QUICK_WAP_WAY`/`timeout_express`（交易时效，见下）/`quit_url`（收银台中途退出回跳地址，与 `return_url` 同值；`quit_url` 属 `biz_content` 业务参数而非公共参数）；公共参数携带 `notify_url`，配置了回跳地址时一并携带 `return_url`
     - 交易时效：`timeout_express` 取 `business.order_timeout`（秒）向上取整换算为分钟（最小 `1m`，默认 1800 秒 → `30m`），使支付宝侧交易时效与本地订单超时取消时效对齐。不传该参数时支付宝按签约协议给默认时效（约 15 天），本地订单早已超时取消而收银台仍可付款，形成资金挂账
  4. 通过 SDK `PageExecute("alipay.trade.wap.pay", "GET")` 生成带 RSA2 签名的收银台跳转 URL，返回 `{"alipay_pay_url": "..."}`；H5 端普通浏览器直接 `window.location.href` 跳转，微信内置浏览器跳引导页凭单号换链（见上）
  5. 用户支付完成后，支付宝回调 `POST /api/v1/payments/callback/alipay`（POST form）
  6. 网关侧不依赖 `Content-Type`，直接读取 raw body 按 `application/x-www-form-urlencoded` 解析通知参数（支付宝部分场景投递的通知不带 urlencoded 头，交给 `ParseForm` 会得到空参数并永远回 `failure` 引发无限重发）；请求体上限 64KB，超限或编码非法直接回 `failure` 且不投递支付服务。**依赖前提**：全局中间件 `SetGPC`（jcbaseGo）须在 form 分支解析后回灌请求体——2026-10-22 线上故障即因其 form 分支 `ParseForm` 消费 body 且不恢复（JSON/XML 分支均有恢复，唯独 form 分支没有），支付宝标准通知的 raw body 被消费 → 回调参数恒为空 → 永远回 `failure` → 支付宝无限重发、用户已付款订单始终未支付；根因修复落在 jcbaseGo（form 分支「读取 + 回灌 + 自行 ParseQuery」，v0.16.4 之后），网关另有 `TestAlipayCallbackBehindSetGPCMiddleware` 经真实中间件链的回归用例锁定。另注意 debugger 看不到回调是正常现象（`/api/v1/payments/callback` 在 debugger 跳过名单内，防回调敏感信息入库），判据应以 nginx access log 与业务日志为准
  7. 后端按加签方式分流验签（剔除 sign/sign_type 后按 key 升序拼接，仅剔除空值——值以 `@` 开头的字段照常参与签名）：公钥模式用 `RsaCheckV1` + 配置的支付宝公钥；证书模式用 `RsaCheckV1WithCert`，按通知里的 `alipay_cert_sn` 在「支付宝公钥证书 + 根证书链」中定位验签公钥，序列号不匹配（证书过期或未同步更新）直接拒绝，不存在「找不到公钥就放行」的路径。验签通过后再核对 `app_id` 与配置一致（支付宝公钥为全商户共用，验签只能证明"来自支付宝"，不核对 app_id 无法阻止跨应用通知重放），仅 `TRADE_SUCCESS`/`TRADE_FINISHED` 视为支付成功，`total_amount` 与支付单金额强制比对，随后复用 `handlePaySuccess` 更新支付单与订单状态
  8. 回调应答为纯文本：受理成功返回 `success`，验签失败/身份不符/参数缺失/DB 异常返回 `failure`，支付宝按通知策略重发（重发期间验签与金额校验保证幂等安全）
  - 迟到回调：支付单已被订单超时取消置为「已关闭」(status=5) 后收到成功回调，仍按终态兜底忽略（不置已支付、不流转订单），但记 `[CRITICAL]` 日志标明"订单已取消而用户仍完成付款，需人工对账退款"，避免挂账只能靠翻明细发现
- 退款：SDK V3 `alipay.trade.refund` 同步接口，`out_request_no` 传退款单号（幂等键），`RefundAmount` 元字符串；`fund_change=N`（重复请求未改变资金）同样视为成功；退款成功后回填 `transaction_id`（支付宝交易号），后续订单状态流转、销量回退与微信路径一致
  - 成功判定：走通用 `Execute` 而非 typed Refund，并自行校验响应体 `code=10000`（SDK 对齐 PHP 行为，HTTP 2xx 时不解析业务码，typed 成功模型亦无 `code` 字段）。退款是资金写操作，网关以 200 返回错误码时若只判 HTTP 状态会被误记"已退款"并回补库存；业务失败时抛出带 `code/sub_code/sub_msg` 的错误
- 配置版本检测：回调受理（微信/支付宝）与退款入口在执行前先做 `getPayConfigCached` 版本检测。仅下单链路检测的话，只处理过回调/退款的实例会长期持有空缓存，导致验签公钥缺失、渠道客户端为 nil 而把真实通知判为失败
- 幂等性：与微信一致——回调按 `payment_no` 幂等，退款按 `refund_no` 唯一索引幂等
- 多次支付：与微信一致，同订单、同支付方式且金额一致时复用已有待支付单及其调起参数
- 配置展示：支付宝配置不完整、密钥自检未通过，或该支付渠道在当前客户端渠道上不可用时，C 端不展示支付宝支付选项
- 离线测试：`services/payment/service/alipay_test.go`（通知验签与身份/状态/金额校验、`timeout_express` 换算、密钥自检 `checkAlipayKeys` 与就绪口径 `AlipayConfigStatus`、网关规范化 `normalizeAlipayGateway`、执行器按网关路由且路径不重复，测试内自生成 RSA 密钥对伪造支付宝签名，无 DB/网络）、`services/payment/service/alipay_cert_test.go`（证书模式必填口径与就绪原因、执行器构建、证书模式通知验签含序列号不匹配拒绝、上传内容可解析性校验（含根证书混入不可解析段须跳过、全段均不可解析才拒绝）、通知地址格式兜底，测试内自签证书）与 `gateway/handler/payment_callback_test.go`（回调参数解析不依赖 Content-Type、体积上限、失败应答，以及经 `SetGPC` 真实中间件链的 form-urlencoded/无 Content-Type 两种投递形态取参回归——后者为 2026-10-22 线上故障的锁定用例，直接构造 gin context 的旧用例覆盖不到中间件消费 body 的场景）均可在 CI 直跑；涉渠道实调的路径仍需真实商户配置才能验证
- 上线配置步骤：
  1. 先在后台「系统管理 → 站点设置」填好「部署域名」（或部署时注入 `SITE_BASE_URL`）：支付页的异步通知/回跳地址全部由它派生，域名没配好之前回调地址只能按当前访问的 host 现推，公网回调必然打不通

  4. 保存后配置热更新即时生效，就绪状态转为「已配置」后可启用渠道开关；保存或上传时密钥/证书自检不通过则弹窗保持打开并展示失败原因，不会误标已配置
  5. 沙箱联调：点「切沙箱」填入沙箱网关并改用沙箱的 AppID/应用私钥/支付宝公钥或沙箱证书（卡片显示「沙箱」标签），联调结束点「切生产」并换回生产凭证

  1. 迟到成功回调/挂账的自动退款（原单金额全额退回，`out_request_no` 用独立退款单号保证幂等）：`business.payment_reconcile.auto_refund_stuck` 开关与配置口径已就位（默认关闭），退款回执需真实商户号联调验证后才能开启

  3. `EncryptKey`（AES 内容加密密钥）接入：用于开放平台开启接口内容加密后的请求/回调解密，需新增配置载体与后台录入；证书模式已接入（见上「加签方式」），本项为剩余能力

- 已落地的原二期项（2026-10-21 支付可靠性改造，见上《支付回调可靠性》小节）：订单超时/取消时调用 `alipay.trade.close`（及微信 `CloseOrder`）主动关闭渠道交易；`alipay.trade.query` / 微信 `QueryOrder` 定时回查待支付单的对账补偿

#### 支付回调可靠性（对账补偿与人工处置）

- 定位：异步回调只是快速路径，渠道查询（微信 `QueryOrder` / 支付宝 `alipay.trade.query`）才是事实来源。系统不再凭本地判断改资金状态，任何「确认支付」都以渠道应答或人工核实到的渠道交易号为前提（方案全文见根目录 `solution-20261021-支付回调可靠性-v2.md`）
- 三条兜底路径（payment 服务 `service/scheduler.go`，Redis 分布式锁 SetNX + Lua 释放，多实例只有一份在跑，每分钟一轮）：
  1. 待支付单回查：扫 `status=1` 且 `pay_type IN (1,2)` 的渠道支付单，创建满 `min_age_seconds`（默认 60s）才起扫（给正常回调留时间），两次回查至少间隔 `throttle_minutes`（默认 5min），累计 `max_reconcile_count`（默认 24 次）后写「放弃对账」流水并停止回查；只回查 `pending_max_minutes`（默认 120min，与微信 prepay 时效对齐；支付宝侧取 `min(该值, business.order_timeout 换算分钟)`，与下单 `timeout_express` 同源）窗口内的单，超窗直接跳过。应答分流：已收款 → `handlePaySuccess` 补同步（`confirm_source=2` 对账补偿、`confirm_ref=reconcile:支付单号`）；未支付/无此交易 → 只推进节流不改状态（`NOT_EXIST` 需连续两轮才关单，渠道已自行关闭的交易本轮即关单）；金额不符 → 拒绝确认并进人工待办；渠道查询失败 → 不改任何资金状态，写 `result=5` 流水
  2. 挂账检测：扫已关闭(5)支付单，渠道已收款则写 `kind=3/result=9` 待办；同一支付单只保留一条待处理记录，否则每分钟一轮会把异常页刷成噪声
  3. 取消前置确认：订单调度器取消超时单之前先 RPC 让支付服务回查渠道（`confirm_ref=cancel-guard`），命中已收款则把订单补同步为已支付并放弃取消（宁可延迟取消，不可误取消已收款单）。之所以必须**前置**：订单状态机 `2: {1,100}` 不含 `6→2`，取消之后再收到成功回调只能挂账退款
- 失败记录重试 `retryFailures`（`runOnce` 里最先执行，2026-10-22 加固）：这条路径处理的是「渠道查询失败 / 补同步中途出错」的单笔待重试记录，一旦绕开扫描的约束就会在最坏时刻（渠道整体不可达）放大调用量，因此与两条扫描共用同一套口径——独立分布式锁 `scheduler:payment:reconcile:retry:lock`、**沿用支付单上的 `last_reconciled_at` 节流指针**（扫描刚查过的单本轮不再重试，同轮渠道调用不会翻倍）、进入循环后在**打渠道之前**先判 `max_reconcile_count`（用满上限直接转放弃，零渠道调用）、同一支付单本轮只打扰渠道一次（跨锁竞态可能留下 pending/stuck 两条待重试行，被跳过的那条不累加 `retry_count`，不算一次尝试）。累计上限刻意**不写进扫描 SQL**：写进去这些行会永远停在待重试态、白白占住批次额度。`recordFailure` 同时改为按 `uk_failures_pending` upsert，重复失败只刷新原因不再新增行（详见 05-数据库设计）
- 关单时同步关闭渠道交易：`ClosePayments` 对已创建渠道交易的待支付单调用渠道 `CloseOrder`（微信 JSAPI 关单 / 支付宝 `alipay.trade.close`），只在「渠道明确未收款」后执行（渠道不允许关闭已付款交易）；关单失败不影响本地关单，钱的事由对账任务继续跟，`enabled=false` 时退回纯本地关单的旧行为
- 唯一收敛点 `handlePaySuccess`（回调、对账、后台同步、人工标记四条路径共用，任何新入口不得自行写订单状态）：金额按分位比对（`yuanToFen`，规避浮点误差）→ 事务内条件更新 `status 1→2`（并发/重复回调只有一笔生效，其余幂等忽略）→ 事务提交后 RPC 同步订单（重试 3 次，仍失败记 `[CRITICAL]`，由对账与取消前置兜底）
- 取证与出口 `payment_notify_logs`（`kind` × `result` 两维，详见 05-数据库设计）：`kind` 1 渠道回调 / 2 对账补同步 / 3 挂账检出 / 4 渠道关单 / 5 后台手动同步 / 6 放弃对账；`result` 1 确认成功 / 2 幂等忽略 / 3 验签或解密失败 / 4 金额不符 / 5 处理异常 / 6 渠道未支付 / 7 渠道无此交易 / 8 关单结果 / 9 资金挂账。成功回调不存 `raw_body`（同一事实已落 `payments`，重复存正文只会把表撑大），失败与挂账必存；`headers` 里的签名与证书序列号**入库前掩码**。散落在 stderr 的 `[CRITICAL]`（挂账、金额不符、放弃对账）由此变成可查询、可销账的队列；流水按 `notify_log_retention_days`（默认 30 天）每日清理
- 后台入口（菜单在「订单管理」组、「售后管理」之后，标题「支付异常」）：
  - 同步支付状态 `POST /api/v1/admin/orders/:id/payment-sync`：向渠道核实并补同步，幂等可反复点；仅待支付族（1/100）订单可用，渠道未收款时零状态改动、只回传渠道事实（`paid/changed/channel_state/transaction_id/amount/payment_no/message`）
  - 标记已支付 `POST /api/v1/admin/orders/:id/payment-mark-paid`：渠道查不到或接口不可用、但线下已核实到账的死角；支付单号、渠道交易号、收款金额、核实依据四项必填，金额与应付做分位比对，成功后支付单与订单一并流转（`confirm_source=3`、`confirm_ref=manual-mark`，操作人写入备注）。仅待支付(1)订单可用——`6→2` 在状态机上必然失败，只会造出半截数据，那种挂账只能走退款
  - 异常队列 `GET /api/v1/admin/payments/anomalies` + 销账 `POST /api/v1/admin/payments/anomalies/:id/handle`（必填核实依据）；入参 `handled` 是筛选选择器（1 待处理 / 2 已处理 / 0 全部），与行数据的 `handled` 落库标记（0 待处理 / 1 已处理）是两套取值，前端选项与接口文档同口径
  - 订单详情新增「支付记录」表（`payments` + `payment_summary` 的 `attempts/succeeded/succeeded_amount`，`succeeded>1` 即重复支付、要立刻提醒去退款）与「通知/对账时间线」（`payment_logs`）。这些是 payment 服务的旁路数据，读不到时以 `payments_error`/`payment_logs_error` 显式告知前端「这里查不到」，不静默返回空表——空表会被读成「这笔订单没有支付记录」，是最坏的误导
  - 改单护栏：`PUT /api/v1/admin/orders/:id/status` 置 2 前先查该订单是否有成功支付单（`GetPayment`），没有就拒绝并引导到上面两个入口。所有订单都有 `payments` 行（现金/货到付款创建即成功），因此不需要任何豁免分支
- 敏感边界与权限：`payment:raw:view` 决定 `raw_body`/`headers` 是否下发，列表页只回摘要 + `has_raw` 标志（前端据此决定是否渲染展开按钮）；该权限点刻意**不进**社区管理员默认权限上限，实际只有超管可展开。社区隔离依据 `payments.community_id`（创建支付单时由网关从订单权威字段带入）与流水快照，`community_id=0` 的流水（连支付单都解析不出的验签失败）只对超管的全量队列可见
- 配置（`business.payment_reconcile`，详见 07-基础设施/02-错误码与配置.md）：`enabled`（总开关，关闭即退回「纯回调 + 纯本地关单」的旧行为）、`cancel_guard`、`auto_refund_stuck`（默认关闭）、`pending_max_minutes=120`、`interval_seconds=60`、`min_age_seconds=60`、`throttle_minutes=5`、`max_reconcile_count=24`、`batch_size=100`、`notify_log_retention_days=30`。三个开关用 `*bool` 而非 `bool + default:"true"`：`CheckAndSetDefault` 的布尔默认值机制无法区分「未配置」与「显式 false」，会把显式关闭强行改回开启，导致回退开关失效
- 两个必须记住的坑：
  - DSN 带 `parseTime=True` 时，datetime 列读回 `string` 字段是 RFC3339 形态（`2026-10-21T14:19:47+08:00`），按 `2006-01-02 15:04:05` 解析必然失败。`withinReconcileWindow` 曾因此恒走「解析失败保守放行」分支，回查时间窗形同虚设；现已统一走 `parseDBTime`（多 layout 容错），新增时间解析勿再直接 `time.Parse`
  - `base.MysqlBaseModel.BeforeCreate` 无条件把 `created_at/updated_at` 覆写为当前时间，测试要造「历史时间」的支付单/流水必须用裸 SQL `Exec INSERT`，走 GORM `Create` 造不出aging数据
- 测试覆盖：`services/payment/service/scheduler_test.go`（T1–T12：回调丢失捞回、未付只推进节流、起扫/节流/上限三道过滤、放弃对账、`NOT_EXIST` 两轮、金额不符进人工、并发确认幂等、挂账检出与去重、关单前核实、总开关零渠道调用、查询失败不改资金状态且重试受节流、重试队列不按轮次自我复制、同单同轮只打扰渠道一次、用满上限零渠道调用即转放弃；渠道调用全部由 `fakeChannels` 替身接管，集成用例直连本地 MySQL/Redis 且 Redis 固定用 DB 1 与容器调度锁隔离）、`services/order/service/scheduler_test.go` 的 `TestSchedulerCancelGuardConfirmsChannel`（T8 取消前置拦截的开/关两态）、`tests/api/73-payment-reliability.spec.ts`（T13–T18 后台入口、改单护栏、社区隔离与原文权限边界；渠道分支按环境实际配置走对应断言，不做 `test.skip`，避免「链路坏了也显示绿」）

#### 支付配置管理（数据库化）

- 支付配置（微信支付 V3、支付宝、渠道开关 `enabled_channels`）存储于数据库 `pay_config` 表（单行，id=1），不再使用 config.yaml
- 后台「系统管理 → 支付配置」页面维护，对应接口：
  - `GET /api/v1/admin/settings/payment`：读取配置；三个回调地址（`wechat.notify_url`/`alipay.notify_url`/`alipay.return_url`）与 `suggested_urls` 一律按**部署域名**（「站点设置」的 `base_url` 优先，未配置时回落 `SITE_BASE_URL` 环境变量兜底，两者都空时按当前请求域名现推且不写库）派生后返回，页面只读；已显式配置域名且库中值与派生值不一致时在读取内自愈回写；私钥与证书内容不回传明文，仅返回 `*_cert_uploaded` 上传状态（支付宝为 `alipay_cert_uploaded` + 证书模式三证书 `alipay_app_cert_uploaded`/`alipay_public_cert_uploaded`/`alipay_root_cert_uploaded`）；出参含 `alipay.mode`（加签方式）、`alipay_ready_message`（支付宝密钥自检失败原因，空表示通过）
  - `PUT /api/v1/admin/settings/payment`：保存配置，即时生效无需重启
    - 保存的是「非敏感字段 + 加签方式」：`alipay.mode` 随表单整行覆写（空串按公钥模式落库），证书与私钥内容一律不经过本接口
    - 异步通知地址在 payment 侧做格式兜底校验（允许留空；非空必须是带域名、无空格换行的 http(s) 绝对地址），不合法时拒绝整行保存并回传原因；自 2026-10-20 起本页不再录入回调地址，此校验作为派生值与存量数据的防线保留
    - 并发保护为乐观锁：请求携带读取时的 `updated_at` 作版本号，与库中当前版本不一致时拒绝保存并返回「支付配置已被其他操作更新，请刷新页面获取最新配置后重新提交」，避免两个后台标签页（或多管理员）互相静默覆盖
    - 版本号冲突用 `codes.FailedPrecondition` 承载（`codes.Internal` 属基础设施错误码，网关不透传原始消息，前端只会看到通用文案），版本细节仅记服务端日志
    - 读取接口内「渠道 AppID 回写到支付配置」这一步同样会推进版本号，故回写成功后必须重读配置再返回，否则前端下一次保存会被自己的版本号误判为冲突；回写携带读取时的版本号，冲突时放弃本次回写
  - `POST /api/v1/admin/settings/payment/cert`：multipart 上传证书文件（支持 `.pem/.key/.txt/.crt`，最大 64KB），文件内容直接存入数据库；后台「粘贴内容写入」同样走本接口（前端把文本包成 `.pem` 文件提交，服务端无需区分来源）
    - `cert_type` 取值：`private_key`（微信商户私钥 / 支付宝应用私钥）、`app_cert`、`alipay_public_cert`、`root_cert`（后三类为支付宝公钥证书模式专用）
    - 支付宝四类内容写库前先按真实链路校验可解析性（私钥签名自检、`CertSN`/`CertPublicKey`/`RootCertSN`），失败即拒绝且不覆盖原文件；扩展名与大小只拦明显错误，内容对不对要到签名阶段才暴露，故在此拦住
    - 单行全量覆写的保存接口不携带证书列，GET 也只回传上传标志；新增的 `pay_config` 敏感列必须沿用「上传接口写 + 保存接口不触碰」这一模式，否则一次普通保存就会把已上传内容清空
  - 读取接口内的「渠道 AppID 回写」是一次整行覆写，必须逐字段回传当前值（含 `alipay_mode`），漏传字段会被写成默认值；本次改造曾漏带 `alipay_mode`，导致每次打开支付配置页都把证书模式重置回公钥模式
- 后台页面权限：无 `settings:update` 权限且非超管时页面为只读——渠道开关、上移/下移、各输入框、证书上传与保存按钮全部禁用，并给出只读提示，避免无权限账号误改资金相关配置
- 热更新：payment 服务进程内缓存配置并以 `updated_at` 作版本号，支付链路调用时检测到版本变更才重建支付客户端；数据库查询异常时降级使用缓存，不阻断支付
- 版本检测入口覆盖下单、回调受理（微信/支付宝）与退款三条链路：漏掉后两者时，只处理过回调/退款的实例会长期持有空配置缓存，验签公钥缺失会把真实通知判为失败
- 微信回调地址：`{域名}/api/v1/payments/callback/wechat`；支付宝回调地址：`{域名}/api/v1/payments/callback/alipay`

#### 客户端渠道管理（渠道管理）

- 各客户端访问渠道（微信小程序 mp / 微信公众号 gzh / 开放平台 App app / 浏览器 H5 h5）的主数据由 user 服务 `client_channels` 表管理，后台「系统管理 → 渠道管理」维护，对应接口：
  - `GET /api/v1/admin/settings/channels`：渠道列表（全部含停用）
  - `PUT /api/v1/admin/settings/channels/:id`：更新名称/AppID/AppSecret/启用/排序；AppSecret 留空保留原值，code 不可变更
- 启用语义：渠道未启用或凭证不完整时，该端登录（Code2Session）与按端支付能力不可用；h5 无需凭证默认启用
- 登录链路：小程序登录改读渠道管理的 mp 渠道配置（config.yaml 微信节点废弃不用，仅保留结构兼容），登录成功后幂等 upsert `user_channel_identities`（用户渠道身份表）
- 支付联动：pay_config 的 `wechat_channels/alipay_channels` 勾选该支付方式适用的客户端渠道（空=全部可用兼容口径）；C 端 `GET /payments/channels` 按请求头 `X-Channel-Code` 与渠道就绪状态取交集渲染；gzh 需公众号 OAuth、app 需 App 支付 SDK，链路开放前勾选也不展示
  - 后台勾选项与服务端能力矩阵同源，技术不可用的组合（微信的 gzh/app，支付宝的 mp/gzh/app）在界面上直接禁用，避免「能勾选但配了也不生效」的误导；客户端渠道本身未启用同样禁用
  - 禁用只针对新增勾选：存量数据里已勾选的不可用项仍可取消（否则历史配置无法纠正），未启用的渠道仍允许关闭

#### 现金支付

- 线下收款/货到付款，创建支付单时直接标记为支付成功并同步订单状态
- 不复用待支付现金单：现金支付无需第三方调起参数，复用待支付记录会跳过"置为已支付并同步订单状态"的副作用，导致订单停留在待支付而前端已提示支付成功
- 不经过第三方支付网关
- 退款时仅记录退款流水，不调用第三方接口
