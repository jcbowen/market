
#### 微信支付

- 支付方式：JSAPI（微信小程序；公众号内 JSAPI 需 OAuth 链路，暂未开放）、H5 支付（微信外浏览器）
- 支付流程：
  1. 前端调用 `POST /api/v1/payments` 传入 `order_id` 和 `channel="wechat"`，不传 openid，并通过 `X-Channel-Code` 请求头声明所在客户端渠道（h5/gzh/mp/alimp/android/ios，未携带按 h5 兑底）
  2. 网关读取当前渠道的绑定（`client_channels.pay_methods`）解析微信支付使用的 `pay_config` 行（config_id），校验该行启用且凭证就绪；绑定不存在或未就绪直接拒绝。能力矩阵：微信可绑定 h5/gzh/mp/pos，其余端保存绑定即被拒。**支付配置行不含 AppID**（见下《支付配置管理》的字段归属说明），下单 AppID 一律来自渠道
  3. 网关按客户端渠道解析 openid 与 AppID：mp 渠道 openid 取用户渠道身份表（user_channel_identities，mp 渠道回落存量 users.openid），AppID 取渠道管理的 mp 渠道配置；h5 渠道无 openid 走 H5 下单，AppID 取渠道管理的 h5 渠道配置；gzh/android/ios 渠道链路未开放直接拒绝。h5/mp 渠道未填 AppID 时该端不展示微信支付，下单同样拒绝（不再回落任何默认值，也不回落到配置行），错误文案直接指向「渠道管理」补全
  4. 创建独立支付单（`payment_no` 使用 `ZF` + UUID），落库渠道快照 `client_channel` 与本笔使用的 `app_id`；有可用 openid 走 JSAPI 统一下单（wego 请求级 AppID 覆盖），否则走 H5 下单。JSAPI 调起参数由 wego `BuildJSAPIPayParams(appID, prepayID)` 生成（签名串拼接与 RSA 签名都在库里，market 不再自建签名实现）
  5. 返回调起参数给前端：小程序端用 `uni.requestPayment` 调起 JSAPI（`signType` 为 RSA），H5 端跳转 `h5_url`（uni-app 未封装浏览器支付）
  6. 用户支付完成后，微信回调 `POST /api/v1/payments/callback/wechat`
  7. 后端通过 wego 验签解密，仅处理 `TRANSACTION.SUCCESS` 通知，更新支付单和订单状态
- 幂等性：
  - 支付回调通过 `payment_no` 保证幂等处理
  - 退款通过 `refund_no` 唯一索引保证幂等，重复提交直接返回成功
- 多次支付：一笔订单在支付成功前可多次发起支付；同订单、同支付方式且金额一致时复用已有待支付单及其调起参数，不再新建（复用仅限微信/支付宝这类需第三方调起参数的渠道）；订单已有支付成功记录时拒绝创建。`GetPayment` 仅查询支付成功（status=2）记录，因此待支付单不会被幂等校验误拦
- 校验失败按 fail-closed 处理：幂等校验与待支付单复用查询若发生数据库异常（非 `ErrRecordNotFound`），直接拒绝创建并返回内部错误，不把故障当作"无支付记录"放行，否则会产生多笔可实际扣款的支付单；底层错误只写服务端日志，对客户端返回统一业务文案
- 多次退款：一笔支付单支持多笔部分退款，累计退款金额不超过支付单金额；支付单累计退完时才标记为"已退款"
- 配置展示：当前渠道绑定里无微信支付、绑定指向的 `pay_config` 行未启用或凭证未就绪、客户端渠道本身未启用，或该渠道绑定了微信支付却没填本端 AppID 时，C 端不展示微信支付选项（渲染与下单同口径，均按绑定解析；收银台付款码同样按此口径决定是否可用）
- 回调归属校验：V3 通知全文加密，必须先按候选配置逐一验签解密拿到 `out_trade_no`，再反查支付单，用单上的 `config_id` 对应行商户号与 `app_id` 快照比对通知的 `mchid`/`appid`，两者都一致才算归属命中（币种非 CNY 一律拒绝）。验签通过只证明「报文由微信发出」，不证明「这笔交易属于本商户」——证书/APIv3 密钥曾在多商户间复用或被泄露时可代入他人通知；而归属依据只能取自支付单快照，取自配置行会因「一商户号服务多渠道」而不确定。空值项（线下单/存量单无快照）跳过比对而非拒绝
- 回调请求体上限：微信 V3 通知是「加密资源 + 少量元数据」的 JSON，正常体量 2KB 以内，网关在读取前先 `MaxBytesReader` 罩住 **64KB**（`wechatNotifyBodyLimit`，与支付宝 `alipayNotifyBodyLimit` 同口径；2026-10-31 补齐，原实现 `c.GetRawData()` 无上限整包读入）。本路由免登录且由渠道主动投递，不设上限等于把网关内存交给任何能打到此 URL 的请求。超限与临时读取失败分开应答：超限报文重投多少次都会超限，回 HTTP 400 + `{"code":"FAIL"}` 且不投递 payment 服务；读取中断/其他错误回 5xx 让微信按间隔重试。判定用 `isBodyTooLarge`（`errors.As(*http.MaxBytesError)`），只认体积超限，不把 `connection reset` 之类误判成报文非法
- 前端约束：仅支付真实完成才提示"支付成功"；用户取消、跳转 H5 支付页或渠道未开通时不提示成功，统一回到订单详情以便重新支付
  - 跳转外部收银台（`redirected`）后不再与站内路由竞争：先注册一次性回站监听（`visibilitychange`/`pageshow`）再跳转，用户从支付宝/微信回到本站tab即自动刷新订单状态，避免停留在「支付中」而重复发起支付
  - 微信内置浏览器选择支付宝（`guided`）时跳转独立引导页（免登录），不叠加 toast 打断操作步骤
- 上线前置：开启微信渠道原本要求先完成「回调兜底、待支付单生命周期、prepay 时效」三项——原因是 wego 无 CloseOrder 接口，订单取消后其待支付单在微信侧约 2 小时内仍可被支付，而该回调会因状态机拒绝 `6→2` 而回滚，形成"钱已扣、系统无成功记录"的资金挂账风险。2026-10-21 支付可靠性改造后这三项已落地（关单前调渠道 `CloseOrder`、取消前置渠道确认、挂账检出进异常队列，见下《支付回调可靠性》小节），仍必须在真实商户环境验证的只剩渠道 `QueryOrder`/`CloseOrder` 回执与自动退款回执（开发计划第 51–53 项）

#### 支付宝支付

- 支付方式：H5 浏览器跳转收银台 `alipay.trade.wap.pay`；支付宝小程序（alimp）内 `alipay.trade.create`（V3）返回 `trade_no`，C 端 `my.tradePay({tradeNO})` 调起；微信生态内无法唤起支付宝，App 支付 SDK 未接入，这些客户端渠道绑定保存即被能力矩阵拒绝，不展示支付宝选项。小程序签名凭证复用支付配置的应用私钥（与 H5 同一条配置或同平台另一条均可），渠道侧（alimp）只存 AppID
- 环境切换（沙箱/生产）：`pay_config.alipay_gateway_url` 为空即生产网关 `https://openapi.alipay.com`，填支付宝沙箱网关 `https://openapi-sandbox.dl.alipaydev.com` 则整条链路（下单、退款、回调验签）切到沙箱。该列可留空，不参与 `IsConfigured()` 必填口径
  - 网关地址入库前由 `normalizeAlipayGateway` 规范化：SDK 自行拼接 V2 的 `/gateway.do` 与 V3 的接口路径，而开放平台复制来的「网关地址」通常自带 `/gateway.do` 后缀，直接入库会拼成 `/gateway.do/gateway.do` 而 404，故只保留到协议+域名（含端口）
  - 沙箱与生产是两套独立的 AppID、应用私钥与支付宝公钥，混用必然签名/验签失败；后台切换网关时若支付宝渠道已启用需二次确认，且沙箱的异步通知同样由支付宝服务器发起，回调地址仍需公网可达
- 加签方式（公钥模式 / 公钥证书模式）：`pay_config.alipay_mode` 取值 `public`（默认，空串按公钥模式兼容存量）与 `cert`，后台支付配置页用单选切换，两种模式的必填项与录入控件不同
  - 命名对照：支付宝开放平台控制台的选项叫「密钥」和「证书」，与官方文档的「公钥模式 / 公钥证书模式」是两个名字同一件事。后台单选按「主名（平台叫法）」展示为 `公钥模式（密钥）`/`公钥证书模式（证书）`，并在说明区写明各自必填项，避免选错方式导致签名/验签失败；存储值与 proto 字段均不受命名调整影响
  - 公钥模式：AppID + 应用私钥 + 支付宝公钥（ textarea 粘贴）；异步通知地址不在本页展示（下单时随请求携带，开放平台无对应配置入口）
  - 公钥证书模式：AppID + 应用私钥 + 应用公钥证书 + 支付宝公钥证书 + 支付宝根证书；三份证书为 `pay_config` 的 `alipay_app_cert`/`alipay_public_cert`/`alipay_root_cert`（mediumtext），**只能经上传接口写入、GET 不回传内容只回传 `*_cert_uploaded` 标志**，保存请求不携带这些列（单行全量覆写会把已上传证书清空）
  - 模式必填口径彼此独立：切换模式后另一模式的残留值（如公钥证书模式下的支付宝公钥）不参与判定，未补齐当前模式必填项即判未就绪（fail-closed），避免「切了模式以为还能用」
  - 公钥证书模式打通 SDK `NewAlipayConfigUtil` 的证书初始化（传入三证书 Content 而非路径），SDK 据此计算 `app_cert_sn`/`root_cert_sn` 并在请求公共参数中携带，响应验签按 `alipay-sn` 头从证书缓存取公钥
- 就绪判定与离线自检：就绪 = 当前加签方式的必填项齐全 **且** 密钥自检通过
  - 自检不联网（`checkAlipayKeys`）：私钥两种模式一致，走与真实下单相同的签名路径（SDK `AloneRsaSign` → `security.RSASign`）；公钥模式校验支付宝公钥可解析（`security.ParseRSAPublicKey`，与回调验签同路径）；公钥证书模式分别按 `CertSN`/`CertPublicKey`/`RootCertSN` 校验三证书可解析（与执行器构建、通知验签同路径），把「私钥粘错、把应用公钥错填成支付宝公钥、证书传到别的位置」这类错误在保存或上传时就暴露，而不是等真实用户点支付才失败
  - 证书与私钥的录入接口（`cert_type` = `app_cert`/`alipay_public_cert`/`root_cert`/`private_key`）在写库前按同一口径校验内容可解析性，失败即拒绝且不覆盖原内容，原因经 `FailedPrecondition` 原样透传到后台界面
  - 根证书为多段文件，真实支付宝根证书中除 RSA 段外还含**国密 SM2 段**（Go 标准库 `x509` 无法解析，报 `unsupported elliptic curve`）。SDK 侧 `RootCertSN` 与通知验签的根证书遍历均改为**跳过无法解析的段**（这些段本就不参与 `root_cert_sn` 计算，与 PHP/Java SDK 只取 RSA 段的口径一致），仅在一段可用 RSA 证书都取不到时才判内容非法；此前"任一段解析失败即整体报错"会让合法的根证书上传失败
  - 录入成功（上传或粘贴）后前端以**录入接口返回的最新配置行**回写服务端维护的字段（就绪/上传状态位与乐观锁版本号），**不整份重读配置**：证书写入是即时落库的，而此刻表单里往往还有未保存的编辑（刚切换的加签方式、已填未存的 AppID），整份重读会把它们覆盖回服务端旧值，表现为「证书上传成功但表单跳回公钥模式」；返回行携带的新版本号同时保证随后的保存不被乐观锁拒绝
  - 后台录入支持「上传文件」与「直接粘贴内容」两种方式：粘贴时前端把文本包成 `.pem` 文件复用同一录入接口，扩展名白名单、64KB 上限与内容校验口径完全一致，服务端无分支差异；因 GET 不回传明文，粘贴框恒为空且留空不提交即表示不修改，界面对此有明确提示
  - 自检失败原因经 `pay_config` → proto `ready_message`（`PayConfigRow` 42 号字段）回传后台展示；后台「已配置」状态、C 端是否展示支付宝、下单是否可用三者同口径（均由 `AlipayConfigStatus` 计算），避免「后台说已配置、用户点了却失败」
- 异步通知地址格式：自 2026-10-20 起本页不再有手填入口，地址一律由**显式部署域名**派生（`{域名}/api/v1/payments/callback/alipay`）并在保存时写库（2026-10-30 起显式域名缺位时派生为空串，不再按当前访问 host 现推落库，见「上线配置步骤」第 1 步）；2026-10-22 起本页也不再展示该地址（手机网站支付的 notify_url 是接口请求参数，开放平台无对应配置入口，展示只会误导用户去平台找地方填；派生值改在「站点设置 → 派生地址」一处核对）。服务端 `SavePayConfig` 仍保留 `checkNotifyURL` 兜底（允许留空——空即未就绪；非空必须是带域名且无空格换行的 http(s) 绝对地址），作为派生值与存量数据的防线。通知地址写错时支付宝会持续重发但永远打不到网关，表现为「用户已付款而订单仍未支付」，属只能在写库前拦住的一类配置错误；这也是「残留旧域名的错地址比空地址危险」的原因
- 支付完成回跳 `return_url`：同为派生只读项（`{域名}/s/#/pages/pay/result`，即免登录支付结果页），仅作体验用途，支付结果一律以异步通知与订单状态为准
  - 存量为空时下单不携带 `return_url`/`quit_url`，用户在收银台完成支付后不会自动回到本站；C 端 H5 以回站监听兜底（`pagesOrder/common/pay.ts` 的 `onReturnToSite`，`visibilitychange`/`pageshow` 一次性绑定），用户手动切回浏览器即刷新订单状态，不会停留在「支付中」而重复下单
  - 派生值必须是浏览器可访问的 http/https 绝对地址，故其质量取决于「站点设置」的部署域名（或 `SITE_BASE_URL`）；填 localhost/内网 IP 时手机根本打不开回跳页，站点设置页对此有标黄提示
- 微信内置浏览器引导（商户侧自行实现，官方已在新签约产品中下线收银台「继续浏览器付款」兜底入口）：C 端按 UA（MicroMessenger）识别微信内置浏览器，选择支付宝时不再直接跳转收银台，改为跳转独立**免登录引导页**（`pagesOrder/pay/alipay`）——微信内展示分步指引「点击右上角 ··· → 在浏览器中打开」并提供「复制支付链接」按钮（Clipboard API 优先、execCommand 兜底）；普通浏览器保持直接跳转
  - **引导页 URL 只携带支付单号，不携带支付链接本身**（2026-10-22 修复）：支付链接含 `#`/`?` 等保留字符，经 uni-app H5 hash 路由 query 传递会被框架编解码破坏（实测 `?` 会被改写为 `=`，与编码层数无关——一层、两层 encodeURIComponent 均复现），破坏后的链接发到支付宝网关即报 `missing-method`。引导页在系统浏览器打开后凭单号调公开接口 `GET /payments/alipay/url` 实时换取新签名的收银台链接（顺带解决旧链接 timestamp 过期问题），微信内则用换取到的链接作复制兜底；payment_no 是 ZF+UUID 不可枚举凭据，接口与状态查询同级别注册在公开路由组，仅对待支付的支付宝单返回链接
  - **发起场景标记 `from=wxh5`**（2026-10-31 起）：引导页换链时固定携带 `from=wxh5`（引导页只存在于「微信内发起」场景），服务端白名单校验后把它编入 `return_url`/`quit_url`。因为该链路支付完成回跳必然落在**无本站登录态的系统浏览器**，结果页 `pages/pay/result` 读到该标记后把「回到首页」按钮替换为「返回微信」（`weixin://` scheme 拉起微信，须在用户点击手势内触发；拉起失败 2 秒内页面未失焦则提示手动切换），用户切回微信后微信内停留的引导页 `onShow` 自动查询并转为完成页；普通浏览器直连支付不携带标记，行为不变
  - **结果页待支付态「继续支付」**（2026-10-31 起）：收银台中途退出（`quit_url`）或支付未完成的回跳落在结果页待支付态时，页面提供「继续支付」按钮——凭当前页支付单号调同一公开换链接口（`from` 按当前页原样携带）取新签名链接后直接唤起支付宝，无需回微信再绕「在浏览器打开」；换链瞬间支付单已被回调落账则仅同步本地状态不跳转，链接换不出则 toast 提示并继续轮询。仍凭同一支付单号换取，不产生新支付单，无重复支付风险
- SDK：`github.com/jcbowen/alipay-sdk-go-all`（自研，对齐支付宝官方 PHP SDK 结构；当前为本地 replace 依赖，合入前需推送 GitHub 并移除 replace）。CI 会 `go mod edit -dropreplace` 后从公共 proxy 拉已发布 tag，故**改动 SDK 必须打新 tag 并同步上调 `go.mod` 的 require 版本**，否则本地 docker 已修好而 CI 镜像仍是旧行为（2026-10-21 的根证书国密段跳过即属此类，待 `v0.0.4`）
- 支付流程：
  1. 前端调用 `POST /api/v1/payments` 传入 `order_id` 和 `channel="alipay"`，通过 `X-Channel-Code` 请求头声明所在客户端渠道（alimp=支付宝小程序，h5=其余浏览器）
  2. 网关读取当前渠道的绑定（`client_channels.pay_methods`）解析支付宝使用的 `pay_config` 行（config_id），校验该行启用且凭证就绪（AppID + 应用私钥 + 支付宝公钥/证书）；能力矩阵：支付宝可绑定 h5/alimp/pos，其余端保存绑定即被拒。`config_id` 与 `client_channel` 随 `CreatePaymentReq` 传入 payment 服务
  3. 创建独立支付单（`payment_no` 使用 `ZF` + UUID），调起参数：`out_trade_no`/`total_amount`（元，两位小数）/`subject`/`timeout_express`（交易时效，见下）；公共参数携带 `notify_url`，配置了回跳地址时一并携带 `return_url`
     - 交易时效：`timeout_express` 取 `business.order_timeout`（秒）向上取整换算为分钟（最小 `1m`，默认 1800 秒 → `30m`），使支付宝侧交易时效与本地订单超时取消时效对齐。不传该参数时支付宝按签约协议给默认时效（约 15 天），本地订单早已超时取消而收银台仍可付款，形成资金挂账
  4. 按 `client_channel` 分流下单：h5 通过 SDK `PageExecute("alipay.trade.wap.pay", "GET")` 生成带 RSA2 签名的收银台跳转 URL，返回 `{"alipay_pay_url": "..."}`，H5 端普通浏览器直接 `window.location.href` 跳转，微信内置浏览器跳引导页凭单号换链（见上）；alimp 走 V3 `alipay.trade.create` 预下单，返回 `{"trade_no":"..."}`，C 端在支付宝小程序内调 `my.tradePay({ tradeNO })` 调起收银台（resultCode 9000 成功 / 8000 已受理跳转 / 其余取消）
     - **alimp 链路尚未打通（2026-10-30 状态）**：`buildAlipayMiniParams` 未传 `buyer_id`（官方小程序支付必填）、未设 `product_code=JSAPI_PAY`，且全链路没有支付宝买家标识来源（C 端未做 `my.getAuthCode` → `alipay.system.oauth.token` 换取 user_id 的环节）。当前代码仅具备「建单 + 调起」骨架，真机支付会失败；**渠道启用对外前必须补齐并在沙箱真机验证**（缺口清单见根目录 todolist 的 P0-1）。
  5. 用户支付完成后，支付宝回调 `POST /api/v1/payments/callback/alipay`（POST form）
  6. 网关侧不依赖 `Content-Type`，直接读取 raw body 按 `application/x-www-form-urlencoded` 解析通知参数（支付宝部分场景投递的通知不带 urlencoded 头，交给 `ParseForm` 会得到空参数并永远回 `failure` 引发无限重发）；请求体上限 64KB，超限或编码非法直接回 `failure` 且不投递支付服务。**依赖前提**：全局中间件 `SetGPC`（jcbaseGo）须在 form 分支解析后回灌请求体——2026-10-22 线上故障即因其 form 分支 `ParseForm` 消费 body 且不恢复（JSON/XML 分支均有恢复，唯独 form 分支没有），支付宝标准通知的 raw body 被消费 → 回调参数恒为空 → 永远回 `failure` → 支付宝无限重发、用户已付款订单始终未支付；根因修复落在 jcbaseGo（form 分支「读取 + 回灌 + 自行 ParseQuery」，v0.16.4 之后），网关另有 `TestAlipayCallbackBehindSetGPCMiddleware` 经真实中间件链的回归用例锁定。另注意 debugger 的 **HTTP 请求日志**看不到回调是正常现象（`/api/v1/payments/callback` 在 debugger 跳过名单内，防回调敏感信息整条入库）；回调的受理与取证由 gateway/payment 的**进程级记录**补齐（见 03-缓存存储与日志.md 7.8 与本页「验签失败取证」），判据以进程记录、`payment_notify_logs` 与业务日志为准
  7. 后端按加签方式分流验签（剔除 sign/sign_type 后按 key 升序拼接，仅剔除空值——值以 `@` 开头的字段照常参与签名）：公钥模式用 `RsaCheckV1` + 配置的支付宝公钥；证书模式用 `RsaCheckV1WithCert`，验签公钥按通知里的 `alipay_cert_sn` 分两条路径取——**有值**时在「支付宝公钥证书 + 根证书链」中按序列号严格定位，定位不到（证书过期或未同步更新）直接拒绝；**缺失**时（官方从未承诺通知侧携带该字段，见 SDK README 的各家 SDK 对照）直接用本商户支付宝公钥证书里的公钥验签。两条路径的信任锚都是本地那份支付宝公钥证书，签名不出自该证书对应的私钥一律拒绝，不存在「找不到公钥就放行」的路径（SDK v0.0.6；此前 v0.0.5 要求该字段必填，导致 2026-10-23 线上合法通知 100% 验签失败）。验签通过后再核对 `app_id` 与配置一致（验签只能证明"来自支付宝"，不核对 app_id 无法阻止跨应用通知重放），仅 `TRADE_SUCCESS`/`TRADE_FINISHED` 视为支付成功，`total_amount` 与支付单金额强制比对，随后复用 `handlePaySuccess` 更新支付单与订单状态。验签不通过时不静默拒绝，会落一条取证记录，字段口径见下「验签失败取证」
  8. 回调应答为纯文本：受理成功返回 `success`，验签失败/身份不符/参数缺失/DB 异常返回 `failure`，支付宝按通知策略重发（重发期间验签与金额校验保证幂等安全）
  - 迟到回调：支付单已被订单超时取消置为「已关闭」(status=5) 后收到成功回调，仍按终态兜底忽略（不置已支付、不流转订单），但记 `[CRITICAL]` 日志标明"订单已取消而用户仍完成付款，需人工对账退款"，避免挂账只能靠翻明细发现
- 退款：SDK V3 `alipay.trade.refund` 同步接口，`out_request_no` 传退款单号（幂等键），`RefundAmount` 元字符串；`fund_change=N`（重复请求未改变资金）同样视为成功；退款成功后回填 `transaction_id`（支付宝交易号），后续订单状态流转、销量回退与微信路径一致
  - 成功判定：走通用 `Execute` 而非 typed Refund，并自行校验响应体 `code=10000`（SDK 对齐 PHP 行为，HTTP 2xx 时不解析业务码，typed 成功模型亦无 `code` 字段）。退款是资金写操作，网关以 200 返回错误码时若只判 HTTP 状态会被误记"已退款"并回补库存；业务失败时抛出带 `code/sub_code/sub_msg` 的错误
- 配置版本检测：回调受理（微信/支付宝）与退款入口在执行前先做 `getPayConfigCached` 版本检测。仅下单链路检测的话，只处理过回调/退款的实例会长期持有空缓存，导致验签公钥缺失、渠道客户端为 nil 而把真实通知判为失败
- 幂等性：与微信一致——回调按 `payment_no` 幂等，退款按 `refund_no` 唯一索引幂等
- 多次支付：与微信一致，同订单、同支付方式且金额一致时复用已有待支付单及其调起参数
- 配置展示：当前渠道绑定里无支付宝、绑定指向的 `pay_config` 行未启用或凭证未就绪、密钥自检未通过时，C 端不展示支付宝支付选项（渲染与下单同口径）

  3. 支付宝开放平台完成「接口加签」，加签方式须与后台所选一致（平台选「密钥」= 后台公钥模式，填应用公钥后取回支付宝公钥；平台选「证书」= 后台公钥证书模式，下载三份证书后录入后台）；手机网站支付的异步通知地址是接口的请求参数，本系统下单时已携带 `notify_url`，无需在开放平台另行配置；签约「手机网站支付」产品

  5. 沙箱联调：点「切沙箱」填入沙箱网关并改用沙箱的 AppID/应用私钥/支付宝公钥或沙箱证书（卡片显示「沙箱」标签），联调结束点「切生产」并换回生产凭证

- 已落地的原二期项（2026-10-21 支付可靠性改造，见上《支付回调可靠性》小节）：订单超时/取消时调用 `alipay.trade.close`（及微信 `CloseOrder`）主动关闭渠道交易；`alipay.trade.query` / 微信 `QueryOrder` 定时回查待支付单的对账补偿
- **V3 响应业务结果判定口径（2026-10-22 修复线上故障）**：所有走通用 `Execute` 的支付宝 V3 调用（查单/关单/退款/付款码 `trade/pay`）统一经 `alipayV3BizError` 判定——V3 正常 2xx 响应体**不含 `code` 字段**（业务结果直接平铺，如 `trade_status`），视为业务成功；仅响应体携带 `code` 且非 10000 时判失败（网关异常以 200 返回错误体的场景）。此前各调用点用 `IsBizSuccess(resp["code"])` 判定，正常响应因 code 缺失恒判失败：对账查单查到 `TRADE_SUCCESS` 仍按「渠道查询失败」**静默**跳过（stdout 无日志，只写 `result=5` 流水），回调丢失的单永远捞不回；退款成功被记失败。另：V3 对不存在的交易等业务拒绝以 4xx 返回，错误码在响应体里，经 `alipayV3ApiErrBody` 解析识别（查单的 `ACQ.TRADE_NOT_EXIST` 可安全走「无此交易」两轮关单口径，付款码的 `ACQ.TRADE_HAS_SUCCESS` 走回查确认）
- **SDK HTTP 超时（2026-10-28）**：`buildAlipayExecutor` 构建执行器后注入 `http.Client{Timeout: 15s}`（`SetHttpClient`）。SDK 默认复用 `http.DefaultClient`，全局无超时，对端不响应时 V3 调用（下单/查单/关单/退款）会永久占用 gRPC 处理协程直至实例被拖垮；微信侧 SDK 本就内置 30s 超时，此前只有支付宝这一路是裸奔。不设 `Transport` 字段即沿用默认连接池，无需额外调参
- **验签失败取证（2026-10-23 改造）**：验签不通过时同时留下三处痕迹，任一单独一条都不足以定位——
  1. 标准日志：附带通知参数的 **key 列表**（只记字段名不记值，避免明文签名/账号进 stdout），用于第一眼区分「签名与本地证书不同源」（SDK 返回不通过但 `err` 为 nil）与「SDK 明确报错」（缺 `sign`、`alipay_cert_sn` 有值却在证书与根证书链都定位不到、证书内容不可解析）。**`alipay_cert_sn` 缺失不是失败原因，也不是「该通知由公钥模式应用发出」的判据**——2026-10-23 生产那条不带该字段的通知，事后用本商户支付宝公钥证书内的公钥复算验签通过，恰恰是证书模式应用发出的；官方各语言 SDK 的通知验签入口也全部不读该字段（对照见 SDK README）。要判断后台所选加签方式与开放平台实际配置是否一致，须看第 2 点的 `verify_key_fp`/`local_cert_sn` 与原文复算结果，不能靠字段有无
  2. payment 进程级记录 `payment_verify_alipay`（`debug_logs`，error 级）：`alipay_mode`、`verify_error`、`param_count`、待验签串长度与指纹 `content_fp`、签名长度与指纹 `sign_fp`，证书模式再加 `notify_cert_sn`/`local_cert_sn`/`cert_sn_matched` 与 `verify_key_fp`（本地验签公钥指纹）。**只落指纹不落原文**：签名值本身不进这条记录，但 `content_fp` + `sign_fp` + `param_count` 三者对照即可判定「两侧算出的待验签串是否同形」，而公钥同源与否由 `verify_key_fp` 直接回答
  3. gateway 进程级记录 `payment_callback_alipay` 与 `payment_notify_logs.raw_body`：受理**失败**时落**通知参数原文（含 `sign`/`sign_type`）+ `content_type`/`body_bytes`/`param_count`**，成功仍只落 4 字段摘要。放开 sign 是刻意为之——复盘「渠道到底发了什么、我们为什么拒」必须有原文与签名值，掩码 sign 无隐私收益（签名把 `out_trade_no`/`total_amount` 一并签死，改任一字段即验不过，重放真实通知也只命中同一笔已支付单的幂等分支），而掩码会让验签类故障永久无法定位。**买家身份字段（`buyer_logon_id`/`buyer_user_id`/`buyer_open_id`）例外，一律脱敏**（保留前 3 后 4，2026-10-28 起）：它们只回答「谁付的」，不参与验签、金额核对与幂等判定，两处落点共用 `common/paynotify.MaskAlipayParams` 保证口径一致——否则网关原文与 `raw_body` 会因一处脱敏一处不脱敏而无法逐字段对照
  - 保留与清理口径：取证记录按类型/客户端 IP 走 `debuglog.QuotaPerMinute=30` 条/分钟封顶（伪造回调刷不满全表上限）；`debug_logs` 由 gateway 的过期清理协程按 `retention_days` + `max_records` 统一裁剪，`payment_notify_logs` 由对账调度器按保留期清理。debugger 属临时排查能力，`DEBUGGER_ENABLED` 用完关回即可——关闭后 `debuglog.Start` 返回 nil，两条进程记录静默消失，但标准日志的 key 列表与 `payment_notify_logs.raw_body` 的原始通知（含 sign）不受影响，仍是可复盘的落库痕迹

#### 支付回调可靠性（对账补偿与人工处置）

- 定位：异步回调只是快速路径，渠道查询（微信 `QueryOrder` / 支付宝 `alipay.trade.query`）才是事实来源。系统不再凭本地判断改资金状态，任何「确认支付」都以渠道应答或人工核实到的渠道交易号为前提（方案全文见根目录 `solution-20261021-支付回调可靠性-v2.md`）
- 三条兜底路径（payment 服务 `service/scheduler.go`，Redis 分布式锁 SetNX + Lua 释放，多实例只有一份在跑，每分钟一轮）：
  1. 待支付单回查：扫 `status=1` 且 `pay_type IN (1,2,5,6)` 的渠道支付单（付款码 5/6 同为在线渠道，2026-10-22 起纳入；现金/货到付款创建即成功，不存在待支付行，故无需排除），创建满 `min_age_seconds`（默认 60s）才起扫（给正常回调留时间），两次回查至少间隔 `throttle_minutes`（默认 5min），累计 `max_reconcile_count`（默认 24 次）后写「放弃对账」流水并停止回查；只回查 `pending_max_minutes`（默认 120min，与微信 prepay 时效对齐；支付宝侧取 `min(该值, business.order_timeout 换算分钟)`，与下单 `timeout_express` 同源）窗口内的单，超窗直接跳过。应答分流：已收款 → `handlePaySuccess` 补同步（`confirm_source=2` 对账补偿、`confirm_ref=reconcile:支付单号`）；未支付/无此交易 → 只推进节流不改状态（`NOT_EXIST` 需连续两轮才关单，渠道已自行关闭的交易本轮即关单）；金额不符 → 拒绝确认并进人工待办；渠道查询失败 → 不改任何资金状态，写 `result=5` 流水
  2. 挂账检测：扫已关闭(5)支付单，渠道已收款则写 `kind=3/result=9` 待办（`kind=3` 为系统检出；后台人工核实产出的同族待办走 `kind=8`，见本节末尾的挂账来源拆分说明）；同一支付单只保留一条待处理记录，否则每分钟一轮会把异常页刷成噪声。扫描窗口自 2026-10-28 起与在途单分档：按 `closed_lookback_minutes`（默认 1440min＝24 小时，按 `updated_at` 即最后一次状态变化过滤）回溯、按 `closed_throttle_minutes`（默认 30min）低频复查，此前沿用 `pending_max_minutes`（120min）导致「关单后才到账」的迟到付款永久漏检；**超出回溯窗口的关闭单调度器不再扫到**——人工兜底走订单详情页「渠道核实挂账」按钮（后台 `POST /admin/orders/:id/payment-sync` 对已取消订单放开）：复用 `reconcileOne(closed=true)` 语义向渠道核实一次，已收款 → 产出挂账待办（含渠道交易号/金额，同一支付单去重），未收款 → 记核实流水消除疑虑；该入口只读渠道 + 写流水，不改任何资金状态（订单状态机不允许 6→2，退款在商户平台人工完成）。另注意支付单定位有回退逻辑：订单下无待支付单时回退最近一笔关闭单，故 cancel-guard 场景下「支付单已被关闭但渠道实际已收款」也能被拦下取消。定位候选（`locateSyncTarget`）按待支付 → 成功 → 已关闭三态依次取单且**不再按 `pay_type` 过滤**（2026-10-23 A4）：线下单同样能被后台按钮与取消护栏定位到，命中后走 `syncOfflinePayment` 的本地口径——现金/货到付款的 `status=2` 单此前对两个入口都是隐形的，「兜底出口」等于不存在
   - 挂账待办的 `kind` 按**检出来源**拆分（2026-10-24 B3）：`kind=3` 系统检出（回调兜底、对账扫描、关单前核实），`kind=8` 后台人工核实。两者事实相同、成因相反——kind=3 说明回调链路有洞，kind=8 说明该单早已超出对账窗口、只能靠人来查，混成一个类别就没法分别统计「回调丢了多少」与「人工兜了多少」。去重**跨这两个 kind**（`hasStuckLog` 用 `kind IN (3,8)`），否则同一笔挂账会在异常页出现两条等价待办；已有待办时重复核实不再登记，但落一条 `kind=5/result=2` 幂等留痕，证明「又核过一次、结论一致」而不占用待办队列
   - 检出留痕：`syncActor`（操作人 ID + 姓名）随后台按钮由网关注入，内部路径（取消前置、对账）留空即系统口径，写入 `detect_remark`「谁核实的 + 当时的支付单状态/支付方式/本地金额/订单状态快照」；判据刻意用「有没有操作人」而非 `reason`——`reason` 描述场景不是身份，用它决定留痕会把系统调用记成人工。身份还会下沉到订单状态日志的 `operator_type/operator_id`（后台补同步落 `admin`，无 ID 时保持 `system` 不猜）。`detect_remark` 与销账依据 `remark` 分列，理由见 05-数据库设计
  3. 取消前置确认：订单调度器取消超时单之前先 RPC 让支付服务回查渠道（`confirm_ref=cancel-guard`），命中已收款则把订单补同步为已支付并放弃取消（宁可延迟取消，不可误取消已收款单）。之所以必须**前置**：订单状态机 `2: {1,100}` 不含 `6→2`，取消之后再收到成功回调只能挂账退款
- 失败记录重试 `retryFailures`（`runOnce` 里最先执行，2026-10-22 加固）：这条路径处理的是「渠道查询失败 / 补同步中途出错」的单笔待重试记录，一旦绕开扫描的约束就会在最坏时刻（渠道整体不可达）放大调用量，因此与两条扫描共用同一套口径——独立分布式锁 `scheduler:payment:reconcile:retry:lock`、**沿用支付单上的 `last_reconciled_at` 节流指针**（扫描刚查过的单本轮不再重试，同轮渠道调用不会翻倍）、进入循环后在**打渠道之前**先判 `max_reconcile_count`（用满上限直接转放弃，零渠道调用）、同一支付单本轮只打扰渠道一次（跨锁竞态可能留下 pending/stuck 两条待重试行，被跳过的那条不累加 `retry_count`，不算一次尝试）。累计上限刻意**不写进扫描 SQL**：写进去这些行会永远停在待重试态、白白占住批次额度。`recordFailure` 同时改为按 `uk_failures_pending` upsert，重复失败只刷新原因不再新增行（详见 05-数据库设计）
- 关单时同步关闭渠道交易：`ClosePayments` 对已创建渠道交易的待支付单调用渠道 `CloseOrder`（微信 JSAPI 关单 / 支付宝 `alipay.trade.close`），只在「渠道明确未收款」后执行（渠道不允许关闭已付款交易）；关单失败不影响本地关单，钱的事由对账任务继续跟，`enabled=false` 时退回纯本地关单的旧行为
- 唯一收敛点 `handlePaySuccess`（回调、对账、后台同步、人工标记四条路径共用，任何新入口不得自行写订单状态）：金额按分位比对（`yuanToFen`，规避浮点误差）→ 事务内条件更新 `status 1→2`（并发/重复回调只有一笔生效，其余幂等忽略）→ 事务提交后 RPC 同步订单（重试 3 次，仍失败记 `[CRITICAL]`，由对账与取消前置兜底）
- 线下收款单（`pay_type=3` 货到付款 / `4` 收银台现金）没有渠道可问——收款事实在创建支付单时就已登记，「核实」只能是本地口径。`SyncPaymentFromChannel` 命中线下单走 `syncOfflinePayment` 早退，不发起任何渠道查询：支付单 `status=2` 就直接补同步订单（订单已取消则按同一路径产出挂账待办），非 `2` 只回传「无渠道可核实，本次不改动」、零状态改动。对账的自愈扫描 `scanPaidMismatch` 同样去掉了 `pay_type` 过滤：此前只扫在线单，线下单一旦「支付单成功、订单没流转」永远进不了自愈，只能靠人工点按钮。取消前置护栏（`cancel-guard`）的支付单定位也去掉了 `pay_type` 过滤，现金单已确认收款时 `paid=true` 会拦下这次取消，避免门店重复收现金而订单停在待支付。线下单的每次核实都落 `kind=5 后台手动同步` 留痕（`result=1` 补同步成功 / `6` 渠道未支付口径的「无渠道可核实」），刻意**不取 `result=9`**——挂账待办已由 `ensureOrderPaidSynced` 的同一判定产出，再落一条会让异常页出现重复条目（`recordOfflineSyncTrace`）
- 退款查单收敛与它的放弃出口（`reconcileRefunds`/`scanPendingRefunds`，2026-10-24 B2 补齐人工出路）：微信退款是异步受理语义，`ProcessRefund` 受理成功只把 `refund_payments` 落「待退款(1)」并回 `completed=false`，终态一律由查单任务按渠道 `RefundQuery` 收敛（`SUCCESS` 落成功并联动支付单，`ABNORMAL/CLOSED` 置失败交由 order 侧重试，`PROCESSING` 只推进节流）。查单/落库失败按笔累加 `retry_count` 并刷新 `updated_at`（该列同时是批次轮转指针），累计达 `refundQueryMaxRetry=10` 即**永久退出自动批次**并写 `result=10` 待办；另有 `escalateStaleRefunds` 超期体检兜住「非微信渠道的落库残单」与历史旧单，只登记待办（`escalated` 去重）不退出批次。**死角**：10 次 × 2 分钟节流约 20-30 分钟就放弃，而微信退款允许 1-3 个工作日到账——渠道后来给出终态时已经没人来收了，而后台「重试退款」又会被 `ProcessRefund` 的幂等分支以「退款处理中，请勿重复提交」拒绝，等于没有出路。出口是 `ResetRefundFlow`（后台 `POST /api/v1/admin/refunds/:id/reset-retry`，由 order 侧 `ResetRefundRetry` 串起）：只允许对待退款(1) 流水把 `retry_count`/`escalated` 归零并刷新节流指针，已成功(2) 与已失败(3) 一律 `FailedPrecondition` 拒绝（前者放开等于允许再次触渠道出款，后者本就能重新发起），核实依据必填、写 `kind=7/result=11` 留痕并销掉该退款单的 `result=10` 待办。全程只改收敛预算，不触渠道、不动钱
- 取证与出口 `payment_notify_logs`（`kind` × `result` 两维，详见 05-数据库设计）：`kind` 1 渠道回调 / 2 对账补同步 / 3 挂账检出（系统） / 4 渠道关单 / 5 后台手动同步 / 6 放弃对账 / 7 人工恢复退款收敛 / 8 挂账检出（后台人工核实） / 9 付款码扣款（2026-10-28 新增：收银台 B扫C 的同步确认结果，付款码支付无异步通知，记成 kind=1 会污染「回调丢失率」口径；`channel` 同日起由 `notifyChannelOf(pay_type)` 归一，付款码 5→1 微信、6→2 支付宝，线下记 0）；`result` 1 确认成功 / 2 幂等忽略 / 3 验签或解密失败 / 4 金额不符 / 5 处理异常 / 6 渠道未支付 / 7 渠道无此交易 / 8 关单结果 / 9 资金挂账 / 10 订单同步失败 / 11 人工恢复退款收敛。成功回调不存 `raw_body`（同一事实已落 `payments`，重复存正文只会把表撑大），失败与挂账必存；`headers` 里的签名与证书序列号**入库前掩码**，支付宝 `raw_body` 的通知参数**含 `sign` 原文**但买家身份字段（`buyer_logon_id`/`buyer_user_id`/`buyer_open_id`）**入库前脱敏**（见上「验签失败取证」，出口由 `payment:raw:view` 权限守住）。散落在 stderr 的 `[CRITICAL]`（挂账、金额不符、放弃对账）由此变成可查询、可销账的队列；`detect_remark` 存「谁、在什么本地状态下」登记了这条流水（系统触发标注为系统），与人工销账依据 `remark` 分列，销账不会覆写留痕；流水按 `notify_log_retention_days`（默认 30 天）每日清理，且**只清 `handled=1`（已销账或正常轨迹）**：`handled=0` 的待办流水到期不删——删掉等于抹掉「这笔钱挂过账」的事实，异常页再也查不到；清理前统计过期未销账条数，非 0 时输出一条 `[CRITICAL]` 日志
- 回调链路排查路径（2026-10-22，三层互补，按「请求到没到 → 验签过没过 → 状态改没改」逐层收窄）：
  1. **网关侧到达与受理**：debugger 进程级日志（`debug_logs` 表 `record_type=process`、`process_type=payment_callback_alipay/wechat`，页面按进程名过滤）。回调路径整条跳过 HTTP 请求日志（凭据第二道防线，见 03-缓存存储与日志.md），排查盲区由进程记录补齐：解析失败/体超限/gRPC 受理失败都落 `failed` 记录（**带通知参数原文含 `sign`**，买家身份字段脱敏 + `content_type`/`body_bytes`/错误/耗时/IP），成功落 `completed` 只带 4 字段摘要（`out_trade_no`/`trade_status`/`total_amount`/`notify_id`）。按 IP 每分钟 30 条封顶，防伪造回调刷量。进程记录走同步库写（开销见 03-缓存存储与日志.md 的「共享同一张表的已知代价」），仅在排障期开启 `DEBUGGER_ENABLED`，用完关回
  2. **验签与处理结论**：`payment_notify_logs`（权威流水，含 `raw_body`/掩码后的 headers，受 `payment:raw:view` 权限保护）；验签失败另有 debugger 进程记录 `process_type=payment_verify_alipay`（`alipay_mode` + 待验签串/签名/验签公钥的指纹与证书序列号命中关系，只落指纹不落原文，见上「验签失败取证」）
  3. **状态收敛**：`payments` 表 + 订单状态日志；对账调度器的每轮动作（捞回/挂账/关单/清理计数）同样在 debugger 进程记录里（`process_type=payment_reconcile`，空转轮次不落库）
- 后台入口（菜单在「订单管理」组、「售后管理」之后，标题「支付异常」）：
  - 同步支付状态 `POST /api/v1/admin/orders/:id/payment-sync`：向渠道核实并补同步，幂等可反复点；待支付族（1/100）订单走「核实并补同步」，已取消（6）订单走「渠道核实挂账」（只读渠道 + 产出待办，不改资金状态，见上「挂账检测」），其余状态直接拒绝；渠道未收款时零状态改动、只回传渠道事实（`paid/changed/channel_state/transaction_id/amount/payment_no/message`）；货到付款/现金单不查渠道，以本地已确认支付单直接补同步（见上「线下收款单」）。操作人身份由网关注入请求（`operator_id`/`operator_name` 取自登录态，前端不传、也无法自证为系统），用于挂账待办的 `kind` 归属、`detect_remark` 留痕与订单状态日志的 `operator_type/operator_id`
  - 标记已支付 `POST /api/v1/admin/orders/:id/payment-mark-paid`：渠道查不到或接口不可用、但线下已核实到账的死角；支付单号、渠道交易号、收款金额、核实依据四项必填，金额与应付做分位比对，成功后支付单与订单一并流转（`confirm_source=3`、`confirm_ref=manual-mark`，操作人写入备注）。仅待支付(1)订单可用——`6→2` 在状态机上必然失败，只会造出半截数据，那种挂账只能走退款
  - 异常队列 `GET /api/v1/admin/payments/anomalies` + 销账 `POST /api/v1/admin/payments/anomalies/:id/handle`（必填核实依据）；入参 `handled` 是筛选选择器（1 待处理 / 2 已处理 / 0 全部），与行数据的 `handled` 落库标记（0 待处理 / 1 已处理）是两套取值，前端选项与接口文档同口径。列表新增「留痕/依据」列（`detect_remark` 优先，历史数据无留痕时回落 `remark`，窄屏隐藏）；「去退款」入口改按 `result=9 资金挂账` 判定而非 `kind=3`——挂账拆成 3/8 两个来源后，按 kind 判会让人工检出的那批丢掉了直达退款的入口
  - 退款恢复自动收敛 `POST /api/v1/admin/refunds/:id/reset-retry`（入口在「售后管理」列表的退款中(4) 行，按钮「恢复自动收敛」，权限 `refund:update`）：`ResetRefundFlow` 的后台出口，见上「退款查单收敛与它的放弃出口」。核实依据必填，服务端先 payment 后 order，payment 拒绝即整体报错、本侧预算不动；只归零收敛预算与销待办，不触渠道、不动钱
  - 订单详情新增「支付记录」表（`payments` + `payment_summary` 的 `attempts/succeeded/succeeded_amount`，`succeeded>1` 即重复支付、要立刻提醒去退款）与「通知/对账时间线」（`payment_logs`）。这些是 payment 服务的旁路数据，读不到时以 `payments_error`/`payment_logs_error` 显式告知前端「这里查不到」，不静默返回空表——空表会被读成「这笔订单没有支付记录」，是最坏的误导
  - 改单护栏：`PUT /api/v1/admin/orders/:id/status` 置 2 前先查该订单是否有成功支付单（`GetPayment`），没有就拒绝并引导到上面两个入口。所有订单都有 `payments` 行（现金/货到付款创建即成功），因此不需要任何豁免分支
- 敏感边界与权限：`payment:raw:view` 决定 `raw_body`/`headers` 是否下发，列表页只回摘要 + `has_raw` 标志（前端据此决定是否渲染展开按钮）；该权限点刻意**不进**社区管理员默认权限上限，实际只有超管可展开。社区隔离依据 `payments.community_id`（创建支付单时由网关从订单权威字段带入）与流水快照，`community_id=0` 的流水（连支付单都解析不出的验签失败）只对超管的全量队列可见
- 配置（`business.payment_reconcile`，详见 07-基础设施/02-错误码与配置.md）：`enabled`（总开关，关闭即退回「纯回调 + 纯本地关单」的旧行为）、`cancel_guard`、`auto_refund_stuck`（默认关闭）、`pending_max_minutes=120`、`closed_lookback_minutes=1440`、`closed_throttle_minutes=30`、`interval_seconds=60`、`min_age_seconds=60`、`throttle_minutes=5`、`max_reconcile_count=24`、`batch_size=100`、`notify_log_retention_days=30`。三个开关用 `*bool` 而非 `bool + default:"true"`：`CheckAndSetDefault` 的布尔默认值机制无法区分「未配置」与「显式 false」，会把显式关闭强行改回开启，导致回退开关失效
- 两个必须记住的坑：
  - DSN 带 `parseTime=True` 时，datetime 列读回 `string` 字段是 RFC3339 形态（`2026-10-21T14:19:47+08:00`），按 `2006-01-02 15:04:05` 解析必然失败。`withinReconcileWindow` 曾因此恒走「解析失败保守放行」分支，回查时间窗形同虚设；现已统一走 `parseDBTime`（多 layout 容错），新增时间解析勿再直接 `time.Parse`
  - `base.MysqlBaseModel.BeforeCreate` 无条件把 `created_at/updated_at` 覆写为当前时间，测试要造「历史时间」的支付单/流水必须用裸 SQL `Exec INSERT`，走 GORM `Create` 造不出aging数据

#### 支付配置管理（数据库化，多行，2026-10-30 重构）

- 支付配置（微信支付 V3、支付宝凭证）存储于数据库 `pay_config` 表（**多行**：每行 `name + platform(wechat/alipay) + enabled + 凭证`，同平台可多条、独立启停），不再使用 config.yaml；「哪个渠道用哪些配置」改由渠道侧 `client_channels.pay_methods` 绑定表达（见下《客户端渠道管理》），本表无渠道勾选
- **AppID 的字段归属两侧刻意不对称**（不是待统一的不一致，勿「修正」）：
  - 微信：AppID 是**渠道身份**——同一商户号可关联多个 AppID（小程序、公众号、H5 各自一个），配置行只到商户号粒度。若把 AppID 放进配置行，一个商户号就得为每个端各建一份配置（商户号、APIv3 密钥、证书全都重复），且回调归属变得不确定，故 `pay_config` 不含 `wechat_app_id`（proto 字段 10 已 reserved），AppID 归 `client_channels.app_id`
  - 支付宝：AppID 是**签名身份**——一个 AppID 对应一套应用密钥与支付宝公钥/证书，配置行按 AppID 唯一，故保留 `alipay_app_id`
  - 唯一性校验（`SavePayConfigRow`）：微信按 `wechat_mch_id` 同平台唯一、支付宝按 `alipay_app_id` 同平台唯一，重复即 `FailedPrecondition` 拒绝；`ListActivePayMethods` 摘要不再回传 AppID（proto 字段 3 已 reserved）
- 一笔支付的身份由三部分共同确定：`config_id`（用哪条配置行的商户号/私钥）+ `client_channel`（哪个端发起）+ `app_id`（该端下单时的 AppID 快照），后两者自 2026-10-30 起随 `CreatePaymentReq` 落 `payments` 表，既是回调归属依据，也是付款码扣款/撤销与待支付单复用的判定输入
- 后台「系统管理 → 支付配置」页面按平台分组维护，对应接口：
  - `GET /api/v1/admin/settings/payment`：配置列表（含每行就绪状态 `ready`/`ready_message`、`*_uploaded` 上传标志与派生回调地址 `suggested_urls`）；回调地址一律按**显式部署域名**派生（「站点设置」的 `base_url` 优先，未配置时回落 `SITE_BASE_URL`，两者都空时派生为空、不回落当前请求域名——否则管理员会照一条不会落库的地址去商户平台配置）；地址回写只由「保存站点设置」与「保存配置行」两个动作触发，读取本接口不写库；域名清空时地址同进退回收为空串；私钥与证书内容不回传明文
  - `POST /api/v1/admin/settings/payment`：新增一条配置（platform 创建后不可变更）
  - `PUT /api/v1/admin/settings/payment/:id`：更新一条配置；须携带读取时的 `updated_at` 作乐观锁版本号，不一致返回 `10007`（提示刷新重试）；私钥/证书留空即保留原值
  - `PUT /api/v1/admin/settings/payment/:id/enabled`：**单独启停**一条配置（窄口径：仅提交 `enabled` + 读取时 `updated_at` 乐观锁，不做整行覆写——列表开关若走全量保存接口会因名称等必填字段缺失被拒「参数错误」）；返回脱敏后的最新配置行供前端渲染
  - `DELETE /api/v1/admin/settings/payment/:id`：删除一条配置；**删除前网关校验无渠道引用**（任一 `client_channels.pay_methods` 含 `<platform>:<id>` 即拒绝），防止删掉仍被渠道绑定的配置
  - `POST /api/v1/admin/settings/payment/cert`：multipart 上传证书文件，**表单字段 `config_id` 指定写入的配置行**（支持 `.pem/.key/.txt/.crt`，最大 64KB），内容直接存入对应行的证书/私钥列；后台「粘贴内容写入」同样走本接口（前端把文本包成 `.pem` 文件提交，服务端无需区分来源）；**成功时返回脱敏后的最新配置行**（含新 `updated_at` 与上传状态位）——上传推进了乐观锁版本，前端以返回行同步表单，随后的保存不再被「已被其他操作更新」拒绝；新增配置时前端先暂存证书（上传接口按行 ID 定位，建行前无行可挂），保存建行后自动依次录入，失败项可再次保存重试
    - `cert_type` 取值：`private_key`（微信商户私钥 / 支付宝应用私钥）、`app_cert`、`alipay_public_cert`、`root_cert`（后三类为支付宝公钥证书模式专用）
    - 支付宝四类内容写库前先按真实链路校验可解析性（私钥签名自检、`CertSN`/`CertPublicKey`/`RootCertSN`），失败即拒绝且不覆盖原内容
- 热更新：payment 服务进程内缓存全部配置行并以「行数 + 各行 `updated_at` 拼接」作版本号，支付链路调用时检测到版本变更才重建支付客户端；数据库查询异常时降级使用缓存，不阻断支付
- 版本检测入口覆盖下单、回调受理（微信/支付宝）与退款三条链路：漏掉后两者时，只处理过回调/退款的实例会长期持有空配置缓存，验签公钥缺失会把真实通知判为失败
- 微信回调地址：`{域名}/api/v1/payments/callback/wechat`；支付宝回调地址：`{域名}/api/v1/payments/callback/alipay`

#### 客户端渠道管理（渠道管理）

- 客户端渠道（h5 浏览器H5 / gzh 微信公众号 / mp 微信小程序 / alimp 支付宝小程序 / android 安卓App / ios iOS App / pos 门店收银台）的主数据由 user 服务 `client_channels` 表管理，后台「系统管理 → 渠道管理」维护，对应接口：
  - `GET /api/v1/admin/settings/channels`：渠道列表（全部含停用；启用渠道在前、停用在后，组内按固定常用顺序返回 h5 → gzh → mp → alimp → android → ios，pos 恒在末位，无排序编辑）
  - `PUT /api/v1/admin/settings/channels/:id`：更新 AppID/AppSecret/启用/支付方式绑定；AppSecret 留空保留原值，code 与名称均不可变更（名称为内置固定项，请求体 `name` 仅作兼容保留、服务端忽略传入值）
- 渠道分类：android/ios 为拆分的独立渠道（App 支付 SDK 未接入，**禁用态展示**，无配置入口）；pos 为特殊渠道（无登录凭证、不参与 C 端登录，绑定支付配置；一旦绑定微信支付同样需要本端 AppID，付款码扣款与撤销都按该 AppID 发）；alimp 仅需 AppID（支付签名复用支付配置的应用私钥）
- 启用语义：渠道未启用或凭证不完整时，该端登录（Code2Session）与按端支付能力不可用；h5/pos 无登录凭证，`IsConfigured()` 只在**绑定了微信支付**时要求 AppID——因此「未配 AppID 的 h5」可以在只绑现金时启用，绑定微信支付后必须补 AppID 才能启用
- **AppID 与商户号的外部约束**（系统内无法校验，只能提示）：渠道填写的微信 AppID 必须已在该支付配置对应商户号下完成关联（微信商户平台「产品中心 → AppID 账号关联」），否则下单会被微信以 appid 与 mchid 不匹配拒绝。保存渠道时服务端拦截「绑定微信支付但 AppID 为空」（`FailedPrecondition`），后台界面对此有三处提示：渠道卡片状态、编辑弹窗字段说明、支付配置页商户号说明
- **支付方式绑定（`pay_methods`，2026-10-30 绑定关系反转）**：渠道编辑弹窗「支付方式」区块配置该端可用的支付方式，为**有序** JSON 数组（顺序即该端收银台展示顺序），每项为 `cash`（货到付款/现金内置项）或 `<platform>:<config_id>`（指向 `pay_config` 行）；「＋添加支付方式」只列出平台兼容且启用就绪的配置。服务端三重兜底校验（绑定保存、C 端渲染、下单时均校验渠道启用 + 配置启用 + 凭证就绪）；能力矩阵：wechat→h5/gzh/mp/pos，alipay→h5/alimp/pos，不兼容组合保存即拒绝
- 删除支付配置前校验无渠道引用：网关遍历 `ListClientChannels` 检查各渠道 `pay_methods` 是否含 `<platform>:<id>`，有引用即拒绝删除
- 登录链路：小程序登录读渠道管理的 mp 渠道配置（config.yaml 微信节点废弃不用，仅保留结构兼容），登录成功后幂等 upsert `user_channel_identities`（用户渠道身份表）；支付宝小程序登录沿用手机号表单（零新增），alimp 渠道 AppID 用于后续支付链路
- 支付联动：C 端 `GET /payments/channels` 按请求头 `X-Channel-Code` 取该渠道绑定 ∩ `ListActivePayMethods`（启用且就绪的配置行）渲染，未携带渠道头按 h5 口径兜底

#### 现金支付

- 线下收款/货到付款，创建支付单时直接标记为支付成功并同步订单状态
- 不复用待支付现金单：现金支付无需第三方调起参数，复用待支付记录会跳过"置为已支付并同步订单状态"的副作用，导致订单停留在待支付而前端已提示支付成功
- 不经过第三方支付网关
- 退款时仅记录退款流水，不调用第三方接口
