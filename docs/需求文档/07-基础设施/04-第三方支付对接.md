
#### 微信支付

- 支付方式：JSAPI（微信小程序；公众号内 JSAPI 需 OAuth 链路，暂未开放）、H5 支付（微信外浏览器）
- 支付流程：
  1. 前端调用 `POST /api/v1/payments` 传入 `order_id` 和 `channel="wechat"`，不传 openid，并通过 `X-Channel-Code` 请求头声明所在客户端渠道（mp/gzh/app/h5）
  2. 后端校验微信支付 V3 配置完整性，不完整时直接返回错误；同时校验该支付渠道在当前客户端渠道上可用（pay_config 适用渠道勾选 ∩ 渠道管理就绪状态），不可用时拒绝
  3. 网关按客户端渠道解析 openid 与 AppID：mp 渠道 openid 取用户渠道身份表（user_channel_identities，mp 渠道回落存量 users.openid），AppID 取渠道管理的 mp 渠道配置；h5 渠道无 openid 走 H5 下单，AppID 优先取 mp 渠道 AppID；gzh/app 渠道链路未开放直接拒绝；未携带渠道头按存量口径（users.openid + pay_config 默认 AppID）
  4. 创建独立支付单（`payment_no` 使用 `ZF` + UUID），有可用 openid 走 JSAPI 统一下单（wego 请求级 AppID 覆盖），否则走 H5 下单
  5. 返回调起参数给前端：小程序端用 `uni.requestPayment` 调起 JSAPI（`signType` 为 RSA），H5 端跳转 `h5_url`（uni-app 未封装浏览器支付）
  6. 用户支付完成后，微信回调 `POST /api/v1/payments/callback/wechat`
  7. 后端通过 wego 验签解密，仅处理 `TRANSACTION.SUCCESS` 通知，更新支付单和订单状态
- 幂等性：
  - 支付回调通过 `payment_no` 保证幂等处理
  - 退款通过 `refund_no` 唯一索引保证幂等，重复提交直接返回成功
- 多次支付：一笔订单在支付成功前可多次发起支付；同订单、同支付方式且金额一致时复用已有待支付单及其调起参数，不再新建（复用仅限微信/支付宝这类需第三方调起参数的渠道）；订单已有支付成功记录时拒绝创建。`GetPayment` 仅查询支付成功（status=2）记录，因此待支付单不会被幂等校验误拦
- 校验失败按 fail-closed 处理：幂等校验与待支付单复用查询若发生数据库异常（非 `ErrRecordNotFound`），直接拒绝创建并返回内部错误，不把故障当作"无支付记录"放行，否则会产生多笔可实际扣款的支付单；底层错误只写服务端日志，对客户端返回统一业务文案
- 多次退款：一笔支付单支持多笔部分退款，累计退款金额不超过支付单金额；支付单累计退完时才标记为"已退款"
- 配置展示：当 `wechat` 支付 V3 配置不完整，或该支付渠道在当前客户端渠道上不可用（适用渠道勾选未命中 / 客户端渠道未就绪）时，C 端不展示微信支付选项
- 前端约束：仅支付真实完成才提示"支付成功"；用户取消、跳转 H5 支付页或渠道未开通时不提示成功，统一回到订单详情以便重新支付
- 上线前置：开启微信渠道前必须先完成 `11-开发计划.md` 中的回调兜底、待支付单生命周期、prepay 时效三项。原因为 wego 无 CloseOrder 接口，订单取消后其待支付单在微信侧约 2 小时内仍可被支付，而该回调会因状态机拒绝 `6→2` 而回滚，形成"钱已扣、系统无成功记录"的资金挂账风险

#### 支付宝支付

- 支付方式：手机网站支付 `alipay.trade.wap.pay`（H5 浏览器跳转支付宝收银台）；微信小程序/公众号处于微信生态内无法唤起支付宝、App 支付 SDK 未接入，这些客户端渠道即使后台勾选也不展示支付宝选项
- 微信内置浏览器引导（商户侧自行实现，官方已在新签约产品中下线收银台「继续浏览器付款」兜底入口）：C 端按 UA（MicroMessenger）识别微信内置浏览器，选择支付宝时不再直接跳转收银台，改为弹出引导蒙层——分步指引「点击右上角 ··· → 在浏览器中打开」并提供「复制支付链接」按钮（Clipboard API 优先、execCommand 兜底），用户转系统浏览器后正常唤起支付宝完成支付；普通浏览器保持直接跳转。蒙层内复制结果提示为蒙层内自绘 toast（uni.showToast 的 H5 z-index 低于蒙层会被遮挡）
- SDK：`github.com/jcbowen/alipay-sdk-go-all`（自研，对齐支付宝官方 PHP SDK 结构；当前为本地 replace 依赖，合入前需推送 GitHub 并移除 replace）
- 支付流程：
  1. 前端调用 `POST /api/v1/payments` 传入 `order_id` 和 `channel="alipay"`，通过 `X-Channel-Code` 请求头声明所在客户端渠道
  2. 后端校验支付宝配置完整性（AppID + 应用私钥 + 支付宝公钥），不完整时直接返回错误；同时校验该支付渠道在当前客户端渠道上可用（pay_config 适用渠道勾选 ∩ 渠道能力就绪），不可用时拒绝
  3. 创建独立支付单（`payment_no` 使用 `ZF` + UUID），调起参数：`out_trade_no`/`total_amount`（元，两位小数）/`subject`/`product_code=QUICK_WAP_WAY`/`timeout_express`（交易时效，见下）/`quit_url`（收银台中途退出回跳地址，与 `return_url` 同值；`quit_url` 属 `biz_content` 业务参数而非公共参数）；公共参数携带 `notify_url`，配置了回跳地址时一并携带 `return_url`
     - 交易时效：`timeout_express` 取 `business.order_timeout`（秒）向上取整换算为分钟（最小 `1m`，默认 1800 秒 → `30m`），使支付宝侧交易时效与本地订单超时取消时效对齐。不传该参数时支付宝按签约协议给默认时效（约 15 天），本地订单早已超时取消而收银台仍可付款，形成资金挂账
  4. 通过 SDK `PageExecute("alipay.trade.wap.pay", "GET")` 生成带 RSA2 签名的收银台跳转 URL，返回 `{"alipay_pay_url": "..."}`；H5 端普通浏览器直接 `window.location.href` 跳转，微信内置浏览器弹引导蒙层（见上）
  5. 用户支付完成后，支付宝回调 `POST /api/v1/payments/callback/alipay`（POST form）
  6. 网关侧不依赖 `Content-Type`，直接读取 raw body 按 `application/x-www-form-urlencoded` 解析通知参数（支付宝部分场景投递的通知不带 urlencoded 头，交给 `ParseForm` 会得到空参数并永远回 `failure` 引发无限重发）；请求体上限 64KB，超限或编码非法直接回 `failure` 且不投递支付服务
  7. 后端 `RsaCheckV1` 验签（支付宝公钥，剔除 sign/sign_type 后按 key 升序拼接，仅剔除空值——值以 `@` 开头的字段照常参与签名），验签不通过拒绝；验签通过后再核对 `app_id` 与配置一致（公钥模式下支付宝公钥为全商户共用，验签只能证明"来自支付宝"，不核对 app_id 无法阻止跨应用通知重放），仅 `TRADE_SUCCESS`/`TRADE_FINISHED` 视为支付成功，`total_amount` 与支付单金额强制比对，随后复用 `handlePaySuccess` 更新支付单与订单状态
  8. 回调应答为纯文本：受理成功返回 `success`，验签失败/身份不符/参数缺失/DB 异常返回 `failure`，支付宝按通知策略重发（重发期间验签与金额校验保证幂等安全）
  - 迟到回调：支付单已被订单超时取消置为「已关闭」(status=5) 后收到成功回调，仍按终态兜底忽略（不置已支付、不流转订单），但记 `[CRITICAL]` 日志标明"订单已取消而用户仍完成付款，需人工对账退款"，避免挂账只能靠翻明细发现
- 退款：SDK V3 `alipay.trade.refund` 同步接口，`out_request_no` 传退款单号（幂等键），`RefundAmount` 元字符串；`fund_change=N`（重复请求未改变资金）同样视为成功；退款成功后回填 `transaction_id`（支付宝交易号），后续订单状态流转、销量回退与微信路径一致
  - 成功判定：走通用 `Execute` 而非 typed Refund，并自行校验响应体 `code=10000`（SDK 对齐 PHP 行为，HTTP 2xx 时不解析业务码，typed 成功模型亦无 `code` 字段）。退款是资金写操作，网关以 200 返回错误码时若只判 HTTP 状态会被误记"已退款"并回补库存；业务失败时抛出带 `code/sub_code/sub_msg` 的错误
- 配置版本检测：回调受理（微信/支付宝）与退款入口在执行前先做 `getPayConfigCached` 版本检测。仅下单链路检测的话，只处理过回调/退款的实例会长期持有空缓存，导致验签公钥缺失、渠道客户端为 nil 而把真实通知判为失败
- 幂等性：与微信一致——回调按 `payment_no` 幂等，退款按 `refund_no` 唯一索引幂等
- 多次支付：与微信一致，同订单、同支付方式且金额一致时复用已有待支付单及其调起参数
- 配置展示：支付宝配置不完整，或该支付渠道在当前客户端渠道上不可用时，C 端不展示支付宝支付选项
- 离线测试：`services/payment/service/alipay_test.go`（通知验签与身份/状态/金额校验、`timeout_express` 换算，测试内自生成 RSA 密钥对伪造支付宝签名，无 DB/网络）与 `gateway/handler/payment_callback_test.go`（回调参数解析不依赖 Content-Type、体积上限、失败应答）均可在 CI 直跑；涉渠道实调的路径仍需真实商户配置才能验证
- 上线配置步骤：
  1. 后台「系统管理 → 支付配置」点击支付宝卡片，填写支付宝 AppID、异步通知 URL（页面自动生成建议值）、支付完成回跳 URL、支付宝公钥，上传应用私钥文件
  2. 支付宝开放平台完成「接口加签」（公钥模式），将异步通知地址配置到应用消息校验；签约「手机网站支付」产品
  3. 保存后配置热更新即时生效，就绪状态转为「已配置」后可启用渠道开关
- 二期项（本机无商户配置、触发路径不可验证，暂不落码）：
  1. 订单超时取消时调用 `alipay.trade.close` 主动关闭渠道侧交易，彻底消除「已关闭支付单收到成功回调」窗口；当前仅靠 `timeout_express` 收窄窗口 + CRITICAL 日志人工兜底
  2. 迟到成功回调的自动退款（原单金额全额退回，`out_request_no` 用独立退款单号保证幂等）；需真实商户配置验证退款回执后才能开启
  3. `alipay.trade.query` 对账补偿：定时扫描待支付单主动向支付宝查询，兜住回调丢失导致的长期挂起（微信侧同样缺此能力，见下"上线前置"）
  4. 通知校验 `seller_id`（收款账户 pid）：配置无 pid 载体（`AlipayConfig` 与 `pay_config` 均只有 AppID/私钥/支付宝公钥/回调地址，微信侧对应字段为 `wechat_mch_id`），故未校验。安全性上当前不缺——`seller_id` 参与签名不可篡改，且 `app_id` 比对已锁定主体，跨商户重放无法通过；要校验需新增配置字段并打通后台录入，见开发计划第 54 项

#### 支付配置管理（数据库化）

- 支付配置（微信支付 V3、支付宝、渠道开关 `enabled_channels`）存储于数据库 `pay_config` 表（单行，id=1），不再使用 config.yaml
- 后台「系统管理 → 支付配置」页面维护，对应接口：
  - `GET /api/v1/admin/settings/payment`：读取配置，同时返回根据当前访问域名自动生成的回调 URL 建议（`suggested_urls`），引导使用人配置到微信商户平台/支付宝开放平台；私钥不回传明文，仅返回 `*_cert_uploaded` 上传状态
  - `PUT /api/v1/admin/settings/payment`：保存配置，即时生效无需重启
  - `POST /api/v1/admin/settings/payment/cert`：multipart 上传证书文件（支持 `.pem/.key/.txt/.crt`，最大 64KB），文件内容直接存入数据库
- 热更新：payment 服务进程内缓存配置并以 `updated_at` 作版本号，支付链路调用时检测到版本变更才重建支付客户端；数据库查询异常时降级使用缓存，不阻断支付
- 版本检测入口覆盖下单、回调受理（微信/支付宝）与退款三条链路：漏掉后两者时，只处理过回调/退款的实例会长期持有空配置缓存，验签公钥缺失会把真实通知判为失败
- 微信回调地址：`{域名}/api/v1/payments/callback/wechat`；支付宝回调地址：`{域名}/api/v1/payments/callback/alipay`

#### 客户端渠道管理（渠道管理）

- 各客户端访问渠道（微信小程序 mp / 微信公众号 gzh / 开放平台 App app / 浏览器 H5 h5）的主数据由 user 服务 `client_channels` 表管理，后台「系统管理 → 渠道管理」维护，对应接口：
  - `GET /api/v1/admin/settings/channels`：渠道列表（全部含停用）
  - `PUT /api/v1/admin/settings/channels/:id`：更新名称/AppID/AppSecret/启用/排序；AppSecret 留空保留原值，code 不可变更
- 启用语义：渠道未启用或凭证不完整时，该端登录（Code2Session）与按端支付能力不可用；h5 无需凭证默认启用
- 登录链路：小程序登录改读渠道管理的 mp 渠道配置（config.yaml 微信节点废弃不用，仅保留结构兼容），登录成功后幂等 upsert `user_channel_identities`（用户渠道身份表）
- 支付联动：pay_config 的 `wechat_channels/alipay_channels` 勾选该支付方式适用的客户端渠道（空=全部可用兼容口径）；C 端 `GET /payments/channels` 按请求头 `X-Channel-Code` 与渠道就绪状态取交集渲染；gzh 需公众号 OAuth、app 需 App 支付 SDK，链路开放前勾选也不展示

#### 现金支付

- 线下收款/货到付款，创建支付单时直接标记为支付成功并同步订单状态
- 不复用待支付现金单：现金支付无需第三方调起参数，复用待支付记录会跳过"置为已支付并同步订单状态"的副作用，导致订单停留在待支付而前端已提示支付成功
- 不经过第三方支付网关
- 退款时仅记录退款流水，不调用第三方接口
