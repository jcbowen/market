### 7.5 消息队列（预留）

当前实现采用同步 gRPC 调用处理订单、库存、通知等业务流程，未引入 Kafka。后续业务量级增长后可按需引入消息队列进行异步解耦。

### 7.6 缓存策略

#### 当前实现口径

一期业务数据（商品、分类、列表等）直接查询 MySQL，**未引入业务缓存**；Redis 当前仅用于定时调度器的**分布式锁**（防止多实例重复扫描）。购物车为 MySQL 存储（`services/cart/model/cart.go`，`carts` 表，user_id+sku_id 唯一键，加购时写入商品名称/规格/图片快照），**不是** Redis Hash；C 端未登录场景的购物车使用本地缓存（`src/client/src/utils/localCart.ts`，uni storage）。

#### Redis Key 命名规范与全量清单

调度器分布式锁格式：`scheduler:{服务名}:{业务}:{动作}:lock`（服务名前缀避免多环境共用 Redis 实例时跨服务键名冲突）

| Key | 所属服务 | 用途 | 锁 TTL |
|-----|----------|------|--------|
| scheduler:order:timeout:cancel:lock | order-service | 超时未支付订单自动取消扫描 | 5min |
| scheduler:order:auto:complete:lock | order-service | 发货后自动完成扫描 | 5min |
| scheduler:order:pickup:complete:lock | order-service | 自提订单自动完成扫描 | 5min |
| scheduler:order:refund:retry:lock | order-service | 退款失败重试扫描 | 5min |
| scheduler:order:refund:auto:approve:lock | order-service | 退款自动同意扫描 | 5min |
| scheduler:product:coupon:expire:lock | product-service | 优惠券过期批量流转 | 5min |
| scheduler:payment:reconcile:pending:lock | payment-service | 待支付单渠道回查（对账补偿，2026-10-21） | 5min |
| scheduler:payment:reconcile:stuck:lock | payment-service | 已关闭支付单的挂账回查（2026-10-21） | 5min |
| scheduler:payment:reconcile:retry:lock | payment-service | 对账失败记录重试（2026-10-22 补锁，与两条扫描同口径） | 5min |
| scheduler:payment:notify:cleanup:YYYY-MM-DD | payment-service | 通知/对账流水过期清理（2026-10-21） | 25h |

加锁机制：`SetNX(key, 随机持有者标识, ttl)` 抢锁，释放时用 Lua 脚本原子比较持有者标识后删除（`services/order/service/scheduler.go`、`services/product/service/scheduler.go`、`services/payment/service/scheduler.go` 同一实现），不会误删他人持有的锁；调度任务均为每分钟 ticker 触发，未抢到锁的实例本轮跳过。

例外：`scheduler:payment:notify:cleanup:{日期}` 是「锁键带日期 + 抢到不释放」的幂等标记（TTL 25h），用于实现集群级**每日一次**的流水清理，不需要释放语义，故不带 `:lock` 后缀。

集成测试约定：`services/payment/service/scheduler_test.go` 的调度器用例固定使用 **Redis DB 1**（`TEST_REDIS_*`/`TEST_MYSQL_*` 环境变量注入，缺省回落本地 docker 栈），与运行中 payment 容器的调度锁（DB 0）隔离；但两者会争抢同一批支付单，跑用例前须 `docker compose stop payment-service`，测毕再启。

防爆破/防重放类业务键（**不是互斥锁**，只做计数与临时封锁）：

| Key | 位置 | 用途与阈值 |
|-----|------|-----------|
| `pickup:lock:{orderId}` / `pickup:fail:{orderId}` | `services/order/service/order.go` | 自提取货码校验失败计数；连续 5 次错误锁定 30min，锁定期内核销返回 FailedPrecondition |
| `loginfail:{scene}:{account}` / `loginfail:{scene}:{account}:lock` | `gateway/handler/login_guard.go` | 后台登录账号失败计数与锁定窗口；5 次/15min，键中带场景段以便 C 端将来接入时共用命名空间；Redis 命令报错时记 `[WARN]` 并放行（fail-open，见 7.4 认证上线前置项口径） |

库存扣减**不使用 Redis**（无预扣、无分布式锁）：靠数据库条件更新 `stock >= ?`、按 ID 升序 `SELECT ... FOR UPDATE`，以及 `stock_op_logs` 复合唯一索引做幂等。

Redis 客户端注意：jcbaseGo 的 `redis.New` 在建实例时 Ping 失败会 panic，**登录锁定这类「缓存抖动不能拖垮主链路」的场景必须自建 `goredis.NewClient`**（构造不建连）并配短读写超时，见 `gateway/handler/login_guard.go`。

#### 其他缓存点（非 Redis）

- **会员状态进程内缓存**：gateway `middleware/user_status.go` 对 C 端会员状态做进程内缓存，拉黑/恢复时经 `InvalidateUserStatusCache` 立即失效；
- **静态资源 HTTP 缓存**：gateway `staticCacheMiddleware` 对带 hash 的静态资源下发 `Cache-Control: public, max-age=31536000, immutable`，入口文件 `no-cache`。
- **站点品牌内存快照**：gateway `gateway/brand` 持有 `site_configs`（user 服务单行表）的快照，TTL 30s + 保存站点设置时 `Invalidate()` 立即失效，派生回调地址、附件外链基址与 HTML 注入统一读取该快照，**每请求 0 次 DB/gRPC**；取数失败沿用旧快照并按 5s 退避重试，不让品牌配置故障放大成整站 500。快照刷新是异步 single-flight 的，进程刚起来时快照为空，故启动期由 `brand.Cache.Warm(ctx)` **同步预取一次**（带超时、失败只记日志不阻断启动）——否则冷启动后的第一个 HTML 请求会注入占位标题，而搜索引擎爬虫抓到的正是这一份。
- **HTML 入口渲染缓存**：`gateway/html_inject.go` 按「模板 mtime+size」缓存原文、按「模板 mtime + 配置 version」缓存渲染结果，逐请求只做一次 map 取值，无字符串替换与读盘；前端重新构建（mtime 变）或站点设置改动（version 变）自动失效，无需重启网关。写入新键时**同步清理同模板的旧键**（键里带 version，每次改站点设置都会生成新键），否则反复改配置会让旧渲染结果常驻内存。
- **refresh 令牌黑名单（Redis）**：`gateway/handler/refresh_guard.go`，键 `refreshjti:<jti>`，TTL 取令牌剩余寿命、到期自动消失无需清理；刷新走 `SETNX` 原子消费、登出主动吊销，Redis 故障时 fail-open 放行（口径与登录锁定一致）。详见 `01-端口与认证.md` 的「refresh 令牌轮换与吊销」。

原规划中的用户/商品/分类/社区列表缓存、秒杀 Redis 预扣、短信验证码缓存等均**未实现**：access_token 失效仍依赖短有效期 + 客户端静默续期（见 7.2，refresh 令牌一侧已由上面的黑名单收口），短信验证码为空实现（见 7.4 sms 预留段）。

### 7.7 文件存储方案

- **存储配置来源**：数据库 `attachment_config` 表（固定单行 id=1），由后台「系统管理 → 附件配置」页面维护（`GET/PUT /api/v1/admin/settings/attachment`，读取时 Secret 脱敏），支持 `local` / 阿里云 OSS（预留 COS），保存后即时生效无需重启；yaml 中的 `upload` 节为历史遗留，运行时不读取（口径与 7.4 一致）。
- **本地模式落盘目录**：可执行文件同级 `attachment/` 目录（部署目录约定，即 `<部署目录>/attachment/`；Docker 部署时 gateway 与 product 服务挂载同一宿主目录 `./bin/attachment`）。
- **目录结构**：`attachment/images/{Ymd}/{dd}/xxx.{ext}`（数据库仅存不含 uploads 前缀的相对路径，如 `images/2026/10/11/xxx.jpg`）。
- **访问 URL**：`https://domain.com/uploads/images/2026/10/11/xxx.jpg`，gateway 经 `/uploads` 静态路由映射该目录；`visit_domain` 配置决定入库的图片绝对地址前缀。
- **附件记录**：`attachment` 表，MD5 秒传（presign 命中直接返回 final_url，confirm 延迟补写 md5）。
- **文件类型限制**：jpg、jpeg、png、gif、bmp、ico、webp、heic（与 jcbaseGo attachment 白名单对齐）。
- **文件大小限制**（分口径，生效的是链路上最严的一道）：网关 multipart 请求体上限 12MB（`http.MaxBytesReader`）；图片单文件上限由 product 服务把守，默认 5MB、可经 `attachment_config.max_size` 调整（本地直传与 OSS presign 同口径）；支付证书 64KB。详见 `06-接口设计/03-后台管理接口.md` 附件上传说明。
- **OSS 扩展**：预签名直传（`POST /api/v1/admin/attachment/presign`，10 分钟有效）+ 上传完成确认（`POST /api/v1/admin/attachment/confirm`）；另有存量本地附件迁移 OSS 的 scan/items/delete-verified 管理接口。
- **图片处理**：一期不处理缩略图，前端通过 CSS 控制显示；二期可接入图片处理服务。

### 7.8 日志规范

- **日志库**：后端当前使用 Go 标准库 `log`，输出进程标准输出；未接入 zap/lumberjack 文件切割（`config.yaml` 的 `log` 节会被解析但运行时代码不读取，属预留）。Docker 部署经 `docker compose logs {service}` 查看；非 Docker 部署由启动方式重定向到 `logs/{service}.log`（见 9.3.5）。
- **级别**：预留（debug / info / warn / error）
- **请求日志**：gateway 中间件 `RequestLoggerMiddleware` 记录每个 HTTP 请求的 method、path（含 query）、client_ip、status、latency、trace_id（`gateway/middleware/logger.go`）
- **debugger 请求日志（可选）**：gateway 可经 jcbaseGo debugger 组件将 HTTP 请求明细（含请求/响应体摘要）写入共享 `debug_logs` 表（MySQL），前端页面 `/jcbase/debug` 查看（支持按 `service_name` 筛选）。配置见 `debugger` 节（02-错误码与配置.md），默认关闭，`DEBUGGER_ENABLED` / `DEBUGGER_ALLOWED_IPS` 环境变量可覆盖；未启用/MySQL 不可达时自动降级，不影响网关主链路，实际状态经 `/health` 的 `debugger` 字段可见（`disabled` / `degraded`+原因 / `on`+页面路径，fail-closed 只记日志时不给路径、给 `note` 说明）。与上一条的自研 `RequestLoggerMiddleware` 并存：后者是轻量运行日志（stdout），前者是可查询的排查数据库，过期清理由组件协程按 `retention_days` + `cleanup_interval_hours` 执行（`retention_days: 0` = 不做过期清理，`max_records: 0` = 不限制条数，`sample_rate: 0` = 一条都不记，绝不等价于清空全表）。
- **debugger 进程级日志（2026-10-22）**：HTTP 请求日志覆盖不到的非请求型链路（支付回调受理、下单后异步任务、payment/order 定时调度器），经组件 `StartProcess`/`EndProcess` 记入同一张 `debug_logs` 表（`record_type=process`，界面按进程名/进程类型/状态过滤，失败记录带错误徽标）。接入约定：
    - 接入层 `common/debuglog` 只做三件事，不复刻组件能力：实例传递（`SetInstance`/`Instance`，组件实例由各服务 main 创建、子包无法直接持有）、nil 安全（未启用/降级时 `Start` 返回 nil，调用方判空即静默）、回调入口按客户端 IP 的频率封顶（`QuotaPerMinute=30` 条/分钟，防伪造回调刷满全表上限——组件采样率只作用于 HTTP 中间件，进程记录无内置限流）
    - gateway 侧记录点：`AlipayCallback`（2026-10-23 改为双口径：受理**成功**只落摘要 `out_trade_no`/`trade_status`/`total_amount`/`notify_id`/结果/耗时/IP，**受理失败落全量通知参数原文（含 `sign`/`sign_type`）+ `content_type`/`body_bytes`/`param_count`/错误**——验签类故障只有拿到原文才可能离线复算待验签串；放开 sign 不构成伪造面，签名把金额与单号一并签死，重放真实通知只命中同一笔已支付单的幂等分支。随原文一起入库的还有买家账号（`buyer_logon_id`/`buyer_id`），与 payment 侧 `payment_notify_logs.raw_body` 既有口径一致，不引入新的暴露面，出口靠 `allowed_ips` 白名单与「排查完立即关回」守住；验签结论仍以 payment 服务的 `payment_notify_logs` 为权威流水，详见 7.9。取证口径全文见 04-第三方支付对接.md「验签失败取证」）/`WechatCallback`（微信 V3 通知体是渠道密文，解析无排查价值，只记体量/结果/错误/耗时/IP）、下单后异步清理购物车（**只记失败**：全成功不落库，部分 SKU 失败才记 error 级并带失败清单——清理是每个订单都走的链路，逐条记录同样会挤占全表上限）
    - payment 侧验签取证记录点（`process_type=payment_verify_alipay`，`service/alipay.go` 的 `recordAlipayVerifyEvidence`）：支付宝验签不通过时落 error 级一条，字段为 `alipay_mode`/`verify_error`/`param_count`/待验签串长度与 `content_fp`/签名长度与 `sign_fp`，证书模式再加 `notify_cert_sn`/`local_cert_sn`/`cert_sn_matched`/`verify_key_fp`。定位「签名与本地证书不同源」还是「`alipay_cert_sn` 有值却在证书与根证书链都定位不到」靠指纹对照即可（缺 `alipay_cert_sn` 本身不是失败原因，SDK v0.0.6 起该分支直接用本商户支付宝公钥证书公钥验签，见 04「验签失败取证」），故**这条刻意不落原文**（原文由上面 gateway 的失败记录与 `payment_notify_logs.raw_body` 承担，避免同一份 sign 在两张表里各存一份）。封顶键取全局固定值而非单号/IP：伪造回调会带随机单号与分散 IP，按单号或 IP 封顶等于不封顶
    - gRPC 服务侧（payment/order）：`bootstrap.RegisterProcessDebugger(cfg, db)` 初始化实例，**连接池复用 main 已有的 `db`**（不自建：每池上限 100/空闲 10，同一进程再挂一份等于把 MySQL `max_connections`（服务端默认 151）的余量吃掉一块，释放函数也只关存储、绝不关池）；与 gateway 共享 `debug_logs` 表、不注册调试页面、不启动过期清理（与 gateway 同表，清理由 gateway 协程统一负责）。来源标识按部署形态区分：一体化部署由 entrypoint 按进程名 sed 覆写配置副本；**compose 部署下各服务共用一份配置模板（`service_name` 均为 gateway）**，故 compose 给 payment/order 两服务注入 `DEBUGGER_SERVICE_NAME`（payment-service/order-service）+ 与 gateway 同源的 `DEBUGGER_ENABLED`（留空=沿用配置文件的 `enabled: false`），环境变量覆盖逻辑在 `common/config.ApplyEnvOverrides`（bootstrap.LoadConfig 已统一调用）
    - **空转轮次不落库**：调度器 60s/1min 一轮，组件 `StartProcess` 创建即落库，全量记录会迅速挤占 `max_records` 全表上限、把 HTTP 请求记录冲掉。故口径为「先跑完子任务、后判定」：无本地状态变更（捞回/挂账/关单/取消/完成/重试/审批）、无失败、无 panic、无流水清理的轮次只打标准日志；有动作的轮次落一条摘要（含各子项计数），失败轮次以 error 级标记。判定函数 `shouldRecordReconcile`/`shouldRecordOrder` 为纯函数，单测覆盖（`scheduler_test.go`）
    - **panic 一定留痕（两处口径统一）**：调度器属旁路能力，一笔异常不得终止整个调度协程，且异常轮次必须落库——否则 panic 被静默恢复后无任何痕迹。payment 侧由 `runReconcileTask` 收口子任务，**结果必须是命名返回值**：panic 越过本体 `return` 后匿名结果槽归零，defer 里对局部变量的写入调用方读不到（实测匿名 `{panics:0}`、命名 `{panics:1}`，`TestRunReconcileTaskPropagatesStat` 锁定）；order 侧 `runOnce` 无子任务级 recover，改为在 `defer` 里统一 `recover` + `recordRound` 落库，panic 时本轮剩余子任务跳过、下一轮重来，协程继续存活（此前订单调度器没有任何 panic 兜底，一笔异常会让后续轮次静默消失）
    - **共享同一张表的已知代价**（三进程一实例：gateway + payment + order）：① 组件 `NewDatabaseStorage` 每次初始化都 `AutoMigrate`，部署重启时三处并发 DDL 可能锁等或报重复列，属可容忍抖动；② `max_records` 裁剪按各实例自己的写入计数均摊触发，三实例互不可见，实际裁剪频率约为单实例的三倍（结果仍是同一上限，只会多删得早一点）；③ 进程记录走两次同步库写（`StartProcess` 创建即 INSERT、`EndProcess` 先 `FindByID` 再 upsert），回调路径在排障开启时每次多 3 个 MySQL 往返（含 `FindByID`），支付宝/微信的重发策略对此有容忍度，用完把 `DEBUGGER_ENABLED` 关回即可
    - 组件 `Config.Level` 默认为 warn（`default:"3"`），**实例化必须显式 `Level: LevelInfo`**，否则 Info 级摘要会被 `shouldLog` 全部丢弃（gateway `registerDebugger` 与 `bootstrap.RegisterProcessDebugger` 均已显式设置，回归由 `common/debuglog` 测试锁定）
- **debugger 与「禁止记录凭据」的对齐**：该策略已落实到组件默认行为，不再依赖人工自觉——
    - 凭据掩码默认开启：`authorization`/`cookie`/`set-cookie` 等头，`password`/`token`/`*_secret`/`captcha`/`sms_code`/`verify_code`/`id_card`/`phone` 等正文字段，以及**同名的查询参数值在 `url` 列里也一并掩成 `***`**（GET 的凭据只体现在查询串上，只掩 `query_params` 会让原文留在 `url` 与 `logger_logs` 里，明文检索即可命中）；页面、导出、存储三条下游路径都拿不到原文（`code` 这类业务状态码字段刻意不掩，避免接口返回值不可读）
    - 凭据入口整条不入库：`/api/v1/auth`、`/api/v1/admin/auth`、`/api/v1/payments/callback` 与两处上传路由在默认 `skip_paths` 内，作为掩码之外的第二道防线（管理端登录必须与 C 端一并覆盖，漏掉即超管账号名与签发的管理员令牌整条进表）
    - **掩码只覆盖 HTTP 中间件路径，进程记录 Fields 不经掩码**：组件的掩码发生在 HTTP 请求捕获环节，`StartProcess`/`EndProcess` 写入的 `logger_logs` 由调用方自己组字段，组件不做二次过滤。因此支付回调的取证原文（含 `sign`）能进 `debug_logs`——这是 2026-10-23 的刻意设计而非掩码漏判：支付宝 `sign` 是对通知字段的 RSA 签名值，不可反推私钥、脱离原文即失效，不属「密码类凭据」，而掩掉它会让验签类故障永久无法定位（论证见 04-第三方支付对接.md「验签失败取证」）。该盲区的外围约束是：回调 HTTP 路径仍在 `skip_paths` 内、进程记录按类型/IP 每分钟封顶、页面走 `allowed_ips` 白名单、排查结束立即关回
    - 上传文件字节默认不进日志（只记部件名/大小/content-type），请求与响应体按 `max_body_size` 有界捕获，截断按 UTF-8 字符边界回退（避免非法字节被 MySQL 严格模式拒绝）
    - 页面默认 fail-closed：`allowed_ips` 为空时调试页面路由不注册（只记日志），需显式配白名单或 `allow_empty_whitelist: true`
    - 白名单鉴权固定走 gin 的 `ClientIP`，其可信度取决于 `security.trusted_proxies`（gin 缺省信任所有代理，未收紧时客户端可伪造代理头）
    - 成本：开启态每个采样请求都会同步写 `debug_logs`，并保留请求/响应正文，属「临时排查」而非长期常驻能力，排查结束立即关回
- **链路追踪**：trace_id 在网关侧生成并写入 gin 上下文（`common/appcontext`），供请求日志与后续服务间透传使用；后端服务日志暂未接入 trace_id
- **敏感信息**：禁止记录密码等凭据，手机号全号需脱敏处理
