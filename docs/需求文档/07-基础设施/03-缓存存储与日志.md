### 7.5 消息队列（预留）

当前实现采用同步 gRPC 调用处理订单、库存、通知等业务流程，未引入 Kafka。后续业务量级增长后可按需引入消息队列进行异步解耦。

### 7.6 缓存策略

#### 当前实现口径

一期业务数据（商品、分类、列表等）直接查询 MySQL，**未引入业务缓存**；Redis 当前仅用于定时调度器的**分布式锁**（防止多实例重复扫描）。购物车为 MySQL 存储（`services/cart/model/cart.go`，`carts` 表，user_id+sku_id 唯一键，加购时写入商品名称/规格/图片快照），**不是** Redis Hash；C 端未登录场景的购物车使用本地缓存（`src/client/src/utils/localCart.ts`，uni storage）。

#### Redis Key 命名规范与全量清单

调度器分布式锁格式：`scheduler:{服务名}:{业务}:{动作}:lock`（服务名前缀避免多环境共用 Redis 实例时跨服务键名冲突）

| Key | 所属服务 | 用途 | 锁 TTL |
|-----|----------|------|--------|
| scheduler:order:timeout:cancel:lock | order-service | 超时未支付订单自动取消扫描 | 5min |
| scheduler:order:auto:complete:lock | order-service | 发货后自动完成扫描 | 5min |
| scheduler:order:pickup:complete:lock | order-service | 自提订单自动完成扫描 | 5min |
| scheduler:order:refund:retry:lock | order-service | 退款失败重试扫描 | 5min |
| scheduler:order:refund:auto:approve:lock | order-service | 退款自动同意扫描 | 5min |
| scheduler:product:coupon:expire:lock | product-service | 优惠券过期批量流转 | 5min |

加锁机制：`SetNX(key, 随机持有者标识, ttl)` 抢锁，释放时用 Lua 脚本原子比较持有者标识后删除（`services/order/service/scheduler.go`、`services/product/service/scheduler.go`），不会误删他人持有的锁；调度任务均为每分钟 ticker 触发，未抢到锁的实例本轮跳过。

防爆破/防重放类业务键（**不是互斥锁**，只做计数与临时封锁）：

| Key | 位置 | 用途与阈值 |
|-----|------|-----------|
| `pickup:lock:{orderId}` / `pickup:fail:{orderId}` | `services/order/service/order.go` | 自提取货码校验失败计数；连续 5 次错误锁定 30min，锁定期内核销返回 FailedPrecondition |
| `loginfail:{scene}:{account}` / `loginfail:{scene}:{account}:lock` | `gateway/handler/login_guard.go` | 后台登录账号失败计数与锁定窗口；5 次/15min，键中带场景段以便 C 端将来接入时共用命名空间；Redis 命令报错时记 `[WARN]` 并放行（fail-open，见 7.4 认证上线前置项口径） |

库存扣减**不使用 Redis**（无预扣、无分布式锁）：靠数据库条件更新 `stock >= ?`、按 ID 升序 `SELECT ... FOR UPDATE`，以及 `stock_op_logs` 复合唯一索引做幂等。

Redis 客户端注意：jcbaseGo 的 `redis.New` 在建实例时 Ping 失败会 panic，**登录锁定这类「缓存抖动不能拖垮主链路」的场景必须自建 `goredis.NewClient`**（构造不建连）并配短读写超时，见 `gateway/handler/login_guard.go`。

#### 其他缓存点（非 Redis）

- **会员状态进程内缓存**：gateway `middleware/user_status.go` 对 C 端会员状态做进程内缓存，拉黑/恢复时经 `InvalidateUserStatusCache` 立即失效；
- **静态资源 HTTP 缓存**：gateway `staticCacheMiddleware` 对带 hash 的静态资源下发 `Cache-Control: public, max-age=31536000, immutable`，入口文件 `no-cache`。
- **站点品牌内存快照**：gateway `gateway/brand` 持有 `site_configs`（user 服务单行表）的快照，TTL 30s + 保存站点设置时 `Invalidate()` 立即失效，派生回调地址、附件外链基址与 HTML 注入统一读取该快照，**每请求 0 次 DB/gRPC**；取数失败沿用旧快照并按 5s 退避重试，不让品牌配置故障放大成整站 500。
- **HTML 入口渲染缓存**：`gateway/html_inject.go` 按「模板 mtime+size」缓存原文、按「模板 mtime + 配置 version」缓存渲染结果，逐请求只做一次 map 取值，无字符串替换与读盘；前端重新构建（mtime 变）或站点设置改动（version 变）自动失效，无需重启网关。

原规划中的 JWT token 黑名单（登出）、用户/商品/分类/社区列表缓存、秒杀 Redis 预扣、短信验证码缓存等均**未实现**：登出与令牌失效依赖 JWT 短有效期 + 客户端静默续期机制（见 7.2），短信验证码为空实现（见 7.4 sms 预留段）。

### 7.7 文件存储方案

- **存储配置来源**：数据库 `attachment_config` 表（固定单行 id=1），由后台「系统管理 → 附件配置」页面维护（`GET/PUT /api/v1/admin/settings/attachment`，读取时 Secret 脱敏），支持 `local` / 阿里云 OSS（预留 COS），保存后即时生效无需重启；yaml 中的 `upload` 节为历史遗留，运行时不读取（口径与 7.4 一致）。
- **本地模式落盘目录**：可执行文件同级 `attachment/` 目录（部署目录约定，即 `<部署目录>/attachment/`；Docker 部署时 gateway 与 product 服务挂载同一宿主目录 `./bin/attachment`）。
- **目录结构**：`attachment/images/{Ymd}/{dd}/xxx.{ext}`（数据库仅存不含 uploads 前缀的相对路径，如 `images/2026/10/11/xxx.jpg`）。
- **访问 URL**：`https://domain.com/uploads/images/2026/10/11/xxx.jpg`，gateway 经 `/uploads` 静态路由映射该目录；`visit_domain` 配置决定入库的图片绝对地址前缀。
- **附件记录**：`attachment` 表，MD5 秒传（presign 命中直接返回 final_url，confirm 延迟补写 md5）。
- **文件类型限制**：jpg、jpeg、png、gif、bmp、ico、webp、heic（与 jcbaseGo attachment 白名单对齐）。
- **文件大小限制**（分口径，生效的是链路上最严的一道）：网关 multipart 请求体上限 12MB（`http.MaxBytesReader`）；图片单文件上限由 product 服务把守，默认 5MB、可经 `attachment_config.max_size` 调整（本地直传与 OSS presign 同口径）；支付证书 64KB。详见 `06-接口设计/03-后台管理接口.md` 附件上传说明。
- **OSS 扩展**：预签名直传（`POST /api/v1/admin/attachment/presign`，10 分钟有效）+ 上传完成确认（`POST /api/v1/admin/attachment/confirm`）；另有存量本地附件迁移 OSS 的 scan/items/delete-verified 管理接口。
- **图片处理**：一期不处理缩略图，前端通过 CSS 控制显示；二期可接入图片处理服务。

### 7.8 日志规范

- **日志库**：后端当前使用 Go 标准库 `log`，输出进程标准输出；未接入 zap/lumberjack 文件切割（`config.yaml` 的 `log` 节会被解析但运行时代码不读取，属预留）。Docker 部署经 `docker compose logs {service}` 查看；非 Docker 部署由启动方式重定向到 `logs/{service}.log`（见 9.3.5）。
- **级别**：预留（debug / info / warn / error）
- **请求日志**：gateway 中间件 `RequestLoggerMiddleware` 记录每个 HTTP 请求的 method、path（含 query）、client_ip、status、latency、trace_id（`gateway/middleware/logger.go`）
- **链路追踪**：trace_id 在网关侧生成并写入 gin 上下文（`common/appcontext`），供请求日志与后续服务间透传使用；后端服务日志暂未接入 trace_id
- **敏感信息**：禁止记录密码等凭据，手机号全号需脱敏处理
