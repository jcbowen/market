### 7.2 认证鉴权方案

#### JWT Token 设计

- 签名算法：HS256（`common/jwt/jwt.go`）
- Access Token 有效期：默认 2 小时，来源是配置项 `jwt.access_token_ttl`（秒，默认 7200）
- Refresh Token 有效期：默认 7 天，来源是配置项 `jwt.refresh_token_ttl`（秒，默认 604800）
- 密钥来源：配置项 `jwt.secret`，**生产环境必须显式覆盖**（留空/默认值即等同公开密钥）

**双 token 机制（token_use 区分）**：payload 含 `token_use` 声明，`access` = 接口访问令牌，`refresh` = 刷新令牌（仅可用于换取新 access token）。Gateway 鉴权中间件**强校验**：`token_use` 非 `access` 的 token 一律拒绝访问业务接口（refresh_token 不能当 access_token 用）；刷新接口反向强校验，仅接受 `token_use=refresh` 且类型匹配的 token（access_token 不能用于刷新）。两类令牌互不可用，防止任一令牌泄露被扩大利用。

**claims 结构体的全部字段**（`json` 键名，`omitempty` 的空值不会出现在 payload 中）：`sub`（ID，序列化为字符串）、`type`（`user`/`admin`）、`token_use`（`access`/`refresh`）、`phone`、`role`、`community_id`、`community_ids`、`permissions`、`username`、`real_name`，加上标准 `iat`/`exp`/`nbf`。签发入口只有 `common/jwt`，两类令牌共用同一结构、按端填不同子集。

**JWT Payload（C端用户，access）** — `gateway/handler/auth.go` 签发，只带 `sub/type/token_use/phone/community_id`，`role`、`permissions` 恒空：
```json
{
  "sub": "1",
  "type": "user",
  "token_use": "access",
  "phone": "13800138000",
  "community_id": 1,
  "iat": 1690000000,
  "nbf": 1690000000,
  "exp": 1690007200
}
```

**JWT Payload（管理员，access）** — `gateway/handler/admin.go` 签发：`role` 为 `super_admin`/`admin`（超管判定实际看 `admin_users.is_super`），`community_id` 为登录时的默认当前社区，`community_ids` 为该账号全部任职社区（供切换社区时免逐请求查库），**`permissions` 恒不写入**（历史上的权限快照已下线，改为每次请求实时解析，见「权限中间件」）：
```json
{
  "sub": "1",
  "type": "admin",
  "token_use": "access",
  "username": "admin",
  "real_name": "管理员",
  "phone": "13800138000",
  "role": "super_admin",
  "community_id": 1,
  "community_ids": [1, 2],
  "iat": 1690000000,
  "nbf": 1690000000,
  "exp": 1690007200
}
```

#### refresh_token 的承载方式（按前端平台分岔）

refresh_token 有效期 7 天，泄漏价值远高于 2 小时的 access_token，故不再交给 JS 保管：

| 前端 | 承载方式 | 说明 |
| --- | --- | --- |
| 后台管理 / POS（浏览器，同源） | **httpOnly cookie** | 登录请求带 `X-Refresh-Cookie: 1`，后端下发 `market_admin_refresh` cookie 且响应体**不再返回** `refresh_token`；JS 读不到 |
| C 端 H5 | **httpOnly cookie** | 同上，`src/client/src/api/config.ts` 的 `REFRESH_COOKIE_HEADER` 由 `isH5()` 决定是否携带；cookie 名为 `market_refresh` |
| C 端微信小程序 / App | **响应体 + 本地存储** | 小程序不自管浏览器 cookie、App 端无同源概念，无 httpOnly cookie 语义；不带该请求头，后端保持旧行为 |

cookie 属性（`src/backend/gateway/handler/token_cookie.go`）：**按端分名分路径**——后台 `market_admin_refresh` + `Path=/api/v1/admin`，C 端 `market_refresh` + `Path=/api/v1`（不给全站请求带上令牌），均 `HttpOnly`、`SameSite=Lax`、`Max-Age` 取 `jwt.refresh_token_ttl`。分名的原因：两端同源同域（同一网关主机），共用一枚 cookie 时「后台登录会覆盖会员登录的令牌」「后台登出把会员会话一起踢下线」，且会员端刷新会拿到后台令牌（跨端 session fixation）。C 端名称保持与历史一致，已登录的 H5 会话不因改名失效。`Secure` 随实际协议判定（先看 `X-Forwarded-Proto`，回看 TLS，口径与附件 `baseURLOf` 一致）——**不能写死 Secure**，否则 HTTP 部署下浏览器直接丢弃该 cookie，登录不可用。

刷新接口的取值口径为「cookie 优先、请求体兜底」，因此同一后端可同时服务新旧前端与三端；登出由 `POST /api/v1/auth/logout`、`POST /api/v1/admin/auth/logout` 下发同名负 `Max-Age` cookie 清除（属性需与下发时一致，否则删不掉），这两个端点不要求登录态——access_token 已过期时也必须能登出。登录/刷新/登出三处都用同一个「按端选名选路径」判定，避免「下发用 A 名、清除用 B 名」的错配。

#### access_token 的 WS 握手承载（2026-10-24 加固）

浏览器 WebSocket 握手无法自定义请求头，后台 WS（`/api/v1/admin/ws`）鉴权原把 access_token
明文放进握手 URL 查询参数——URL 会落入浏览器历史与网关/代理访问日志。现改为：

- 后台登录/刷新时随 `X-Refresh-Cookie: 1` 声明**同步下发 `market_admin_access` httpOnly cookie**
  （与 refresh cookie 同域同路径 `Path=/api/v1/admin`、同 `Secure`/`SameSite=Lax` 判定，
  `Max-Age` 取 access 有效期；登出时一并清除）
- `WSAuthMiddleware`（`gateway/middleware/ws.go`）按 **cookie 优先、查询参数兜底**
  取令牌映射为 `Authorization` 头；查询参数仅兼容旧前端缓存与 POS 等未带 cookie 的客户端

#### 令牌轮换与吊销（黑名单，P1-5 + C5）

refresh_token 有效期 7 天，若不轮换，一枚泄漏的令牌可在有效期内无限续命；若只轮换不吊销，旧令牌与新令牌同时可用（重放）。故两端刷新都**轮换 + 把旧令牌 jti 拉黑**（`src/backend/gateway/handler/token_guard.go`，类型 `tokenGuard`）：

- **access 也进黑名单（C5，2026-10-28）**：access_token 有效期 2 小时（`JWT_ACCESS_TOKEN_TTL`，默认 7200），原先**不带 jti**、鉴权也不查黑名单，于是「登出」只清了 cookie 与前端本地存储，服务端在剩余 2 小时内照旧认这枚令牌——被盗的 access 与已登出的会话都照常调接口。现在 `common/jwt` 给 access 与 refresh **一律签入随机 jti**（`newJTI` 失败即拒绝签发，不再退化成「签出一枚永远无法单独吊销的令牌」），`AuthMiddleware` 逐请求查验一次黑名单。
- **查验挂在热路径上的取舍**：每个鉴权请求多一次 Redis `EXISTS`（健康 Redis 亚毫秒，远小于同请求后续的 gRPC 权限解析）；命令上限从 1s 压到 **500ms**，Redis 故障时最坏只给每个请求加 500ms；失败告警按 **30s 节流**（CAS 抢打印权，逐请求刷屏会掩盖真实故障线索）。
- **登出双吊销**：C 端 `Logout` 与后台 `AdminLogout`（POS 交班后的强制登出走同一入口）都调 `revokePresentedTokens`，按本端令牌类型同时吊销 **access 与 refresh** 两枚 jti。access 从 `Authorization` 头取，并兜底读后台为 WS 握手下发的 `market_admin_access` httpOnly cookie——只清 cookie 不读它，那枚令牌就漏掉了。登出路由是公开路由，令牌在此自行解析，类型/用途不符一律跳过（防拿 A 端登出吊销 B 端令牌）。
- **原子消费**：`consume(jti, ttl)` 用 Redis `SET NX`（Lua 保证「判断 + 落键」原子）把旧 refresh 的 jti 一次性消费掉——命中即说明该 jti 已被用过，直接拒绝（11002）。改原子前是 `revoked → revoke` 两步，并发双提交会双双通过，重放窗口等于令牌有效期。
- **最小 TTL 兜底**：刷新消费（`consume`）时若令牌剩余寿命非正，仍按 `tokenGuardMinTTL`（1 分钟）落键，覆盖并发对手的重放窗口；主动 `revoke` 遇到非正 TTL 则不落键（令牌本就即将失效）。
- **fail-open**：Redis 不可用/超时时放行，不因缓存故障把全站登录与鉴权打挂——黑名单是纵深防御的一层，不是唯一鉴权依据；代价是这期间登出/吊销暂不生效，令牌退回「按过期时间自然失效」。
- **键命名**：`tokenjti:<jti>` 单一命名空间（access 与 refresh 共用；jti 每令牌唯一随机，不会串键），与登录锁定键（`loginfail`）刻意分开。本次改动之前签发、不带 jti 的历史令牌不参与黑名单（空 jti 一律按未吊销处理）。
- **已知边界（明确取舍，非缺陷）**：① 刷新时不吊销上一枚 access——前端可能在途并发请求，吊销会让它们莫名 401；② 已建立的 WebSocket 长连接不受登出影响（吊销在握手时生效），下一次握手才被拒；③ 停用/删除管理员无法按 jti 精确吊销（没有「管理员 → 全部 jti」的索引），靠后台链路的实时权限解析与刷新时的账号状态校验兜住（见下）。

#### 客户端静默续期机制

C 端请求层（`src/client/src/api/request.ts`）实现 401 自动续期与重放，业务调用方对令牌过期无感知：

- **401 识别**：HTTP 状态码 401 或业务码命中 `UNAUTHORIZED_CODES`（11001 未登录或 token 已过期、11002 token 无效）时，抛出内部 `UnauthorizedError` 交由统一请求入口处理，不外泄给业务调用方。
- **互斥刷新**：模块级单例 `refreshingPromise` 保证并发触发的多个 401 共享同一次刷新请求，刷新结束置回 null；防止并发重复刷新导致 refresh_token 被轮换后旧值立即失效的竞态。
- **刷新与重放**：`POST /auth/refresh` 换取新令牌对并持久化（即**滑动续期**），成功后重放原请求（仅重放 1 次）。图片上传（`uni.uploadFile`）走同样的静默续期 + 重放逻辑。令牌来源按平台分岔：H5 走 `doRefreshByCookie()`（空请求体 + `X-Refresh-Cookie: 1`，凭 cookie 续期，响应体无 `refresh_token` 可写），小程序/App 仍读本地存储的 refresh_token 放进请求体。
- **失败兜底**：refresh_token 缺失或被服务端判定无效时，清空本地 access_token / refresh_token 并跳转登录页；网络异常时保留本地令牌，后续请求可再触发重试，不误杀登录态。
- **防递归**：刷新请求为裸 `uni.request` 直调，不经过 request 封装，天然不会再触发静默续期。
- **登出清理**：退出登录时清除本地 access_token / refresh_token；H5 额外调用 `POST /api/v1/auth/logout` 请后端清除 httpOnly cookie（JS 删不掉的那一份），该请求失败不阻塞本地登出（`src/client/src/stores/user.ts`）。
- **后台侧现状**：后台请求层**尚未接入 401 自动静默续期**——access_token 过期即 `redirectToLogin()`。`store.refreshAccessToken()` 仍保留，当前唯一调用点是 WebSocket 重连前主动续期（`src/admin/src/utils/orderNotify.ts`）；`POST /api/v1/admin/auth/refresh` 端点可供测试与外部调用方使用。给后台接入自动续期需先把 access_token 移出 JS 可读载体并改造「刷新页面恢复登录态」的状态机，见 `11-开发计划.md` 上线前置项。

#### 鉴权流程

1. 客户端请求携带 `Authorization: Bearer <access_token>`
2. Gateway 中间件解析 JWT，验证签名和有效期
3. 从 token 中提取用户身份信息，注入请求上下文
4. 后端服务从上下文中获取用户信息，进行数据隔离

#### 限流与登录防护

- **来源 IP 口径**：`ClientIP()` 是否采信 `X-Forwarded-For` 等代理头，由配置 `security.trusted_proxies`（或环境变量 `TRUSTED_PROXIES`）经 `applyTrustedProxies` → `SetTrustedProxies` 决定；未配置即不信任任何代理，只认直连地址（否则伪造头换 IP 可绕过全部按 IP 的限流）。`RealIPMiddleware` 紧随其后把最终 `ClientIP()` 固化进请求上下文（`appcontext.KeyRealIP`），供访问日志与 IP 定位使用，避免各处重复判定。
- **限流桶（令牌桶，`gateway/middleware/ratelimit.go`）**：命中限流返回 HTTP 429 + 业务码 `errcode.RateLimit`；按 IP 的桶带 `Retry-After: 1`，按用户 ID 的桶（`UserRateLimitMiddleware`）带 `Retry-After: 12`。

| 范围 | 键 | rate / 容量 | 位置 |
|---|---|---|---|
| 接口分组 `/api/v1`（C 端）与 `/api/v1/admin`（后台），**两组共用同一个桶实例** | 客户端 IP | 缺省 100 / 150（可配，见下） | `gateway/main.go` 的 `apiLimiter` |
| C 端认证入口 `/auth/phone-code`、`/auth/login/phone`、`/auth/weixin-login`、`/auth/refresh` | 客户端 IP | 10 / 30 | `cAuthLimiter` |
| 后台 `/auth/login`、`/auth/refresh`、`/auth/logout` | 客户端 IP | 5 / 50 | `adminAuthLimiter` |
| C 端下单 `POST /orders` | 用户 ID | 0.08 / 5 | `UserRateLimitMiddleware`（须置于鉴权中间件之后） |
| C 端图片上传 `POST /upload/image`（2026-10-31 新增，头像与履约签收照片共用） | 用户 ID | 0.05 / 6（稳态约 180 张/小时） | 同上，路由级挂载 |

- **上传桶的联调口径**：桶是独立实例且不可配（不像接口桶有环境变量出口），连续传第 7 张图起撞 429 + 业务码 10005 属设计内行为，按响应头 `Retry-After: 12` 等待补桶即可，不是故障、前端无需特判（429 走 `showError` 直接吐司服务端文案）。真实用户场景（换头像 + 每单几张签收照）用不到稳态上限；若确要为压测/批量导入放宽，只能改 `gateway/main.go` 的路由参数重新发布，不建议为此下调线上防护阈值。

- **接口桶阈值可配，生产保持缺省**：`security.api_rate_qps` / `security.api_rate_burst`（环境变量 `RATE_LIMIT_API_QPS` / `RATE_LIMIT_API_BURST` 覆盖，非正数 fail-fast 拒绝启动，缺省 100/150；启动日志会打印实际生效值）。上调的唯一已知必要场景是本机接口测试：整套用例从同一客户端 IP 串行打出，实测峰值 116~133 r/s 贴着缺省阈值跑，会在随机某条用例上撞出 429（2026-10-29 取证：`api/49` 的现金支付被「请求频率限制」打红，serial 分组因此整组续跑、被完整性闸门报成 11 条 flaky）。本地 `docker-compose.yml` 的 gateway 段已默认注入 2000/3000（`.env` 不配也行，配了按 `.env` 覆盖）；生产 compose 不引用本项、恒走缺省，确有整体验证需求（如某办公出口整体被限）时经 `security.api_rate_qps` 配置文件项或 compose 显式注入调整。认证入口桶、后台登录桶、按用户下单桶都是独立实例且不可配，收紧口径不随本项变化。
- **接口桶不覆盖静态资源**（2026-10-29 由浏览器实测纠正）：曾把 IP 桶挂在全局中间件链上，H5 首屏要拉几十张商品图与若干 hash chunk，与接口共用一个桶时 chunk 被判 429，uni-h5 直接显示「连接服务器超时，点击屏幕重试」——用户看到的是假故障，运维也查不到真实原因。静态资源由 nginx/CDN 承接，网关侧不参与令牌桶；洪水兜底的回归口径改打「所有环境恒为 10/30」的 C 端认证入口桶（与可配的接口桶解耦，断言不随环境配置漂移），见 `tests/api/58-security-middleware.spec.ts`「突发超量认证请求触发 429 限流」与「静态资源与只读接口不吃认证入口的令牌桶」。
- **后台分组必须显式挂 `apiLimiter`**：`/api/v1/admin` 直接挂在 `Engine` 上而非 `apiV1` 分组之下，Gin 的 `group.Use` 不跨树继承；漏挂会让后台接口完全不限流，两组各挂一份则单 IP 实际额度翻倍。

- **闲置桶淘汰**：桶按 key 存在内存 map 中，取桶时顺带扫描（无后台协程，与读写同一把锁）：闲置超过 30 分钟的桶被删除，两次扫描最少间隔 5 分钟。这是防「IP 维度桶随扫描源无限增长」的内存兜底——没有淘汰时，单个限流中间件的 map 可被分布式源 IP 打爆。
- **按账号的登录失败锁定**（后台，`gateway/handler/login_guard.go`）：Redis 键 `loginfail:{scene}:{account}`（计数，15 分钟窗口）与 `...:lock`（锁定期）。阈值 5 次失败/15 分钟；账号不存在与密码错误统一文案，防枚举账号；状态校验（禁用）置于密码校验之后，防泄露账号状态；锁定计数只在「凭证确实错误」时累加，user-service 故障/数据库故障按内部错误返回、不污染计数（否则服务抖机会把正常管理员连带锁在门外）。
  - Redis 不可达时**放行**（fail-open）：单次命令 1 秒超时，失败只记 `[WARN]`，登录继续走密码校验。该实现刻意直连 go-redis 而不用 jcbaseGo 的 `redis.New`——后者建实例时 Ping 失败会 panic，会把缓存抖动变成登录入口 500。运维口径见 `11-开发计划.md` 第 70 项。
  - C 端手机号登录不接入锁定（当前不校验验证码、任何号码恒成功，没有「失败」可计），试探只由上表的按 IP 限流兜底；键名预留了场景段，接入验证码后按 `loginScenePhone` 场景分开计数即可。

#### 多端登录策略

- 同一用户多端登录共享 token（微信小程序、支付宝小程序、H5、Android 使用同一账号）
- 通过 `union_id`（微信）或 `phone`（手机号）关联多端账号
- 首次支付宝登录时，若未绑定手机号，引导绑定手机号以关联微信端账号

#### 权限中间件（后台 = 权限点 RBAC，实时解析）

不存在 casbin 或 `permissions` / `role_permission` 关联表，模型是「角色 → 权限点编码列表（JSON 列）→ 员工在社区任职挂角色」三张表：`admin_roles`（`permissions` JSON 列；`community_id=0` 为全局内置角色，`>0` 为该社区私有角色，唯一键 `uk_role_community_code`）、`admin_users`（账号，含 `is_super`）、`admin_communities`（员工在某社区的任职行 + 该任职使用的角色）。

- **鉴权入口**：`gateway/middleware/auth.go` 校验签名、有效期、`token_use=access` 与 `type` 白名单，把 claims 注入请求上下文；`gateway/middleware/permission.go` 的 `RequirePermission(编码...)` 挂在每条后台路由上（具备其一即通过），`RequireCommunityAccess()` 全局 `Use` 校验社区语境。
- **权限不写在 token 里**：多社区模型下权限随「当前社区」变化，JWT 快照无法表达，故后台 token 的 `permissions` 恒为空，改为**逐请求实时解析**——网关经 `SetPermissionResolver` 注入 user 服务 `GetAdminContext(admin_id, community_id)`，服务端取该员工在此社区的任职角色权限并集。同一请求内在 gin context 记忆化（只解析一次），**服务端与网关均不做跨请求缓存**，因此改角色/权限后立即生效，代价是每请求一次 gRPC + 若干条 SQL。
- **超管判定**：一律看 `admin_users.is_super` 的实时值（`AdminContextInfo.IsSuper`），网关统一经 `middleware.IsSuperAdmin(c)` 取数——它复用同一请求内记忆化的 `GetAdminContext` 结果，不额外增加 RPC。claims 里的 `role` 字符串 `super_admin` **不再参与任何鉴权判定**，只作展示与存量兼容：它是登录时绘制的快照，降权/停用后照抄快照等于把旧授权续到令牌过期，`PUT /admins/:id`（降权超管可自恢复角色）与「系统管理」全部超管专用接口都曾踩这个坑，现全部改走实时口径。实时解析不可用时按非超管处理（fail-closed）。
- **社区权限上限**：普通管理员的权限并集还要与内置 `community_admin` 角色的权限取交集，交集后仍残留的 `"*"` 通配一律展开为 `DefaultCommunityAdminPermissions`（不含 community/region/settings 等系统级权限点），防止社区管理员自建含 `"*"` 的角色后读写全局支付配置。`community_id=0`（无社区语境）时不做交集。
- **当前社区从哪来**：请求头 `X-Community-Id` 优先，缺省回退 JWT 的 `community_id`（登录时的默认社区）。`RequireCommunityAccess` **只看实时解析结果**（`GetAdminContext` 的 `IsSuper`/`Bound`）：claims 里的 `role`/`community_ids` 是登录时绘制的快照，降权或解除任职后照抄快照等于把旧授权续到令牌过期，故判定完全不看快照；实时解析失败（user 服务抖动/不可用）时同样拒绝（fail-closed），不再回退快照降级放行——挂了权限码的同一请求在 `RequirePermission` 上本就是 403，回退快照换不到可用性，只会留下越权面。越权与解析失败均返回 403。
- **停用即时生效**：`GetAdminContext` 对 `admin_users.status ≠ 1` 一律返回「非超管、空权限、`bound=false`」，因此超管在账号管理页停用某管理员后，该账号的后台请求**当场**在 `RequirePermission`/`RequireCommunityAccess` 上失败，不必等 access_token 自然过期或重登。「账号不存在」与「已停用」对外表现一致（返回空权限而非报错），不透露账号状态。后台 `POST /api/v1/admin/auth/refresh` 另有一道实时校验：按 `claims.UserID` 查库，账号已删除按令牌无效处理、`status≠1` 返回 11006，停用账号立即失去续期能力（不必等 7 天 refresh 令牌自然过期）。
- **刷新令牌重推导权限上下文**：`AdminHandler.RefreshToken` 不照抄旧令牌里的 `role`/`community_id`/`community_ids`，而是按实时账号数据重推导后再签发（否则被降权的超管可凭 7 天有效期的 refresh 无限续期 `super_admin` 快照）。
- **多社区隔离的两层落点**：网关层 = 上述 403 + handler 把社区 ID 写进 gRPC 请求；服务层 = 按请求里的 `community_id` 过滤数据。**C 端不采信该请求头**，一律以 JWT 的社区语境为准。
- 角色码语义（供理解 claims 的 `role`）：`super_admin` 超管（不限制社区）、`community_admin` 内置社区管理员（受上限约束）、`staff` 普通员工；实际可见范围由「任职社区 + 角色权限点」共同决定，而非由角色码硬编码。
