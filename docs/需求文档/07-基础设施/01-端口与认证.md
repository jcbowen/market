### 7.2 认证鉴权方案

#### JWT Token 设计

- 签名算法：HS256（`common/jwt/jwt.go`）
- Access Token 有效期：默认 2 小时，来源是配置项 `jwt.access_token_ttl`（秒，默认 7200）
- Refresh Token 有效期：默认 7 天，来源是配置项 `jwt.refresh_token_ttl`（秒，默认 604800）
- 密钥来源：配置项 `jwt.secret`，**生产环境必须显式覆盖**（留空/默认值即等同公开密钥）

**双 token 机制（token_use 区分）**：payload 含 `token_use` 声明，`access` = 接口访问令牌，`refresh` = 刷新令牌（仅可用于换取新 access token）。Gateway 鉴权中间件**强校验**：`token_use` 非 `access` 的 token 一律拒绝访问业务接口（refresh_token 不能当 access_token 用）；刷新接口反向强校验，仅接受 `token_use=refresh` 且类型匹配的 token（access_token 不能用于刷新）。两类令牌互不可用，防止任一令牌泄露被扩大利用。

**claims 结构体的全部字段**（`json` 键名，`omitempty` 的空值不会出现在 payload 中）：`sub`（ID，序列化为字符串）、`type`（`user`/`admin`）、`token_use`（`access`/`refresh`）、`phone`、`role`、`community_id`、`community_ids`、`permissions`、`username`、`real_name`，加上标准 `iat`/`exp`/`nbf`。签发入口只有 `common/jwt`，两类令牌共用同一结构、按端填不同子集。

**JWT Payload（C端用户，access）** — `gateway/handler/auth.go` 签发，只带 `sub/type/token_use/phone/community_id`，`role`、`permissions` 恒空：
```json
{
  "sub": "1",
  "type": "user",
  "token_use": "access",
  "phone": "13800138000",
  "community_id": 1,
  "iat": 1690000000,
  "nbf": 1690000000,
  "exp": 1690007200
}
```

**JWT Payload（管理员，access）** — `gateway/handler/admin.go` 签发：`role` 为 `super_admin`/`admin`（超管判定实际看 `admin_users.is_super`），`community_id` 为登录时的默认当前社区，`community_ids` 为该账号全部任职社区（供切换社区时免逐请求查库），**`permissions` 恒不写入**（历史上的权限快照已下线，改为每次请求实时解析，见「权限中间件」）：
```json
{
  "sub": "1",
  "type": "admin",
  "token_use": "access",
  "username": "admin",
  "real_name": "管理员",
  "phone": "13800138000",
  "role": "super_admin",
  "community_id": 1,
  "community_ids": [1, 2],
  "iat": 1690000000,
  "nbf": 1690000000,
  "exp": 1690007200
}
```

#### refresh_token 的承载方式（按前端平台分岔）

refresh_token 有效期 7 天，泄漏价值远高于 2 小时的 access_token，故不再交给 JS 保管：

| 前端 | 承载方式 | 说明 |
| --- | --- | --- |
| 后台管理 / POS（浏览器，同源） | **httpOnly cookie** | 登录请求带 `X-Refresh-Cookie: 1`，后端下发 `market_refresh` cookie 且响应体**不再返回** `refresh_token`；JS 读不到 |
| C 端 H5 | **httpOnly cookie** | 同上，`src/client/src/api/config.ts` 的 `REFRESH_COOKIE_HEADER` 由 `isH5()` 决定是否携带 |
| C 端微信小程序 / App | **响应体 + 本地存储** | 小程序不自管浏览器 cookie、App 端无同源概念，无 httpOnly cookie 语义；不带该请求头，后端保持旧行为 |

cookie 属性（`src/backend/gateway/handler/token_cookie.go`）：名称 `market_refresh`、`Path=/api/v1`（不给全站请求带上令牌）、`HttpOnly`、`SameSite=Lax`、`Max-Age` 取 `jwt.refresh_token_ttl`。`Secure` 随实际协议判定（先看 `X-Forwarded-Proto`，回看 TLS，口径与附件 `baseURLOf` 一致）——**不能写死 Secure**，否则 HTTP 部署下浏览器直接丢弃该 cookie，登录不可用。

刷新接口的取值口径为「cookie 优先、请求体兜底」，因此同一后端可同时服务新旧前端与三端；登出由 `POST /api/v1/auth/logout`、`POST /api/v1/admin/auth/logout` 下发同名负 `Max-Age` cookie 清除（属性需与下发时一致，否则删不掉），这两个端点不要求登录态——access_token 已过期时也必须能登出。

#### 客户端静默续期机制

C 端请求层（`src/client/src/api/request.ts`）实现 401 自动续期与重放，业务调用方对令牌过期无感知：

- **401 识别**：HTTP 状态码 401 或业务码命中 `UNAUTHORIZED_CODES`（11001 未登录或 token 已过期、11002 token 无效）时，抛出内部 `UnauthorizedError` 交由统一请求入口处理，不外泄给业务调用方。
- **互斥刷新**：模块级单例 `refreshingPromise` 保证并发触发的多个 401 共享同一次刷新请求，刷新结束置回 null；防止并发重复刷新导致 refresh_token 被轮换后旧值立即失效的竞态。
- **刷新与重放**：`POST /auth/refresh` 换取新令牌对并持久化（即**滑动续期**），成功后重放原请求（仅重放 1 次）。图片上传（`uni.uploadFile`）走同样的静默续期 + 重放逻辑。令牌来源按平台分岔：H5 走 `doRefreshByCookie()`（空请求体 + `X-Refresh-Cookie: 1`，凭 cookie 续期，响应体无 `refresh_token` 可写），小程序/App 仍读本地存储的 refresh_token 放进请求体。
- **失败兜底**：refresh_token 缺失或被服务端判定无效时，清空本地 access_token / refresh_token 并跳转登录页；网络异常时保留本地令牌，后续请求可再触发重试，不误杀登录态。
- **防递归**：刷新请求为裸 `uni.request` 直调，不经过 request 封装，天然不会再触发静默续期。
- **登出清理**：退出登录时清除本地 access_token / refresh_token；H5 额外调用 `POST /api/v1/auth/logout` 请后端清除 httpOnly cookie（JS 删不掉的那一份），该请求失败不阻塞本地登出（`src/client/src/stores/user.ts`）。
- **后台侧现状**：后台请求层**尚未接入静默续期**——access_token 过期即 `redirectToLogin()`。`store.refreshToken()` 已随本次改造移除（全仓无调用点），`POST /api/v1/admin/auth/refresh` 端点保留，仅测试与外部调用方使用。给后台接入续期需先把 access_token 移出 JS 可读载体并改造「刷新页面恢复登录态」的状态机，见 `11-开发计划.md` 上线前置项。

#### 鉴权流程

1. 客户端请求携带 `Authorization: Bearer <access_token>`
2. Gateway 中间件解析 JWT，验证签名和有效期
3. 从 token 中提取用户身份信息，注入请求上下文
4. 后端服务从上下文中获取用户信息，进行数据隔离

#### 限流与登录防护

- **来源 IP 口径**：`ClientIP()` 是否采信 `X-Forwarded-For` 等代理头，由配置 `security.trusted_proxies`（或环境变量 `TRUSTED_PROXIES`）经 `applyTrustedProxies` → `SetTrustedProxies` 决定；未配置即不信任任何代理，只认直连地址（否则伪造头换 IP 可绕过全部按 IP 的限流）。`RealIPMiddleware` 紧随其后把最终 `ClientIP()` 固化进请求上下文（`appcontext.KeyRealIP`），供访问日志与 IP 定位使用，避免各处重复判定。
- **限流桶（令牌桶，`gateway/middleware/ratelimit.go`）**：命中限流返回 HTTP 429 + 业务码 `errcode.RateLimit`，并带 `Retry-After: 1`。

| 范围 | 键 | rate / 容量 | 位置 |
|---|---|---|---|
| 全站默认（挂在中间件链上，含后台与 C 端已鉴权接口） | 客户端 IP | 100 / 150 | `gateway/main.go` |
| C 端认证入口 `/auth/phone-code`、`/auth/login/phone`、`/auth/weixin-login`、`/auth/refresh` | 客户端 IP | 10 / 30 | `cAuthLimiter` |
| 后台 `/auth/login`、`/auth/refresh` | 客户端 IP | 1 / 20 | `adminAuthLimiter` |
| C 端下单 `POST /orders` | 用户 ID | 0.08 / 5 | `UserRateLimitMiddleware`（须置于鉴权中间件之后） |

- **闲置桶淘汰**：桶按 key 存在内存 map 中，取桶时顺带扫描（无后台协程，与读写同一把锁）：闲置超过 30 分钟的桶被删除，两次扫描最少间隔 5 分钟。这是防「IP 维度桶随扫描源无限增长」的内存兜底——没有淘汰时，单个限流中间件的 map 可被分布式源 IP 打爆。
- **按账号的登录失败锁定**（后台，`gateway/handler/login_guard.go`）：Redis 键 `loginfail:{scene}:{account}`（计数，15 分钟窗口）与 `...:lock`（锁定期）。阈值 5 次失败/15 分钟；账号不存在与密码错误统一文案，防枚举账号；状态校验（禁用）置于密码校验之后，防泄露账号状态；锁定计数只在「凭证确实错误」时累加，user-service 故障/数据库故障按内部错误返回、不污染计数（否则服务抖机会把正常管理员连带锁在门外）。
  - Redis 不可达时**放行**（fail-open）：单次命令 1 秒超时，失败只记 `[WARN]`，登录继续走密码校验。该实现刻意直连 go-redis 而不用 jcbaseGo 的 `redis.New`——后者建实例时 Ping 失败会 panic，会把缓存抖动变成登录入口 500。运维口径见 `11-开发计划.md` 第 70 项。
  - C 端手机号登录不接入锁定（当前不校验验证码、任何号码恒成功，没有「失败」可计），试探只由上表的按 IP 限流兜底；键名预留了场景段，接入验证码后按 `loginScenePhone` 场景分开计数即可。

#### 多端登录策略

- 同一用户多端登录共享 token（微信小程序、支付宝小程序、H5、Android 使用同一账号）
- 通过 `union_id`（微信）或 `phone`（手机号）关联多端账号
- 首次支付宝登录时，若未绑定手机号，引导绑定手机号以关联微信端账号

#### 权限中间件（后台 = 权限点 RBAC，实时解析）

不存在 casbin 或 `permissions` / `role_permission` 关联表，模型是「角色 → 权限点编码列表（JSON 列）→ 员工在社区任职挂角色」三张表：`admin_roles`（`permissions` JSON 列；`community_id=0` 为全局内置角色，`>0` 为该社区私有角色，唯一键 `uk_role_community_code`）、`admin_users`（账号，含 `is_super`）、`admin_communities`（员工在某社区的任职行 + 该任职使用的角色）。

- **鉴权入口**：`gateway/middleware/auth.go` 校验签名、有效期、`token_use=access` 与 `type` 白名单，把 claims 注入请求上下文；`gateway/middleware/permission.go` 的 `RequirePermission(编码...)` 挂在每条后台路由上（具备其一即通过），`RequireCommunityAccess()` 全局 `Use` 校验社区语境。
- **权限不写在 token 里**：多社区模型下权限随「当前社区」变化，JWT 快照无法表达，故后台 token 的 `permissions` 恒为空，改为**逐请求实时解析**——网关经 `SetPermissionResolver` 注入 user 服务 `GetAdminContext(admin_id, community_id)`，服务端取该员工在此社区的任职角色权限并集。同一请求内在 gin context 记忆化（只解析一次），**服务端与网关均不做跨请求缓存**，因此改角色/权限后立即生效，代价是每请求一次 gRPC + 若干条 SQL。
- **超管判定**：看 `admin_users.is_super`（`AdminContextInfo.IsSuper` → 直接放行、权限解析短路）；claims 里的 `role` 字符串 `super_admin` 只是存量兼容与社区访问校验用（`RequireCommunityAccess` 判 `uc.Role == "super_admin"`）。
- **社区权限上限**：普通管理员的权限并集还要与内置 `community_admin` 角色的权限取交集，交集后仍残留的 `"*"` 通配一律展开为 `DefaultCommunityAdminPermissions`（不含 community/region/settings 等系统级权限点），防止社区管理员自建含 `"*"` 的角色后读写全局支付配置。`community_id=0`（无社区语境）时不做交集。
- **当前社区从哪来**：请求头 `X-Community-Id` 优先，缺省回退 JWT 的 `community_id`（登录时的默认社区）。`RequireCommunityAccess` 先查 claims 的 `community_ids` 快照，未命中再实时查任职（覆盖登录后被追加授权的社区），越权返回 403。
- **多社区隔离的两层落点**：网关层 = 上述 403 + handler 把社区 ID 写进 gRPC 请求；服务层 = 按请求里的 `community_id` 过滤数据。**C 端不采信该请求头**，一律以 JWT 的社区语境为准。
- 角色码语义（供理解 claims 的 `role`）：`super_admin` 超管（不限制社区）、`community_admin` 内置社区管理员（受上限约束）、`staff` 普通员工；实际可见范围由「任职社区 + 角色权限点」共同决定，而非由角色码硬编码。
