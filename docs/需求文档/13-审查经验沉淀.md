## 一、证伪条目速查（再命中同类疑点，先查这里，不要重新排查）

1. **`["*"]` 权限上限绕过系统级收窄 —— 误报。** `GetAdminContext` 在 `intersectPermissions` 之后还执行 `expandCommunityPermissions`，把残留的 `"*"` 展开为默认社区权限集（不含 `community/region/settings` 系统级码）；网关 `"*"` 放行分支对社区管理员不可达，仅作纵深保留。
2. **payment「SQLite 部署下幂等分支形同虚设」—— 前提不成立。** 全仓运行驱动是 MySQL，无 SQLite 部署形态；该疑点只剩「1062 裸子串泛匹配可误判非冲突错误」这一条（已改 `common/dberr` 精确判定）。
3. **client「秒杀按原价扣减造成资损」—— 不成立，实为误导展示。** `flashSalePriceEnabled = false`，下单按原价收款，前端展示价不进计价；真实缺陷是「宣称低价却按原价收钱」的展示口径（已修）。
4. **free_shipping nil 解引用 —— 当前不可达。** product 侧批量接口缺失即整体报错、不返回部分结果；定性为对称性防御缺口（已补齐）。
5. **admin 越权/XSS 类 —— 未发现实际越权。** 后端 `RequirePermission` 覆盖全部写接口、数据导入有超管双闸、富文本有服务端白名单。
6. **`sanitize.go` 两条疑似项（已判定）：** ① `writeContentNodes` 递归无深度上限——正文有 1MB 上限，全用 `<div>` 嵌套约 20 万层，远低于 Go 默认栈上限，**当前不可触发 fatal**，登记为观察项（未来放开内容上限时须同步复查）；② `safeContentURL` 放行 `/\evil.com`——清洗策略本就允许任意 http(s) 外链，该形态不越安全边界，仅注释级瑕疵，不修。

- P1#6 退款汇算句柄混用：真实风险是「读到事务提交前的旧快照」，而非账目错乱——退款行 `FOR UPDATE` 与订单行条件更新已挡住主要资损路径（已统一事务句柄根治）。
- P1#11 确认页重入：`u-button` 已绑 `:loading` 拦住连点，真实窗口是 `payOrder` 抛错后按钮恢复可点（已补显式守卫 + 成功即离页）。
- P1#4 `users.phone` 单列唯一：当时无触发路径（`wxLogin` 零调用点），属潜伏缺陷而非线上故障；已改 `*string` 提前消解。
- `grpc.NewClient` 是懒连接、本身不发起建连，真实风险在 RPC 调用无截止时间（已加缺省 15s deadline 拦截器）。

## 三、运维 / 上线口径

- **班次双开清理脚本已随 `migrations/` 目录删除**（确认各环境均为新库、无存量双开班次）。未来若接手带存量班的库：AutoMigrate 给存量行新增的唯一列一律填 NULL，历史数据不受新唯一索引约束，须先按 git 历史重建收敛脚本（保留同组 id 最大一条、其余置 `status=2` 并补 `active_flag=1`），别直接带存量上线——否则「StartShift 先查后拦」会让老操作员永久开不了工。
- **接口测试吞吐贴限流阈值**：全套接口用例单 IP 峰值实测 116~133 r/s，缺省阈值 100/150 会打出零星 429 表现为 flaky。本地 `docker-compose.yml` 已注入 2000/3000；不走 compose 直启进程跑测试需自设 `RATE_LIMIT_API_QPS/BURST`。
- **验证闸门口径**：`--reporter=line` 会覆盖配置里的 json reporter，完整性闸门将读到**陈旧报告**照常「通过」——验证必须跑默认 reporter 或显式带 json reporter，阅报告先核对 `stats.expected` 与实际用例数。

## 五、功能排查经验（2026-10-31 部分退款可见性修复）

用户报障「一笔订单部分退款成功后，C 端订单详情/售后 tab、POS 核销、后台订单列表均无售后痕迹」，全链路排查沉淀：

- **「服务端已回填、网关漏输出」是一类独立缺陷形态。** `fillRefundedAmounts` 在订单服务 ListOrders 里早已回填 `RefundedAmount`，但网关后台列表接口装配 `gin.H` 时漏掉了该键，前端 `hasPartialRefund` 逻辑写好了也永远是死代码。排查「前端为什么不显示」时必须先抓真实接口响应确认字段是否存在，不能只看前端代码下结论。
- **「状态不变、钱已部分退走」的字段必须在查询侧随身携带。** 部分退款完成后订单回到退款前状态（如已完成 5），任何只按 status 判定售后的展示（进度入口、售后标记、履约提示）都会漏。修复口径：列表/详情统一带 `refunded_amount`（money 口径），详情/履约商品行带行级 `refunded_quantity`（按 refunds.status=5 GROUP BY 汇算），展示层「保留原值 + 附加已退」而不是改写原值。
- **瞬态展示字段走 `gorm:"-"` 模型字段 + proto 转换层透出**，与 `Refund.OrderNo/Items/OrderItemCount` 既有模式一致；proto3 数字 0 经 JSON 序列化被 `omitempty` 省略，消费方一律按缺省=0 处理，文档接口契约必须写明。
- **多端共享查询口径要收敛到服务端单点**：`refundedQuantitiesByOrders` 一次 GROUP BY 覆盖订单集合，C 端详情、履约工作台（均经 GetOrder）与列表页共用，禁止各端各自汇算（口径漂移必然发生）。
- **C 端售后 tab 的语义纠偏**：按订单状态 7/8 过滤会让「部分退款后回到状态 5」的订单从售后入口消失；售后维度（refund 单）与订单维度（order 单）是两个实体，tab 语义应为售后单列表（`GET /orders/refunds`），点击跳转关联订单详情。
- **gin 同级静态路由与 `:id` 通配可共存**（`/orders/refunds` 与 `/orders/:id` 已有 `/orders/status-counts`、`/orders/frequent-products` 先例），静态优先匹配，注册顺序无实际影响但就近可读性优先。
