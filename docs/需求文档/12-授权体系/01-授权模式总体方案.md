# 授权模式总体方案（license-cloud）

> **状态：方案讨论稿（2026-10-24），代码未实施。** 本文档是授权体系的单一权威设计来源，涵盖商业模式、凭证设计、验证机制、注册流程、版本渠道、热更新联动与实施计划。后续实施以本文档为准，重大设计变更先改文档再改代码。

## 1. 背景与目标

market 从自用项目转型为授权销售的产品，需要一套体系解决三件事：

1. **管能不能用**：客户部署后必须获得授权才能使用，支持订阅（时间到期）与买断（版本封顶）两种并行模式；
2. **管能跑哪些版本**：客户只能运行为其授权的版本范围，支持内测 / 公测 / 分批正式发布，逐步放量；
3. **管客户是谁**：客户自助注册登记，后台可见全部客户与激活实例，支持续费、吊销、换机。

核心原则：**客户端只带验证能力，不带签发能力**；云服务掌握签发权，是唯一权威。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 云服务 | `license-cloud`，独立部署于国内 VPS 的授权服务，管理多个项目 |
| 项目（project） | 被授权的一个产品（market 是第一个），每项目独立密钥对、版本体系、配置 |
| License | 授权凭证，JWT 格式 + Ed25519 签名，客户持有的"许可证" |
| 实例（instance） | 客户的一套具体部署，首次启动生成随机实例 ID 落持久卷（Docker 重建不丢），激活时与 License 绑定；换机由云服务对账识别（见 6.5） |
| 档位（edition） | 功能分档。当前仅两档：`basic`（基础功能全开放）/ `pos`（含收银台） |
| 渠道（channel） | 版本发布通道：`internal`（内测）→ `beta`（公测）→ `stable`（正式） |
| 密钥环（keyring） | SDK 内置的多把公钥集合；按 License 的 `kid` 选用对应公钥验签，支撑密钥平滑轮换（见 5.3） |

## 3. 总体架构

```
┌─────────────────────────────┐         ┌──────────────────────────────┐
│  云服务 license-cloud        │         │  客户部署（每客户一套）        │
│  （国内 VPS，仅你部署一份）    │         │                              │
│                             │  签发   │  ┌────────────────────────┐  │
│  · 私钥签名（唯一签发权）     │ ─────→ │  │ SDK（编译进 gateway）    │  │
│  · 注册登记 / 激活 / 心跳     │  心跳   │  │ · 内置公钥（只验不签）   │  │
│  · 版本发布 + 渠道 + 灰度     │ ←───── │  │ · 本地验签 + 版本比对    │  │
│  · 吊销 / 续费 / 换机         │  版本   │  │ · 心跳协程               │  │
│  · 邮件通知（阿里云企业邮箱） │ ─────→ │  │ · 更新检测 + 缓存就绪    │  │
│  · 版本包中转存储             │  下载   │  │ · 门禁中间件             │  │
└─────────────────────────────┘ ─────→ │  └────────────────────────┘  │
                                        │  data/license/（持久化）      │
                                        └──────────────────────────────┘
```

三条铁律：

1. **公钥只进不出**：客户机器上只有验证能力。二进制被拆穿也造不出新 License；
2. **云服务是唯一权威**：能不能用、能装哪个版本，最终以云服务心跳返回为准（本地验签是离线兜底）；
3. **客户零 GitHub 依赖**：版本检测与下载全部直连云服务，GitHub token 不离开 CI 与云服务。

## 4. 商业模式模型

License 由两个正交维度组合，签发给不同客户用不同组合：

| 维度 | 取值 | 语义 |
|---|---|---|
| 类型（type） | `subscription` | 订阅制，`expires_at` 到期；到期进宽限期后停用 |
| | `perpetual` | 买断制，无到期时间；`version_policy.max_version` 封顶（如买断 1.x） |
| 档位（edition） | `basic` | 基础功能全开放（社区团购、商品、订单、会员等） |
| | `pos` | 含收银台（当前唯一增值功能，后续可扩展） |

组合示例：买断 1.x + pos 档 / 订阅一年 + basic 档 / 订阅一年 + pos 档。

版本策略（`version_policy`）三种模式：

| 模式 | 配置 | 适用 |
|---|---|---|
| `range` | `min_version` ~ `max_version` | 默认，如订阅期内全放行、买断封顶 1.99.99 |
| `list` | 精确版本列表 | 试点客户、定制版 |
| `prefix` | 允许的 major.minor 前缀列表 | 精细控制（允许 1.0.*、1.1.*） |

预发布版本（如 `1.1.0-rc1`）默认不放行，需显式加入策略。

## 5. License 凭证设计

License 为 JWT（Ed25519 签名，`alg=EdDSA`），claims：

| 字段 | 类型 | 说明 |
|---|---|---|
| `jti` | string | License 唯一编号（如 `LIC-7F3K9Q2M`） |
| `iss` | string | 云服务地址 |
| `sub` | string | 项目标识（`market`） |
| `kid` | string | 签名所用密钥对 ID（支持多公钥轮换） |
| `customer` | object | `{name, contact, phone, email, industry}` 注册时收集 |
| `type` | string | `subscription` / `perpetual` |
| `edition` | string | `basic` / `pos` |
| `features` | array | 具体功能开关（由 edition 展开，便于细调） |
| `version_policy` | object | 第 4 节的三种模式之一 |
| `instance_id` | string | 激活时绑定的实例 ID（未激活为空） |
| `iat` / `exp` | number | 签发时间 / 到期时间（买断无 exp） |

安全属性：私钥仅存云服务（文件权限 600 + 加密备份）；公钥集合编译期内置于 SDK。客户提取公钥无法伪造——这是非对称签名的根本保障。

### 5.1 三种"证书"的到期语义

授权体系里有三样东西容易被笼统叫作"证书"，到期语义完全不同：

| 东西 | 会到期吗 | 到期语义 | 处理 |
|---|---|---|---|
| License 凭证本体 | **会**（订阅制） | `exp` 到期是商务设计：进宽限期 → 停用（第 8 节状态机）；买断制无时间到期，但有 `version_policy` 版本封顶——大版本发布时买断证"功能性地到期" | 状态机 + 版本闸门，均已设计 |
| 签名密钥对（Ed25519） | **不会** | 非对称密钥没有 X.509 意义上的有效期；"到期"只发生在主动轮换时 | 轮换协议，见 5.3 |
| TLS 传输证书 | 会 | 云服务域名（Let's Encrypt 90 天自动续）；客户自己的域名属客户业务 | 自动化 / 客户自理，**与授权体系无关**——授权验证不依赖任何证书的在线状态 |

结论：**不存在"证书突然过期导致系统莫名其妙不能用"的失败模式**。唯一按时钟走的停止就是订阅到期，而这本来就是商业模式本身。

### 5.2 微信/支付宝平台证书迁移的借鉴

他们从"平台证书"迁到"公钥模式"的原因：平台证书是 X.509——自带有效期，商户必须定期下载证书清单、刷新序列号、处理新旧交替窗口，证书下载接口还成为硬依赖（接口一抖验签就停摆）；而对"确认对方身份"这个目的，PKI 证书链没有任何增益，信任本来就从首次安全下载建立。迁到裸公钥后：一个字符串，无到期、无序列号、无刷新逻辑。

我们的设计从一开始就是**裸 Ed25519 公钥**（无 X.509、无证书链、无在线下载），方向与他们迁移后一致。他们踩过坑才显出重要的两件事，我们直接补齐：

| 借鉴点 | 我们的设计 |
|---|---|
| 密钥必须有 ID | License claims 已带 `kid`，客户端按 `kid` 从**密钥环**选用对应公钥验签——没有 `kid` 就无法安全退役旧钥 |
| 轮换是协议，不是事件 | 三阶段协议见 5.3，把"换钥"从事故应急变成例行操作 |

另一个我们独有、他们没有的优势：**心跳遥测精确知道每个实例的 SDK 版本**（因而知道每个实例密钥环里有哪些公钥）——旧钥什么时候能退役，看数据说话，不用猜。

### 5.3 密钥轮换协议：播种 → 切换 → 退役

SDK 内置的是**密钥环**（多把公钥集合），不是单把。轮换的本质顺序：**新公钥先到达客户端 → 云服务才换签署钥 → 确认无人需要旧钥 → 才移除旧公钥**。

| 阶段 | 云服务动作 | 客户端行为 | 风险与兜底 |
|---|---|---|---|
| ① 播种 | 新 SDK 密钥环加入新公钥（旧公钥保留），随版本通道下发 | 装上新版的实例，密钥环有两把 | 零风险，纯增量 |
| ② 切换 | 新签发的 License 改用新私钥签 | 新证带新 `kid`，密钥环含新公钥的实例正常验签 | 唯一风险="老 SDK 激活新证"验签失败。兜底：云服务 DB 存 License 权威记录，可按心跳上报的 SDK 版本**用旧钥自动重签同一份 License**——重签零成本，轮换因此近乎无感 |
| ③ 退役 | 心跳确认无活跃实例还需要旧钥 → 后续 SDK 版本移除旧公钥 | 不影响任何人（存量老证已在本地点验；续期时自然重签为新钥） | — |

**私钥泄露响应**（微信/支付宝靠 CRL/OCSP 撤销列表，我们没有 PKI 基础设施，用注册表兜底）：

1. 立即压缩执行阶段 ①②，切换到新钥；
2. 伪造的 License 签名本身无法与真证区分——但云服务 `licenses` 表记录着**实际签发过的每一个 `jti`**，心跳上报的 `jti` 不在表中即判定伪造 → 实例标红 + 吊销；
3. 诚实边界：这仍是"发现后处置"（与 6.5.6 拷贝 `data/` 同类），签名机制的作用是让伪造**可发现、可吊销**，而不是泄露后瞬间免疫。

**例行轮换**：借鉴其"密钥轮换是日常卫生而非事故响应"的终态，建议每 2 年或大版本边界主动轮换一次——协议成熟后这是无感操作。

## 6. 客户生命周期与注册激活流程

### 6.1 全新部署引导注册（替代 env 配置）

客户首次打开管理后台，SDK 检测到无 License、无试用记录时，进入**引导注册页**（全屏向导，两步，不进系统）：

**第一步：邮箱验证**（仅支持 QQ 邮箱）

| 字段 | 必填 | 说明 |
|---|---|---|
| 邮箱 | 是 | **仅支持 QQ 邮箱（@qq.com）**，前端+云服务双重校验 |

点「发送验证码」→ 云服务发 6 位数字验证码到该 QQ 邮箱 → 客户输入。

**第二步：补全信息**

| 字段 | 必填 | 说明 |
|---|---|---|
| 邮箱验证码 | 是 | 第一步收到的一次性验证码 |
| 企业 / 店铺名称 | 是 | |
| 联系人 | 是 | |
| 手机号 | 是 | 频率限制防刷（暂不接短信验证码） |
| 邮箱 | 是 | 自动带填（**即通知邮箱**，授权到期、异常、更新通知都发这里） |
| 业态 | 否 | 社区团购 / 便利店 / 生鲜 / 其他 |
| 来源渠道 | 否 | 客户从哪了解产品 |
| 同意服务条款 | 是 | |

提交后 SDK 调云服务 `POST /register`：创建 customer 记录 + 自动创建试用 License（绑定实例 ID）+ 下发凭证。**注册即试用，全程网页完成，客户不碰任何配置文件。**

> QQ 邮箱限制的影响：无 QQ 邮箱的客户由卖方在云后台手动创建账号。选 QQ 邮箱的原因：目标客群（社区商超经营者）覆盖率高、验证码送达率好。

### 6.4 注册验证码机制

| 项 | 设计 |
|---|---|
| 格式 | 6 位数字，Redis 存储（`reg:code:<email>`），TTL 5 分钟 |
| 发送限频 | 同邮箱 60 秒 1 封；同 IP 每天 10 封；同实例每天 3 封 |
| 错误锁定 | 连续错 5 次作废当前验证码，需重新发送 |
| 已注册邮箱 | 提示「该邮箱已注册，请直接激活或联系卖方」（自助场景友好性优先于防枚举） |
| 送达风险 | 阿里云企业邮箱发往 qq.com，新域名可能进垃圾箱；邮件模板注明「请查看垃圾箱」，并在卖方失联告警中附带注册失败原因 |

### 6.2 试用转正

1. 云后台可见全部注册客户（含联系方式、激活实例、试用剩余天数）；
2. 联系转化后，后台签发正式 License，Key 发送到客户注册邮箱；
3. 客户在「授权管理」页输入 Key → 云服务激活绑定 → 覆盖试用凭证，进入正式授权；
4. 试用期数据完整保留，转正无感。

### 6.3 离线降级

云服务不可达时允许先本地试用（`trial_require_activation=false` 默认），后台常驻提示"联网完成注册"；配为 `true` 时试用也需联网登记一次，防止删库重装白嫖。

### 6.5 实例绑定：Docker 部署与镜像分发场景

客户用 Docker 部署时有两个天然疑问：**重新构建会不会掉授权？镜像打包分发会不会把授权带飞？** 本节把机制一次说清。

#### 6.5.1 授权数据住在哪：持久卷，不进镜像

| 文件 | 位置 | 说明 |
|---|---|---|
| `license.key` | `data/license/`（卷） | 正式凭证；Dockerfile **不 COPY 任何授权文件** |
| `instance.json` | `data/license/`（卷） | 实例 ID + 生成时间 |
| `trial.json` | `data/license/`（卷） | 试用记录（安装时间 + 实例 ID） |

`LICENSE_DATA_DIR` 默认 `/app/data/license`——**复用现有 data 持久卷，不新增卷**；客户备份 `data/` 目录即自动含授权，备份策略统一。

#### 6.5.2 重新构建不会掉授权（Docker 铁律）

授权在卷里、镜像里没有授权文件，因此一切"只动镜像不动卷"的操作都安全：

| 客户操作 | 授权 | 说明 |
|---|---|---|
| `docker compose build` / `docker build` 重建镜像 | 不掉 | 卷不动，只换镜像 |
| `up -d --force-recreate` 重建容器 | 不掉 | 同上（热更"本地拼镜像"正依赖此性质） |
| `docker compose down` → `up`（不带 `-v`） | 不掉 | 卷保留 |
| 热更新安装 / 回滚 | 不掉 | 同上 |
| `docker compose down -v` / `docker volume prune` | **掉** | `-v` 连卷删除；需重新激活或恢复备份 |
| 手动删 `data/license`、备份漏拷 data | **掉** | 同上 |

运维纪律（写进部署文档）：**备份 = 拷整个 `data/`；清理 = 永远不对 data 卷用 `-v`**。

#### 6.5.3 镜像分发带不走授权

| 分发方式 | 授权是否外泄 | 机制 |
|---|---|---|
| `docker save` 导出镜像分享 | 否 | save 只含镜像层，**volume 内容永远不在镜像里** |
| `docker commit` 运行中容器成镜像 | 否 | commit 明确排除挂载的卷；data 是挂载的所以带不走 |
| 只拷 `license.key`（漏了 instance.json） | 否 | 新机器生成新实例 ID → 激活走槽位制：有槽则正常占用（正当扩容），满槽则拒绝（见 6.5.5） |
| 连 `data/` 整个打包搬走 | **是（可检测）** | 同一实例 ID 双机运行 → 云服务对账发现 → 告警/宽限/吊销（策略可配） |
| 朋友拿干净镜像全新部署 | 否（新试用） | 无证无实例 → 走注册 → 30 天试用，登记在案 |

#### 6.5.4 实例 ID：随机 UUID，不绑机器指纹

首次启动生成随机 UUID 写入 `instance.json`，激活时写入 License 并重新签名。**刻意不用机器指纹**（machine-id / MAC / CPU ID）：Docker 容器每次重建 `/etc/machine-id` 都会变，网卡 MAC 也不稳定——用指纹等于"热更一次授权抖一次"，还会误伤服务器迁移、重装、IP 变动的正经客户。UUID 落卷与容器生命周期解耦，检测交给云服务对账。

#### 6.5.5 多实例分级处置：先分性质，再定动作

关键认知：**"同一授权多处启动"分两种性质，走两条通道，处置完全不同**——正当扩容（多门店）要放行，拷贝分发要拦住，一刀切就会误伤正经客户。

**通道一（正当）：实例槽位制 `max_instances`**

| 项 | 规则 |
|---|---|
| 默认槽位 | 1（单店客户）；多门店客户签发时给 N，后台随时可扩容/缩容 |
| 占槽 | 每激活一个实例 ID 占一个槽；授权管理页可见"已用 x/N" |
| 满槽激活 | 拒绝 + 邮件通知双方（"授权支持 N 个实例，已用完"）+ 后台收到扩容申请，卖方一键扩容即转正当 |
| 槽位回收 | 实例 30 天无心跳自动回收（提前 3 天邮件通知）；关店/淘汰机器的自然清理，避免换一次店永久少一槽 |
| 客户可见 | 授权管理页展示本证全部实例清单（域名/位置/脱敏 IP/版本/渠道/部署形态/最后心跳）——客户能自查"这台我没见过的机器"，卖方省一半客服 |

**通道二（越权）：三层对账，默认只告警**

| 层 | 规则 | 默认处置 | 可选升级 |
|---|---|---|---|
| 满槽激活 | 第 N+1 个实例激活 | 拒绝 + 通知双方 | 卖方一键扩容（转正当） |
| 双活检测 | 同一实例 ID 最近 2 次心跳源 IP 不同且间隔 < 1.5×周期；或 24h 内 ≥3 个源 IP（阈值可配，给家用宽带动态 IP 留余量）；**集群/主备场景经部署形态标注 + 节点 IP 池豁免**（6.5.9） | 告警（邮件卖方 + 后台标红） | `soft_block`：仅新 IP 侧导"授权校验中"页（旧 IP 服务不断）；`revoke`：吊销整证 |
| 注册密度 | 同 IP 段短时间大量新注册/新试用 | 告警 | 拒绝新注册 |

**为什么默认只告警、不自动拦**：误报场景真实存在——客户主备 HA 共享实例 ID、迁移前后新旧机器重叠跑、家用宽带 NAT 出口漂移。自动吊销=误伤+客诉，对 SOHO 客群，人工看一眼后台的成本远低于误杀损失。`soft_block` 是折中：只影响"突然出现的那台"，原 IP 服务不断，谁在跑、谁是拷贝，一目了然。

**双活 vs 迁移的甄别**：

| 形态 | 特征 | 处置 |
|---|---|---|
| 迁移（正经） | 旧 IP 停跳、新 IP 接管同一实例 ID | 自动接受：记录 + 通知卖方；旧 IP 停跳超 7 天自动转 `migrated`、告警消逸（IP 变更全流程见 6.5.9） |
| 双活（可疑） | 两个 IP 在同一时间窗内交替/同时心跳 | 进入通道二分级处置 |

**激活被拒时的提示**（客户体验，减少工单）："此授权已绑定 N/N 个实例。如需在新服务器部署：请停用原实例释放槽位，或联系卖方扩容。"

**卖方后台动作**：实例清单上可一键 确认迁移 / 释放槽位 / 扩容 / 吊销，全部写审计日志。

#### 6.5.6 边界（如实）

- 拷贝 `data/` = 复制凭证，对账是"发现后处置"，不是瞬间技术阻断；一次性搬运（拷 `data/` 到新机后关停旧机）形态上等同于"迁移"会被自动接受，靠迁移通知 + 事后处置接住（6.5.9）；
- 镜像分享白嫖的是新试用而非正式授权，每次试用登记在案；同 IP 段密度阈值可缓刷但拦不住多 QQ 邮箱，属商务边界；
- 客户改 compose 把 data 卷去掉、授权落进容器层 → commit/save 才可能带授权——属客户自行破坏部署约定，文档提醒；
- `soft_block` 只影响"突然出现的 IP 侧"，拦不住两台机器轮流用同一实例 ID 交替上线的时间差攻击（间隔 > 判定窗即漏检）——提高敏感度靠调阈值，属成本权衡。

#### 6.5.7 站点域名采集：自动带、只展示、不绑定

| 项 | 设计 |
|---|---|
| 采集方式 | 心跳自动上报 `base_url`（gateway 从站点配置 / 请求 Host 推断），**客户零输入**；授权页可手动补充正式域名（自动值可能是内网 IP） |
| 存储 | `instances.domain`（可空），变化时更新并留变更记录 |
| 用途 | ① 后台实例清单标识"哪台机器是哪个店"（比脱敏 IP 直观）② 远程支持排障（客户说"我店挂了"，一看域名即知是哪台）③ 弱风控标记（同域名出现在多实例、30 天内域名变更 >3 次）——仅后台标记，不阻断 |
| 明确不做 | **不绑定授权**：客户换域名、加 CDN、多入口域名（admin / h5 / api 分域）是正当权利，一绑定就误伤；**不做域名归属验证**（DNS TXT / 文件验证流程重，自部署场景无意义） |
| 边界 | 域名非授权锚点：换域名、域名漂移、解析故障一律不影响授权状态与对账判定 |

#### 6.5.8 集群/负载均衡部署（一套部署多副本）

客户把一套部署扩成多副本 + LB（gateway 多副本 + Nginx/SLB，或 k8s replicas>1）是私有部署常见形态。设计原则一句话：**实例 = 逻辑部署，不是一个进程。**

| 项 | 设计 |
|---|---|
| 实例 ID 共享 | 多副本挂同一份 `data/license`（共享存储/NAS/volume）；`instance.json` 按"原子创建、先到先得"生成，后启动的副本直接复用——**一套集群无论几个副本只占 1 个槽位**（商务语义正确：客户买的是一套） |
| 验签 | 每个副本独立本地验签（纯本地、零协调成本），门禁中间件每副本都挂——任何副本都可能接到业务请求，不能只拦 leader |
| 心跳 leader 选举 | 只有 leader 副本上报心跳：复用现有 Redis（`SET instance:leader:<id> NX EX 30`，10s 续租），非 leader 静默——避免 N 个副本发 N 份心跳、频率语义混乱 |
| 更新检测/下载 | 同样只 leader 做；`data/updates` 共享，leader 下载完写就绪标记，任意副本/后台均可发起安装 |
| 防误伤 | 心跳带 `leader_failover` 标记；云服务为每个实例维护**已知节点 IP 池**（形态标注 + 手工录入 + 有界 auto-learn，完整设计见 6.5.9），池内 IP 变化（leader 漂移、副本扩缩）记录不告警——LB 集群不会触发双活检测（6.5.5） |
| 主备容灾 | 按同集群处理：备机平时不心跳或作为池内成员；主备切换时 IP 变化走"池内/迁移"逻辑，后台可一键确认 |

**为什么不每副本一个实例 ID**：那客户扩 3 个副本就要 3 个槽位，"我就一套为什么占 3 个"必然产生商务纠纷；且 3 份心跳源 IP 不同会直接踩爆双活检测，误判成分发。

#### 6.5.9 部署形态标注与节点 IP 池：手工录入，按形态定报警

自动检测"这是不是集群"有先天缺陷：**第一份来自第二个 IP 的心跳，本身就是双活告警的触发时刻**——等云服务"学会"这是集群，报警已经发出去了。正确姿势是**手工标注 + 预先录入节点 IP**，把误报消灭在发生之前。

**一、部署形态：三态，手工标注**

| 形态 | 值 | 含义 |
|---|---|---|
| 单机 | `single` | 一套部署一个节点（默认） |
| 集群/负载均衡 | `cluster` | 多副本 + LB，节点 IP 会变（leader 漂移/扩缩容） |
| 主备容灾 | `ha` | 主机 + 备机，平时只有一台在跳 |

三个设置入口（任选，后设覆盖先设）：

| 入口 | 时机 | 说明 |
|---|---|---|
| 激活时客户自报 | 首次激活页 | 增加一步"部署形态"（默认单机）；选集群可展开填节点 IP（可跳过，卖方后补）——**集群客户从第一天起就不误报** |
| 卖方后台改 | 任何时候 | 客户说"我们上了 LB/Nginx"之后，实例详情页一键改形态 |
| 云服务自动建议 | 观察 7 天 | 实例持续多 IP 心跳但形态仍为 single → 后台徽标"疑似集群，待确认"——只提示、不改态 |

**二、节点 IP 池：录进去就静默**

`instance_nodes` 表，每个实例一张池：

| 规则 | 设计 |
|---|---|
| 手工录入 | 卖方后台逐条加：单个 IP 或 **CIDR 段**（云上集群多为同 VPC 段，一条段覆盖全部节点）+ 节点命名（"节点1-北京"、"备机"） |
| 激活自带 | 客户激活时填的节点 IP 自动入池（来源标记 `activation`） |
| 自动学习 auto-learn | `cluster` 形态默认开，但**有界**：新 IP 落在已录入的 CIDR 段内（无段则同 /24）才自动入池 + 发通知卖方；段外新 IP 一律告警——防止拷贝者的 IP 悄悄混进池子 |
| `single` 形态 | 不开 auto-learn（单机出现第二个 IP 就应该告警） |
| 管理权 | 池的增删只在卖方后台；客户授权页**只读可见**自己的节点清单——防攻击者自己往池里加白名单 |

**三、按形态的报警矩阵（核心）**

| 观测到的事件 | 单机 | 集群/主备·IP 在池内 | 集群/主备·池外新 IP |
|---|---|---|---|
| 相邻两次心跳 IP 不同 | 记录 + 通知卖方（不拦、不标红） | **静默**（leader 漂移/节点轮换属正常） | 段内 → 自动入池 + 通知；段外 → 告警 |
| 一个心跳周期内两个 IP 交替 | **双活告警**（拷贝 signature） | 静默（多节点轮流上报） | 涉及池外 IP → 双活告警 |
| 旧 IP 停跳 ≥7 天、新 IP 接管 | 迁移记录，告警消逸 | 同左 | 同左 |

**四、IP 变更不需要联系我们解绑——IP 不是锚点，实例 ID 才是**

客户换 IP（云厂商重新分配、服务器迁移、宽带变动）是高频正当操作，**默认全自动接受**：

| 场景 | 默认动作 |
|---|---|
| 实例 ID 不变、IP 变了 | 自动接受；记录 IP 变更事件 + 通知卖方（知会性质，不是待办事项） |
| 整机更换（新机器 = 新实例 ID） | 走激活流程占一个新槽位——**这种情况才需要联系我们**（扩容/换机），但也不是"解绑 IP" |
| 同一实例 ID 两个 IP 同期交替心跳 | 双活告警（拷贝 signature，见上方矩阵） |

可选 **`strict_ip` 严格模式**（按实例开，默认关）：任何新 IP 先挂起待卖方确认（批准才入池；拒绝则 `soft_block` 该 IP 侧）。用于：高价值客户主动要求 IP 钉死，或已疑似滥用进入排查期。开启前明确告知客户"今后换 IP 需联系卖方"——选择权交给客户，不默认施加。

**一条如实边界**：客户把 `data/` 整套拷到新机器并关停旧机——旧 IP 停跳、新 IP 接管同一实例 ID，形态上就是"迁移"，会被自动接受。这类一次性搬运只能靠"迁移通知 + 事后处置"接住（收到通知发现客户没提过要搬机器，就去查），技术上无法与真迁移区分，已并入 6.5.6 边界。

### 6.6 一个客户多张证：叠加组合与多套部署

同一 customer 多张 License 有两种形态，机制不同，先区分：

| 形态 | 场景 | 机制 |
|---|---|---|
| **叠加组合** | 一套部署上同时用多张证（基础授权 + 收银台增值包） | 组合三规则（本节下文） |
| **多套部署** | 一个客户买多套，分别部署在不同位置（多家门店各跑一套） | 槽位制 + customer 维度配套（6.6.1） |

**叠加组合规则三条**：

| 维度 | 规则 | 理由 |
|---|---|---|
| **版本策略** | **交集**（所有证的交集，取最严格） | 防止用一张宽泛的证绕过另一张严格证的商务意图（如试点证只放行 1.0.1） |
| **功能档位** | **并集**（任一证开放即有权使用） | 客户买第二张 pos 证就是为了开收银台；订阅证到期只停它覆盖的功能，不影响买断证的基础功能 |
| **到期状态** | **每张证独立走自己的状态机**，门禁按 feature 粒度判定 | 请求涉及功能 X 时：存在"开放 X 且当前有效"的证即放行； pos 订阅到期 = 收银台停用、基础功能（另一张买断证）照常 |

**实例绑定改为 N:N**：一个实例可绑多张证（一套部署同时用 basic+pos），一张证也可绑多个实例（槽位）。`instances` 与 `licenses` 之间经 `instance_licenses` 关联表多对多，每对独立状态（active/migrated/reclaimed）并各占一个槽位——精细到"每个店有没有收银台"。

**一次心跳全量搞定**：心跳上报实例 ID，云服务返回其全部关联证的组合结果（版本交集 + 功能并集 + 各证到期时间），客户端零额外请求。

**激活与展示**：

- 凭证存储 `data/license/licenses/` 目录多 `*.key` 文件，逐张独立验签；激活任一张正式证即终结试用（6.2 覆盖语义保留）；
- 授权页"添加授权"追加第二张 key（云服务校验同 customer/同 project/有槽位后生效）；移除某证需二次确认（功能会收缩）；
- 授权页卡片列表逐张展示（类型/档位/覆盖功能/到期/版本范围/状态）+ 汇总行"组合生效：版本取交集、功能取并集"；
- 卖方后台签发界面支持"给已有客户追加授权"；签发时若与客户已有证**版本交集为空**（basic 允许 1.x + pos 允许 2.x）→ 弹警告"该组合将导致无可用版本"，防止签出死组合（真出现了则部署 blocked，提示授权冲突联系卖方）。

#### 6.6.1 多套部署（一处客户多处门店）配套

槽位制本体已覆盖：客户签 1 张 N 槽证，或 N 张单店证，各店部署各激活各的，**互不干扰**（本地验签自己的证；双活检测按实例 ID 隔离，N 家店是 N 个不同实例 ID，不会被误判为分发）。补三处运营配套：

| 配套 | 设计 |
|---|---|
| **实例命名** | 激活时允许给实例起名（"海淀店"，可选，默认用自动采集的域名）；后台实例清单与客户总览显示——比域名更直白 |
| **客户总览页** | 任何一套部署的授权页可查"我名下全部部署"（customer 维度：每店的到期/版本/在线状态）——解决 5 家店 5 套系统散落各处没人盯；授权状态非经营数据，可见性由 `customer.overview_visible` 开关控制（默认开，店主可关） |
| **批量运营** | 卖方后台按 customer 批量续期（勾选该客户全部证统一延长到期）；签发新证时默认带出该客户已有证的版本策略——保证同客户各店版本范围一致，配合 10.2 的 customer 级灰度，实现"同客户同进同退" |

### 6.7 自助购买与续费（云服务托管页 + 内嵌客户端）

卖方在云后台按项目配置**收费方案**，客户在自己系统的授权页点「购买 / 续费 / 升级」，打开**云服务托管的网页**自助完成——不联系卖方、不碰任何配置文件。托管页同时服务三个转化场景：试用转正、到期续费、档位升级。

**一、收费方案配置（云后台，按项目）**

| 字段 | 说明 |
|---|---|
| 方案名 | 如「订阅 basic 一年」「买断 1.x + pos」 |
| 类型/档位/时长 | subscription 或 perpetual；basic/pos；时长（买断无时长） |
| 价格 | 人民币（`price_cents` + `currency=CNY`）；支持**续费优惠价**（`renewal_price_cents`，老客户专享） |
| 含实例槽位 | 方案默认 `max_instances`（升级方案可带更多槽，配合 6.5.5 槽位制） |
| 状态/排序 | 上架/下架、展示顺序 |

方案即第 4 节两个正交维度的实例化——后台能配出什么组合，客户就能买什么组合。

**二、客户端入口与嵌入方式**

| 项 | 设计 |
|---|---|
| 入口 | 授权页（关于页授权卡片）「购买 / 续费 / 升级」按钮；试用到期引导页、grace 拦截页也挂同一链接——**一个托管页收敛所有转化入口** |
| 取链接 | SDK 调 `POST /api/v1/renewal/token`（实例令牌）→ 云服务签发**续费令牌**（短时效 JWT：绑定 instance + customer + project + 回跳 origin）→ 返回托管页 URL |
| 嵌入方式 | **iframe 内嵌**（默认）：云服务按令牌内 origin 动态回 `Content-Security-Policy: frame-ancestors`，兼容客户多域名/IP 访问形态（6.5.7）；**支付环节破框**：微信/支付宝 H5 网关禁嵌套，托管页检测到网关支付时 `top.location` 跳出到顶层（人工转账模式无此限制，可全程 iframe） |
| 为什么不是纯新窗口 | 内嵌保留"还在自己系统里"的体验；破框只发生在必须网关支付的阶段，见上 |

**三、下单与支付（两模式，默认人工）**

| 模式 | 流程 | 适用 |
|---|---|---|
| **人工转账（默认，立即可用）** | 托管页按方案创建订单 → 展示卖方收款账号（银行/支付宝，云后台按项目配置，**仅下单后可见**）→ 客户转账 → 点「我已支付」（可上传转账截图）→ 订单转 `pending_confirm` → 邮件通知卖方 → 卖方后台核对确认 | 无商户号的个人/早期阶段 |
| **网关支付（Phase B）** | 托管页调起微信 Native/JSAPI 或支付宝 → 客户扫码 → 网关回调云服务 → 自动确认开通 | 有企业商户号后按项目开启 |

订单规则：`order_no` 唯一；**金额以下单时方案价为准**，卖方确认时若方案已改价 → 订单标红需人工核对（防扯皮）；`pending` 订单超时可配自动取消（人工模式建议 24h，转账可能慢）；重复提交幂等（同实例同方案进行中订单直接复用）。

**四、确认后自动开通（客户无感）**

1. 卖方确认（或网关回调）→ 云服务按方案**重签 / 延期 License**：订阅从 `max(now, exp)` 起算（不吞剩余时间）；升级 = 按新方案重签；加购第二档走 6.6 组合授权；
2. 把该实例心跳**临时调到 1 分钟**（复用 7.1 单客户端调频）——续费生效最快 1 分钟内，一小时后自动恢复默认频率；
3. 心跳响应携带最新签发的 License（按 `jti`+`iat` 比对），客户端**原子覆盖本地 `licenses/*.key`**——客户零操作；
4. 邮件通知客户「已续费至 X 年 X 月 X 日」；托管页轮询订单状态，展示「已开通」+ 新到期日，授权卡片同步刷新。

**五、边界（如实）**

- 人工模式的对账靠卖方核对，做不到全自动——这是无商户号阶段的既定取舍，网关支付是纯增量；
- 托管页在云服务域名下，客户浏览器直连；页面不持有 License 密钥，令牌短时效 + 单用途 + 绑定实例；
- 价格以云后台实时配置为准，客户端不缓存价格（避免展示与实际不符）；
- 退款/发票 Phase C，卖方线下处理；
- 托管页本身不需要客户登录——续费令牌即身份（magic link 语义）。

### 6.8 授权掉了怎么办：先分诊，再重新激活

客户说"授权掉了"至少对应五种原因，恢复路径完全不同。授权页按现象给对应指引，不让客户猜：

| 客户看到的现象 | 实际原因 | 恢复路径 |
|---|---|---|
| 陌生的"未授权/请激活"页 | `data/license` 真丢了（`down -v`、手删、备份漏拷 `data/`、搬服务器没带过来） | 重新激活（本节） |
| 红条"授权异常，X 天后停用" | 到期 / 被吊销 / 网络问题心跳失联进宽限期 | 续费（6.7）或等网络恢复；刚续费/卖方刚处理完 → 点「立即同步」不等心跳 |
| "授权校验中"页 | 双活 `soft_block`：另一台机器在用同一实例 ID | 停掉另一台即恢复 |
| 新版本装不上 | 版本超出授权范围 | 升级授权（6.7）或回退版本 |
| —— | 整机搬服务器（正常诉求，非故障） | 带走 `data/`；没带就重新激活占新槽（6.5.9） |

**一、重新激活（文件真丢了）**

前提：门禁放行登录与授权页，客户管理员能自救（第 7 节设计）。

| 情形 | 流程 |
|---|---|
| **密钥还在**（授权页截图、购买邮件） | 授权页输入 Key → 云服务校验 → **老实例已静默超期**（默认 7 天无心跳，或槽位已被回收）→ 自动释放旧绑定、重绑当前实例，邮件通知双方；**老实例还在心跳** → 激活拒绝 + 通知卖方（防盗用），客户找卖方「确认换机」后一键释放重绑 |
| **密钥没了** | ① 翻购买/续费邮件——里面带**一键激活链接**，点了就激活（最优自愈路径，多数情况不用找卖方）；② 卖方后台「重发密钥/激活链接」到客户注册邮箱 |
| **试用期丢了**（没买过正版） | 重新注册走试用；同 QQ 邮箱会被云服务识别"已试用过"（试用登记在案）→ 引导购买或联系卖方补登，防删库重装反复白嫖 |

激活安全：接口限流 + 连续错误锁定（复用注册验证码机制）；激活成功即写入 `licenses/` + `instance.json`，系统完全恢复——**重绑不重置任何时间**，剩余有效期原样保留。

**二、卖方后台恢复动作**

| 动作 | 用途 |
|---|---|
| 重发密钥 / 激活链接 | 客户密钥丢失（邮件送达注册邮箱） |
| 确认换机 / 释放槽位 | 老实例仍在跳、但客户确实搬了机器 |
| 试用补登 / 延期 | 误删 `data/` 的试用客户挽回 |
| 重新签发（换 `jti`） | 证内容要大幅修改（档位/版本策略变化），重签比逐个解释省事 |

**三、根治：把"掉"的概率和损失降到底**

- 备份纪律照旧——**备份 = 拷整个 `data/`，清理永远别对 data 卷用 `-v`**（授权页常驻提示 + 购买/续费邮件带一句）；
- 授权页常显 **实例 ID + 授权密钥**（一键复制）——客户截图或存进密码管理器，重装即恢复；
- 邮件自带一键激活链接——密钥丢失也能自愈；
- 「立即同步」按钮——续费成功或卖方刚处理完，客户点一下立刻心跳 + 换发凭证，不用干等一个心跳周期。

### 6.9 帮助中心：异常页的自助入口

客户遇到异常页时，页面上应有「查看帮助」——点一下直达这个异常的解法。FAQ 托管在云服务、免登录、按场景自动定位，内容与 6.8 分诊表同源。

**一、入口清单（全异常场景挂帮助链接）**

| 异常页 / 横幅 | 场景标识 `scene` | 对应 FAQ 条目（= 6.8 分诊表行） |
|---|---|---|
| 未授权 / 请激活页（gateway 门禁导流） | `license_lost` | 重新激活 |
| 红条「授权异常，X 天后将停止服务」 | `grace` | 到期 / 吊销 / 心跳失联怎么处理 |
| 「授权校验中」页（soft_block） | `soft_block` | 双活：另一台机器在用同一实例 ID |
| 新版本装不上 / 启动 blocked | `version_blocked` | 版本超出授权范围 |
| 激活被拒（满槽 / 已绑其他实例 / 已注册） | `activate_rejected` | 激活失败怎么办 |
| 心跳失联提示 | `offline` | 网络问题自查 |
| 试用到期横幅 | `trial_expiring` | 试用转正 |

**二、托管位置与鉴权：云服务、免登录**

- 与续费托管页同源同理：内容随时改、集中维护、客户端零缓存——改错即改，全员即时生效；
- **关键差异：FAQ 不需要任何令牌**。真丢了凭证的客户连实例令牌都没有（`license_lost` 场景），公开可访问是硬要求；
- 公开页 = 可被爬 → 加频率限制；内容不含任何客户数据、签发表、价格细节（价格只在续费页出现）；
- 客户端只配一个 `LICENSE_HELP_BASE_URL`（默认云服务地址），SDK 在各异常页统一拼 `?scene=xxx`。

**三、上下文传递：不问客户选**

异常页把场景标识写进 URL 参数，FAQ 页打开后**自动滚动 + 高亮对应条目并展开处理步骤**——客户点「查看帮助」看到的就是自己这个问题的解法，不用从目录里翻。

**四、内容组织：与 6.8 分诊表同源**

每条目统一四段：**现象**（页面原文 / 截图）→ **原因**（人话版）→ **自助步骤**（编号列表）→ **仍不行 → 联系支持**。FAQ 目录就是分诊表的镜像——一份内容两处呈现：授权页内嵌摘要 + 云服务全文。

**五、个性化层（有令牌时增强）**

红条 / soft_block / 版本超限等令牌仍有效的场景，带令牌打开 FAQ 页时顶部显示**「您的授权状态」实时卡片**（到期日 / 心跳状态 / 实例 ID）+ 定制化建议；无令牌（`license_lost`）只显示公开内容。同一套条目，两层展示。

**六、联系支持（轻量表单）**

FAQ 页底部「提交问题」：问题描述 + 联系方式 +（有令牌时**自动附带**实例 ID / 版本 / 心跳状态）→ 云服务建 `support_tickets` 记录 → 邮件通知卖方 + 后台待办列表。把「客户找卖方」路径产品化：卖方收到的每个求助都自带排障信息，不用来回问。状态仅 `pending` / `resolved` 两态——不是工单系统，复杂售后走线下。

**七、卖方管理**

按项目隔离；条目 CRUD / 排序 / 上下架；Markdown 编辑；修改历史。FAQ 是运营资产，更新不进客户端版本。

**八、通知邮件统一带链接**

第 8.2 节全部发给客户的邮件，统一带「查看帮助」链接指向对应条目——客户在邮箱里也能自助，不用回电脑前登录。

**边界（如实）**：FAQ 是建议性质文案，不做能力承诺（如「保证 X 分钟恢复」）；公开页加爬虫限频；支持表单不是 SLA 入口，响应时效靠卖方自律。

## 7. 三道验证关卡

| 时机 | 动作 | 断网时 |
|---|---|---|
| **启动时**（硬） | SDK 读全部 License → 逐张验签 → 组合版本取交集 → 实例绑定（N:N） | 照常启动（纯本地） |
| **运行中**（软） | 心跳上报实例 ID + 当前版本，返回：授权状态 + 最新版本策略 + 公告 + **可用更新列表** + 下次心跳频率 + **最新签发的 License**（续费/升级后按 `jti`+`iat` 比对原子换发本地凭证，见 6.7） | 进入宽限期（见第 8 节） |
| **安装前**（闸门） | 装新版本前再问一次云服务：放行吗（防发布后收回） | 默认放行 + 警告（可配严格） |

心跳是远程控制的通道：吊销、续期恢复、版本策略收紧，都在下一次心跳后生效（最迟一个心跳周期）。

### 7.1 心跳频率：云服务权威下发，可指定单个客户端

客户端配置的间隔只是「期望值」，**生效频率以云服务响应为准**：

| 项 | 规则 |
|---|---|
| 默认频率 | 6 小时（项目级默认） |
| 可调范围 | 1 分钟 ~ 项目上限 |
| 三级覆盖 | **实例 > 客户 > 项目**：可改项目默认、改单个客户（作用于其全部实例）、改单个实例（只作用于这一台） |
| 下限拒绝 | 客户端请求间隔 **短于 1 分钟**（如 30 秒）→ 云服务返回 429 + 正确频率，客户端按响应调整 |
| 下发方式 | 每次心跳响应带 `next_heartbeat_in`（秒），客户端按此调度下一次；首次启动立即心跳一次 |
| 本地失联判定 | 按云服务下发的频率计算：`最后成功心跳 + interval×2` 未更新即进宽限期，不用本地配置 |

#### 7.1.1 单客户端调频的操作设计

| 项 | 设计 |
|---|---|
| 入口 | 客户列表/详情页、实例详情页，心跳频率行内可改；快捷档位 1m/5m/15m/1h/6h/24h + 自定义（下限 1 分钟，云服务校验） |
| 显示 | 每个实例行显示当前生效频率 + **来源标记**（实例覆盖/客户覆盖/项目默认），改没改过一眼可见；列表可筛选"存在覆盖"的实例 |
| 生效时机 | **调疏立即生效**（如 1m→6h，客户端下一次就按新间隔调度）；**调密有最多一个旧周期的延迟**（如 6h→1m，客户端要发完当前周期的心跳才收到新频率）——客户端在 NAT 后无入站端口，云服务无法反向推送，后台在保存时提示"最长 X 后生效" |
| 恢复 | 覆盖可随时删除、恢复项目默认；**不设自动过期**（临时调密忘了删会让对方服务器持续高负载，靠"存在覆盖"筛选 + 创建人/时间标注人工清理） |
| 审计 | 每次调频写 audit_logs：谁、何时、把哪个对象从什么改成什么 |

#### 7.1.2 单客户端调频的典型场景

| 场景 | 操作 |
|---|---|
| 催某一个逾期客户续费 | 该客户调到 1 分钟 → 后台点吊销，最多 1 分钟后他的系统亮红条 |
| 灰度重点客户观察 | 把灰度名单里的几个客户调到 5 分钟，后台实时看谁装了新版本 |
| 客户报障排查期 | 临时调到 1 分钟，心跳日志（版本/IP/域名）变密集，便于定位 |
| 高价值客户稳定期 | 调疏到 24h，减少无谓请求 |

云服务侧按项目限流防滥用，每次调频写审计日志。

### 7.2 心跳状态可见性与并发治理

#### 7.2.1 上次/下次心跳可见（后台）

| 项 | 设计 |
|---|---|
| 实例列表列 | 最后心跳"X 分钟前"（tooltip 具体时间）+ 预计下次"Y 分钟后"（= 最后成功心跳 + 当前生效频率） |
| 状态灯 | 绿=正常（未到预计时刻）；黄=超过预计但在容忍窗内（网络抖动，观察）；红=超过预计 + interval×2 → 失联，进入第 8 节宽限期链路 |
| 全局看板 | 项目卡片：在线 x/y 实例、失联清单（标红，一键跳详情） |
| 客户端侧 | 授权页同步展示"下次同步 X 分钟后"，客户可自检 |

预计下次心跳两个用途：① 卖方巡检一眼看出"谁该来还没来"，不用翻心跳日志；② 给失联判定（第 8 节）提供统一的时间基准。

#### 7.2.2 并发治理：惊群分三层，治本在客户端抖动

**问题真实存在**：项目级调密（如强推版本时全项目调到 1 分钟）会让大量客户端在同一时刻醒来打过来；批量重启（热更、同时开机）同理——客户端同步睡眠、同步唤醒、同刻到达，形成自激振荡。

| 层 | 手段 | 说明 |
|---|---|---|
| 客户端（治本） | **调度抖动**：sleep = interval × (1 ± 10%) 随机偏移；首次启动心跳再延迟随机 0~60s | 打破同步振荡；批量重启不惊群。成本最低、效果最大 |
| 云服务（限流） | 单实例 <1min → 429（已有）；项目级 + 单 IP 限流，超限返回 429 + Retry-After，客户端指数退避重试 | 防失控客户端打爆服务 |
| 云服务（写路径） | JWT 实例令牌本地验签（**读路径零 DB 查询**）+ 心跳日志 channel→worker 批量插库 + `last_heartbeat_at` 内存聚合（每实例 ≤1 次/5s flush） | 高 QPS 下 DB 是瓶颈；分钟级精度对"X 分钟前"展示无感 |
| 架构 | 云服务无状态多副本 + LB，实例状态全在 DB/Redis | 根本扩容手段 |

授权状态实时性配套：JWT claims 带授权状态（短有效期）+ Redis revocation 列表（吊销即写）——心跳读路径不查库也能做到近实时（吊销后最快一个心跳周期生效，与调密下限一致）。

## 8. 失败链路与邮件通知

### 8.1 状态机

```
trial(30天) ─┬─ 注册转正 ─→ valid(订阅期内/买断)
             └─ 到期未转 ─┐
                          ├─→ grace(7天) ─满─→ blocked(拒绝启动)
valid ── 到期/吊销/验签失败/心跳超时 ─┘         ↑
                                              │ 激活/续费/云服务恢复
                              grace 内任意时刻恢复 ─┘
```

- **grace 期内**：服务一切正常，后台顶部红色横幅「授权异常，X 天后将停止服务」；
- **grace 期满**：下次启动**拒绝启动**，日志写明原因与恢复办法（SSH 放好授权凭证 `data/license/licenses/` 重启即恢复，或恢复后在 7 天窗口内本可在网页操作）；
- grace 天数默认 7 天，云后台按项目可配；
- 以上为**单证状态机**：一个客户持多张证时，每张证独立走本状态机，门禁按 feature 粒度组合判定（版本取交集、功能取并集、到期各算各的，见 6.6）。

### 8.2 邮件通知（云服务单通道）

本地零 SMTP 配置，全部通知由云服务发出：

| 触发 | 收件人 | 内容 |
|---|---|---|
| 发送注册验证码 | 客户（QQ 邮箱） | 6 位验证码，5 分钟有效 |
| 注册成功 | 客户 | 欢迎 + 试用天数说明 |
| 试用剩 7 / 3 / 1 天 | 客户 | 试用到期提醒 + 购买引导 |
| 进入 grace（授权异常） | 客户 + 卖方 | 异常原因 + X 天后停用 |
| grace 剩 3 天 / 1 天 | 客户 + 卖方 | 最后通牒 |
| 停用生效 | 客户 + 卖方 | 已停用 + 恢复办法 |
| 心跳失联超 3 个周期 | 卖方 | 客户 XXX 失联告警（含最后已知版本/IP） |
| 实例 IP 变更 / 迁移 | 卖方 | 知会性质（非待办）：实例 XXX 的 IP 从 A 变为 B；如客户未提及搬机器则人工核查（6.5.9） |
| 卖方重发密钥 | 客户 | 授权密钥 + 一键激活链接（6.8） |
| 激活成功（重绑/换机） | 双方 | 实例绑定确认；老实例被释放的告知（6.8） |
| 续费 / 恢复成功 | 客户 | 确认通知 |

- 发送方式：阿里云企业邮箱（`smtp.mxh.aliyun.com`）+ jcbaseGo SMTP 组件，配置在云服务；
- 收件邮箱取客户注册邮箱（`customer.email`），卖方邮箱取云服务配置；
- 所有发给客户的邮件统一带「查看帮助」链接（指向对应 FAQ 条目，见 6.9）——客户在邮箱里也能自助。

## 9. 30 天试用机制

| 项 | 设计 |
|---|---|
| 试用天数 | 云后台按项目配 `trial_days`，默认 30，设 0 关闭试用 |
| 触发 | 全新部署无 License，注册后自动进入 |
| 凭证 | 本地试用凭据 `data/license/trial.json`（安装时间戳 + 实例 ID），纯本地、离线可试 |
| 功能 | 默认全功能（`trial_edition` 可限制档位） |
| 提醒 | 后台常驻横幅"试用中，剩余 X 天"；剩 7/3/1 天邮件（第 8.2 节） |
| 到期 | 自动转入失败链路（grace → blocked） |
| 防白嫖 | `trial_require_activation=true` 时试用需联网登记（可选） |

## 10. 版本发布与渠道

### 10.1 渠道层级

`internal`（内测）> `beta`（公测）> `stable`（正式），高层级可见低层级版本：内测客户能看到全部，公测客户能看到 beta + stable，正式客户只看 stable。

### 10.2 归属与灰度

- 渠道归属：customer 级默认 + instance 级覆盖（云后台可把单个实例拉进内测）；
- **灰度发布：按 customer 分桶**（推荐方案）。release 设 `rollout_percent`（如 10%），按 `hash(customer_id) % 100 < rollout_percent` 判定，同客户每次计算结果一致、不会忽而在忽而不在；
- 为什么按 customer 而不是按 instance 分桶：**同一客户的多套部署（多门店）必须同渠道同版本**。market 是多服务架构，一个客户的多实例若装不同大版本，跨实例交互会出现 proto 偏斜；按 customer 分桶天然保证同进同退；
- 后台同时支持「指定名单」覆盖：勾选特定客户直接进灰度（不等哈希命中），用于重点客户先行验证；
- 实例级渠道覆盖优先于 customer 级，customer 级优先于哈希灰度。
- 强推：`mandatory=true` 的版本（安全修复），可配宽限期后未安装则进 grace。

### 10.3 版本包流转（CI → OSS → 云服务 ingest → 人工发布 → 客户）

预签名 URL 是这套流水线的钥匙：OSS 的预签名 URL 同时支持 **PUT（上传）** 和 **GET（下载）**——云服务不碰包本身，只握签发权。

```
CI release 成功
  ① 向云服务申领上传票据 POST /internal/upload-ticket（版本号+文件清单+sha256）
  ② CI 拿票据里的预签名 PUT URL，逐文件直传 OSS（凭据不落地 CI）
  ③ CI 上报完成 POST /internal/ingest-complete
  ④ 云服务 HeadObject 核对：对象存在 + size/元数据 sha256 与申报一致
     ├─ 一致 → 生成 releases 记录（status=ingested，待人工发布）
     └─ 异常 → 邮件通知卖方，记录标红，禁止发布
  ⑤ 人工后台审核（版本号/体积/sha256/CI 来源/校验结果）→ 选渠道+灰度%+强推 → 点发布 status=published
  ⑥ 客户心跳/检测拿到放行版本 → 请求云服务换下载票据（实例令牌+放行校验）
  ⑦ 云服务签发 OSS 预签名 GET URL（15 分钟有效）→ 客户直连 OSS 下载（流量不走云服务）
```

**OSS 桶结构**（对象路径不可变，一个版本只写一次）：

```
oss://{bucket}/{project}/{version}/market-{version}-linux-{arch}.tar.gz
oss://{bucket}/{project}/{version}/checksums.txt
```

**①~③ 上传票据模式**（替代 CI 持 AccessKey）：CI 不持有任何 OSS 凭据，上传权全部来自云服务签发的短时效预签名 PUT URL；云服务事先知道“应有哪几个文件、多大、sha256 多少”，上传中断/缺文件在 ④ 必然暴露。

**④ ingest 校验**（零流量优先）：CI PUT 时带 `x-oss-meta-sha256` 用户元数据，云服务 HeadObject 直接读元数据对账；另起异步 job 流式下载复验 sha256 + 校验包结构（8 个二进制 + static/ + checksums.txt），失败置 status=ingest_failed + 邮件。

**异常通知人工**：

| 异常 | 检测点 | 通知 |
|---|---|---|
| 上传中断/缺文件 | ingest-complete 时文件数与申报不符；ticket 超时未完成 | 邮件卖方 |
| sha256 不符 | HeadObject 元数据 vs 申报 / 异步复验 | 邮件 + 后台标红，禁止发布 |
| 包结构错误 | 异步解压校验 | 邮件 + 后台标红 |
| OSS 对象 404/权限错 | HeadObject 失败 | 邮件 |
| 包 ingested 后超 24h 未人工处理 | 定时 job | 提醒邮件（防忘发布） |

**⑦ 客户下载**：放行校验（渠道/灰度/授权范围/安装闸门）全过才签发 URL；URL 15 分钟有效，客户下载中断/过期自动回云服务重签；客户侧仍以 checksums.txt 做 sha256 终验。**收益：云服务带宽≈0（只签发几十字节的 URL），客户下载走 OSS/CDN 加速，而"能不能下"始终由云服务把关。**

**可选增强**：OSS 事件通知（对象创建→MNS）自动触发 ④，替代 CI 主动调 ingest-complete；多一份基础设施依赖，默认不做。

## 11. 热更新机制（直连云服务版）

沿用「本地拼镜像」安装方案（底座本地已有，拼装秒级，回滚=切 tag），检测与分发改直连云服务：

### 11.1 检测（三个触发源）

| 触发 | 说明 |
|---|---|
| 定时 | gateway 内置 updater，默认每 6 小时（可配） |
| 心跳顺带 | 每次心跳响应里带 `available_updates`，零额外请求 |
| 手动 | 后台「检查更新」按钮 / `market-admin update --check` |

### 11.2 就绪（下载缓存）

检测到放行版本 → 向云服务申领下载票据（实例令牌 + 放行校验，见 10.3）→ 拿到 OSS 预签名 GET URL（15 分钟有效，过期自动重签）→ 流式下载（sha256 对账 checksums.txt）→ 解压到 `data/updates/<版本>/` → 写 `state.json` 就绪标记 → 后台显示「新版本就绪待安装」（含渠道标签、体积、发布时间）。**重启不丢，随时可装。**

### 11.3 安装

| 触发 | 说明 |
|---|---|
| 后台按钮 | 「授权管理 / 关于」页点安装 |
| CLI | `market-admin update --install` |
| 自动窗口 | 可选：stable 渠道 + 配置维护窗口（如凌晨 2-5 点）自动装 |

安装时序（与授权闸门合流）：

```
下载校验(已就绪) → 云服务闸门复核(放行吗) → 本地拼镜像
   → 改 .env 版本号 → up -d → 健康检查 → 失败自动回滚
```

前几步失败线上零感知；唯一切换点是改版本号重启，失败自动回滚旧版本（旧镜像本地常驻）。

## 12. SDK 设计与接入方式

### 12.1 SDK 不开源，私有 module

**Go SDK 引入不等于 cloud 项目开源。** 依赖分发用私有 Go module：

- `license-cloud` 仓库设为 **Private**；SDK 是仓库内独立子 module（`sdk/go.mod`，`github.com/jcbowen/license-cloud/sdk`）；
- 接入项目配置 `GOPRIVATE=github.com/jcbowen/license-cloud/*` + 只读 deploy token（`git config` 或 `.netrc`）；
- **SDK 只含客户端逻辑**（验签、心跳、状态机、updater、页面辅助），服务端代码在 `server/` 独立 module，不随 SDK 分发；
- 即使 SDK 被逆向，也只能得到公钥——无签发能力。

sidecar 备选（`agent/`）：非 Go 项目用，独立进程提供本地 HTTP（`/status`、`/verify`），任何语言可接。

### 12.2 SDK API 面（market 接入全部改动）

```go
// ① gateway main.go：初始化 + 起协程（两行）
lic, _ := sdk.Init(sdk.Config{
    CloudURL:         "https://license.jiuchet.com",
    ProjectKey:       "market",
    DataDir:          "/app/license",   // 持久化目录
    HeartbeatEvery:   24 * time.Hour,
    UpdateCheckEvery: 6 * time.Hour,
    AutoInstall:      false,
})
lic.StartHeartbeat(ctx)
lic.StartUpdateChecker(ctx, installer)   // installer：market 实现的安装回调

// ② 中间件链加一行（未授权导授权页，登录/授权/静态资源放行）
r.Use(lic.GinMiddleware(sdk.WithExemptPaths(...)))

// ③ 挂后台 API（授权状态/注册激活/检查更新/安装更新）
sdk.RegisterHandlers(adminGroup, lic)
```

market 侧改动总计：`main.go` 两行、中间件一行、路由注册一行、`.env` 一组 `LICENSE_*`、关于页接入 `lic.Status()`、Docker 挂载 `data/license`。**授权逻辑零实现，全在 SDK。**

### 12.3 配置项（.env，接入项目）

| 配置 | 默认 | 说明 |
|---|---|---|
| `LICENSE_ENABLED` | `true` | 总开关；`false` 全绕过（自用/开发） |
| `LICENSE_CLOUD_URL` | 空 | 云服务地址 |
| `LICENSE_PROJECT_KEY` | `market` | 项目标识 |
| `LICENSE_DATA_DIR` | `/app/data/license` | 授权数据目录：**复用现有 data 持久卷，不新增卷**；备份 data 即含授权（见 6.5） |
| `LICENSE_HEARTBEAT_HOURS` | `6` | 心跳**期望**间隔；实际以云服务响应下发的 `next_heartbeat_in` 为准（见 7.1） |
| `LICENSE_UPDATE_CHECK_HOURS` | `6` | 更新检测间隔 |
| `LICENSE_AUTO_INSTALL` | `false` | stable 渠道是否自动装 |

### 13.2 数据模型（多项目隔离）

| `instance_licenses` | instance ↔ license 多对多关联（各占一个槽位）+ 每对独立状态；心跳返回组合结果（见 6.6） |
| `instance_nodes` | 实例节点 IP 池：instance + ip/cidr + 节点命名 + 来源（`manual`/`activation`/`auto-learn`）+ 首末见时间；池内 IP 不触发双活告警（见 6.5.9） |
| `plans` | 收费方案（按项目）：名称 + 类型/档位/时长 + `price_cents` + `currency` + 续费优惠价 `renewal_price_cents` + 默认槽位 + 上下架状态（见 6.7） |
| `orders` | 自助订单：`order_no` 唯一 + customer/license/plan + 金额（下单定格）+ 状态（`pending`/`pending_confirm`/`paid`/`cancelled`/`rejected`）+ 渠道（`manual`/`wechat`/`alipay`）+ 转账截图 + 确认人/时间（见 6.7） |

| `releases` | 版本发布：渠道 + 灰度% + 强推 + OSS 对象键/size/sha256 + 状态（`ingested`/`published`/`rejected`/`ingest_failed`）+ CI 来源 run id + ingest/发布时间 |
| `notifications` | 邮件发送记录 |
| `audit_logs` | 卖方操作审计 |

### 13.3 部署

- 国内 VPS + 已备案域名 + HTTPS（Let's Encrypt 或云厂商证书）；
- Docker 单容器（Go 二进制 + MySQL + 本地包存储，或外接云数据库）；
- 与客户系统分机部署；对外只暴露 443；
- 监控：uptime 告警到卖方邮箱（云服务自身可用性——它挂了全体客户进宽限期）。

## 14. 安全边界与风险（如实）

| 风险 | 现实 | 缓解 |
|---|---|---|
| 本地验签可被 patch | 防不住决心破解的专业人员 | 商业约束（法务+续费）；验签点分散、二进制剥离符号，提高门槛 |
| 云服务单点 | 挂了全体客户进宽限期 | 分机部署 + 监控告警 + 宽限期兜底 |
| 私钥泄露 | 灾难级 | 仅存服务器（600 权限+加密备份）；泄露后换钥：多公钥机制让新旧凭证平滑过渡 |
| 一证多部署 / 镜像分发 | 拷贝 data 复制凭证、镜像分享白嫖试用 | 槽位制放行正当扩容 + 越权分级处置（满槽拒绝/双活告警/可选软隔离或吊销）+ 正经迁移甄别，见 6.5 |
| 试用白嫖 | 删库重装 | `trial_require_activation` 联网登记（可选） |
| 注册接口被刷 | 垃圾注册 | 手机号频率限制 + 实例签名 + 同 IP 限流 |
