# 小程序发版方案（mp-release）

> **状态：方案定稿（2026-10-25），代码未实施。** 本文档是 market 小程序端发版的单一权威设计来源，涵盖微信平台约束、商业模式三路线、服务商模式与云服务边界、域名注入方案、域名审计结论与交付 SOP。与 `01-授权模式总体方案.md` 联动（该文档管服务端授权，本文档管小程序端发版）；重大设计变更先改文档再改代码。

## 1. 背景与核心权衡

market 以 Docker 部署方式售卖（私有化，每客户一套），服务端交付由 license-cloud 授权体系管控（见 01 文档）。但**小程序端是微信平台侧的独立发布体系，与 Docker 部署正交**：Docker 化只解决服务端交付，不解决小程序发版。

核心权衡只有一句话：**卖源码 = 同时交出小程序发版权**。买断制交付源码是既定模式，因此必须显式决策发版权归属——三种路线见第 3 节。

另需注意范围：**只有小程序包需要微信审核**；admin 后台（相对路径 + nginx 同源反代）与 C 端 H5 均随 Docker 自由更新，不进入本方案。

## 2. 微信平台硬约束（任何路线都绕不开）

| # | 约束 | 说明 |
|---|---|---|
| 1 | appid 构建时定死 | manifest.json 的 `mp-weixin.appid` 编译期内置，运行时不可改；交付源码必须参数化替换（否则等于送出卖方 appid） |
| 2 | 每次代码更新必须提审 | 上传 → 提审 → 发布，普通类目审核 1~7 天；`wx.getUpdateManager` 只强制客户端换新版，更新本身仍要提审，无静默热更通道 |
| 3 | 域名白名单 | 每个 appid 后台单独登记 request 合法域名：已备案 + HTTPS，不支持通配符/IP/localhost；子域名继承主域名备案 |
| 4 | 支付商户号与 appid 绑定 | 需同主体（或已关联）；一套客户一套商户参数，后端按实例配置（Docker 各自 DB 天然隔离） |
| 5 | 体验版免审验收 | 上传后不提审即为体验版，客户管理员/体验成员扫码验收，验收后再提审——交付 SOP 的必经环节 |
| 6 | 版本回退免复审 | 发布后出问题可回退到上一线上版本，不需要重新提审——发版兜底手段 |

## 3. 三条商业模式路线

| | A · 客户自带 appid | B · 服务商代开发 | C · SaaS 单 appid |
|---|---|---|---|
| 机制 | 客户用企业资质自注册小程序，卖方交付源码 + SOP，客户自行构建提审 | 卖方申请微信第三方平台，客户扫码授权，卖方 API 代上传/提审/发布 | 卖方一个 appid，多租户共用 |
| 发版权 | 归客户 | 收回到卖方 | 完全自主 |
| 客户资质 | 企业主体（认证 ¥300/年） | 仍需自己的 appid（可代提交注册流程，主体仍是客户） | 无（客户是平台子账号） |
| 发版效率 | 每客户独立，依赖客户配合 | 后台一键批量；体验版验收 + 免复审回退 | 一次提审全体生效 |
| 数据独立性 | 独立（客户自己的服务器） | 独立 | 不独立（数据在卖方） |
| 适用 | **现阶段默认**（买断私有化） | 规模化后 / 订阅制 | 备选商业模式，与私有化互斥 |

**决策：A 先行，B 规模化后升级，C 列为备选。** A 与既定「私有化买断 + license-cloud 授权」模式自洽；B 的前置门槛是微信第三方平台资质（企业主体 + 平台创建审核），资质就绪前不值得投入；C 是另一种生意，不在当前路线图。

## 4. B 路线设计：服务商代开发与云服务边界

### 4.1 模块边界（核心原则：数据层共享，运行时与凭证隔离）

B 路线落地为 license-cloud 云服务体系内的**独立进程模块 `mp-release`**，不塞进主服务：

```
┌─ license-cloud 云服务体系（国内 VPS + 备案域名）──────────┐
│                                                          │
│  主服务（关键路径·已有）      mp-release（独立进程·新增）   │
│  签发/心跳/渠道/灰度/续费      微信第三方平台 API          │
│  挂了=全体客户进宽限期          token 独立存储刷新          │
│         │                      上传→体验版→提审→发布→回退  │
│         │                      授权消息回调 endpoint       │
│         │                      挂了=本周不能发新版         │
│         └──────────┬──────────────────┘                  │
│             共享 MySQL + 卖方管理后台（同一个）             │
└──────────────────────────────────────────────────────────┘
```

- **共享**：MySQL（customers/instances/releases/渠道灰度全部复用，新增两张表）、卖方管理后台（同一个，加发版页）
- **隔离**：微信 API 调用、`component_access_token`/`authorizer_access_token` 凭证、授权消息回调全部只在 mp-release 进程内；微信侧限流/token 过期/回调异常不触碰心跳主链路（01 文档 13.3：主服务挂了全体客户进宽限期，故障域必须分开）
- **不动**：客户端 Go SDK 完全不参与小程序发版，「公钥只进不出」铁律不受影响；主服务不引入任何微信依赖
- **价值前提**：放进云服务而非另起系统，是为了复用 01 文档已有能力——渠道/灰度分桶（10.2）、客户档案与自动采集域名（决策 16）、OSS 票据模式（决策 18）

### 4.2 数据模型新增（两张表）

| 表 | 要点 |
|---|---|
| `mp_authorizations` | project + customer ↔ appid 授权关系：授权状态、授权时间、`authorizer_refresh_token`（加密存储）、小程序主体信息、类目配置快照 |
| `mp_releases` | 小程序版本发布记录：模板版本（template_id）+ appid + `ext_json`（含 base_url）+ user_version + 审核单号 + 状态机（`uploaded` → `trial` → `auditing` → `published` → `reverted`）+ 发布时间/回退记录 |

### 4.3 与渠道/灰度体系打通（放进云服务的核心收益）

- 小程序模板版本纳入现有 `releases` + 渠道（internal/beta/stable）+ 灰度分桶（按 customer 哈希，决策 13）：**一次「发布」动作同时决定服务端版本与小程序模板各放给哪些客户**
- 版本对账：心跳已上报服务端版本，`mp_releases` 有各 appid 小程序线上版本——后台出「服务端 1.2.0 / 小程序 1.2.0」一致性视图，错配标红（防小程序新包调服务端新接口）
- 小程序版本号与服务端版本号解耦、渠道一致：小程序可独立于服务端发版（如纯 UI 修复），但走同一套放量控制

### 4.4 发版流程（服务商 API 时序）

一次性（每客户）：

1. 卖方在微信开放平台创建第三方平台（类型：代小程序实现开发），配置授权事件接收 URL（指向 mp-release，需公网可达——license-cloud 备案域名正好承接）
2. 客户管理员扫码授权（预授权码 → 授权码）
3. mp-release 收回调 → 换取 `authorizer_access_token` + `authorizer_refresh_token`，落 `mp_authorizations`

日常（每次发版）：

1. 小程序代码入代码模板库（addtotemplate）→ `template_id`（版本升级时重新入）
2. 对每个目标客户 commit（`template_id` + 该客户的 `ext_json` + user_version）——域名注入见第 5 节
3. 可选：发体验版给客户验收
4. submit_audit 提审 → 轮询审核状态（每 appid 独立审核，1~7 天，不能合并）
5. release 发布；出问题 revert 回退免复审

### 4.5 客户侧预检（提审前，mp-release 代查）

| 预检项 | 数据来源 | 不达标的处置 |
|---|---|---|
| 小程序类目配置（零售/食品等，决定是否需要食品经营许可证等资质） | 授权时拉取 | 阻断提审，引导客户在 mp 后台配置 |
| request 合法域名是否登记客户自己的部署域名 | 心跳自动采集的 base_url（决策 16） | 提示卖方联系客户补登记 |
| 商户号与 appid 绑定 | 授权信息 | 仅影响支付，不阻断提审；提示客户 |

## 5. 域名注入：ext_json 方案（已决策，方案二）

### 5.1 为什么否决编译期内置

每个客户连自己的域名是根本需求。编译期内置（每客户改 .env 构建一次）下：

- A 路线：客户自己构建，改错是隐蔽坑——小程序能打开但请求打到卖方服务器，表现为「数据不对/接口报错」，客户以为是产品 bug
- B 路线：卖方给 N 个客户发版就要维护 N 个构建变体，**发版成本 × N 全压在卖方**，与服务商模式「一键批量」的初衷背道而驰

### 5.2 ext_json 机制与代码改动

微信第三方平台的标准姿势：**一份模板 + N 份配置**。

- 小程序代码只入一次代码模板库（`template_id`），包内不内置任何客户域名
- 给某客户发版时，API 传该客户的 `ext_json`（含 `base_url`：客户自己 Docker 部署的域名）
- 小程序启动时 `uni.getExtConfigSync()`（mp-weixin 条件编译）读取

`src/client/src/api/config.ts` 的 BASE_URL 优先级改为：

```
ext_json.base_url（uni.getExtConfigSync，服务商代开发时）
  > VITE_APP_API_BASE_URL（.env.production，A 路线客户自行构建时）
  > 占位符（交付版回退值，明显连不通）
```

对 A 路线客户：`getExtConfigSync` 返回空（非服务商代开发），自动走 .env——同一份代码两条路线通吃。

配套改动：

| 改动 | 位置 | 内容 |
|---|---|---|
| 占位符化 | `src/client/.env.production` | `VITE_APP_API_BASE_URL` 改为占位符（如 `https://your-domain.example.com/s/api/v1`）；卖方本机构建用 `.env.production.local`（gitignore）覆盖，机制不变 |
| 回退值同步 | `src/client/src/api/config.ts:19` | 回退值同步改占位符 |
| ext_json 读取 | `src/client/src/api/config.ts` | 按上述优先级重构 + 单测覆盖三条分支 |
| appid 参数化 | `manifest.json` + `scripts/build-mp.js`（node，跨平台） | 构建时传 `--appid` + `--base-url` 写入；缺参即报错退出，不允许静默用卖方值 |

### 5.3 失败模式设计（核心原则：让错误暴露，而不是隐藏）

交付版所有域名相关默认值一律占位符：客户忘配时小程序**直接连不通**，一眼可见；而非悄悄打到卖方服务器。同理构建脚本缺参拒绝构建。

## 7. 交付替换清单与 SOP（A 路线）

### 7.1 交付替换清单（五项，一次过）

| # | 项 | 位置 | 卖方值 | 交付动作 |
|---|---|---|---|---|
| 1 | 小程序 appid | `manifest.json` `mp-weixin.appid` | `wxdb854c7f606605f5` | 构建脚本参数化替换 |
| 2 | 小程序 BASE_URL | `.env.production` `VITE_APP_API_BASE_URL` | `https://market.jiuchet.com/s/api/v1` | 占位符（客户填自己域名） |
| 3 | BASE_URL 回退值 | `api/config.ts:19` | 同左 | 同步占位符 |
| 4 | nginx server_name | `deploy/nginx.conf.example` | `market.jiuchet.com` | 客户改自己域名 |
| 5 | 支持邮箱 | admin 关于页 | `jiuqi@jiuchet.com` | 交付时可换（无功能影响） |

### 7.2 客户侧发版 SOP

1. 注册小程序：企业主体 + 微信认证（¥300/年）
2. 小程序后台登记 request 合法域名 = 自己 Docker 部署的域名（已备案 + HTTPS）
3. 微信开发者工具导入交付源码
4. 改 `.env.production` 域名 + 构建时传自己 appid（`scripts/build-mp.js`）
5. 上传 → 发体验版扫码验收
6. 提审 → 发布（普通类目 1~7 天）

### 7.3 壳化策略（压低提审频次）

私有化下每改一次 UI = 每个客户一次提审，成本极高。小程序端只承载框架级变更；活动、装修、文案、公告等全部走后端配置/后台开关。重要 bugfix 优先走服务端热更（01 文档第 11 节机制）。
