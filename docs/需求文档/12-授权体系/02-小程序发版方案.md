# 小程序发版方案（mp-relay）

> **状态：方案定稿（2026-10-25，v2 改版），代码未实施。** 本文档是 market 小程序端发版的单一权威设计来源，涵盖微信平台约束、商业模式三路线、**卖方托管发版（无资质版）**设计、域名注入方案、域名审计结论与交付 SOP。与 `01-授权模式总体方案.md` 联动（该文档管服务端授权，本文档管小程序端发版）；重大设计变更先改文档再改代码。
>
> **v2 改版说明（2026-10-25）**：原方案设计为「微信第三方平台服务商代开发」（mp-release 模块），经讨论确认为**过度设计**——本项目是源码售卖模式，客户自有 appid、自配、自发是天经地义，发版权归客户。现方案改为**卖方托管发版（无资质版）**：不依赖第三方平台资质，卖方侧持客户上传密钥 + appsecret，代客户完成上传/提审/发布全流程，代码不经过客户服务器。服务商模式降为远期可选项（第 3 节 B 路线）。

## 1. 背景与核心权衡

market 以 Docker 部署方式售卖（私有化，每客户一套），服务端交付由 license-cloud 授权体系管控（见 01 文档）。但**小程序端是微信平台侧的独立发布体系，与 Docker 部署正交**：Docker 化只解决服务端交付，不解决小程序发版。

本项目模式的两个基本事实：

1. **买断制交付源码**：发版权天然归客户——客户自有 appid、客户自己配域名、客户自己发布
2. **客户无技术能力跑构建**（node/npm）：不能要求客户自己构建上传，卖方必须协助

核心设计目标：**在不依赖微信第三方平台资质、不经过客户服务器的前提下，让零技术能力的客户也能完成小程序发版**，且每次发版客户只需做两件事：扫体验版二维码验收、点确认。

另需注意范围：**只有小程序包需要微信审核**；admin 后台（相对路径 + nginx 同源反代）与 C 端 H5 均随 Docker 自由更新，不进入本方案。

## 2. 微信平台硬约束（任何路线都绕不开）

| # | 约束 | 说明 |
|---|---|---|
| 1 | appid 构建时定死 | manifest.json 的 `mp-weixin.appid` 编译期内置，运行时不可改；交付源码必须参数化替换（否则等于送出卖方 appid） |
| 2 | 每次代码更新必须提审 | 上传 → 提审 → 发布，普通类目审核 1~7 天；`wx.getUpdateManager` 只强制客户端换新版，更新本身仍要提审，无静默热更通道 |
| 3 | 域名白名单 | 每个 appid 后台单独登记 request 合法域名：已备案 + HTTPS，不支持通配符/IP/localhost；子域名继承主域名备案 |
| 4 | 支付商户号与 appid 绑定 | 需同主体（或已关联）；一套客户一套商户参数，后端按实例配置（Docker 各自 DB 天然隔离） |
| 5 | 体验版免审验收 | 上传后不提审即为体验版，客户管理员/体验成员扫码验收，验收后再提审——交付 SOP 的必经环节 |
| 6 | 版本回退免复审 | 发布后出问题可回退到上一线上版本，不需要重新提审——发版兜底手段 |

## 3. 三条商业模式路线

| | A · 客户自带 appid | B · 服务商代开发 | C · SaaS 单 appid |
|---|---|---|---|
| 机制 | 客户用企业资质自注册小程序；卖方交付源码 + 托管发版服务 | 卖方申请微信第三方平台，客户扫码授权，卖方 API 代上传/提审/发布 | 卖方一个 appid，多租户共用 |
| 发版权 | 归客户（**卖方受托执行**） | 收回到卖方 | 完全自主 |
| 客户资质 | 企业主体（认证 ¥300/年） | 仍需自己的 appid | 无（客户是平台子账号） |
| 发版效率 | 卖方托管：一次构建 N 客户分发，客户只验收 | 后台一键批量 | 一次提审全体生效 |
| 数据独立性 | 独立（客户自己的服务器） | 独立 | 不独立（数据在卖方） |
| 适用 | **现阶段默认**（买断私有化） | 远期可选（资质就绪后） | 备选商业模式，与私有化互斥 |

**决策：A 先行（配卖方托管发版服务），B/C 列为远期。** A 与既定「私有化买断 + license-cloud 授权」模式自洽；B 的前置门槛是微信第三方平台资质（企业主体 + 平台创建审核），A 路线的托管发版服务已能满足客户需求，B 不再必要则不投入；C 是另一种生意，不在当前路线图。

## 4. 发版权归属与卖方托管发版（核心设计）

### 4.1 关键事实：三个动作的凭证边界（方案的技术基础）

| 动作 | 可用通道 | 凭证 | 资质门槛 |
|---|---|---|---|
| 上传代码 | miniprogram-ci（微信官方 Node 包，无需开发者工具） | 客户小程序的**代码上传密钥**（mp 后台生成，管理员扫码） | 无 |
| 提审 | REST API `submitaudit` | 客户小程序的 **appid + appsecret** | 无 |
| 发布 / 回退 | REST API `release` / `revertcode` | 同上 | 无 |

三个已核实的关键结论（2026-10-25 查证）：

1. **普通小程序没有 REST 上传通道**——`/wxa/commit` 是第三方平台专属接口，普通 appid 调不了；无头上传只有 miniprogram-ci 一条路
2. **提审/发布/回退不需要任何第三方平台资质**——appid + appsecret 换 access_token 直调 REST API 即可，`component_verify_ticket` 回调那套公网 endpoint 完全不需要
3. **miniprogram-ci 的 ext_json 注入 = 改写构建产物里的 `ext.json` 文件**（`extEnable` + `ext` 字段），上传时随包上传——这是「一份构建产物 + N 份客户配置」的技术落点（见第 5 节）

因此，**不依赖第三方平台资质即可搭出完整代发链路**，客户侧唯一的技术动作是一次性配置（见 4.3）。

### 4.2 两段式链路

```
        ┌───────────── 卖方侧（发版服务 mp-relay） ─────────────┐
        │                                                      │
        │  构建产物（卖方 CI 构建一次）                          │
        │  dist/mp-weixin/                                     │
        │        │                                             │
        │        ▼  ① 按客户改写 ext.json（base_url/appid）     │
        │  客户化产物目录                                        │
        │        │                                             │
        │        ├─ 上传段 ──────────────► miniprogram-ci        │
        │        │   （持客户上传密钥）      │                   │
        │        │                            ▼                  │
        │        │                      微信（体验版）            │
        │        │                            │                  │
        │        └─ 提审发布段 ────────────► REST API            │
        │             （持客户 appsecret）    submitaudit/release │
        │                                                      │
        └──────────────────────────────────────────────────────┘
                     ▲                        ▲
                     │                        │
              客户上传密钥               客户 appsecret
              （仅上传+预览权限）      （提审/发布/回退）
                     │                        │
              客户 mp 后台              客户 mp 后台
              开发设置→代码上传          开发设置→开发者ID
```

- **上传段**：卖方侧跑 miniprogram-ci，持客户上传密钥，代码直达微信——不经过客户服务器
- **提审发布段**：卖方侧持客户 appsecret 换 access_token，直调 REST API
- **两段凭证分离**：上传密钥泄露的最坏结果是「别人能往你小程序上传代码」（提审发布做不了）；appsecret 侧 IP 白名单可收紧到卖方服务器

### 4.3 客户一次性配置清单（三项，可远程协助完成）

客户只需在自己小程序 mp 后台操作一次，之后每次发版只做验收：

| # | 配置项 | 位置 | 用途 | 注意事项 |
|---|---|---|---|---|
| 1 | 代码上传密钥 | 开发设置 → 小程序代码上传 → 管理员扫码生成 `.key` 文件 | 上传段凭证 | **必须配置 IP 白名单 = 卖方服务器 IP**（微信强制要求，不配不能用）；密钥仅上传+预览权限，遗失可重置 |
| 2 | appsecret（AppSecret） | 开发设置 → 开发者ID | 提审/发布/回退凭证 | 同一页面可配置 IP 白名单；重置后旧 secret 失效需同步卖方 |
| 3 | request 合法域名 | 开发设置 → 服务器域名 | 小程序请求通道 | 填客户自己 Docker 部署的域名（已备案 + HTTPS） |

配置方式：客户把密钥文件和三样值通过约定渠道（加密邮件/企业微信文件等）发给卖方，卖方录入发版服务（加密存储）。**卖方侧全操作审计，客户可见每次发版记录**（时间、版本号、审核单号、状态）。

### 4.4 部署形态与演进路径

| 阶段 | 形态 | 触发条件 |
|---|---|---|
| **阶段 1：CLI 工具（早期）** | 卖方侧一个 Node CLI（miniprogram-ci + REST API 封装），卖方人肉触发；微信通知客户扫码验收，客户确认后卖方点提审 | 客户个位数，现在 |
| **阶段 2：客户自助页面（规模化后）** | admin 后台加「小程序发布」页：配置区（appid/appsecret/上传密钥，客户自助录入）+ 操作区（上传 → 体验版二维码 → 提审 → 轮询审核 → 发布 → 回退）+ 版本记录 | 客户量上升到人肉运营成为瓶颈 |

**与 license-cloud 的关系：完全解耦，不进云服务主进程。** 本服务不需要第三方平台资质、不需要授权消息回调 endpoint、不碰任何授权关键路径。跑在卖方自己的运维机器上即可（阶段 1 甚至就是卖方开发机上跑的 CLI）。阶段 2 的自助页面若要托管，另起轻量服务，不复用也不干扰 license-cloud 主进程（故障域分离原则同 01 文档 13.3）。

### 4.5 安全设计（客户把 secret 交给卖方的信任坎）

| 措施 | 说明 |
|---|---|
| 上传密钥强制 IP 白名单 | 微信官方机制：密钥只能在白名单 IP 上使用（填卖方服务器 IP），泄露也调不动 |
| appsecret 侧 IP 白名单 | 提审/发布/回退的 access_token 调用同样可收紧到卖方服务器 IP |
| 加密存储 | 卖方侧密钥/appsecret 加密落库，不明文 |
| 全操作审计 | 每次上传/提审/发布/回退记录时间、操作人、版本号、审核单号，客户可查 |
| 权限最小化 | 上传密钥天然只含上传+预览权限；提审发布通道与上传通道凭证分离，单点泄露不扩散 |
| 客户可随时收回 | mp 后台可重置密钥/secret，重置后同步卖方即可，授权关系天然可逆 |

### 4.6 数据模型（阶段 2 自助页面时新增，两张表）

| 表 | 要点 |
|---|---|
| `mp_clients` | 客户小程序配置：customer ↔ appid、appsecret（加密）、上传密钥引用、域名白名单状态、IP 白名单状态 |
| `mp_release_logs` | 发版记录：客户 + 版本号 + `ext_json`（含 base_url）+ 审核单号 + 状态机（`uploaded` → `trial` → `auditing` → `published` → `reverted`）+ 操作记录 |

## 5. 域名注入：ext_json 方案（已决策，方案二）

### 5.1 为什么否决编译期内置

每个客户连自己的域名是根本需求。编译期内置（每客户改 .env 构建一次）下：

- A 路线客户自己构建时，改错是隐蔽坑——小程序能打开但请求打到卖方服务器，表现为「数据不对/接口报错」，客户以为是产品 bug
- 卖方托管发版时，N 个客户 = N 个构建产物，**构建成本 × N 全压在卖方**

### 5.2 ext_json 机制与代码改动

微信官方机制：**一份构建产物 + N 份配置**。

- 卖方 CI 构建一次小程序产物（`dist/build/mp-weixin/`），包内不内置任何客户域名（uni 构建默认不产出 ext.json，`getExtConfigSync` 返回空自动走 .env 兜底）
- 每客户发版前，在产物目录创建/改写 `ext.json`：`extEnable: true` + `ext: { base_url: 客户自己 Docker 部署的域名 }`（第三方平台场景另需 `extAppid`，本方案不需要）
- miniprogram-ci 上传时 ext.json 随包上传，小程序启动时 `uni.getExtConfigSync()`（mp-weixin 条件编译）读取

`src/client/src/api/config.ts` 的 BASE_URL 优先级改为：

```
ext_json.base_url（uni.getExtConfigSync，卖方托管发版时）
  > VITE_APP_API_BASE_URL（.env.production，客户自行构建时的兜底通道）
  > 占位符（交付版回退值，明显连不通）
```

对客户自行构建的场景：`getExtConfigSync` 返回空，自动走 .env——同一份代码两种发版形态通吃。

配套改动：

| 改动 | 位置 | 内容 |
|---|---|---|
| 占位符化 | `src/client/.env.production` | `VITE_APP_API_BASE_URL` 改为占位符（如 `https://your-domain.example.com/s/api/v1`）；卖方本机构建用 `.env.production.local`（gitignore）覆盖，机制不变 |
| 回退值同步 | `src/client/src/api/config.ts` | 回退值同步改占位符 |
| ext_json 读取 | `src/client/src/api/config.ts` | 按上述优先级重构 + 单测覆盖三条分支 |
| appid 参数化 | `manifest.json` + `scripts/build-mp.js`（node，跨平台） | 微信/支付宝双平台：构建时传 `--platform mp-weixin\|mp-alipay` + `--appid` 写入（或本机 `manifest.local.json` 对应平台节覆盖）；缺参即报错退出，不允许静默用卖方值 |
| ext.json 改写工具 | 发版服务 CLI（阶段 1） | 上传前按客户改写产物目录 ext.json |

### 5.3 失败模式设计（核心原则：让错误暴露，而不是隐藏）

交付版所有域名相关默认值一律占位符：客户忘配时小程序**直接连不通**，一眼可见；而非悄悄打到卖方服务器。同理构建脚本缺参拒绝构建。

### 5.4 版本号注入（2026-10-29 已实施）

C 端构建时从 git 读取版本号注入，与后端 `build.mjs` 的 `common/version.AppVersion` 注入同一套取值优先级：`APP_VERSION` 环境变量（CI tag 时注入）→ `git describe --tags --abbrev=0` → 兜底 `dev`。

**格式收敛**（各平台硬约束）：iOS App Store 强制 `CFBundleShortVersionString` 为 `x.y.z` 三段纯数字（带 `-beta` 提审被拒），Android 国内市场审核兼容性参差，支付宝有 `x.y.z` 格式校验，故 **versionName 统一剔除 `v` 前缀与 `-` 预发布后缀**（`v0.1.0-beta` → `0.1.0`）；**versionCode = git tag 数量**（整数递增，App versionCode 与统计同口径）；完整原始版本串经 vite define 注入运行时，仅在关于页展示。

| 改动 | 位置 | 内容 |
|---|---|---|
| manifest 版本同步 | `scripts/gen-version.js` | 构建前同步改写 `manifest.json` 顶层 `versionName`/`versionCode`（改写结果随代码提交，不做临时恢复——App 云打包与 miniprogram-ci 上传读的就是仓库 manifest；注意必须先于 `build-mp.js` 读 original 执行，否则版本号会被 appid 的备份-恢复机制洗掉） |
| 编译期常量 | `vite.config.ts` define | `__APP_VERSION__` / `__APP_VERSION_CODE__` / `__APP_VERSION_RAW__` / `__APP_BUILD_TIME__`（与 gen-version.js 逻辑同步维护，未共享模块是规避 vite config 加载 CJS 的转译坑） |
| 运行时聚合 | `src/utils/version.ts` | 版本号、运行环境（`X-App-Env`：dev/release，按 `import.meta.env.DEV`）、版本环境（`X-App-Stage`：develop/trial/release/gray，经 `uni.getAccountInfoSync().miniProgram.envVersion`，官方文档确认微信/支付宝支持、支付宝多 gray 灰度版、京东不支持；H5/App 恒为 release） |
| 请求头携带 | `src/api/request.ts` | 全部请求与上传统一携带 `X-App-Version` / `X-App-Version-Code` / `X-App-Env` / `X-App-Stage`（后端当前仅透传不消费） |
| 关于页 | `pagesMine/about/about.vue` | 展示版本号、版本码、运行环境、版本环境、构建版本与构建时间；入口在用户中心「关于」 |

请求头完整清单见 `06-接口设计/01-通用规范.md`。

### 5.5 构建产物优化（2026-10-29 已实施）

微信开发者工具「体验评分」三项整改，均在构建配置/源码层面完成，产物已验证：

| 项 | 位置 | 内容 |
|---|---|---|
| 压缩声明 | `manifest.json` → `mp-weixin.setting` | `minified` / `minifyWXSS` / `minifyWXML`（构建时经 uni-cli-shared 合并进 dist 的 `project.config.json`；产物 JS 本身已由 vite/esbuild 压缩，此项为评分工具读取的声明开关，勿开 `uglifyFileName` 文件名混淆） |
| 按需注入 | `manifest.json` → `mp-weixin.lazyCodeLoading` | `requiredComponents`（该键透传进 dist 的 `app.json`；基础库 ≥ 2.11.1，官方推荐项，开启后需全页面回归） |
| 分包归位 | 源码物理移动 | 仅单分包使用的代码移入分包目录：`utils/pay.ts → pagesOrder/common/`、`utils/regionCache.ts → pagesMine/common/`、`static/qrcode.min.js → pagesOrder/order/`（qrcode 的类型声明为 `declare module '*.min.js'` 通配模式，移动后不受影响） |

注意事项：

- 跨分包共享代码必须留在主包（微信分包机制约束）：`api/marketing.ts`、`utils/coupon.ts`、`utils/region.ts` 被多个分包引用，不可移动；体验评分对这 3 个文件的「主包未使用 JS」告警属工具对多分包共享场景的已知局限，保留即可
- vite 编译的 Vue3 项目不支持 `manifest.json` 的 `optimization.subPackages` 分包优化（编译器内部该逻辑仅对 uni-app x 生效），分包归位只能物理移动文件
- 后续新增仅单分包使用的代码时同理放分包目录（如 `pagesOrder/common/`），避免打进主包

### 7.2 客户侧流程（托管发版形态）

**一次性配置**（可远程协助，三项见 4.3）：

1. 注册小程序：企业主体 + 微信认证（¥300/年）
2. 生成代码上传密钥 + 配 IP 白名单（卖方服务器 IP）
3. 提供 appsecret + 登记 request 合法域名（= 自己 Docker 部署的域名）

**每次发版**（客户只做两件事）：

1. 卖方上传完成 → 通知客户扫码验收体验版
2. 客户确认无误 → 卖方提审 → 审核通过 → 发布（客户可要求回退）

### 7.3 壳化策略（压低提审频次）

私有化下每改一次 UI = 每个客户一次提审，成本极高。小程序端只承载框架级变更；活动、装修、文案、公告等全部走后端配置/后台开关。重要 bugfix 优先走服务端热更（01 文档第 11 节机制）。
